# ❓ FAQ:常見問題與解答

在此可找到 Nuxt I18n Micro 常見問題的解答與疑難排解方法。

## 🚀 開始使用時的問題

### ❓ 若某個路由無法載入怎麼辦?

使用 `Nuxt I18n Micro` 時,某些路由可能無法如預期載入,特別是當路由器未自動為子資料夾中的路由指派名稱時。

**解決方式:**
可透過在對應的 Vue 檔中新增以下內容,手動為頁面定義路由名稱:

```javascript
definePageMeta({ name: 'pageName' })
```

這能確保路由正確註冊,讓應用中的導覽順暢無阻。

### ❓ 為什麼 `$t` 或其他 i18n composables 在 Nuxt 外掛中無效?

在 Nuxt 外掛或工具函式中使用 Nuxt I18n composables(`$t`、`$getLocale`、`$localePath` 等)可能不如預期,並導致執行時錯誤。

**原因與解法:**
Nuxt composables 需要特定上下文(例如 Nuxt hooks 或 Vue setup 函式)才能存取 Nuxt 實例。若在這些上下文之外使用(例如在工具函式或外掛中),主控台可能會出現以下錯誤:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**解法 1:使用 `runWithContext`**
在非同步操作後呼叫 i18n composables 時,使用 [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) 以保留必要的上下文。

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**解法 2:先取得值**
或者先取得翻譯值,再傳入工具函式。

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**解法 3:在服務中傳遞翻譯鍵**
在服務或工具函式中,改為傳遞翻譯鍵而非直接使用 `$t`。然後在元件中取得翻譯。

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 語系切換

### ❓ 不改變 URL 就切換語系?

可以 —— 但取決於你的[路由策略](/guides/routing-strategies)。

**`no_prefix` 策略** —— 語系不屬於 URL。可使用 `$switchLocale()` 在維持相同路徑下切換語系並重新載入翻譯:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

或以 `useI18nLocale().setLocale('de')` 只更新偏好。若要在客戶端完整重新載入翻譯,建議使用 `$switchLocale()`。

**前綴策略**(`prefix`、`prefix_except_default`、…)—— 語系與 URL 相連。`$switchLocale()` 一律導覽至在地化路由。並無 `redirect: false` 選項。

若你只需要目標 URL(例如語言切換連結),請改用 `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

所有切換方法請見 [Route & Locale Switching](/api/methods#-route-locale-switching)。

### ❓ 切換語系時頁面捲到頂端(或跳動)?

這是預期行為 —— 是 **Vue Router / Nuxt 的捲動行為**,並非 nuxt-i18n-micro 特有的問題。

在前綴策略(`prefix`、`prefix_except_default`、…)下,`$switchLocale()` 會執行正常的客戶端導覽(`/en/page` → `/de/page`)。Nuxt 預設的 [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) 在路由變更時會捲到頂端(除了透過 `savedPosition` 的瀏覽器上一頁/下一頁)。

nuxt-i18n-micro 不會額外做隱藏式的捲動處理 —— 請在你的應用中使用一個小型包裝元件。

**`SwitchLocalePreserve` 包裝元件**

將 [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) 複製到你的專案(`components/SwitchLocalePreserve.vue`)。可運作的示範:[`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue)。

在頁面上設定 `scrollToTop: false`,並包裹你的切換 UI。以 `data-locale` 標記可點擊的目標 —— 包裝元件會攔截點擊、呼叫 `$switchLocale`,並在翻譯長度改變版面時還原捲動位置:

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

該元件會:

1. **點擊時** —— 讀取插槽內被點擊元素上的 `data-locale`(按鈕、連結或任何自訂標記)。
2. **`$switchLocale` 之前** —— 儲存 `scrollY` 與被點擊元素的位置(讓它保持在游標下方)。
3. **導覽期間** —— 一次性 patch `router.options.scrollBehavior`,回傳 `\{ top: scrollY \}` 而非捲到頂端。
4. **導覽後** —— 等待 `page:finish`,然後重新套用捲動,同時透過 `ResizeObserver` 捕捉因翻譯長度不同而造成的版面偏移。

在使用此包裝元件的頁面上必須設定 `scrollToTop: false`。文件:[Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta)。

請勿在被包裝的控制項上直接呼叫 `$switchLocale` —— 包裝元件會處理切換。對於在包裝外的 `<NuxtLink :to="$switchLocalePath('fr')">`,捲動行為會遵循 Nuxt 正常路由,除非你另外新增自己的 `app/router.options.ts`。

## 🌐 翻譯問題

### ❓ 為什麼在頁面轉場期間,翻譯會失效,特別是使用 `defineAsyncComponent` 時?

在 `nuxt-i18n-micro` 搭配頁面轉場時,翻譯可能在轉場期間短暫失效。此問題發生於路由在轉場完成前就改變,導致新頁面的翻譯還在載入,而舊頁面仍可見。

**根本原因:**

- 頁面轉場在翻譯完全載入前就改變路由
- `defineAsyncComponent` 與 `useAsyncData` 可能延遲翻譯載入
- 載入期間翻譯鍵可能顯示為原始路徑

**解法 1:累積合併(內建,無需設定)**

在 v3 中,模組會自動使用累積合併策略。在同一語系內導覽時,新頁面的翻譯會合併到現行字典,而非取代它。這代表前一頁的翻譯在轉場動畫期間仍然可用。轉場結束後(`page:transition:finish` hook),舊鍵會自動清除。

無需設定 —— 開箱即用。

**解法 2:明確的路由上下文**

若你偏好手動控制,可明確將目前路由傳入 `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**解法 3:載入狀態**

實作載入狀態,以優雅地處理翻譯載入:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ 為什麼在 Vercel 上 SSR 期間翻譯鍵無法解析?

**SSR 上 `$fetch` 的限制**
在 Vercel 這類無伺服器平台上,`$fetch` 只能從 CDN 抓取靜態檔,而無法從內部 Nitro 伺服器抓取。這代表除非設定正確的 base URL,否則靜態翻譯檔可能無法直接存取。

**設定 `apiBaseClientHost` 與 `apiBaseServerHost` 修正**
若翻譯託管於外部 CDN 或不同網域,請對客戶端請求使用 `apiBaseClientHost`,對伺服器端請求使用 `apiBaseServerHost`。`apiBaseUrl` 應只包含路徑前綴(例如 `_locales`)。

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

或透過環境變數:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

翻譯就會在客戶端與伺服器端,皆從 `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` 抓取。

## 🔗 路由與導覽問題

### ❓ 可以在翻譯字串中直接使用 `NuxtLink` 或 `<i18n-link>` 嗎?

可以,`Nuxt I18n Micro` 透過 `<i18n-t>` 元件,允許在翻譯中使用 `NuxtLink` 或 `<i18n-link>`,特別有助於處理語法及 RTL 語言的需求,無需分割翻譯字串。

**範例:**

翻譯檔:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue 範本:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

這讓翻譯中可放入動態連結,同時保持適當的在地化結構。

## 🏗️ 建置與部署問題

### ❓ 為什麼翻譯 payload 會被放在 `public/_locales/` 底下(或在 Edge 上進到伺服器 bundle)?

SSR 與客戶端都需要相同的 `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json` payload。它們如何被打包,取決於 Nitro 的目標:

**說明:**

- **Node(預設):**模組**不會**將翻譯以 Nitro `serverAssets` / Rollup `raw:` 內嵌(這會在大字典時撐爆建置記憶體)。它會將預合併的樹狀結構複製到 `public/<apiBaseUrl>/`(預設 `_locales`),SSR 以 `readFile` 讀取那些檔案。客戶端 `$fetch` 相同的 URL —— 可作為靜態檔或透過 Nitro 處理器提供。
- **Edge**(`nitro.node === false`):SSR 沒有可持久使用的 public 檔案系統,因此 payload 會透過 Nitro `serverAssets`(`assets:i18n`)內嵌。建議使用 `translationPayloads.mode: 'source'`,讓內嵌保持精簡。只有同時需要 CDN/靜態複本時,才設定 `publicAssets: true`。
- **`prerenderRoutes`:**可選。在 premerged 模式下,`publicAssets` 已寫入 `\{page\}/\{locale\}/data.json`,因此預渲染那些路由通常多餘。

### ❓ 為什麼會出現關於 `@unhead/vue` 或未定義物件的建置錯誤,特別是在 Cloudflare Pages 上?

**原因:**
某些專案在使用 `nuxt-i18n-micro` 時,可能因建置衝突或缺少相依而出錯。特別是:

- 部署到 **Cloudflare Pages** 或 **Cloudflare Workers** 時,可能需要額外的相容性旗標。
- 若相依套件如 `@unhead/vue` 未正確安裝,預渲染步驟可能失敗。
- 某些模組(例如 **nuxthub**、**nitro-cloudflare-dev**)若未搭配正確旗標或相依,可能引入衝突。

**可能解法:**

**解法 1:手動安裝 `@unhead/vue`**
若建置錯誤提到找不到 `@unhead/vue`,請將它直接安裝到專案相依中:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

這可確保它在 Nitro 預渲染階段可用。

**解法 2:加入 Cloudflare 相容性旗標**
使用 Cloudflare Pages 或 Cloudflare Workers 時,Node.js 相容性通常預設為停用。請在 `wrangler.toml` 中啟用:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

此旗標可讓許多 Node.js 模組(包括 `nuxt-i18n-micro` 所使用者)順利執行。

## 🔍 SEO 與 `@nuxtjs/seo`

### ❓ 錯誤:`nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

發生原因是 **`@nuxtjs/seo`** 引入了較舊的 **`nuxt-site-config` 3.x**,而其 i18n 外掛僅為 `@nuxtjs/i18n` 註冊,並不支援 **nuxt-i18n-micro**。

**修正:**

1. 升級到 **`@nuxtjs/seo` 3+**(內含支援 micro 的 `nuxt-site-config` 4+)。
2. 在 `modules` 中,將 **`nuxt-i18n-micro` 放在 `@nuxtjs/seo` 之前**。
3. 保留 **`i18n.meta: true`** 以支援語系相關的 head 標籤。

完整範例請參閱 [SEO 指南 —— Nuxt SEO 章節](/guides/seo#nuxt-seo-nuxtjs-seo)。

## 🔧 設定與相容性

### ❓ `Nuxt I18n Micro` 是受 `vue-i18n` 啟發嗎?那 modifier 呢?

雖然 `Nuxt I18n Micro` 作為 `nuxt-i18n` 的效能替代方案,但它是獨立於 `vue-i18n` 開發的。雖然某些方法名稱與參數可能相似,底層實作差異甚大。

**Modifier**:維護者曾考慮過 modifier,但結論是像 `<i18n-t>` 與 `<i18n-link>` 這類元件已能有效滿足這類需求。

例如:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

這種做法很有彈性,因此目前並未釋出 modifier。不過若有需求,未來版本可能會加入。
