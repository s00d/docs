# ❓ الأسئلة الشائعة: المشاكل الشائعة والحلول

اعثر على إجابات للأسئلة الشائعة وحلول للمشاكل الشائعة مع Nuxt I18n Micro.

## 🚀 مشاكل البدء

### ❓ ماذا لو لم يُحمَّل مسار ما؟

عند استخدام `Nuxt I18n Micro`، قد لا تُحمَّل بعض المسارات كما هو متوقّع، خاصةً إذا لم يعيّن الموجّه اسمًا تلقائيًا لمسار في مجلد فرعي.

**الحل:**
لمعالجة ذلك، عرّف اسم المسار يدويًا للصفحة بإضافة ما يلي إلى ملف Vue المقابل:

```javascript
definePageMeta({ name: 'pageName' })
```

يضمن هذا تسجيل المسار بشكل صحيح، مما يتيح التنقل السلس داخل التطبيق.

### ❓ لماذا لا يعمل `$t` أو composables i18n الأخرى في إضافات Nuxt؟

قد لا تعمل composables الخاصة بـ Nuxt I18n (`$t` و`$getLocale` و`$localePath` وغيرها) كما هو متوقّع داخل إضافات Nuxt أو الدوال المساعدة، مما يؤدي إلى أخطاء في وقت التشغيل.

**السبب والحل:**
تتطلّب composables في Nuxt سياقات محدّدة (مثل خطافات Nuxt أو دوال إعداد Vue) للوصول إلى مثيل Nuxt. إذا استُخدمت خارج هذه السياقات (مثل الدوال المساعدة أو الإضافات)، فقد يظهر الخطأ التالي في وحدة التحكم:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**الحل 1: استخدم `runWithContext`**
لاستدعاء composables i18n بعد عملية غير متزامنة، استخدم [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) للحفاظ على السياق اللازم.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**الحل 2: اجلب القيمة أولًا**
بدلًا من ذلك، اجلب قيمة الترجمة أولًا، ثم مرّرها إلى دالة مساعدة.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**الحل 3: مرّر مفاتيح الترجمة في الخدمات**
في الخدمات أو الدوال المساعدة، مرّر مفاتيح الترجمة بدلاً من استخدام `$t` مباشرةً. ثم اجلب الترجمة في المكوّن.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 تبديل اللغة

### ❓ هل يمكن تبديل اللغة دون تغيير عنوان URL؟

نعم — لكن ذلك يعتمد على [استراتيجية التوجيه](/guides/routing-strategies) لديك.

**استراتيجية `no_prefix`** — اللغة ليست جزءًا من عنوان URL. استخدم `$switchLocale()` لتغيير اللغة وإعادة تحميل الترجمات مع البقاء على المسار نفسه:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

أو حدّث التفضيل فقط باستخدام `useI18nLocale().setLocale('de')`. لإعادة تحميل الترجمة كاملة من جانب العميل، يُفضَّل استخدام `$switchLocale()`.

**استراتيجيات البادئة** (`prefix` و`prefix_except_default` وغيرها) — اللغة وعنوان URL مرتبطان. تنتقل `$switchLocale()` دائمًا إلى المسار المترجَم. لا يوجد خيار `redirect: false`.

إذا كنت تحتاج فقط إلى عنوان URL الهدف (مثل رابط مبدّل اللغة)، فاستخدم `$switchLocalePath()` بدلًا من ذلك:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

اطلع على [التوجيه وتبديل اللغة](/api/methods#-route-locale-switching) لجميع طرق التبديل.

### ❓ تنتقل الصفحة إلى الأعلى (أو تقفز) عند تبديل اللغة؟

هذا متوقّع — إنه **سلوك تمرير Vue Router / Nuxt**، وليس شيئًا خاصًا بـ nuxt-i18n-micro.

مع استراتيجيات البادئة (`prefix` و`prefix_except_default` وغيرها)، تُنفّذ `$switchLocale()` تنقّلًا عاديًا من جانب العميل (`/en/page` → `/de/page`). الافتراضي لـ [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) في Nuxt يمرّر إلى الأعلى عند تغييرات المسار (باستثناء الرجوع/التقدّم في المتصفح عبر `savedPosition`).

لا تضيف nuxt-i18n-micro معالجة تمرير خفية — استخدم مكوّنًا مغلِّفًا صغيرًا في تطبيقك.

**المغلِّف `SwitchLocalePreserve`**

انسخ [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) إلى مشروعك (`components/SwitchLocalePreserve.vue`). عرض توضيحي عملي: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

في الصفحة، عيّن `scrollToTop: false` ولفّ واجهة المبدّل. علّم العناصر القابلة للنقر بـ `data-locale` — يعترض المغلِّف النقرات، ويستدعي `$switchLocale`، ويستعيد التمرير (بما في ذلك عندما يغيّر طول الترجمة التخطيط):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

المكوّن:

1. **عند النقر** — يقرأ `data-locale` على العنصر المنقور داخل الفتحة (الأزرار أو الروابط أو أي ترميز مخصّص).
2. **قبل** `$switchLocale` — يخزّن `scrollY` وموضع العنصر المنقور (يبقيه تحت المؤشر).
3. **أثناء** التنقّل — يُرقّع `router.options.scrollBehavior` مرة واحدة ويُعيد `\{ top: scrollY \}` بدلًا من التمرير إلى الأعلى.
4. **بعد** التنقّل — ينتظر `page:finish`، ثم يعيد تطبيق التمرير بينما يلتقط `ResizeObserver` أي إزاحات تخطيط بسبب اختلاف أطوال الترجمة.

يجب تعيين `scrollToTop: false` على الصفحات التي تستخدم فيها هذا المغلِّف. التوثيق: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

لا تستدعِ `$switchLocale` مباشرةً على عناصر التحكّم الملتفّة — يتعامل المغلِّف مع التبديل. بالنسبة إلى `<NuxtLink :to="$switchLocalePath('fr')">` خارج المغلِّف، يتبع سلوك التمرير التوجيه العادي في Nuxt ما لم تُضِف ملف `app/router.options.ts` الخاص بك.

## 🌐 مشاكل الترجمة

### ❓ لماذا تتعطّل الترجمات أثناء انتقالات الصفحة، خاصةً مع `defineAsyncComponent`؟

عند استخدام `nuxt-i18n-micro` مع انتقالات الصفحات، قد تتوقف الترجمات لفترة وجيزة أثناء الانتقال. تحدث هذه المشكلة لأن المسار يتغيّر قبل اكتمال الانتقال، مما يؤدي إلى تحميل ترجمات الصفحة الجديدة بينما لا تزال الصفحة القديمة مرئية.

**السبب الجذري:**

- تسبب انتقالات الصفحة تغييرات في المسار قبل تحميل الترجمات بالكامل
- يمكن أن يؤخّر `defineAsyncComponent` و`useAsyncData` تحميل الترجمة
- قد تظهر مفاتيح الترجمة كمسارات خام أثناء التحميل

**الحل 1: الدمج التراكمي (مدمج، لا حاجة للإعداد)**

في الإصدار v3، تستخدم الوحدة تلقائيًا استراتيجية دمج تراكمي. عند التنقل داخل اللغة نفسها، تُدمج ترجمات الصفحة الجديدة في القاموس النشط بدلًا من استبداله. هذا يعني أن الترجمات من الصفحة السابقة تبقى متاحة أثناء تأثير الانتقال. بعد انتهاء الانتقال (خطاف `page:transition:finish`)، تُنظَّف المفاتيح القديمة تلقائيًا.

لا حاجة إلى إعداد — يعمل هذا خارج الصندوق.

**الحل 2: سياق مسار صريح**

إذا كنت تفضّل التحكّم اليدوي، مرّر المسار الحالي صراحةً إلى `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**الحل 3: حالات التحميل**

نفّذ حالات التحميل للتعامل مع تحميل الترجمة بأناقة:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ لماذا لا تُحلّ مفاتيح الترجمة أثناء SSR على Vercel؟

**قيود `$fetch` على SSR**
في المنصات بدون خادم مثل Vercel، يمكن لـ `$fetch` فقط جلب الملفات الثابتة من CDN وليس من خادم Nitro الداخلي. هذا يعني أن ملفات الترجمة الثابتة قد لا تكون متاحة مباشرةً ما لم يُضبَط عنوان URL الأساسي بشكل صحيح.

**الحل بضبط `apiBaseClientHost` و`apiBaseServerHost`**
إذا كانت الترجمات مستضافة خارجيًا على CDN أو نطاق مختلف، استخدم `apiBaseClientHost` للطلبات من جانب العميل و`apiBaseServerHost` للطلبات من جانب الخادم. يجب أن يحتوي `apiBaseUrl` على البادئة فقط (مثل `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

أو عبر متغيرات البيئة:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

ستُجلب الترجمات من `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` على كل من العميل والخادم.

## 🔗 مشاكل التوجيه والتنقل

### ❓ هل يمكنني استخدام `NuxtLink` أو `<i18n-link>` مباشرةً في نصوص الترجمة؟

نعم، يسمح `Nuxt I18n Micro` باستخدام `NuxtLink` أو `<i18n-link>` داخل الترجمات من خلال مكوّن `<i18n-t>`، وهو مفيد خاصةً للتعامل مع القواعد ومتطلّبات اللغات RTL دون تقسيم نصوص الترجمة.

**مثال:**

ملف الترجمة:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

قالب Vue:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

يتيح هذا روابط ديناميكية داخل الترجمات مع الحفاظ على هيكل التوطين الصحيح.

## 🏗️ مشاكل البناء والنشر

### ❓ لماذا تنتهي حمولات الترجمة تحت `public/_locales/` (أو في حزمة الخادم على Edge)؟

يحتاج كل من SSR والعميل إلى نفس الحمولات `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. تعتمد كيفية تعبئتها على هدف Nitro:

**التفسير:**

- **Node (الافتراضي):** الوحدة **لا** تُضمِّن الترجمات كـ Nitro `serverAssets` / Rollup `raw:` (تلك الطريقة كانت تُفجّر ذاكرة البناء مع الفهارس الكبيرة). بدلًا من ذلك تنسخ الشجرة المدموجة مسبقًا إلى `public/<apiBaseUrl>/` (الافتراضي `_locales`) ويقرأ SSR تلك الملفات باستخدام `readFile`. يقوم العميل بـ `$fetch` لنفس العناوين — إما كملفات ثابتة أو عبر معالج Nitro.
- **Edge** (`nitro.node === false`): لا يوجد نظام ملفات عام دائم لـ SSR، لذلك تُضمَّن الحمولات عبر Nitro `serverAssets` (`assets:i18n`). يُفضَّل `translationPayloads.mode: 'source'` حتى يبقى التضمين مضغوطًا. عيّن `publicAssets: true` فقط إذا كنت تحتاج أيضًا إلى نسخة CDN/ثابتة.
- **`prerenderRoutes`:** اختياري. في الوضع premerged يكتب `publicAssets` بالفعل `\{page\}/\{locale\}/data.json`، لذا فإن التوليد المسبق لتلك المسارات عادةً ما يكون زائدًا.

### ❓ لماذا يظهر لي خطأ بناء يشير إلى `@unhead/vue` أو كائن غير معرَّف، خاصةً على Cloudflare Pages؟

**السبب:**
تواجه بعض المشاريع تعارضات في البناء أو تبعيات مفقودة عند استخدام `nuxt-i18n-micro`. بشكل خاص:

- قد تتطلّب عمليات النشر على **Cloudflare Pages** أو **Cloudflare Workers** رايات توافق إضافية.
- يمكن أن تفشل خطوات التوليد المسبق إذا لم تكن التبعيات مثل `@unhead/vue` مثبَّتة بشكل صحيح.
- يمكن لبعض الوحدات (مثل **nuxthub** و**nitro-cloudflare-dev**) أن تُحدث تعارضات ما لم تُضبط برايات أو تبعيات صحيحة.

**الحلول الممكنة:**

**الحل 1: ثبّت `@unhead/vue` يدويًا**
إذا اشتكى خطأ البناء من عدم العثور على `@unhead/vue`، ثبّتها مباشرةً في تبعيات مشروعك:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

يضمن هذا توفّرها أثناء مرحلة التوليد المسبق في Nitro.

**الحل 2: أضف رايات توافق Cloudflare**
عند استخدام Cloudflare Pages أو Cloudflare Workers، غالبًا ما يكون توافق Node.js معطّلًا افتراضيًا. فعّله في ملف `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

تتيح هذه الراية للعديد من وحدات Node.js (بما فيها التي يستخدمها `nuxt-i18n-micro`) العمل بسلاسة.

## 🔍 SEO و`@nuxtjs/seo`

### ❓ الخطأ: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

يحدث هذا عندما تسحب **`@nuxtjs/seo`** إصدارًا قديمًا من **`nuxt-site-config` 3.x** يسجّل إضافة i18n الخاصة به فقط لـ `@nuxtjs/i18n` وليس لـ **nuxt-i18n-micro**.

**الحل:**

1. الترقية إلى **`@nuxtjs/seo` 3+** (تتضمّن `nuxt-site-config` 4+ مع دعم micro).
2. ضع **`nuxt-i18n-micro` قبل `@nuxtjs/seo`** في `modules`.
3. أبقِ **`i18n.meta: true`** للحصول على وسوم رأس (head) واعية باللغة.

اطّلع على [دليل SEO — قسم Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo) للحصول على مثال كامل.

## 🔧 الإعداد والتوافق

### ❓ هل `Nuxt I18n Micro` مستوحى من `vue-i18n`؟ ماذا عن المعدِّلات (modifiers)؟

بينما يعمل `Nuxt I18n Micro` كبديل عالي الأداء لـ `nuxt-i18n`، فهو مبني باستقلالية عن `vue-i18n`. رغم أن بعض أسماء الدوال والمعاملات قد تكون متشابهة، إلا أن الوظائف الأساسية تختلف اختلافًا كبيرًا.

**المعدِّلات**: نظر المشرف في البداية في المعدِّلات، لكنه استنتج أن مكوّنات مثل `<i18n-t>` و`<i18n-link>` تلبّي تلك الاحتياجات بفعالية.

على سبيل المثال:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

هذا النهج مرن، لذا فإن إصدار المعدِّلات ليس ضروريًا حاليًا. ومع ذلك، قد تُضاف المعدِّلات في إصدارات مستقبلية إذا كان هناك طلب.
