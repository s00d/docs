# ❓ FAQ: Časté problémy a řešení

Najděte odpovědi na často kladené otázky a řešení běžných problémů s Nuxt I18n Micro.

## 🚀 Problémy se zahájením

### ❓ Co když se routa nenačte?

Při použití `Nuxt I18n Micro` se některé routy nemusí načíst, jak se očekává, obzvláště pokud router automaticky nepřiřadí název route v podadresářích.

**Řešení:**
Chcete-li to řešit, definujte název route pro stránku ručně přidáním následujícího do odpovídajícího Vue souboru:

```javascript
definePageMeta({ name: 'pageName' })
```

Tím zajistíte správnou registraci routy a umožníte bezproblémovou navigaci v aplikaci.

### ❓ Proč `$t` nebo jiné i18n composables nefungují v Nuxt pluginech?

Nuxt I18n composables (`$t`, `$getLocale`, `$localePath` a další) nemusí uvnitř Nuxt pluginů nebo utility funkcí fungovat, jak se očekává, což vede k runtime chybám.

**Příčina a řešení:**
Nuxt composables vyžadují konkrétní kontexty (například Nuxt hooks nebo Vue setup funkce) pro přístup k Nuxt instanci. Použití mimo tyto kontexty (například v utility funkcích nebo pluginech) může v konzoli způsobit následující chybu:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Řešení 1: Použijte `runWithContext`**
Pro volání i18n composables po asynchronní operaci použijte [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) k zachování potřebného kontextu.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Řešení 2: Nejprve získejte hodnotu**
Alternativně nejprve získejte hodnotu překladu a pak ji předejte utility funkci.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Řešení 3: Předávejte klíče překladů ve službách**
Ve službách nebo utility funkcích předávejte klíče překladů místo přímého použití `$t`. Pak překlad získejte v komponentě.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Přepínání locale

### ❓ Přepnutí locale beze změny URL?

Ano, ale záleží na vaší [strategii routování](/guides/routing-strategies).

**Strategie `no_prefix`**: locale není součástí URL. Pro změnu locale a znovunačtení překladů při setrvání na stejné cestě použijte `$switchLocale()`:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Nebo aktualizujte jen preferenci přes `useI18nLocale().setLocale('de')`. Pro plné znovunačtení překladů na klientu preferujte `$switchLocale()`.

**Prefixové strategie** (`prefix`, `prefix_except_default`, …): locale a URL jsou propojené. `$switchLocale()` vždy naviguje na lokalizovanou routu. Volba `redirect: false` neexistuje.

Pokud potřebujete jen cílovou URL (například odkaz pro přepínač jazyka), použijte místo toho `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Všechny metody přepínání najdete v [Přepínání route a locale](/api/methods#-route-locale-switching).

### ❓ Stránka se při přepnutí locale posouvá nahoru (nebo skáče)?

To je očekávané. Jde o **chování scrollování Vue Router / Nuxt**, ne o nic specifického pro nuxt-i18n-micro.

S prefixovými strategiemi (`prefix`, `prefix_except_default`, …) provádí `$switchLocale()` normální klientskou navigaci (`/en/page` → `/de/page`). Výchozí Nuxt [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) skroluje na začátek při změně routy (kromě prohlížečových back/forward přes `savedPosition`).

nuxt-i18n-micro nepřidává skryté zpracování scrollování. Použijte v aplikaci malou wrapper komponentu.

**Wrapper `SwitchLocalePreserve`**

Zkopírujte [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) do svého projektu (`components/SwitchLocalePreserve.vue`). Funkční demo: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

Na stránce nastavte `scrollToTop: false` a obalte UI přepínače. Klikatelné cíle označte pomocí `data-locale`. Wrapper zachytí kliknutí, zavolá `$switchLocale` a obnoví scroll (i když se změna délky překladů promítne do layoutu):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Komponenta:

1. **Při kliknutí**: čte `data-locale` na kliknutém elementu uvnitř slotu (tlačítka, odkazy nebo libovolný vlastní markup).
2. **Před** `$switchLocale`: uloží `scrollY` a pozici kliknutého elementu (udrží ho pod kurzorem).
3. **Během** navigace: jednou patchne `router.options.scrollBehavior` a vrátí `\{ top: scrollY \}` místo scrollování na začátek.
4. **Po** navigaci: počká na `page:finish`, pak znovu aplikuje scroll, zatímco `ResizeObserver` zachytí posuny layoutu z různých délek překladů.

`scrollToTop: false` je povinné na stránkách, kde tento wrapper používáte. Dokumentace: [Nuxt: `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Nevolejte `$switchLocale` přímo na obalených kontrolkách. Přepínání zajišťuje wrapper. Pro `<NuxtLink :to="$switchLocalePath('fr')">` mimo wrapper následuje chování scrollování normální Nuxt routing, pokud nepřidáte vlastní `app/router.options.ts`.

## 🌐 Problémy s překlady

### ❓ Proč se překlady během přechodů mezi stránkami rozbíjí, obzvláště s `defineAsyncComponent`?

Při použití `nuxt-i18n-micro` s přechody mezi stránkami mohou překlady během přechodu krátce přestat fungovat. Tento problém nastává, protože se routa mění dřív, než přechod skončí, což způsobuje, že se překlady pro novou stránku načítají, zatímco je stará stránka stále viditelná.

**Hlavní příčina:**

- Přechody stránek způsobují změnu route dřív, než jsou překlady plně načtené
- `defineAsyncComponent` a `useAsyncData` mohou zdržet načtení překladů
- Klíče překladů se během načítání mohou zobrazit jako holé cesty

**Řešení 1: Kumulativní merge (vestavěné, žádná konfigurace)**

Ve v3 modul automaticky používá kumulativní merge strategii. Při navigaci v rámci stejného locale se nové překlady stránky slučují do aktivního slovníku místo jeho nahrazení. To znamená, že překlady z předchozí stránky zůstávají dostupné během přechodové animace. Po dokončení přechodu (hook `page:transition:finish`) se staré klíče automaticky uklidí.

Žádná konfigurace není potřeba, funguje to hned po instalaci.

**Řešení 2: Explicitní kontext route**

Pokud preferujete manuální kontrolu, explicitně předávejte aktuální routu do `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Řešení 3: Loading stavy**

Implementujte loading stavy pro elegantní zpracování načítání překladů:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Proč se klíče překladů během SSR na Vercelu neresolvují?

**Omezení `$fetch` na SSR**
Na serverless platformách jako Vercel může `$fetch` fetchovat statické soubory pouze z CDN, ne z interního Nitro serveru. To znamená, že statické soubory překladů nemusí být přímo dostupné, pokud není nastavena správná base URL.

**Oprava nastavením `apiBaseClientHost` a `apiBaseServerHost`**
Pokud jsou překlady hostované externě na CDN nebo jiné doméně, použijte `apiBaseClientHost` pro klientské požadavky a `apiBaseServerHost` pro serverové požadavky. `apiBaseUrl` by měla obsahovat jen prefix cesty (například `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Nebo přes proměnné prostředí:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Překlady se pak budou fetchovat z `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` na klientu i na serveru.

## 🔗 Problémy s routováním a navigací

### ❓ Můžu použít `NuxtLink` nebo `<i18n-link>` přímo v řetězcích překladů?

Ano, `Nuxt I18n Micro` umožňuje použití `NuxtLink` nebo `<i18n-link>` v překladech přes komponentu `<i18n-t>`, což je zvláště užitečné pro řešení požadavků na gramatiku a RTL jazyky bez rozdělování překladových řetězců.

**Příklad:**

Soubor s překlady:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue šablona:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

To umožňuje dynamické odkazy v překladech při zachování správné lokalizační struktury.

## 🏗️ Problémy s buildem a nasazením

### ❓ Proč payloady překladů končí pod `public/_locales/` (nebo v server bundlu na Edge)?

SSR i klient potřebují stejné payloady `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. Způsob jejich zabalení závisí na Nitro targetu:

**Vysvětlení:**

- **Node (výchozí):** modul **nevkládá** překlady jako Nitro `serverAssets` / Rollup `raw:` (to vyhazovalo build RAM na velkých katalozích). Místo toho kopíruje premerged strom do `public/<apiBaseUrl>/` (výchozí `_locales`) a SSR tyto soubory čte pomocí `readFile`. Klient `$fetch`uje stejné URL, buď jako statické soubory nebo přes Nitro handler.
- **Edge** (`nitro.node === false`): neexistuje trvalý veřejný FS pro SSR, takže se payloady vkládají přes Nitro `serverAssets` (`assets:i18n`). Preferujte `translationPayloads.mode: 'source'`, aby embed zůstal kompaktní. `publicAssets: true` nastavte, jen když potřebujete také CDN/statickou kopii.
- **`prerenderRoutes`:** volitelné. V premerged režimu `publicAssets` už zapisuje `\{page\}/\{locale\}/data.json`, takže prerenderování těchto rout je obvykle redundantní.

### ❓ Proč dostávám build error odkazující na `@unhead/vue` nebo undefined objekt, obzvláště na Cloudflare Pages?

**Příčina:**
Některé projekty zažívají konflikty buildu nebo chybějící závislosti při použití `nuxt-i18n-micro`. Zejména:

- Nasazení na **Cloudflare Pages** nebo **Cloudflare Workers** mohou vyžadovat další flagy kompatibility.
- Kroky prerenderingu mohou selhat, pokud nejsou závislosti jako `@unhead/vue` správně nainstalované.
- Některé moduly (například **nuxthub**, **nitro-cloudflare-dev**) mohou způsobovat konflikty, pokud nejsou nakonfigurované se správnými flagy nebo závislostmi.

**Možná řešení:**

**Řešení 1: Nainstalujte `@unhead/vue` ručně**
Pokud build error uvádí, že nemůže najít `@unhead/vue`, nainstalujte ho přímo do závislostí projektu:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Tím zajistíte dostupnost během Nitro prerender fáze.

**Řešení 2: Přidejte Cloudflare compatibility flagy**
Při použití Cloudflare Pages nebo Cloudflare Workers je Node.js kompatibilita často ve výchozím stavu vypnutá. Zapněte ji ve `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Tento flag umožňuje mnoha Node.js modulům (včetně těch používaných `nuxt-i18n-micro`) hladce běžet.

## 🔍 SEO a `@nuxtjs/seo`

### ❓ Chyba: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Toto se stává, když **`@nuxtjs/seo`** táhne starý **`nuxt-site-config` 3.x**, který registruje svůj i18n plugin jen pro `@nuxtjs/i18n`, ne pro **nuxt-i18n-micro**.

**Oprava:**

1. Upgradujte na **`@nuxtjs/seo` 3+** (obsahuje `nuxt-site-config` 4+ s podporou micro).
2. V `modules` umístěte **`nuxt-i18n-micro` před `@nuxtjs/seo`**.
3. Zachovejte **`i18n.meta: true`** pro locale-aware head tagy.

Kompletní příklad najdete v [Průvodci SEO: sekce Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo).

## 🔧 Konfigurace a kompatibilita

### ❓ Je `Nuxt I18n Micro` inspirován `vue-i18n`? A co modifikátory?

Zatímco `Nuxt I18n Micro` slouží jako výkonová alternativa k `nuxt-i18n`, je postaven nezávisle na `vue-i18n`. I když mohou být některé názvy metod a parametrů podobné, spodní funkčnost se výrazně liší.

**Modifikátory**: Údržbář původně modifikátory zvažoval, ale došel k závěru, že komponenty jako `<i18n-t>` a `<i18n-link>` tyto potřeby efektivně řeší.

Například:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Tento přístup je flexibilní, takže vydání modifikátorů je aktuálně nepotřebné. Modifikátory však mohou být přidány v budoucích vydáních, pokud bude poptávka.
