# ❓ FAQ: Časté problémy a řešení

Najděte odpovědi na často kladené otázky a řešení běžných problémů s Nuxt I18n Micro.

## 🚀 Problémy při startu

### ❓ Co dělat, pokud se routa nenačte?

Při použití `Nuxt I18n Micro` se některé routy nemusí načíst podle očekávání, zejména pokud router automaticky nepřiřadí routě v podsložkách název.

**Řešení:**
Chcete-li to řešit, ručně definujte název routy pro stránku přidáním následujícího do odpovídajícího Vue souboru:

```javascript
definePageMeta({ name: 'pageName' })
```

Tímto zajistíte, že routa je řádně registrována, což umožňuje bezproblémovou navigaci v aplikaci.

### ❓ Proč `$t` nebo jiné i18n composables nefungují v Nuxt pluginech?

Nuxt I18n composables (`$t`, `$getLocale`, `$localePath` atd.) nemusí fungovat podle očekávání v Nuxt pluginech nebo utility funkcích, což vede k runtime chybám.

**Příčina a řešení:**
Nuxt composables vyžadují specifické kontexty (např. Nuxt hooky nebo Vue setup funkce) pro přístup k Nuxt instanci. Pokud jsou používány mimo tyto kontexty (např. v utility funkcích nebo pluginech), v konzoli se může objevit následující chyba:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Řešení 1: Použijte `runWithContext`**
Chcete-li volat i18n composables po asynchronní operaci, použijte [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) k zachování potřebného kontextu.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Řešení 2: Nejprve získejte hodnotu**
Alternativně nejprve získejte hodnotu překladu a poté ji předejte utility funkci.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Řešení 3: Předávejte překladové klíče v službách**
V službách nebo utility funkcích předávejte překladové klíče místo přímého použití `$t`. Poté v komponentě získejte překlad.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Přepínání locale

### ❓ Přepnout locale bez změny URL?

Ano — ale záleží na vaší [strategii routování](/guides/routing-strategies).

**Strategie `no_prefix`** — locale není součástí URL. Použijte `$switchLocale()` ke změně locale a opětovnému načtení překladů při zachování stejné cesty:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Nebo aktualizujte pouze preferenci pomocí `useI18nLocale().setLocale('de')`. Pro plné znovunačtení překladů na straně klienta preferujte `$switchLocale()`.

**Prefix strategie** (`prefix`, `prefix_except_default`, …) — locale a URL jsou propojeny. `$switchLocale()` vždy naviguje na lokalizovanou routu. Neexistuje volba `redirect: false`.

Pokud potřebujete pouze cílovou URL (například odkaz v jazykovém přepínači), použijte místo toho `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Viz [Přepínání rout a locale](/api/methods#-route-locale-switching) pro všechny metody přepínání.

### ❓ Stránka skroluje nahoru (nebo skáče) při přepínání locale?

To se očekává — je to **chování skrolování Vue Router / Nuxt**, nikoli něco specifického pro nuxt-i18n-micro.

S prefix strategiemi (`prefix`, `prefix_except_default`, …) `$switchLocale()` provede normální klientskou navigaci (`/en/page` → `/de/page`). Výchozí [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) v Nuxt při změně routy skroluje nahoru (kromě zpět/vpřed prohlížeče přes `savedPosition`).

nuxt-i18n-micro nepřidává skryté zpracování skrolování — použijte ve své aplikaci malou wrapper komponentu.

**Wrapper `SwitchLocalePreserve`**

Zkopírujte [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) do svého projektu (`components/SwitchLocalePreserve.vue`). Funkční ukázka: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

Na stránce nastavte `scrollToTop: false` a obalte své přepínací UI. Klikatelné cíle označte pomocí `data-locale` — wrapper zachytí kliknutí, zavolá `$switchLocale` a obnoví skrolování (včetně případů, kdy délka překladu mění layout):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Komponenta:

1. **Při kliknutí** — přečte `data-locale` na kliknutém prvku uvnitř slotu (tlačítka, odkazy nebo jakýkoli vlastní markup).
2. **Před** `$switchLocale` — uloží `scrollY` a pozici kliknutého prvku (drží ho pod kurzorem).
3. **Během** navigace — jednou zapatchuje `router.options.scrollBehavior` a vrátí `\{ top: scrollY \}` místo skrolování nahoru.
4. **Po** navigaci — počká na `page:finish`, poté znovu aplikuje skrolování, zatímco `ResizeObserver` zachytává posuny layoutu z různých délek překladů.

`scrollToTop: false` je vyžadováno na stránkách, kde tento wrapper používáte. Dokumentace: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Nevolávejte `$switchLocale` přímo na obalených ovládacích prvcích — wrapper zajišťuje přepínání. Pro `<NuxtLink :to="$switchLocalePath('fr')">` mimo wrapper následuje chování skrolování normální routování Nuxt, pokud si nepřidáte vlastní `app/router.options.ts`.

## 🌐 Problémy s překlady

### ❓ Proč se překlady během přechodů mezi stránkami rozbíjejí, zejména s `defineAsyncComponent`?

Při použití `nuxt-i18n-micro` s přechody stránek mohou překlady během přechodu krátce přestat fungovat. Tento problém nastává, protože se routa mění před dokončením přechodu, což způsobuje, že překlady pro novou stránku se načítají, zatímco je stále vidět stará stránka.

**Kořenová příčina:**

- Přechody stránek způsobují změnu rout před úplným načtením překladů
- `defineAsyncComponent` a `useAsyncData` mohou zpozdit načítání překladů
- Překladové klíče se během načítání mohou objevit jako surové cesty

**Řešení 1: Kumulativní slučování (vestavěné, není potřeba konfigurace)**

Ve v3 modul automaticky používá strategii kumulativního slučování. Při navigaci v rámci stejného locale jsou překlady nové stránky sloučeny do aktivního slovníku místo jeho nahrazení. To znamená, že překlady z předchozí stránky zůstávají dostupné během přechodové animace. Po dokončení přechodu (`page:transition:finish` hook) jsou staré klíče automaticky vyčištěny.

Žádná konfigurace není potřeba — funguje to hned po vybalení.

**Řešení 2: Explicitní kontext routy**

Pokud dáváte přednost ruční kontrole, explicitně předejte aktuální routu do `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Řešení 3: Stavy načítání**

Implementujte stavy načítání pro elegantní zpracování načítání překladů:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Proč se překladové klíče neřeší při SSR na Vercelu?

**Omezení `$fetch` při SSR**
Na serverless platformách jako Vercel může `$fetch` načítat pouze statické soubory z CDN a ne z interního Nitro serveru. To znamená, že statické překladové soubory nemusí být přímo dostupné, pokud není nastavena správná základní URL.

**Oprava nastavením `apiBaseClientHost` a `apiBaseServerHost`**
Pokud jsou překlady hostovány externě na CDN nebo jiné doméně, použijte `apiBaseClientHost` pro klientské požadavky a `apiBaseServerHost` pro serverové požadavky. `apiBaseUrl` by měla obsahovat pouze prefix cesty (např. `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Nebo přes proměnné prostředí:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Překlady budou načteny z `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` na klientu i serveru.

## 🔗 Problémy s routováním a navigací

### ❓ Mohu použít `NuxtLink` nebo `<i18n-link>` přímo v překladových řetězcích?

Ano, `Nuxt I18n Micro` umožňuje použití `NuxtLink` nebo `<i18n-link>` uvnitř překladů prostřednictvím komponenty `<i18n-t>`, což je zvláště užitečné pro zpracování gramatických požadavků a požadavků RTL jazyků bez rozdělování překladových řetězců.

**Příklad:**

Překladový soubor:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue šablona:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

To umožňuje dynamické odkazy uvnitř překladů při zachování správné lokalizační struktury.

## 🏗️ Problémy s buildem a nasazením

### ❓ Proč překladové payloady končí pod `public/_locales/` (nebo v serverovém bundle na Edge)?

SSR i klient potřebují stejné payloady `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. Jak jsou zabalené, závisí na Nitro cíli:

**Vysvětlení:**

- **Node (výchozí):** modul **nevkládá** překlady jako Nitro `serverAssets` / Rollup `raw:` (to při velkých katalozích vyhazovalo RAM při buildu). Místo toho kopíruje premerged strom do `public/<apiBaseUrl>/` (výchozí `_locales`) a SSR tyto soubory čte pomocí `readFile`. Klient `$fetch`uje stejné URL — buď jako statické soubory, nebo přes Nitro handler.
- **Edge** (`nitro.node === false`): pro SSR neexistuje trvalý veřejný FS, takže se payloady vkládají přes Nitro `serverAssets` (`assets:i18n`). Preferujte `translationPayloads.mode: 'source'`, aby vložení zůstalo kompaktní. Nastavte `publicAssets: true` pouze pokud potřebujete také CDN/statickou kopii.
- **`prerenderRoutes`:** volitelné. V režimu premerged `publicAssets` již zapisuje `\{page\}/\{locale\}/data.json`, takže prerenderování těchto rout je obvykle nadbytečné.

### ❓ Proč dostávám chybu buildu odkazující na `@unhead/vue` nebo nedefinovaný objekt, zejména na Cloudflare Pages?

**Příčina:**
Některé projekty mají při použití `nuxt-i18n-micro` konflikty buildu nebo chybějící závislosti. Konkrétně:

- Nasazení na **Cloudflare Pages** nebo **Cloudflare Workers** mohou vyžadovat další kompatibilní flagy.
- Prerenderovací kroky mohou selhat, pokud nejsou správně nainstalovány závislosti jako `@unhead/vue`.
- Některé moduly (např. **nuxthub**, **nitro-cloudflare-dev**) mohou zavést konflikty, pokud nejsou nakonfigurovány správnými flagy nebo závislostmi.

**Možná řešení:**

**Řešení 1: Ručně nainstalujte `@unhead/vue`**
Pokud chyba buildu stěžuje na to, že nenachází `@unhead/vue`, nainstalujte jej přímo do závislostí projektu:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

To zajistí, že je dostupný během fáze Nitro prerender.

**Řešení 2: Přidejte kompatibilní flagy pro Cloudflare**
Při použití Cloudflare Pages nebo Cloudflare Workers je kompatibilita Node.js často ve výchozím nastavení zakázána. Povolte ji ve svém `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Tato flag umožňuje mnoha Node.js modulům (včetně těch, které používá `nuxt-i18n-micro`) hladce běžet.

## 🔍 SEO a `@nuxtjs/seo`

### ❓ Chyba: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Toto se stává, když **`@nuxtjs/seo`** stáhne starou **`nuxt-site-config` 3.x**, která registruje svůj i18n plugin pouze pro `@nuxtjs/i18n`, ne pro **nuxt-i18n-micro**.

**Oprava:**

1. Upgradujte na **`@nuxtjs/seo` 3+** (obsahuje `nuxt-site-config` 4+ s podporou micro).
2. Umístěte **`nuxt-i18n-micro` před `@nuxtjs/seo`** v `modules`.
3. Ponechte **`i18n.meta: true`** pro locale-aware head tagy.

Kompletní příklad viz [Průvodce SEO — sekce Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo).

## 🔧 Konfigurace a kompatibilita

### ❓ Je `Nuxt I18n Micro` inspirován `vue-i18n`? Co modifikátory?

Zatímco `Nuxt I18n Micro` slouží jako výkonová alternativa k `nuxt-i18n`, je postaven nezávisle na `vue-i18n`. I když některé názvy metod a parametry mohou být podobné, základní funkcionalita se výrazně liší.

**Modifikátory**: Údržbář zpočátku zvažoval modifikátory, ale dospěl k závěru, že komponenty jako `<i18n-t>` a `<i18n-link>` tyto potřeby efektivně řeší.

Například:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Tento přístup je flexibilní, takže vydání modifikátorů je momentálně zbytečné. Modifikátory však mohou být přidány v budoucích vydáních, pokud bude poptávka.
