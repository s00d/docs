# ❓ FAQ: सामान्य समस्याएँ और समाधान

Nuxt I18n Micro के साथ अक्सर पूछे जाने वाले प्रश्नों के उत्तर और सामान्य समस्याओं के समाधान खोजें।

## 🚀 शुरुआत की समस्याएँ

### ❓ यदि कोई रूट लोड न हो तो क्या करें?

`Nuxt I18n Micro` का उपयोग करते समय, कुछ रूट्स अपेक्षित रूप से लोड नहीं हो सकते हैं, खासकर यदि router सबफ़ोल्डर में एक रूट को स्वचालित रूप से नाम नहीं देता है।

**समाधान:**
इसका समाधान करने के लिए, संबंधित Vue फ़ाइल में निम्नलिखित जोड़कर पेज के लिए रूट नाम को मैन्युअल रूप से परिभाषित करें:

```javascript
definePageMeta({ name: 'pageName' })
```

यह सुनिश्चित करता है कि रूट ठीक से पंजीकृत है, जिससे एप्लिकेशन के भीतर सहज नेविगेशन सक्षम होता है।

### ❓ Nuxt plugins में `$t` या अन्य i18n composables क्यों काम नहीं करते?

Nuxt I18n composables (`$t`, `$getLocale`, `$localePath`, आदि) Nuxt plugins या utility functions के भीतर अपेक्षित रूप से काम नहीं कर सकते हैं, जिसके परिणामस्वरूप runtime त्रुटियाँ हो सकती हैं।

**कारण और समाधान:**
Nuxt composables को Nuxt instance तक पहुँचने के लिए विशिष्ट संदर्भों (जैसे Nuxt hooks या Vue setup functions) की आवश्यकता होती है। यदि इन संदर्भों के बाहर उपयोग किया जाए (जैसे utility functions या plugins में), तो console में निम्नलिखित त्रुटि दिखाई दे सकती है:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**समाधान 1: `runWithContext` का उपयोग करें**
अतुल्यकालिक ऑपरेशन के बाद i18n composables को कॉल करने के लिए, आवश्यक संदर्भ संरक्षित करने के लिए [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) का उपयोग करें।

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**समाधान 2: पहले मान प्राप्त करें**
वैकल्पिक रूप से, पहले अनुवाद मान प्राप्त करें, फिर इसे एक utility function को पास करें।

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**समाधान 3: Services में Translation Keys पास करें**
Services या utility functions में, `$t` का सीधे उपयोग करने के बजाय अनुवाद keys पास करें। फिर, कंपोनेंट में अनुवाद प्राप्त करें।

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 लोकेल स्विचिंग

### ❓ URL बदले बिना लोकेल स्विच करें?

हाँ — लेकिन यह आपकी [रूटिंग रणनीति](/guides/routing-strategies) पर निर्भर करता है।

**`no_prefix` रणनीति** — लोकेल URL का हिस्सा नहीं है। एक ही path पर रहते हुए लोकेल बदलने और अनुवादों को पुनः लोड करने के लिए `$switchLocale()` का उपयोग करें:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

या केवल `useI18nLocale().setLocale('de')` के साथ preference अपडेट करें। पूर्ण client-side अनुवाद reload के लिए, `$switchLocale()` को प्राथमिकता दें।

**Prefix रणनीतियाँ** (`prefix`, `prefix_except_default`, …) — लोकेल और URL जुड़े हुए हैं। `$switchLocale()` हमेशा स्थानीयकृत रूट पर navigate करता है। कोई `redirect: false` विकल्प नहीं है।

यदि आपको केवल लक्षित URL की आवश्यकता है (उदाहरण के लिए, एक भाषा switcher लिंक), तो इसके बजाय `$switchLocalePath()` का उपयोग करें:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

सभी switching methods के लिए [Route & Locale Switching](/api/methods#-route-locale-switching) देखें।

### ❓ लोकेल स्विच करते समय पेज ऊपर स्क्रॉल हो जाता है (या jump करता है)?

यह अपेक्षित है — यह **Vue Router / Nuxt scroll behavior** है, nuxt-i18n-micro के लिए विशिष्ट कुछ नहीं।

Prefix रणनीतियों (`prefix`, `prefix_except_default`, …) के साथ, `$switchLocale()` एक सामान्य client navigation (`/en/page` → `/de/page`) करता है। Nuxt का डिफ़ॉल्ट [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) रूट परिवर्तनों पर ऊपर स्क्रॉल करता है (`savedPosition` के माध्यम से browser back/forward को छोड़कर)।

nuxt-i18n-micro छिपा हुआ scroll handling नहीं जोड़ता — अपने ऐप में एक छोटा wrapper कंपोनेंट का उपयोग करें।

**`SwitchLocalePreserve` wrapper**

[`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) को अपने प्रोजेक्ट (`components/SwitchLocalePreserve.vue`) में कॉपी करें। कार्यशील demo: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue)।

पेज पर, `scrollToTop: false` सेट करें और अपने switcher UI को wrap करें। clickable targets को `data-locale` से चिह्नित करें — wrapper clicks को intercept करता है, `$switchLocale` को कॉल करता है, और scroll को पुनर्स्थापित करता है (जब अनुवाद लंबाई layout बदलती है तब भी):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

कंपोनेंट:

1. **क्लिक पर** — slot के अंदर clicked element पर `data-locale` पढ़ता है (buttons, links, या कोई भी custom markup)।
2. **पहले** `$switchLocale` — `scrollY` और clicked element स्थिति संग्रहीत करता है (इसे cursor के नीचे रखता है)।
3. **navigation के दौरान** — `router.options.scrollBehavior` को एक बार patch करता है और top पर scroll करने के बजाय `\{ top: scrollY \}` लौटाता है।
4. **navigation के बाद** — `page:finish` की प्रतीक्षा करता है, फिर scroll को पुनः लागू करता है जबकि एक `ResizeObserver` विभिन्न अनुवाद लंबाइयों से layout shifts को पकड़ता है।

`scrollToTop: false` उन पेजों पर आवश्यक है जहाँ आप इस wrapper का उपयोग करते हैं। Docs: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta)।

wrapped controls पर सीधे `$switchLocale` को कॉल न करें — wrapper switching को संभालता है। wrapper के बाहर `<NuxtLink :to="$switchLocalePath('fr')">` के लिए, scroll behavior सामान्य Nuxt रूटिंग का पालन करता है जब तक कि आप अपना स्वयं का `app/router.options.ts` नहीं जोड़ते।

## 🌐 अनुवाद संबंधी समस्याएँ

### ❓ Page transitions के दौरान अनुवाद क्यों टूटते हैं, विशेष रूप से `defineAsyncComponent` के साथ?

Page transitions के साथ `nuxt-i18n-micro` का उपयोग करते समय, transition के दौरान अनुवाद संक्षिप्त रूप से काम करना बंद कर सकते हैं। यह समस्या इसलिए होती है क्योंकि transition पूरा होने से पहले रूट बदल जाता है, जिससे नए पेज के लिए अनुवाद लोड होते हैं जबकि पुराना पेज अभी भी दिखाई देता है।

**मूल कारण:**

- Page transitions अनुवाद पूरी तरह से लोड होने से पहले रूट परिवर्तन का कारण बनते हैं
- `defineAsyncComponent` और `useAsyncData` अनुवाद लोडिंग में देरी कर सकते हैं
- लोडिंग के दौरान अनुवाद keys raw paths के रूप में दिखाई दे सकती हैं

**समाधान 1: Cumulative Merge (अंतर्निहित, कॉन्फ़िग की आवश्यकता नहीं)**

v3 में, मॉड्यूल स्वचालित रूप से एक cumulative merge रणनीति का उपयोग करता है। एक ही locale के भीतर navigate करते समय, नए पेज के अनुवाद सक्रिय dictionary को प्रतिस्थापित करने के बजाय उसमें मर्ज हो जाते हैं। इसका अर्थ है कि पिछले पेज के अनुवाद transition animation के दौरान उपलब्ध रहते हैं। Transition समाप्त होने के बाद (`page:transition:finish` hook), पुरानी keys स्वचालित रूप से साफ़ कर दी जाती हैं।

कोई कॉन्फ़िगरेशन आवश्यक नहीं है — यह out of the box काम करता है।

**समाधान 2: स्पष्ट Route Context**

यदि आप मैन्युअल नियंत्रण पसंद करते हैं, तो वर्तमान रूट को स्पष्ट रूप से `$_t` पर पास करें:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**समाधान 3: Loading States**

अनुवाद लोडिंग को सुरुचिपूर्ण ढंग से संभालने के लिए loading states लागू करें:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Vercel पर SSR के दौरान अनुवाद keys क्यों resolve नहीं होतीं?

**SSR पर `$fetch` की सीमाएँ**
Vercel जैसे serverless प्लेटफ़ॉर्म पर, `$fetch` केवल CDN से static फ़ाइलें ला सकता है, आंतरिक Nitro server से नहीं। इसका अर्थ है कि static अनुवाद फ़ाइलें सीधे पहुँच योग्य नहीं हो सकतीं जब तक कि सही base URL सेट न हो।

**`apiBaseClientHost` और `apiBaseServerHost` सेट करके ठीक करें**
यदि अनुवाद CDN या भिन्न domain पर बाहरी रूप से hosted हैं, तो client-side अनुरोधों के लिए `apiBaseClientHost` और server-side अनुरोधों के लिए `apiBaseServerHost` का उपयोग करें। `apiBaseUrl` में केवल path prefix (जैसे `_locales`) होना चाहिए।

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

या पर्यावरण चरों के माध्यम से:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

अनुवाद client और server दोनों पर `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` से लाए जाएँगे।

## 🔗 रूटिंग और नेविगेशन संबंधी समस्याएँ

### ❓ क्या मैं अनुवाद strings में सीधे `NuxtLink` या `<i18n-link>` का उपयोग कर सकता हूँ?

हाँ, `Nuxt I18n Micro` `<i18n-t>` कंपोनेंट के माध्यम से अनुवादों के भीतर `NuxtLink` या `<i18n-link>` का उपयोग करने की अनुमति देता है, जो अनुवाद strings को विभाजित किए बिना व्याकरण और RTL भाषा आवश्यकताओं को संभालने के लिए विशेष रूप से सहायक है।

**उदाहरण:**

अनुवाद फ़ाइल:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue template:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

यह उचित स्थानीयकरण संरचना को संरक्षित करते हुए अनुवादों के भीतर dynamic लिंक की अनुमति देता है।

## 🏗️ Build और Deployment संबंधी समस्याएँ

### ❓ अनुवाद payloads `public/_locales/` (या Edge पर server bundle में) क्यों जाते हैं?

SSR और client दोनों को समान `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json` payloads की आवश्यकता होती है। उन्हें कैसे package किया जाता है यह Nitro target पर निर्भर करता है:

**व्याख्या:**

- **Node (डिफ़ॉल्ट):** मॉड्यूल अनुवादों को Nitro `serverAssets` / Rollup `raw:` के रूप में **embed नहीं करता** (जो बड़े catalogs पर build RAM उड़ा देता था)। इसके बजाय यह premerged tree को `public/<apiBaseUrl>/` (डिफ़ॉल्ट `_locales`) में कॉपी करता है और SSR उन फ़ाइलों को `readFile` के साथ पढ़ता है। Client समान URLs को `$fetch` करता है — या तो static फ़ाइलों के रूप में या Nitro handler के माध्यम से।
- **Edge** (`nitro.node === false`): SSR के लिए कोई durable public FS नहीं है, इसलिए payloads Nitro `serverAssets` (`assets:i18n`) के माध्यम से embed किए जाते हैं। `translationPayloads.mode: 'source'` को प्राथमिकता दें ताकि embed compact रहे। `publicAssets: true` केवल तभी सेट करें जब आपको CDN/static कॉपी भी चाहिए।
- **`prerenderRoutes`:** वैकल्पिक। premerged मोड में `publicAssets` पहले से ही `\{page\}/\{locale\}/data.json` लिखता है, इसलिए उन रूट्स को prerender करना आमतौर पर अनावश्यक है।

### ❓ मुझे `@unhead/vue` या अपरिभाषित ऑब्जेक्ट को संदर्भित करने वाली build error क्यों मिलती है, विशेष रूप से Cloudflare Pages पर?

**कारण:**
`nuxt-i18n-micro` का उपयोग करते समय कुछ प्रोजेक्ट्स को build conflicts या गुम dependencies का अनुभव होता है। विशेष रूप से:

- **Cloudflare Pages** या **Cloudflare Workers** पर deployments को अतिरिक्त compatibility flags की आवश्यकता हो सकती है।
- यदि `@unhead/vue` जैसी dependencies ठीक से इंस्टॉल नहीं हैं तो Prerendering चरण विफल हो सकते हैं।
- कुछ मॉड्यूल (जैसे **nuxthub**, **nitro-cloudflare-dev**) सही flags या dependencies के साथ कॉन्फ़िगर न किए जाने पर conflicts ला सकते हैं।

**संभावित समाधान:**

**समाधान 1: `@unhead/vue` को मैन्युअल रूप से इंस्टॉल करें**
यदि build error `@unhead/vue` न मिलने की शिकायत करती है, तो इसे सीधे अपने प्रोजेक्ट की dependencies में इंस्टॉल करें:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

यह सुनिश्चित करता है कि यह Nitro prerender चरण के दौरान उपलब्ध है।

**समाधान 2: Cloudflare compatibility flags जोड़ें**
Cloudflare Pages या Cloudflare Workers का उपयोग करते समय, Node.js compatibility अक्सर डिफ़ॉल्ट रूप से निष्क्रिय होती है। इसे अपने `wrangler.toml` में सक्षम करें:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

यह flag कई Node.js मॉड्यूल (जिनमें `nuxt-i18n-micro` द्वारा उपयोग किए जाने वाले भी शामिल हैं) को सुचारू रूप से चलने की अनुमति देता है।

## 🔍 SEO और `@nuxtjs/seo`

### ❓ त्रुटि: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

यह तब होता है जब **`@nuxtjs/seo`** एक पुराना **`nuxt-site-config` 3.x** लाता है जो केवल `@nuxtjs/i18n` के लिए अपने i18n plugin को पंजीकृत करता है, **nuxt-i18n-micro** के लिए नहीं।

**ठीक करें:**

1. **`@nuxtjs/seo` 3+** पर upgrade करें (जिसमें micro समर्थन के साथ `nuxt-site-config` 4+ शामिल है)।
2. `modules` में **`nuxt-i18n-micro` को `@nuxtjs/seo` से पहले** रखें।
3. locale-aware head tags के लिए **`i18n.meta: true`** रखें।

पूर्ण उदाहरण के लिए [SEO गाइड — Nuxt SEO अनुभाग](/guides/seo#nuxt-seo-nuxtjs-seo) देखें।

## 🔧 कॉन्फ़िगरेशन और अनुकूलता

### ❓ क्या `Nuxt I18n Micro` `vue-i18n` से प्रेरित है? Modifiers के बारे में क्या?

जबकि `Nuxt I18n Micro` `nuxt-i18n` के लिए एक प्रदर्शन विकल्प के रूप में कार्य करता है, यह `vue-i18n` से स्वतंत्र रूप से बनाया गया है। जबकि कुछ method नाम और parameters समान हो सकते हैं, अंतर्निहित कार्यक्षमता काफी भिन्न है।

**Modifiers**: maintainer ने शुरू में modifiers पर विचार किया, लेकिन निष्कर्ष निकाला कि `<i18n-t>` और `<i18n-link>` जैसे कंपोनेंट्स प्रभावी रूप से उन आवश्यकताओं को पूरा करते हैं।

उदाहरण के लिए:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

यह दृष्टिकोण लचीला है, इसलिए modifiers जारी करना वर्तमान में अनावश्यक है। हालाँकि, यदि मांग है तो भविष्य के releases में modifiers जोड़े जा सकते हैं।
