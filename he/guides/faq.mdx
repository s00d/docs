# ❓ שאלות נפוצות: בעיות ופתרונות

מצאו תשובות לשאלות נפוצות ופתרונות לבעיות שכיחות עם Nuxt I18n Micro.

## 🚀 בעיות התחלה

### ❓ מה אם route לא נטען?

בשימוש ב-`Nuxt I18n Micro`, routes מסוימים עשויים לא להיטען כצפוי, במיוחד אם ה-router אינו מקצה אוטומטית שם ל-route בתתי-תיקיות.

**פתרון:**
כדי לטפל בזה, הגדירו ידנית את שם ה-route עבור העמוד על ידי הוספת הבא לקובץ ה-Vue המתאים:

```javascript
definePageMeta({ name: 'pageName' })
```

זה מבטיח שה-route נרשם כראוי, ומאפשר ניווט חלק בתוך האפליקציה.

### ❓ מדוע `$t` או composables אחרים של i18n אינם עובדים ב-Nuxt plugins?

Composables של Nuxt I18n (`$t`, `$getLocale`, `$localePath` וכו') עשויים לא לעבוד כצפוי בתוך Nuxt plugins או פונקציות עזר, מה שגורם לשגיאות runtime.

**סיבה ופתרון:**
Composables של Nuxt דורשים הקשרים ספציפיים (למשל, Nuxt hooks או פונקציות setup של Vue) כדי לגשת למופע Nuxt. אם משתמשים בהם מחוץ להקשרים אלה (למשל, בפונקציות עזר או תוספים), השגיאה הבאה עשויה להופיע בקונסולה:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**פתרון 1: השתמשו ב-`runWithContext`**
כדי לקרוא ל-composables של i18n לאחר פעולה אסינכרונית, השתמשו ב-[`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) כדי לשמר את ההקשר הדרוש.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**פתרון 2: אחזרו ערך תחילה**
לחלופין, אחזרו את ערך התרגום תחילה, ואז העבירו אותו לפונקציית עזר.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**פתרון 3: העבירו מפתחות תרגום בשירותים**
בשירותים או בפונקציות עזר, העבירו את מפתחות התרגום במקום להשתמש ב-`$t` ישירות. לאחר מכן, אחזרו את התרגום בקומפוננטה.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 החלפת Locale

### ❓ להחליף locale מבלי לשנות את ה-URL?

כן — אבל זה תלוי ב[אסטרטגיית הניתוב](/guides/routing-strategies) שלכם.

**אסטרטגיית `no_prefix`** — locale אינו חלק מה-URL. השתמשו ב-`$switchLocale()` כדי לשנות locale ולטעון תרגומים מחדש בעודכם נשארים על אותו נתיב:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

או עדכנו העדפה בלבד עם `useI18nLocale().setLocale('de')`. לטעינה מחדש מלאה של תרגומים בצד הלקוח, העדיפו את `$switchLocale()`.

**אסטרטגיות prefix** (`prefix`, `prefix_except_default`, ...) — locale ו-URL מקושרים. `$switchLocale()` תמיד מנווט ל-route המוקם. אין אפשרות `redirect: false`.

אם אתם צריכים רק את ה-URL היעד (לדוגמה, קישור מחליף שפה), השתמשו ב-`$switchLocalePath()` במקום:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

ראו [Route & Locale Switching](/api/methods#-route-locale-switching) לכל שיטות ההחלפה.

### ❓ עמוד גולל למעלה (או קופץ) בעת החלפת locale?

זה צפוי — זו **התנהגות גלילה של Vue Router / Nuxt**, לא משהו ספציפי ל-nuxt-i18n-micro.

עם אסטרטגיות prefix (`prefix`, `prefix_except_default`, ...), `$switchLocale()` מבצע ניווט לקוח רגיל (`/en/page` → `/de/page`). ה-[`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) ברירת המחדל של Nuxt גולל למעלה בשינויי route (למעט חזור/קדימה של הדפדפן באמצעות `savedPosition`).

nuxt-i18n-micro אינו מוסיף טיפול גלילה נסתר — השתמשו בקומפוננטת wrapper קטנה באפליקציה שלכם.

**Wrapper של `SwitchLocalePreserve`**

העתיקו את [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) לפרויקט שלכם (`components/SwitchLocalePreserve.vue`). דמו עובד: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

בעמוד, הגדירו `scrollToTop: false` ועטפו את ממשק ה-switcher שלכם. סמנו יעדים לקליק עם `data-locale` — ה-wrapper מיירט קליקים, קורא ל-`$switchLocale`, ומשחזר גלילה (כולל כאשר אורך התרגום משנה layout):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

הקומפוננטה:

1. **בקליק** — קוראת `data-locale` באלמנט שנקלק בתוך ה-slot (כפתורים, קישורים או כל markup מותאם).
2. **לפני** `$switchLocale` — שומרת `scrollY` ואת מיקום האלמנט שנקלק (שומרת אותו מתחת לסמן).
3. **במהלך** הניווט — משנה את `router.options.scrollBehavior` פעם אחת ומחזירה `\{ top: scrollY \}` במקום לגלול למעלה.
4. **אחרי** הניווט — ממתינה ל-`page:finish`, אז מיישמת מחדש גלילה בזמן ש-`ResizeObserver` תופס שינויי layout מאורכי תרגום שונים.

`scrollToTop: false` נדרש בעמודים שבהם אתם משתמשים ב-wrapper הזה. תיעוד: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

אל תקראו ל-`$switchLocale` ישירות על פקדים עטופים — ה-wrapper מטפל בהחלפה. עבור `<NuxtLink :to="$switchLocalePath('fr')">` מחוץ ל-wrapper, התנהגות הגלילה עוקבת אחר ניתוב Nuxt רגיל אלא אם כן אתם מוסיפים `app/router.options.ts` משלכם.

## 🌐 בעיות תרגום

### ❓ מדוע תרגומים נשברים במהלך מעברי עמודים, במיוחד עם `defineAsyncComponent`?

בשימוש ב-`nuxt-i18n-micro` עם מעברי עמודים, תרגומים עשויים להפסיק לעבוד לרגע במהלך המעבר. בעיה זו מתרחשת כי ה-route משתנה לפני שהמעבר הושלם, מה שגורם לתרגומים לעמוד החדש להיטען בעוד שהעמוד הישן עדיין נראה.

**סיבה שורשית:**

- מעברי עמודים גורמים לשינויי route לפני שהתרגומים נטענו במלואם
- `defineAsyncComponent` ו-`useAsyncData` יכולים לעכב טעינת תרגום
- מפתחות תרגום עשויים להופיע כנתיבים גולמיים במהלך הטעינה

**פתרון 1: Cumulative Merge (מובנה, ללא צורך בקונפיגורציה)**

ב-v3, המודול משתמש אוטומטית באסטרטגיית cumulative merge. בניווט בתוך אותו locale, תרגומי עמוד חדש ממוזגים למילון הפעיל במקום להחליף אותו. משמעות הדבר היא שתרגומים מהעמוד הקודם נשארים זמינים במהלך אנימציית המעבר. לאחר סיום המעבר (hook של `page:transition:finish`), מפתחות ישנים מנוקים אוטומטית.

אין צורך בקונפיגורציה — זה עובד מיד.

**פתרון 2: הקשר Route מפורש**

אם אתם מעדיפים שליטה ידנית, העבירו במפורש את ה-route הנוכחי ל-`$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**פתרון 3: מצבי טעינה**

יישמו מצבי טעינה כדי לטפל בטעינת תרגומים בחן:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ מדוע מפתחות תרגום אינם נפתרים במהלך SSR ב-Vercel?

**מגבלות `$fetch` ב-SSR**
בפלטפורמות serverless כמו Vercel, `$fetch` יכול להביא רק קבצים סטטיים מה-CDN ולא משרת Nitro פנימי. משמעות הדבר היא שקבצי תרגום סטטיים עשויים לא להיות נגישים ישירות אלא אם כן ה-base URL הנכון מוגדר.

**תיקון על ידי הגדרת `apiBaseClientHost` ו-`apiBaseServerHost`**
אם תרגומים מתארחים חיצונית ב-CDN או בדומיין אחר, השתמשו ב-`apiBaseClientHost` לבקשות בצד לקוח וב-`apiBaseServerHost` לבקשות בצד שרת. `apiBaseUrl` צריך להכיל רק את קידומת הנתיב (למשל, `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

או באמצעות משתני סביבה:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

התרגומים יובאו מ-`https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` הן בלקוח והן בשרת.

## 🔗 בעיות ניתוב וניווט

### ❓ האם ניתן להשתמש ב-`NuxtLink` או `<i18n-link>` ישירות במחרוזות תרגום?

כן, `Nuxt I18n Micro` מאפשר את השימוש ב-`NuxtLink` או `<i18n-link>` בתוך תרגומים דרך הקומפוננטה `<i18n-t>`, שמועילה במיוחד לטיפול בדרישות דקדוק ושפות RTL מבלי לפצל מחרוזות תרגום.

**דוגמה:**

קובץ תרגום:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

תבנית Vue:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

זה מאפשר קישורים דינמיים בתוך תרגומים תוך שמירה על מבנה לוקליזציה תקין.

## 🏗️ בעיות Build ופריסה

### ❓ מדוע מטעני תרגום מסתיימים תחת `public/_locales/` (או ב-server bundle ב-Edge)?

SSR והלקוח שניהם צריכים את אותם payloads של `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. איך הם נארזים תלוי ביעד Nitro:

**הסבר:**

- **Node (ברירת מחדל):** המודול **אינו** מטמיע תרגומים כ-Nitro `serverAssets` / Rollup `raw:` (זה פוצץ RAM של build על קטלוגים גדולים). במקום זאת הוא מעתיק את העץ הפרה-ממוזג ל-`public/<apiBaseUrl>/` (ברירת מחדל `_locales`) ו-SSR קורא את הקבצים הללו עם `readFile`. הלקוח `$fetch`-ים את אותם URLs — כקבצים סטטיים או דרך handler של Nitro.
- **Edge** (`nitro.node === false`): אין FS ציבורי עמיד ל-SSR, כך ש-payloads מוטמעים באמצעות Nitro `serverAssets` (`assets:i18n`). העדיפו `translationPayloads.mode: 'source'` כך שההטמעה נשארת קומפקטית. הגדירו `publicAssets: true` רק אם אתם צריכים גם עותק CDN/סטטי.
- **`prerenderRoutes`:** אופציונלי. במצב premerged `publicAssets` כבר כותב `\{page\}/\{locale\}/data.json`, כך ש-prerendering של routes אלה בדרך כלל מיותר.

### ❓ מדוע אני מקבל שגיאת build המתייחסת ל-`@unhead/vue` או אובייקט לא מוגדר, במיוחד ב-Cloudflare Pages?

**סיבה:**
פרויקטים מסוימים חווים התנגשויות build או תלויות חסרות בשימוש ב-`nuxt-i18n-micro`. בפרט:

- פריסות ב-**Cloudflare Pages** או **Cloudflare Workers** עשויות לדרוש דגלי תאימות נוספים.
- שלבי prerendering יכולים להיכשל אם תלויות כמו `@unhead/vue` אינן מותקנות כראוי.
- מודולים מסוימים (למשל, **nuxthub**, **nitro-cloudflare-dev**) יכולים להכניס התנגשויות אלא אם כן הם מוגדרים עם דגלים או תלויות נכונים.

**פתרונות אפשריים:**

**פתרון 1: התקינו `@unhead/vue` ידנית**
אם שגיאת ה-build מתלוננת שלא מוצאת את `@unhead/vue`, התקינו אותה ישירות בתלויות הפרויקט שלכם:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

זה מבטיח שהיא זמינה במהלך שלב ה-prerender של Nitro.

**פתרון 2: הוסיפו דגלי תאימות של Cloudflare**
בשימוש ב-Cloudflare Pages או Cloudflare Workers, תאימות Node.js לעתים קרובות מושבתת כברירת מחדל. הפעילו אותה ב-`wrangler.toml` שלכם:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

דגל זה מאפשר למודולי Node.js רבים (כולל אלה שנעשה בהם שימוש על ידי `nuxt-i18n-micro`) לפעול בצורה חלקה.

## 🔍 SEO ו-`@nuxtjs/seo`

### ❓ שגיאה: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

זה קורה כאשר **`@nuxtjs/seo`** מושך פנימה **`nuxt-site-config` 3.x** ישן שרק רושם את תוסף ה-i18n שלו עבור `@nuxtjs/i18n`, לא עבור **nuxt-i18n-micro**.

**תיקון:**

1. שדרגו ל-**`@nuxtjs/seo` 3+** (כולל `nuxt-site-config` 4+ עם תמיכת micro).
2. הכניסו את **`nuxt-i18n-micro` לפני `@nuxtjs/seo`** ב-`modules`.
3. שמרו על **`i18n.meta: true`** לתגי head מודעי locale.

ראו את [מדריך SEO — סעיף Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo) לדוגמה מלאה.

## 🔧 קונפיגורציה ותאימות

### ❓ האם `Nuxt I18n Micro` מקבל השראה מ-`vue-i18n`? מה לגבי modifiers?

בעוד ש-`Nuxt I18n Micro` משמש כחלופת ביצועים ל-`nuxt-i18n`, הוא נבנה באופן עצמאי מ-`vue-i18n`. בעוד ששמות מתודות ופרמטרים מסוימים עשויים להיות דומים, הפונקציונליות הבסיסית שונה משמעותית.

**Modifiers**: המתחזק שקל בתחילה modifiers, אך הגיע למסקנה שקומפוננטות כמו `<i18n-t>` ו-`<i18n-link>` מטפלות ביעילות בצרכים אלה.

לדוגמה:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

גישה זו גמישה, כך ששחרור modifiers כרגע אינו נחוץ. עם זאת, modifiers עשויים להתווסף בשחרורים עתידיים אם תהיה דרישה.
