# ❓ UKK: Yleisiä ongelmia ja ratkaisuja

Löydä vastaukset usein kysyttyihin kysymyksiin ja ratkaisut yleisiin ongelmiin Nuxt I18n Micron kanssa.

## 🚀 Aloittamiseen liittyviä ongelmia

### ❓ Mitä tehdä, jos reitti ei lataudu?

Kun käytät `Nuxt I18n Microa`, tietyt reitit eivät välttämättä lataudu odotetusti, erityisesti jos router ei automaattisesti anna nimeä alikansioiden reitille.

**Ratkaisu:**
Ratkaise tämä määrittämällä reitin nimi manuaalisesti sivulle lisäämällä seuraava vastaavaan Vue-tiedostoon:

```javascript
definePageMeta({ name: 'pageName' })
```

Tämä varmistaa, että reitti on rekisteröity oikein ja mahdollistaa saumattoman navigoinnin sovelluksessa.

### ❓ Miksi `$t` tai muut i18n-koostetoiminnot eivät toimi Nuxt-plugineissa?

Nuxt I18n -koostetoiminnot (`$t`, `$getLocale`, `$localePath` jne.) eivät välttämättä toimi odotetusti Nuxt-plugineissa tai apuohjelmafunktioissa, mikä johtaa ajonaikaisiin virheisiin.

**Syy ja ratkaisu:**
Nuxt-koostetoiminnot vaativat tiettyjä konteksteja (esim. Nuxt-hookit tai Vuen setup-funktiot) päästäkseen Nuxt-instanssiin. Jos niitä käytetään näiden kontekstien ulkopuolella (esim. apuohjelmafunktioissa tai plugineissa), konsoliin voi ilmestyä seuraava virhe:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Ratkaisu 1: Käytä metodia `runWithContext`**
Kutsuaksesi i18n-koostetoimintoja asynkronisen operaation jälkeen, käytä metodia [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) tarvittavan kontekstin säilyttämiseen.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Ratkaisu 2: Hae arvo ensin**
Vaihtoehtoisesti hae käännösarvo ensin ja välitä se sitten apuohjelmafunktioon.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Ratkaisu 3: Välitä käännösavaimet palveluissa**
Palveluissa tai apuohjelmafunktioissa välitä käännösavaimet sen sijaan, että käyttäisit `$t`-metodia suoraan. Hae sitten käännös komponentissa.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Kielen vaihtaminen

### ❓ Voiko kieltä vaihtaa muuttamatta URL-osoitetta?

Kyllä — mutta se riippuu [reititysstrategiastasi](/guides/routing-strategies).

**Strategia `no_prefix`** — kieli ei ole osa URL-osoitetta. Käytä `$switchLocale()`-metodia kielen vaihtamiseen ja käännösten uudelleenlataamiseen samalla polulla pysyen:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Tai päivitä vain mieltymystä metodilla `useI18nLocale().setLocale('de')`. Täydellistä asiakaspuolen käännösten uudelleenlatausta varten suosi metodia `$switchLocale()`.

**Prefiksistrategiat** (`prefix`, `prefix_except_default`, …) — kieli ja URL on kytketty yhteen. `$switchLocale()` navigoi aina paikallistettuun reittiin. `redirect: false` -asetusta ei ole.

Jos tarvitset vain kohde-URL:n (esimerkiksi kielenvaihtajalinkin), käytä sen sijaan metodia `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Katso kaikki vaihtomenetelmät kohdasta [Reitti- ja kielenvaihtaminen](/api/methods#-route-locale-switching).

### ❓ Sivu vierii ylös (tai hyppää), kun kieltä vaihdetaan?

Se on odotettua — se on **Vue Routerin / Nuxtin vieritys-käyttäytymistä**, ei jotain nuxt-i18n-microlle erityistä.

Prefiksistrategioilla (`prefix`, `prefix_except_default`, …) `$switchLocale()` suorittaa tavallisen asiakasnavigoinnin (`/en/page` → `/de/page`). Nuxtin oletusarvoinen [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) vierittää yläreunaan reitinvaihdoissa (paitsi selaimen taakse/eteenpäin `savedPosition`-arvon kautta).

nuxt-i18n-micro ei lisää piilotettua vieritysten käsittelyä — käytä pientä wrapper-komponenttia sovelluksessasi.

**`SwitchLocalePreserve`-wrapper**

Kopioi tiedosto [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) projektiisi (`components/SwitchLocalePreserve.vue`). Toimiva demo: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

Aseta sivulla `scrollToTop: false` ja kääri vaihtaja-UI. Merkitse klikattavat kohteet `data-locale`-attribuutilla — wrapper sieppaa klikkaukset, kutsuu `$switchLocale`-metodia ja palauttaa vieritystilan (myös silloin kun käännöksen pituus muuttaa asettelua):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Komponentti:

1. **Klikkauksessa** — lukee `data-locale`-attribuutin slotin sisällä olevasta klikatusta elementistä (painikkeet, linkit tai mikä tahansa mukautettu merkintä).
2. **Ennen** `$switchLocale`-kutsua — tallentaa `scrollY`:n ja klikatun elementin sijainnin (pitää sen kursorin alla).
3. **Navigoinnin aikana** — päivittää `router.options.scrollBehavior`-arvon kerran ja palauttaa `\{ top: scrollY \}` sen sijaan, että vierittäisi yläreunaan.
4. **Navigoinnin jälkeen** — odottaa `page:finish`-tapahtumaa, sitten palauttaa vierityksen, kun `ResizeObserver` nappaa asettelun muutokset erilaisista käännöspituuksista.

`scrollToTop: false` on vaadittava sivuilla, joilla käytät tätä wrapperia. Dokumentaatio: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Älä kutsu `$switchLocale`-metodia suoraan käärittyihin ohjaimiin — wrapper hoitaa vaihtamisen. Wrapperin ulkopuolella olevan `<NuxtLink :to="$switchLocalePath('fr')">`-elementin vierityskäyttäytyminen seuraa tavanomaista Nuxt-reititystä, ellet lisää omaa tiedostoa `app/router.options.ts`.

## 🌐 Käännösongelmat

### ❓ Miksi käännökset menevät rikki sivujen siirtymissä, erityisesti metodin `defineAsyncComponent` kanssa?

Kun käytät `nuxt-i18n-microa` sivujen siirtymien kanssa, käännökset voivat lakata toimimasta hetkellisesti siirtymän aikana. Tämä johtuu siitä, että reitti muuttuu ennen kuin siirtymä on valmis, jolloin uuden sivun käännökset alkavat latautua vanhan sivun ollessa vielä näkyvissä.

**Perussyy:**

- Sivujen siirtymät aiheuttavat reitinvaihtoja ennen kuin käännökset on täysin ladattu
- `defineAsyncComponent` ja `useAsyncData` voivat viivyttää käännösten latausta
- Käännösavaimet saattavat näkyä raakoina polkuina latauksen aikana

**Ratkaisu 1: Kumulatiivinen yhdistäminen (sisäänrakennettu, ei asetuksia tarvita)**

V3:ssa moduuli käyttää automaattisesti kumulatiivista yhdistämisstrategiaa. Kun navigoidaan saman kielen sisällä, uuden sivun käännökset yhdistetään aktiiviseen sanakirjaan sen sijaan, että sitä korvattaisiin. Tämä tarkoittaa, että edellisen sivun käännökset pysyvät saatavilla siirtymäanimaation aikana. Kun siirtymä on valmis (`page:transition:finish`-hook), vanhat avaimet siivotaan automaattisesti.

Asetuksia ei tarvita — tämä toimii suoraan asennuksesta.

**Ratkaisu 2: Eksplisiittinen reittikonteksti**

Jos haluat manuaalisen hallinnan, välitä nykyinen reitti eksplisiittisesti metodille `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Ratkaisu 3: Lataustilat**

Toteuta lataustilat käsittelemään käännösten latausta sulavasti:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Miksi käännösavaimet eivät resolvoidu SSR:n aikana Vercelissä?

**`$fetch`-rajoitukset SSR:ssä**
Serverless-alustoilla kuten Vercel `$fetch` voi hakea vain staattisia tiedostoja CDN:stä eikä sisäiseltä Nitro-palvelimelta. Tämä tarkoittaa, että staattiset käännöstiedostot eivät välttämättä ole suoraan saatavilla, ellei oikeaa base-URL:ää ole asetettu.

**Korjaus asetuksilla `apiBaseClientHost` ja `apiBaseServerHost`**
Jos käännökset on isännöity ulkoisesti CDN:llä tai eri domainissa, käytä asetusta `apiBaseClientHost` asiakaspuolen pyyntöihin ja `apiBaseServerHost` palvelinpuolen pyyntöihin. Asetuksen `apiBaseUrl` tulee sisältää vain polkuprefiksi (esim. `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Tai ympäristömuuttujien kautta:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Käännökset haetaan osoitteesta `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` sekä asiakkaalla että palvelimella.

## 🔗 Reititys- ja navigointiongelmat

### ❓ Voinko käyttää `NuxtLink`-komponenttia tai `<i18n-link>`-komponenttia suoraan käännösmerkkijonoissa?

Kyllä, `Nuxt I18n Micro` sallii `NuxtLink`- tai `<i18n-link>`-komponentin käytön käännöksissä `<i18n-t>`-komponentin kautta, mikä on erityisen hyödyllistä käsittelemään kielioppia ja RTL-kielten vaatimuksia jakamatta käännösmerkkijonoja.

**Esimerkki:**

Käännöstiedosto:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue-templaatti:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Tämä mahdollistaa dynaamiset linkit käännösten sisällä säilyttäen oikean paikallistamisrakenteen.

## 🏗️ Build- ja käyttöönotto-ongelmat

### ❓ Miksi käännöspayloadit päätyvät `public/_locales/`-hakemistoon (tai palvelinbundleen Edgessä)?

SSR ja asiakas tarvitsevat molemmat samat `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json` -payloadit. Miten ne paketoidaan, riippuu Nitro-kohteesta:

**Selitys:**

- **Node (oletus):** moduuli **ei** upota käännöksiä Nitro `serverAssets`- tai Rollup `raw:` -muodossa (se räjäytti buildin RAMin suurilla luetteloilla). Sen sijaan se kopioi esiyhdistetyn puun hakemistoon `public/<apiBaseUrl>/` (oletus `_locales`) ja SSR lukee nämä tiedostot metodilla `readFile`. Asiakas kutsuu `$fetch`-metodia samoihin URL-osoitteisiin — joko staattisina tiedostoina tai Nitro-käsittelijän kautta.
- **Edge** (`nitro.node === false`): SSR:lle ei ole pysyvää julkista tiedostojärjestelmää, joten payloadit upotetaan Nitro `serverAssets`-tiedostojen (`assets:i18n`) kautta. Suosi asetusta `translationPayloads.mode: 'source'`, jotta upotus pysyy tiiviinä. Aseta `publicAssets: true` vain, jos tarvitset myös CDN/staattisen kopion.
- **`prerenderRoutes`:** valinnainen. Esiyhdistetyssä tilassa `publicAssets` jo kirjoittaa polun `\{page\}/\{locale\}/data.json`, joten niiden reittien esirenderöinti on yleensä tarpeetonta.

### ❓ Miksi saan build-virheen, joka viittaa `@unhead/vue`-pakettiin tai määrittelemättömään objektiin, erityisesti Cloudflare Pagesissa?

**Syy:**
Joissakin projekteissa esiintyy buildin ristiriitoja tai puuttuvia riippuvuuksia `nuxt-i18n-micron` käytön yhteydessä. Erityisesti:

- **Cloudflare Pagesille** tai **Cloudflare Workersille** tehdyt käyttöönotot voivat vaatia ylimääräisiä yhteensopivuuslippuja.
- Esirenderöintivaiheet voivat epäonnistua, jos riippuvuudet kuten `@unhead/vue` eivät ole asennettu oikein.
- Tietyt moduulit (esim. **nuxthub**, **nitro-cloudflare-dev**) voivat aiheuttaa ristiriitoja, ellei niitä ole määritetty oikeilla lipuilla tai riippuvuuksilla.

**Mahdolliset ratkaisut:**

**Ratkaisu 1: Asenna `@unhead/vue` manuaalisesti**
Jos build-virhe valittaa, ettei se löydä pakettia `@unhead/vue`, asenna se suoraan projektisi riippuvuuksiin:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Tämä varmistaa, että se on käytettävissä Nitro-esirenderöintivaiheessa.

**Ratkaisu 2: Lisää Cloudflare-yhteensopivuusliput**
Cloudflare Pagesin tai Cloudflare Workersin käytön yhteydessä Node.js-yhteensopivuus on usein oletusarvoisesti pois päältä. Ota se käyttöön tiedostossasi `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Tämä lippu sallii monien Node.js-moduulien (mukaan lukien `nuxt-i18n-micron` käyttämien) toimivan sujuvasti.

## 🔍 SEO ja `@nuxtjs/seo`

### ❓ Virhe: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Tämä tapahtuu, kun **`@nuxtjs/seo`** vetää mukaansa vanhan **`nuxt-site-config` 3.x** -version, joka rekisteröi i18n-pluginin vain `@nuxtjs/i18n`-moduulille, ei **nuxt-i18n-microlle**.

**Korjaus:**

1. Päivitä versioon **`@nuxtjs/seo` 3+** (sisältää `nuxt-site-config` 4+ micro-tuen kanssa).
2. Aseta **`nuxt-i18n-micro` ennen `@nuxtjs/seo`**-moduulia listassa `modules`.
3. Pidä **`i18n.meta: true`** kielitietoisia head-tageja varten.

Katso koko esimerkki kohdasta [SEO-opas — Nuxt SEO -osio](/guides/seo#nuxt-seo-nuxtjs-seo).

## 🔧 Konfiguraatio ja yhteensopivuus

### ❓ Onko `Nuxt I18n Micro` `vue-i18n`-vaikutteinen? Entä modifieret?

Vaikka `Nuxt I18n Micro` toimii suorituskykyvaihtoehtona `nuxt-i18n`-moduulille, se on rakennettu itsenäisesti `vue-i18n`-moduulista. Vaikka jotkin metodinimet ja parametrit voivat olla samankaltaisia, taustatoiminnallisuus eroaa merkittävästi.

**Modifierit**: Ylläpitäjä harkitsi alun perin modifiereja, mutta päätteli, että komponentit kuten `<i18n-t>` ja `<i18n-link>` vastaavat tehokkaasti näihin tarpeisiin.

Esimerkiksi:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Tämä lähestymistapa on joustava, joten modifierien julkaiseminen ei ole tällä hetkellä välttämätöntä. Modifiereja voidaan kuitenkin lisätä tulevissa julkaisuissa, jos kysyntää on.
