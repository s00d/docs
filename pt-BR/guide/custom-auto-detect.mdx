---
title: "Detecção personalizada de locale"
description: "Escolha o locale você mesmo — por domínio, cabeçalho ou perfil de usuário — com um plugin de servidor e useI18nLocale().setLocale()."
---

A detecção integrada lê a URL, um cookie e o `Accept-Language`. Quando o locale depende de outra coisa — o domínio, um cabeçalho de geolocalização definido pelo seu CDN, um perfil de usuário — defina-o você mesmo em um plugin que roda antes do plugin de i18n. O módulo então carrega as traduções desse locale e o usa para redirecionamentos exatamente como se o tivesse detectado. As regras que decidem quando um locale escolhido prevalece sobre a URL estão em [Detecção de locale](/pt-BR/guide/locale-detection); esta página mostra como conectar sua própria fonte.

## Defina o locale em um plugin de servidor {#set-the-locale-in-a-server-plugin}

```ts
// plugins/i18n-locale.server.ts
export default defineNuxtPlugin({
  name: 'i18n-custom-locale',
  enforce: 'pre',
  order: -10, // before the i18n plugin (order -5)
  setup() {
    const { setLocale } = useI18nLocale()
    const host = (useRequestHeaders(['host']).host ?? '').split(':')[0]! // without the port

    if (host.endsWith('.de')) setLocale('de')
    else if (host.endsWith('.fr')) setLocale('fr')
  },
})
```

`setLocale(code)` grava o estado do locale (`useState('i18n-locale')`) e, quando um cookie de locale está configurado, o cookie. Use-o em vez de escrever `useState` ou `useCookie` você mesmo. Passe apenas códigos de locales habilitados.

Mantenha o plugin como `.server.ts` quando ele lê cabeçalhos da requisição: eles não existem no navegador. Um plugin `.client.ts` é o lugar para fontes exclusivas do navegador, como `localStorage`.

## Desative a etapa integrada de Accept-Language {#turn-off-the-built-in-accept-language-step}

Seu plugin e o `Accept-Language` podem discordar. Para deixar que apenas seu código (mais a URL e o cookie) decida, desative o cabeçalho:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    autoDetectLanguage: false,
  },
})
```

[`autoDetectLanguage`](/pt-BR/api/module-options#autodetectlanguage) controla apenas a etapa do cabeçalho. A URL e um cookie válido continuam contando.

## O que acontece em seguida {#what-happens-next}

O efeito de `setLocale` depende da [estratégia](/pt-BR/guide/strategy):

| Estratégia | Efeito de `setLocale('de')` no plugin |
| --- | --- |
| `no_prefix` | A página é renderizada em alemão; a URL não muda. |
| `prefix`, `prefix_except_default` | Em um caminho sem prefixo onde [`autoDetectPath`](/pt-BR/api/module-options#autodetectpath) permite redirecionamentos (por padrão apenas `/`), o servidor responde `302` para a URL em alemão. Uma URL com prefixo de locale o mantém. |
| `prefix_and_default` | Sem redirecionamento: a URL sem prefixo é uma página válida do locale padrão. |

Nas estratégias com prefixo, um locale na URL é a escolha do usuário e seu plugin não o sobrescreve. `autoDetectPath: '*'` é a exceção: o servidor então move URLs com prefixo com base no cookie e no `Accept-Language` e ignora o estado, mas `setLocale()` também grava o cookie quando há um configurado, então a partir da próxima requisição a escolha do seu plugin pode redirecionar uma URL com prefixo. Mantenha `'/'` ou use `'no_prefix'` quando URLs de locale explícitas precisarem prevalecer. Use seu plugin para escolher onde o visitante chega, não para reescrever links que ele seguiu.

## Respeite um locale escolhido pelo usuário {#respect-a-locale-the-user-picked}

Quando um usuário troca de idioma, a troca grava o cookie. Pule sua própria detecção quando já houver uma preferência válida:

```ts
// plugins/i18n-locale.server.ts
import { detectLocaleFromAcceptLanguage } from '@i18n-micro/utils/accept-language'

export default defineNuxtPlugin({
  name: 'i18n-custom-locale',
  enforce: 'pre',
  order: -10,
  setup() {
    const { getPreferredLocale, setLocale, validLocales } = useI18nLocale()
    if (getPreferredLocale()) return // valid state or cookie: keep it

    const country = useRequestHeaders(['x-country'])['x-country']
    if (country === 'JP') return setLocale('ja')

    const header = useRequestHeaders(['accept-language'])['accept-language']
    setLocale(detectLocaleFromAcceptLanguage(header, validLocales))
  },
})
```

`getPreferredLocale()` retorna o estado ou o cookie somente quando é um locale habilitado, então um cookie obsoleto não impede a detecção. `detectLocaleFromAcceptLanguage` é o matcher sensível a q-values que o próprio módulo usa (instale `@i18n-micro/utils` para importá-lo); `setLocale(null)` não faz nada.

## Um domínio por locale {#one-domain-per-locale}

Se cada domínio deve servir seus próprios locales, você não precisa de um plugin: dê a cada locale um `baseUrl`, defina `baseDefault: true` no locale padrão de cada domínio e faça o build uma vez (um site estático ainda executa `nuxi generate` por domínio). Veja [Camadas e domínios](/pt-BR/guide/layers#multiple-domains).
