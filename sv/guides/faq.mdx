# ❓ FAQ: Vanliga problem och lösningar

Hitta svar på vanliga frågor och lösningar på vanliga problem med Nuxt I18n Micro.

## 🚀 Problem vid komma-igång

### ❓ Vad händer om en rutt inte laddas?

När du använder `Nuxt I18n Micro` kan vissa rutter kanske inte laddas som förväntat, särskilt om routern inte automatiskt tilldelar ett namn till en rutt i undermappar.

**Lösning:**
För att åtgärda detta, definiera ruttnamnet manuellt för sidan genom att lägga till följande i motsvarande Vue-fil:

```javascript
definePageMeta({ name: 'pageName' })
```

Detta säkerställer att rutten registreras korrekt och möjliggör sömlös navigering i applikationen.

### ❓ Varför fungerar inte `$t` eller andra i18n-composables i Nuxt-plugins?

Nuxt I18n-composables (`$t`, `$getLocale`, `$localePath` med flera) kanske inte fungerar som förväntat inom Nuxt-plugins eller verktygsfunktioner, vilket resulterar i runtime-fel.

**Orsak och lösning:**
Nuxt-composables kräver specifika kontexter (till exempel Nuxt-hooks eller Vue setup-funktioner) för att komma åt Nuxt-instansen. Om de används utanför dessa kontexter (till exempel i verktygsfunktioner eller plugins) kan följande fel visas i konsolen:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Lösning 1: Använd `runWithContext`**
För att anropa i18n-composables efter en asynkron operation, använd [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) för att bevara den nödvändiga kontexten.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Lösning 2: Hämta värdet först**
Alternativt, hämta översättningsvärdet först och skicka det sedan till en verktygsfunktion.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Lösning 3: Skicka översättningsnycklar i tjänster**
I tjänster eller verktygsfunktioner, skicka översättningsnycklarna i stället för att använda `$t` direkt. Hämta sedan översättningen i komponenten.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Lokalbyte

### ❓ Byta lokal utan att ändra URL:en?

Ja — men det beror på din [routingstrategi](/guides/routing-strategies).

**Strategin `no_prefix`** — lokalen är inte en del av URL:en. Använd `$switchLocale()` för att ändra lokal och ladda om översättningar medan du stannar på samma sökväg:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Eller uppdatera endast preferensen med `useI18nLocale().setLocale('de')`. För en fullständig omladdning av översättningar på klientsidan, föredra `$switchLocale()`.

**Prefixstrategier** (`prefix`, `prefix_except_default`, …) — lokal och URL är länkade. `$switchLocale()` navigerar alltid till den lokaliserade rutten. Det finns inget `redirect: false`-alternativ.

Om du bara behöver mål-URL:en (till exempel en språkväxlarlänk), använd `$switchLocalePath()` i stället:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Se [Rutt- och lokalbyte](/api/methods#-route-locale-switching) för alla växlingsmetoder.

### ❓ Sidan scrollar till toppen (eller hoppar) vid lokalbyte?

Det är förväntat — det är **Vue Router / Nuxt scroll-beteende**, inte något specifikt för nuxt-i18n-micro.

Med prefixstrategier (`prefix`, `prefix_except_default`, …) utför `$switchLocale()` en normal klientnavigering (`/en/page` → `/de/page`). Nuxts standard [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) scrollar till toppen vid ruttändringar (utom bakåt/framåt i webbläsaren via `savedPosition`).

nuxt-i18n-micro lägger inte till dold scrollhantering — använd en liten wrapper-komponent i din app.

**Wrappern `SwitchLocalePreserve`**

Kopiera [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) till ditt projekt (`components/SwitchLocalePreserve.vue`). Fungerande demo: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

På sidan, sätt `scrollToTop: false` och omslut ditt växlar-UI. Markera klickbara mål med `data-locale` — wrappern fångar upp klick, anropar `$switchLocale` och återställer scrollen (även när översättningslängden ändrar layouten):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Komponenten:

1. **Vid klick** — läser `data-locale` på det klickade elementet inuti sloten (knappar, länkar eller vilken anpassad markup som helst).
2. **Före** `$switchLocale` — sparar `scrollY` och det klickade elementets position (håller det under muspekaren).
3. **Under** navigering — patchar `router.options.scrollBehavior` en gång och returnerar `\{ top: scrollY \}` i stället för att scrolla till toppen.
4. **Efter** navigering — väntar på `page:finish`, tillämpar sedan scrollen på nytt medan en `ResizeObserver` fångar layoutförändringar från olika översättningslängder.

`scrollToTop: false` krävs på sidor där du använder denna wrapper. Dokumentation: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Anropa inte `$switchLocale` direkt på omslutna kontroller — wrappern hanterar växlingen. För `<NuxtLink :to="$switchLocalePath('fr')">` utanför wrappern följer scroll-beteendet normal Nuxt-routing om du inte lägger till din egen `app/router.options.ts`.

## 🌐 Översättningsproblem

### ❓ Varför slutar översättningar att fungera under sidövergångar, särskilt med `defineAsyncComponent`?

När du använder `nuxt-i18n-micro` med sidövergångar kan översättningar kortvarigt sluta fungera under övergången. Detta problem uppstår eftersom rutten ändras innan övergången slutförs, vilket gör att översättningar för den nya sidan laddas medan den gamla sidan fortfarande är synlig.

**Grundorsak:**

- Sidövergångar orsakar ruttändringar innan översättningar är fullt laddade
- `defineAsyncComponent` och `useAsyncData` kan fördröja översättningsladdningen
- Översättningsnycklar kan visas som råa sökvägar under laddning

**Lösning 1: Kumulativ sammanslagning (inbyggd, ingen konfiguration behövs)**

I v3 använder modulen automatiskt en kumulativ sammanslagningsstrategi. När du navigerar inom samma lokal slås översättningar för den nya sidan samman in i den aktiva ordboken i stället för att ersätta den. Detta innebär att översättningar från den föregående sidan förblir tillgängliga under övergångsanimationen. Efter att övergången är slutförd (`page:transition:finish`-hook) rensas gamla nycklar bort automatiskt.

Ingen konfiguration behövs — detta fungerar direkt.

**Lösning 2: Explicit ruttkontext**

Om du föredrar manuell kontroll, skicka den aktuella rutten explicit till `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Lösning 3: Laddningstillstånd**

Implementera laddningstillstånd för att hantera översättningsladdning på ett elegant sätt:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Varför resolvas inte översättningsnycklar under SSR på Vercel?

**Begränsningar för `$fetch` på SSR**
På serverlösa plattformar som Vercel kan `$fetch` endast hämta statiska filer från CDN:et och inte från den interna Nitro-servern. Detta innebär att statiska översättningsfiler kanske inte är direkt tillgängliga om inte rätt bas-URL är satt.

**Åtgärda genom att sätta `apiBaseClientHost` och `apiBaseServerHost`**
Om översättningar hostas externt på en CDN eller annan domän, använd `apiBaseClientHost` för klientförfrågningar och `apiBaseServerHost` för serverförfrågningar. `apiBaseUrl` ska endast innehålla sökvägsprefixet (till exempel `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Eller via miljövariabler:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Översättningarna kommer att hämtas från `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` på både klient och server.

## 🔗 Problem med routing och navigering

### ❓ Kan jag använda `NuxtLink` eller `<i18n-link>` direkt i översättningssträngar?

Ja, `Nuxt I18n Micro` tillåter användning av `NuxtLink` eller `<i18n-link>` inuti översättningar via komponenten `<i18n-t>`, vilket är särskilt användbart för att hantera grammatik och krav för RTL-språk utan att dela upp översättningssträngar.

**Exempel:**

Översättningsfil:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue-mall:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Detta tillåter dynamiska länkar inuti översättningar samtidigt som korrekt lokaliseringsstruktur bevaras.

## 🏗️ Problem vid bygge och distribution

### ❓ Varför hamnar översättnings-payloads under `public/_locales/` (eller i serverbundeln på Edge)?

SSR och klienten behöver båda samma `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`-payloads. Hur de paketeras beror på Nitro-målet:

**Förklaring:**

- **Node (standard):** modulen bäddar **inte** in översättningar som Nitro `serverAssets` / Rollup `raw:` (det sprängde bygg-RAM på stora kataloger). I stället kopierar den det premergade trädet till `public/<apiBaseUrl>/` (standard `_locales`) och SSR läser dessa filer med `readFile`. Klienten `$fetch`ar samma URL:er — antingen som statiska filer eller via Nitro-hanteraren.
- **Edge** (`nitro.node === false`): det finns inget beständigt publikt filsystem för SSR, så payloads bäddas in via Nitro `serverAssets` (`assets:i18n`). Föredra `translationPayloads.mode: 'source'` så att inbäddningen förblir kompakt. Sätt `publicAssets: true` endast om du också behöver en CDN/statisk kopia.
- **`prerenderRoutes`:** valfritt. I premerged-läge skriver `publicAssets` redan `\{page\}/\{locale\}/data.json`, så prerendering av dessa rutter är vanligtvis överflödigt.

### ❓ Varför får jag ett byggfel som hänvisar till `@unhead/vue` eller ett odefinierat objekt, särskilt på Cloudflare Pages?

**Orsak:**
Vissa projekt upplever byggkonflikter eller saknade beroenden vid användning av `nuxt-i18n-micro`. Särskilt:

- Distributioner på **Cloudflare Pages** eller **Cloudflare Workers** kan kräva ytterligare kompatibilitetsflaggor.
- Prerender-steg kan misslyckas om beroenden som `@unhead/vue` inte är korrekt installerade.
- Vissa moduler (till exempel **nuxthub**, **nitro-cloudflare-dev**) kan orsaka konflikter om de inte konfigureras med rätt flaggor eller beroenden.

**Möjliga lösningar:**

**Lösning 1: Installera `@unhead/vue` manuellt**
Om byggfelet klagar på att `@unhead/vue` inte hittas, installera det direkt i ditt projekts beroenden:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Detta säkerställer att det är tillgängligt under Nitros prerender-fas.

**Lösning 2: Lägg till Cloudflare-kompatibilitetsflaggor**
När du använder Cloudflare Pages eller Cloudflare Workers är Node.js-kompatibilitet ofta inaktiverad som standard. Aktivera den i din `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Denna flagga tillåter många Node.js-moduler (inklusive de som används av `nuxt-i18n-micro`) att köras smidigt.

## 🔍 SEO och `@nuxtjs/seo`

### ❓ Fel: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Detta händer när **`@nuxtjs/seo`** drar in en gammal **`nuxt-site-config` 3.x** som endast registrerar sin i18n-plugin för `@nuxtjs/i18n`, inte för **nuxt-i18n-micro**.

**Åtgärd:**

1. Uppgradera till **`@nuxtjs/seo` 3+** (inkluderar `nuxt-site-config` 4+ med micro-stöd).
2. Placera **`nuxt-i18n-micro` före `@nuxtjs/seo`** i `modules`.
3. Behåll **`i18n.meta: true`** för lokalmedvetna head-taggar.

Se [SEO-guiden — Nuxt SEO-sektionen](/guides/seo#nuxt-seo-nuxtjs-seo) för ett fullständigt exempel.

## 🔧 Konfiguration och kompatibilitet

### ❓ Är `Nuxt I18n Micro` inspirerad av `vue-i18n`? Vad är det med modifierare?

Även om `Nuxt I18n Micro` fungerar som ett prestandaalternativ till `nuxt-i18n`, är den byggd oberoende av `vue-i18n`. Även om vissa metodnamn och parametrar kan vara liknande skiljer sig den underliggande funktionaliteten avsevärt.

**Modifierare**: Underhållaren övervägde inledningsvis modifierare, men drog slutsatsen att komponenter som `<i18n-t>` och `<i18n-link>` effektivt täcker de behoven.

Till exempel:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Detta tillvägagångssätt är flexibelt, så att släppa modifierare är för närvarande onödigt. Modifierare kan dock läggas till i framtida releaser om det finns efterfrågan.
