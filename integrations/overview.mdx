The `@i18n-micro/*` packages are lightweight, framework-specific ports of Nuxt I18n Micro. They give you the same translation engine, pluralization, and formatting outside of Nuxt, with a minimal footprint focused on essentials.

<Note>
  These packages are **standalone**, not wrappers around the Nuxt module. Every framework package builds on the shared `@i18n-micro/core` runtime and `@i18n-micro/types` type definitions, so behavior and message formats are consistent across ecosystems.
</Note>

## What the packages give you

- **Core translation features.** `t`, `ts`, `tc`, `tn`, `td`, `tdr`, and `has` behave identically to the Nuxt module.
- **Essential components.** A small set of UI primitives (`I18nT`, `I18nLink`, `I18nSwitcher`, `I18nGroup`) implemented idiomatically for each framework.
- **Router adapter pattern.** You bring your own router. Implement the `I18nRoutingStrategy` interface and the components handle locale-aware links, active state, and locale switching for you.
- **TypeScript support.** Full type definitions plus optional key-level typing through `@i18n-micro/types-generator`.

Compared to the Nuxt module, these packages do not include file-based routing, auto locale detection, or SEO meta injection (except for Astro, which handles SSR itself). You wire routing up through the adapter, which keeps each package small and framework-agnostic.

## Shared `createI18n` options

Every framework package exposes a `createI18n` (or `I18nProvider`) entry point that accepts the same options. Only the option type is renamed per framework (`VueI18nOptions`, `ReactI18nOptions`, `SolidI18nOptions`, and so on).

| Property         | Type                                                       | Required | Default          | Description                                    |
| ---------------- | ---------------------------------------------------------- | -------- | ---------------- | ---------------------------------------------- |
| `locale`         | `string`                                                   | Yes      | —                | Current locale code (for example `'en'`).      |
| `fallbackLocale` | `string`                                                   | No       | Same as `locale` | Fallback when a translation is missing.        |
| `messages`       | `Record<string, Translations>`                             | No       | `{}`             | Initial translation messages per locale.       |
| `plural`         | `PluralFunc`                                               | No       | `defaultPlural`  | Custom pluralization function.                 |
| `missingWarn`    | `boolean`                                                  | No       | `true`           | Log a warning when a key is missing.           |
| `missingHandler` | `(locale: string, key: string, routeName: string) => void` | No       | —                | Custom handler for missing translations.       |

Anything beyond these is framework-specific and is documented on that package's page.

## The router adapter contract

Routing features (locale-prefixed links, `switchLocale`, active state) go through an adapter that implements the `I18nRoutingStrategy` interface. This is what decouples i18n from any specific router.

```typescript
interface I18nRoutingStrategy {
  getCurrentPath: () => string
  linkComponent?: unknown // Framework-specific link component
  push: (target: { path: string }) => void
  replace: (target: { path: string }) => void
  resolvePath?: (to: string | { path?: string }, locale: string) => string | { path?: string }
  getRoute?: () => { fullPath: string; query: Record<string, unknown> }
}
```

Each package ships a built-in adapter for its most common router:

- **Vue** exposes `createVueRouterAdapter` for `vue-router`.
- **React** exposes `createReactRouterAdapter` for `react-router-dom`. Custom adapters for Next.js and TanStack Router are documented on the React page.
- **Solid** exposes `createSolidRouterAdapter` for `@solidjs/router`. It also requires `getCurrentPathAccessor` for reactive active states.
- **Astro** uses a file-based routing adapter documented on the Astro page.

You can skip the adapter entirely if you don't need routing features. The translation API works standalone.

## Choosing between the Nuxt module and integration packages

| Feature                | Nuxt module   | Integration packages |
| ---------------------- | ------------- | -------------------- |
| Translation methods    | Yes           | Yes                  |
| Components             | Yes           | Yes (subset)         |
| Router integration     | Automatic     | Via adapter          |
| SSR support            | Yes           | Astro only           |
| DevTools               | Yes           | Yes                  |
| Auto locale detection  | Yes           | Astro only           |
| SEO meta tags          | Yes           | Astro only           |
| File-based routing     | Yes           | No                   |

If you are building on Nuxt, use the module. If you are building on any other framework, pick the matching integration package.
