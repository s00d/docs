---
title: "Runtime translation overrides"
description: "Patch, replace, and lazy-load translations at runtime with $mergeTranslations, $setTranslation, and $loadPageTranslations."
---

Nuxt I18n Micro builds a per-page translation dictionary at build time, but you can still change what `$t()` returns at runtime. This is useful for CMS-driven content, per-tenant overrides, DevTools editors, or lazy-loading translations whose keys are not known at build time.

Three methods drive runtime overrides:

- [`$mergeTranslations`](/api/methods) merges a patch into the active dictionary.
- [`$setTranslation`](/api/methods) replaces the value at a specific key.
- [`$loadPageTranslations`](/api/methods) loads an entire page's dictionary for a given locale.

All three are available through `useNuxtApp()` (or the `useI18n()` helper) and act on the **active locale's dictionary** in memory.

## Merging a patch with `$mergeTranslations`

`$mergeTranslations(newTranslations)` deep-merges the given object into the active locale, keeping existing sibling keys intact:

```typescript
const { $mergeTranslations } = useNuxtApp()

$mergeTranslations({
  welcome: 'Bienvenue, {username}!',
  menu: {
    dashboard: 'Tableau de bord',
  },
})
```

If `menu.home` already exists, it stays. Only `menu.dashboard` is added (or replaced). Use this whenever you need to layer overrides on top of build-time data without dropping keys.

<Tip>
`$mergeTranslations` is the safest way to inject CMS content. If a key already exists in your build, the CMS value wins for this session, but no other keys are affected.
</Tip>

## Replacing a key with `$setTranslation`

`$setTranslation(key, value)` replaces the value at a specific key. Unlike `$mergeTranslations`, this is a **replace**, not a merge, so any sibling keys under the same path are removed.

```typescript
const { $setTranslation } = useNuxtApp()

$setTranslation('aaa', { fff: 'ggg' }) // replaces the whole `aaa` subtree
$setTranslation('aaa', 'text')          // replaces `aaa` with a string
$setTranslation('ddd', 1111)            // scalar at the top level
$setTranslation('aaa.bbb', 'nested')    // dotted path
```

<Warning>
This is a **replace**, not a merge. If you write `$setTranslation('menu', { home: 'Home' })`, any other keys under `menu` are removed. Use `$mergeTranslations` when existing siblings should survive.
</Warning>

## Loading a page dictionary with `$loadPageTranslations`

`$loadPageTranslations(locale, routeName, translations)` loads an entire dictionary for a specific page in a specific locale. Use this when translation keys are not known at build time (for example, editor previews, blog CMS content, or A/B tested copy).

```typescript
const { $loadPageTranslations } = useNuxtApp()

await $loadPageTranslations('en', 'about', {
  title: 'About Us',
  description: 'Learn more about our company',
})
```

After the call resolves, `$t()` on the `about` page (in English) can resolve `title` and `description`. Call it again with new data to update the same locale-page pair.

## Combining the three methods

A common pattern is to load a page dictionary once and then patch individual keys as the user edits them:

```typescript
const { $loadPageTranslations, $mergeTranslations, $setTranslation } = useNuxtApp()

// Bootstrap all keys for the page.
await $loadPageTranslations('en', 'article', article.value.translations)

// Merge a partial CMS patch on top.
$mergeTranslations({
  cta: {
    label: article.value.ctaLabel,
  },
})

// Fine-grained edit from a WYSIWYG.
$setTranslation('article.title', article.value.title)
```

## Notes

- Overrides live only in the active runtime. They do not persist across reloads or SSR requests.
- Overrides apply to the active locale only. Switch locale first if you need to patch another one.
- `$loadPageTranslations` accepts any translations object shape your app expects. The module does not validate the structure.
- Runtime overrides do not touch the build-time `.json` files or the cached payloads.
