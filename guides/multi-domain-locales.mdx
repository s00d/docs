---
title: "Multi-domain locales"
description: "Serve different locales from different domains with per-locale baseUrl and Nuxt layers."
---

Some multilingual projects need each language on its own domain (`example.com`, `de.example.com`, `example.fr`) rather than under a locale prefix. Nuxt I18n Micro supports two complementary patterns for this:

- **Per-locale `baseUrl`** for canonical, `hreflang`, and Open Graph URLs.
- **Nuxt layers** so each domain deployment can activate the locale it serves.

## Per-locale `baseUrl` and `baseDefault`

Add a `baseUrl` field to each locale object to make cross-locale SEO links point at the correct domain. Use `baseDefault: true` on a locale that should be served without a locale prefix on its own domain.

```typescript nuxt.config.ts
export default defineNuxtConfig({
  i18n: {
    meta: true,
    defaultLocale: 'en',
    locales: [
      {
        code: 'en',
        iso: 'en-US',
        baseUrl: 'https://example.com',
        baseDefault: true,
      },
      {
        code: 'de',
        iso: 'de-DE',
        baseUrl: 'https://de.example.com',
      },
      {
        code: 'fr',
        iso: 'fr-FR',
        baseUrl: 'https://example.fr',
      },
    ],
  },
})
```

With this setup, `hreflang` and `og:url` links resolve to each locale's own domain rather than to a locale-prefixed path on a single host.

<Warning>
Using `baseUrl` can lead to duplication of internal routes as external links, which complicates routing and maintenance. Consider creating external links directly for specific locales when the URL structures diverge substantially.
</Warning>

## Deploying each domain as a layer

The other half of the pattern uses [Nuxt Layers](/guides/layers) so each domain deployment builds with only the locales it needs. This distributes load, keeps translation payloads focused, and lets you deploy the same repository to multiple hosts.

### Base layer

Define the full set of locales in a base layer:

```typescript base/nuxt.config.ts
export default defineNuxtConfig({
  i18n: {
    locales: [
      { code: 'en', iso: 'en-US', dir: 'ltr' },
      { code: 'de', iso: 'de-DE', dir: 'ltr' },
      { code: 'es', iso: 'es-ES', dir: 'ltr' },
    ],
    defaultLocale: 'en',
    translationDir: 'locales',
    meta: true,
    autoDetectLanguage: true,
  },
})
```

### Domain-specific layer for `fr.example.com`

```typescript fr/nuxt.config.ts
export default defineNuxtConfig({
  extends: '../base',
  i18n: {
    locales: [
      { code: 'en', iso: 'en-US', dir: 'ltr', disabled: true },
      { code: 'fr', iso: 'fr-FR', dir: 'ltr' },
      { code: 'de', iso: 'de-DE', dir: 'ltr', disabled: true },
      { code: 'es', iso: 'es-ES', dir: 'ltr', disabled: true },
    ],
    defaultLocale: 'fr',
    autoDetectLanguage: false,
  },
})
```

### Domain-specific layer for `de.example.com`

```typescript de/nuxt.config.ts
export default defineNuxtConfig({
  extends: '../base',
  i18n: {
    locales: [
      { code: 'en', iso: 'en-US', dir: 'ltr', disabled: true },
      { code: 'fr', iso: 'fr-FR', dir: 'ltr', disabled: true },
      { code: 'de', iso: 'de-DE', dir: 'ltr' },
      { code: 'es', iso: 'es-ES', dir: 'ltr', disabled: true },
    ],
    defaultLocale: 'de',
    autoDetectLanguage: false,
  },
})
```

`disabled: true` removes those locales from the router, the language switcher, and all SEO tags for that deployment. Only the active locale ships in the build.

### Deploy each layer to its own host

- Deploy the `fr` layer configuration to `fr.example.com`.
- Deploy the `de` layer configuration to `de.example.com`.
- Deploy the base or a dedicated `en` layer to `example.com`.

Each domain therefore serves the correct locale with the correct default and none of the routing noise from other languages.

## Routing and DNS

Ensure that your platform (nginx, Cloudflare, ALB) routes each domain to the correct build. Nuxt I18n Micro does not perform host-based routing itself. The layer configuration determines what gets bundled for each host.

If you also want the incoming request to influence the runtime locale on shared hosts, combine this pattern with a custom detection plugin. See [custom language detection](/guides/custom-language-detection).

## Best practices

- **Keep the base configuration generic.** Put the full locale roster and shared defaults in the base layer.
- **Isolate domain-specific logic.** Each domain layer should only override what changes.
- **Verify SEO tags per domain.** Test that `canonical`, `hreflang`, and `og:url` resolve to the domain you expect for each deployment.
- **Prefer separate builds over runtime host sniffing** when the routing strategy differs per domain (`no_prefix` on one, `prefix` on another). See [runtime overrides](/guides/runtime-overrides) for the limits of runtime configuration.
