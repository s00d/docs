---
title: "useI18nLocale"
description: "useI18nLocale liest und schreibt den Locale-State und das Locale-Cookie — der Einstiegspunkt für eigene Locale-Erkennung."
---

`useI18nLocale()` gibt Zugriff auf die Locale, die die App gewählt hat: den State `i18n-locale` und das Locale-Cookie. Verwenden Sie es in einem Plugin, das die Locale selbst erkennt (Domain, Benutzerprofil, Header), statt `useState('i18n-locale')` oder das Cookie von Hand zu schreiben. Seine Gültigkeitsprüfungen verwenden die aktivierten Locales, einschließlich Runtime-Overrides.

## Signatur {#signature}

```ts
useI18nLocale(): { getEffectiveLocale: (route: unknown, getLocaleFromRoute: GetLocaleFromRoute) => string; getLocale: () => string | null; getPreferredLocale: () => string | null; hashCookie: CookieRef; isValidLocale: (locale: string | null | undefined) => locale is string; locale: any; localeCookie: CookieRef; resolveInitialLocale: (options: ResolveInitialLocaleOptions) => string; setLocale: (locale: string | null) => void; syncLocale: (locale: string | null) => void; validLocales: string[] }
```

Zentraler Einstiegspunkt für die i18n-Locale-Verwaltung.
Kombiniert useState('i18n-locale'), das Locale-Cookie und Synchronisierungs-Utilities.

## Rückgabewerte {#returned-values}

| Mitglied | Typ | Beschreibung |
| --- | --- | --- |
| `locale` | `Ref<string \| null>` | Die Ref `useState('i18n-locale')`. |
| `localeCookie` | `Ref<string \| null>` | Das Cookie [`localeCookie`](/de/api/module-options#localecookie); ein einfaches `{ value: null }`, wenn die Option `null` ist. |
| `hashCookie` | `Ref<string \| null>` | Das Cookie `hash-locale` bei Hash-Routing; sonst `{ value: null }`. |
| `validLocales` | `string[]` | Codes der aktivierten Locales. |
| `setLocale(locale)` | `(locale: string \| null) => void` | State und Cookies schreiben. Validiert nicht und lädt keine Übersetzungen. |
| `syncLocale(locale)` | `(locale: string \| null) => void` | Nur die Cookies schreiben. |
| `getLocale()` | `() => string \| null` | Der State, dann das Präferenz-Cookie (bei Hash-Routing das Hash-Cookie). Nicht validiert. |
| `getPreferredLocale()` | `() => string \| null` | Der erste **gültige** Wert aus State und Präferenz-Cookie, oder `null`. |
| `getEffectiveLocale(route, getLocaleFromRoute)` | `(route, fn) => string` | Bei Hash-Routing der State, falls gesetzt; sonst `getLocaleFromRoute(route)`. |
| `resolveInitialLocale(options)` | `(options: ResolveInitialLocaleOptions) => string` | `options.urlLocale`, dann ein gültiger State, dann `options.serverLocale`, dann die Locale der Route. Speichert das Ergebnis im State, wenn der State nicht gültig ist; auf dem Client schreibt es außerdem das Cookie. |
| `isValidLocale(locale)` | `(locale) => locale is string` | Ob `locale` in `validLocales` enthalten ist. |

Die Cookies sind ein Jahr gültig, mit `path: '/'` und `sameSite: 'lax'`.

## Beispiel {#example}

```ts
// plugins/locale-from-domain.server.ts
export default defineNuxtPlugin({
  name: 'locale-from-domain',
  enforce: 'pre',
  setup() {
    const { setLocale, isValidLocale } = useI18nLocale()
    const host = useRequestURL().hostname // e.g. de.example.com
    const code = host.split('.')[0]
    if (isValidLocale(code)) setLocale(code)
  },
})
```

Das Loader-Plugin des Moduls liest den State beim Start, daher muss ein Plugin, das ihn setzt, zuerst laufen (`enforce: 'pre'`). Wie der State mit der URL, dem Cookie und `Accept-Language` konkurriert: [Locale-Erkennung](/de/guide/locale-detection). Vollständige Anleitung: [Eigene Erkennung](/de/guide/custom-auto-detect).

`setLocale()` wechselt die angezeigten Übersetzungen nicht. Um die Locale der aktuellen Seite zu ändern, rufen Sie [`$switchLocale()`](/de/api/methods#$switchlocale) auf.
