---
title: "Seitenkonfiguration"
description: "Eine Seite mit $defineI18nRoute auf bestimmte Locales beschränken, ihr eigene Pfade, Inline-Übersetzungen geben oder SEO-Tags abschalten."
---

`$defineI18nRoute` setzt i18n-Optionen für eine Seite aus der Seite selbst heraus. Verwende es, wenn eine Seite nur in einigen Locales existiert, einen eigenen lokalisierten Pfad braucht, ein paar eigene Übersetzungen mitbringt oder keine hreflang-/canonical-Tags erhalten darf. Das Modul liest den Aufruf zur Build-Zeit und baut ihn in die generierten Routen ein.

## Eine Seite auf bestimmte Locales beschränken {#restrict-a-page-to-some-locales}

```vue
<!-- pages/product/index.vue -->
<script setup lang="ts">
const { $defineI18nRoute } = useNuxtApp()

$defineI18nRoute({
  locales: ['en', 'de'],
})
</script>
```

Unter der Standardstrategie `prefix_except_default` werden nur `/product` und `/de/product` generiert; die Seite hat in keiner anderen Locale eine Route. Dasselbe lässt sich in `nuxt.config.ts` mit [`routeLocales`](/de/api/module-options#routelocales) festlegen.

`$defineI18nRoute` ist eine Nuxt-App-Injection, kein Compiler-Makro: Hole es immer aus `useNuxtApp()` und rufe es mit dem `$` auf. Nur `$defineI18nRoute(` wird vom Build-Schritt erkannt.

## Inline-Übersetzungen hinzufügen {#add-inline-translations}

Übergib ein Objekt statt eines Arrays. Seine Schlüssel sind die erlaubten Locales, seine Werte werden für die aktive Locale in das Wörterbuch der Seite eingefügt.

```vue
<script setup lang="ts">
const { $defineI18nRoute } = useNuxtApp()

$defineI18nRoute({
  locales: {
    en: { greeting: 'Hello' },
    de: { greeting: 'Hallo' },
    fr: {}, // allowed, no inline keys
  },
})
</script>

<template>
  <h1>{{ $t('greeting') }}</h1>
</template>
```

Inline-Übersetzungen werden für jede Locale in der Seitenkomponente ausgeliefert. Bevorzuge [Seiten-Übersetzungsdateien](/de/guide/translations) für alles, was größer als ein paar Schlüssel ist; behalte Inline-Schlüssel für in sich geschlossene Seiten und Komponenten.

## Lokalisierte Pfade festlegen {#set-localized-paths}

```ts
$defineI18nRoute({
  locales: ['en', 'de'],
  localeRoutes: {
    en: '/welcome',
    de: '/willkommen',
  },
})
```

Mit `prefix_except_default` und `defaultLocale: 'en'` ergibt das `/welcome` und `/de/willkommen`. Ein `path` innerhalb eines Inline-Locale-Objekts bewirkt dasselbe: `locales: { de: { path: '/willkommen' } }`. Dynamische Parameter, verschachtelte Routen und die Alternative auf Konfigurationsebene werden unter [Lokalisierte Pfade](/de/guide/custom-locale-routes) behandelt.

## SEO-Tags abschalten {#turn-off-seo-tags}

```ts
$defineI18nRoute({
  disableMeta: true, // no hreflang, canonical or og:locale tags on this page
})

$defineI18nRoute({
  disableMeta: ['de'], // only the de version has no tags
})
```

Die Alternative auf Konfigurationsebene ist [`routeDisableMeta`](/de/api/module-options#routedisablemeta). Was die Tags sind, steht auf der Seite [SEO](/de/guide/seo).

## Was der Build lesen kann {#what-the-build-can-read}

Der Build-Schritt findet den Aufruf in jeder Seitendatei und wertet sein Argument aus, ohne deine App auszuführen. Das funktioniert, wenn die Konfiguration Folgendes ist:

- ein literales Objekt (Strings, Arrays, verschachtelte Objekte, Template-Literale, ternäre Ausdrücke über `process.env.NODE_ENV`);
- aus Konstanten aufgebaut, die im selben `<script setup>` deklariert sind (`const locales = ['en', 'de']`, Spreads eingeschlossen);
- ein Array von Objekten mit einem `code`-Feld (`[{ code: 'en' }, { code: 'de' }]`).

Er kann keine Werte lesen, die aus einem anderen Modul importiert werden, oder irgendetwas, das deine App zur Laufzeit braucht (Composables, `await`, abgerufene Daten). In diesem Fall protokolliert der Build `Ignored the $defineI18nRoute() config in <file>`, und die Seite behält die Standard-Locales und -Routen.

Zur Laufzeit fügt der Aufruf nur die Inline-Übersetzungen für die aktuelle Locale ein und führt sie erneut zusammen, wenn sich die Locale ändert. `locales`, `localeRoutes` und `disableMeta` wirken nur über den Build, daher erfordert eine Änderung einen Rebuild (der Dev-Server baut beim Speichern neu).
