---
title: "Eigene Locale-Erkennung"
description: "Wähle die Locale selbst – nach Domain, Header oder Benutzerprofil – mit einem Server-Plugin und useI18nLocale().setLocale()."
---

Die eingebaute Erkennung liest die URL, ein Cookie und `Accept-Language`. Wenn die Locale von etwas anderem abhängt – der Domain, einem Geo-Header deines CDN, einem Benutzerprofil –, setze sie selbst in einem Plugin, das vor dem i18n-Plugin läuft. Das Modul lädt dann die Übersetzungen dieser Locale und verwendet sie für Weiterleitungen genau so, als hätte es sie selbst erkannt. Die Regeln, wann eine gewählte Locale Vorrang vor der URL hat, stehen unter [Locale-Erkennung](/de/guide/locale-detection); diese Seite zeigt, wie du deine eigene Quelle einbindest.

## Locale in einem Server-Plugin setzen {#set-the-locale-in-a-server-plugin}

```ts
// plugins/i18n-locale.server.ts
export default defineNuxtPlugin({
  name: 'i18n-custom-locale',
  enforce: 'pre',
  order: -10, // before the i18n plugin (order -5)
  setup() {
    const { setLocale } = useI18nLocale()
    const host = (useRequestHeaders(['host']).host ?? '').split(':')[0]! // without the port

    if (host.endsWith('.de')) setLocale('de')
    else if (host.endsWith('.fr')) setLocale('fr')
  },
})
```

`setLocale(code)` schreibt den Locale-Zustand (`useState('i18n-locale')`) und, wenn ein Locale-Cookie konfiguriert ist, das Cookie. Verwende es, anstatt selbst `useState` oder `useCookie` zu schreiben. Übergib nur aktivierte Locale-Codes.

Belasse das Plugin als `.server.ts`, wenn es Request-Header liest: Diese existieren im Browser nicht. Ein `.client.ts`-Plugin ist der richtige Ort für reine Browser-Quellen wie `localStorage`.

## Den eingebauten Accept-Language-Schritt abschalten {#turn-off-the-built-in-accept-language-step}

Dein Plugin und `Accept-Language` können sich widersprechen. Damit nur dein Code (plus URL und Cookie) entscheidet, schalte den Header ab:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    autoDetectLanguage: false,
  },
})
```

[`autoDetectLanguage`](/de/api/module-options#autodetectlanguage) steuert nur den Header-Schritt. Die URL und ein gültiges Cookie zählen weiterhin.

## Was danach passiert {#what-happens-next}

Die Wirkung von `setLocale` hängt von der [Strategie](/de/guide/strategy) ab:

| Strategie | Wirkung von `setLocale('de')` im Plugin |
| --- | --- |
| `no_prefix` | Die Seite wird auf Deutsch gerendert; die URL ändert sich nicht. |
| `prefix`, `prefix_except_default` | Auf einem Pfad ohne Präfix, auf dem [`autoDetectPath`](/de/api/module-options#autodetectpath) Weiterleitungen erlaubt (standardmäßig nur `/`), antwortet der Server mit `302` auf die deutsche URL. Eine URL mit Locale-Präfix behält es. |
| `prefix_and_default` | Keine Weiterleitung: Die URL ohne Präfix ist eine gültige Seite der Standard-Locale. |

Bei den Präfix-Strategien ist eine Locale in der URL die Wahl des Benutzers, und dein Plugin überschreibt sie nicht. `autoDetectPath: '*'` ist die Ausnahme: Der Server leitet dann URLs mit Präfix anhand von Cookie und `Accept-Language` um und ignoriert den Zustand. `setLocale()` schreibt aber auch das Cookie, wenn eines konfiguriert ist, sodass ab dem nächsten Request die Wahl deines Plugins eine URL mit Präfix umleiten kann. Behalte `'/'` bei oder verwende `'no_prefix'`, wenn explizite Locale-URLs Vorrang haben müssen. Nutze dein Plugin, um zu bestimmen, wo ein Besucher landet, nicht um Links umzuschreiben, denen er gefolgt ist.

## Eine vom Benutzer gewählte Locale respektieren {#respect-a-locale-the-user-picked}

Sobald ein Benutzer die Sprache wechselt, schreibt der Wechsel das Cookie. Überspringe deine eigene Erkennung, wenn bereits eine gültige Präferenz existiert:

```ts
// plugins/i18n-locale.server.ts
import { detectLocaleFromAcceptLanguage } from '@i18n-micro/utils/accept-language'

export default defineNuxtPlugin({
  name: 'i18n-custom-locale',
  enforce: 'pre',
  order: -10,
  setup() {
    const { getPreferredLocale, setLocale, validLocales } = useI18nLocale()
    if (getPreferredLocale()) return // valid state or cookie: keep it

    const country = useRequestHeaders(['x-country'])['x-country']
    if (country === 'JP') return setLocale('ja')

    const header = useRequestHeaders(['accept-language'])['accept-language']
    setLocale(detectLocaleFromAcceptLanguage(header, validLocales))
  },
})
```

`getPreferredLocale()` gibt den Zustand oder das Cookie nur zurück, wenn es sich um eine aktivierte Locale handelt, sodass ein veraltetes Cookie die Erkennung nicht blockiert. `detectLocaleFromAcceptLanguage` ist der q-Wert-bewusste Matcher, den das Modul selbst verwendet (installiere `@i18n-micro/utils`, um ihn zu importieren); `setLocale(null)` bewirkt nichts.

## Eine Domain pro Locale {#one-domain-per-locale}

Wenn jede Domain ihre eigenen Locales ausliefern soll, brauchst du kein Plugin: Gib jeder Locale eine `baseUrl`, setze `baseDefault: true` auf der Standard-Locale jeder Domain und baue einmal (eine statische Site führt `nuxi generate` trotzdem pro Domain aus). Siehe [Layer und Domains](/de/guide/layers#multiple-domains).
