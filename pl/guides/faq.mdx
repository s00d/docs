# ❓ FAQ: typowe problemy i rozwiązania

Znajdź odpowiedzi na często zadawane pytania i rozwiązania typowych problemów z Nuxt I18n Micro.

## 🚀 Problemy z rozpoczęciem pracy

### ❓ Co jeśli trasa się nie ładuje?

Przy używaniu `Nuxt I18n Micro` niektóre trasy mogą się nie ładować zgodnie z oczekiwaniami, szczególnie jeśli router nie przypisuje automatycznie nazwy trasie w podfolderach.

**Rozwiązanie:**
Aby to rozwiązać, zdefiniuj ręcznie nazwę trasy dla strony, dodając do odpowiedniego pliku Vue:

```javascript
definePageMeta({ name: 'pageName' })
```

To zapewnia poprawną rejestrację trasy, umożliwiając płynną nawigację w aplikacji.

### ❓ Dlaczego `$t` lub inne composables i18n nie działają w pluginach Nuxt?

Composables Nuxt I18n (`$t`, `$getLocale`, `$localePath` itd.) mogą nie działać zgodnie z oczekiwaniami w pluginach Nuxt lub funkcjach użytkowych, powodując błędy w runtime.

**Przyczyna i rozwiązanie:**
Composables Nuxt wymagają konkretnych kontekstów (np. hooków Nuxt lub funkcji setup Vue) do dostępu do instancji Nuxt. Używane poza tymi kontekstami (np. w funkcjach użytkowych lub pluginach) mogą powodować pojawienie się w konsoli następującego błędu:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Rozwiązanie 1: użyj `runWithContext`**
Aby wywołać composables i18n po asynchronicznej operacji, użyj [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext), aby zachować niezbędny kontekst.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Rozwiązanie 2: pobierz wartość najpierw**
Alternatywnie pobierz wartość tłumaczenia najpierw, a następnie przekaż ją do funkcji użytkowej.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Rozwiązanie 3: przekazuj klucze tłumaczeń w serwisach**
W serwisach lub funkcjach użytkowych przekazuj klucze tłumaczeń zamiast używać bezpośrednio `$t`. Następnie pobierz tłumaczenie w komponencie.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Przełączanie lokalizacji

### ❓ Przełączyć lokalizację bez zmiany URL?

Tak — ale zależy to od Twojej [strategii routingu](/guides/routing-strategies).

**Strategia `no_prefix`** — lokalizacja nie jest częścią URL. Użyj `$switchLocale()`, aby zmienić lokalizację i przeładować tłumaczenia, pozostając na tej samej ścieżce:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Lub zaktualizuj tylko preferencję przez `useI18nLocale().setLocale('de')`. Dla pełnego przeładowania tłumaczeń po stronie klienta preferuj `$switchLocale()`.

**Strategie z prefiksem** (`prefix`, `prefix_except_default`, …) — lokalizacja i URL są powiązane. `$switchLocale()` zawsze przechodzi do zlokalizowanej trasy. Nie ma opcji `redirect: false`.

Jeśli potrzebujesz tylko docelowego URL (na przykład link przełącznika języka), użyj `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Zobacz [Przełączanie tras i lokalizacji](/api/methods#-route-locale-switching), aby poznać wszystkie metody przełączania.

### ❓ Strona przewija się na górę (lub skacze) przy przełączaniu lokalizacji?

To oczekiwane — to **zachowanie Vue Router / Nuxt scroll behavior**, a nie coś specyficznego dla nuxt-i18n-micro.

Ze strategiami z prefiksem (`prefix`, `prefix_except_default`, …), `$switchLocale()` wykonuje normalną nawigację klienta (`/en/page` → `/de/page`). Domyślny [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) Nuxt przewija na górę przy zmianach trasy (z wyjątkiem powrotu/naprzód przeglądarki przez `savedPosition`).

nuxt-i18n-micro nie dodaje ukrytej obsługi przewijania — użyj małego wrappera komponentu w swojej aplikacji.

**Wrapper `SwitchLocalePreserve`**

Skopiuj [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) do swojego projektu (`components/SwitchLocalePreserve.vue`). Działający pokaz: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

Na stronie ustaw `scrollToTop: false` i owinj UI przełącznika. Oznacz klikalne cele przez `data-locale` — wrapper przechwytuje kliknięcia, wywołuje `$switchLocale` i przywraca przewinięcie (w tym gdy długość tłumaczenia zmienia layout):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Komponent:

1. **Po kliknięciu** — odczytuje `data-locale` na klikniętym elemencie w slocie (przyciski, linki lub dowolny niestandardowy znacznik).
2. **Przed** `$switchLocale` — zapisuje `scrollY` i pozycję klikniętego elementu (utrzymuje go pod kursorem).
3. **Podczas** nawigacji — patchuje `router.options.scrollBehavior` raz i zwraca `\{ top: scrollY \}` zamiast przewijania na górę.
4. **Po** nawigacji — czeka na `page:finish`, następnie ponownie stosuje przewinięcie, podczas gdy `ResizeObserver` wychwytuje przesunięcia układu wynikające z różnych długości tłumaczeń.

`scrollToTop: false` jest wymagane na stronach, na których używasz tego wrappera. Dokumentacja: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Nie wywołuj bezpośrednio `$switchLocale` na owiniętych kontrolkach — wrapper obsługuje przełączanie. Dla `<NuxtLink :to="$switchLocalePath('fr')">` poza wrapperem zachowanie przewijania podąża za normalnym routingiem Nuxt, chyba że dodasz własne `app/router.options.ts`.

## 🌐 Problemy z tłumaczeniami

### ❓ Dlaczego tłumaczenia psują się podczas przejść stron, zwłaszcza z `defineAsyncComponent`?

Przy używaniu `nuxt-i18n-micro` z przejściami stron tłumaczenia mogą chwilowo przestać działać podczas przejścia. Ten problem występuje, ponieważ trasa zmienia się przed zakończeniem przejścia, powodując ładowanie tłumaczeń nowej strony, podczas gdy stara strona jest jeszcze widoczna.

**Główna przyczyna:**

- Przejścia stron powodują zmiany tras przed pełnym załadowaniem tłumaczeń
- `defineAsyncComponent` i `useAsyncData` mogą opóźnić ładowanie tłumaczeń
- Klucze tłumaczeń mogą się pojawiać jako surowe ścieżki podczas ładowania

**Rozwiązanie 1: kumulatywne scalanie (wbudowane, bez konfiguracji)**

W v3 moduł automatycznie używa strategii kumulatywnego scalania. Podczas nawigacji w obrębie tej samej lokalizacji tłumaczenia nowej strony są scalane z aktywnym słownikiem zamiast go zastępować. Oznacza to, że tłumaczenia z poprzedniej strony pozostają dostępne podczas animacji przejścia. Po zakończeniu przejścia (hook `page:transition:finish`) stare klucze są czyszczone automatycznie.

Nie jest wymagana żadna konfiguracja — to działa od razu.

**Rozwiązanie 2: jawny kontekst trasy**

Jeśli wolisz ręczną kontrolę, jawnie przekaż bieżącą trasę do `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Rozwiązanie 3: stany ładowania**

Wdrażaj stany ładowania, aby graciously obsługiwać ładowanie tłumaczeń:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Dlaczego klucze tłumaczeń nie rozwiązują się podczas SSR na Vercel?

**Ograniczenia `$fetch` w SSR**
Na platformach serverless takich jak Vercel `$fetch` może pobierać tylko pliki statyczne z CDN, a nie z wewnętrznego serwera Nitro. Oznacza to, że statyczne pliki tłumaczeń mogą nie być bezpośrednio dostępne, chyba że ustawiony jest prawidłowy bazowy URL.

**Napraw przez ustawienie `apiBaseClientHost` i `apiBaseServerHost`**
Jeśli tłumaczenia są hostowane zewnętrznie na CDN lub innej domenie, użyj `apiBaseClientHost` dla żądań po stronie klienta i `apiBaseServerHost` dla żądań po stronie serwera. `apiBaseUrl` powinien zawierać tylko prefiks ścieżki (np. `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Lub przez zmienne środowiskowe:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Tłumaczenia będą pobierane z `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` zarówno na kliencie, jak i serwerze.

## 🔗 Problemy z routingiem i nawigacją

### ❓ Czy mogę używać `NuxtLink` lub `<i18n-link>` bezpośrednio w ciągach tłumaczeń?

Tak, `Nuxt I18n Micro` pozwala używać `NuxtLink` lub `<i18n-link>` w tłumaczeniach przez komponent `<i18n-t>`, co jest szczególnie pomocne przy obsłudze gramatyki i wymagań języków RTL bez dzielenia ciągów tłumaczeń.

**Przykład:**

Plik tłumaczeń:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Szablon Vue:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

To pozwala na dynamiczne linki w tłumaczeniach przy zachowaniu odpowiedniej struktury lokalizacji.

## 🏗️ Problemy z buildem i wdrożeniem

### ❓ Dlaczego payloady tłumaczeń kończą pod `public/_locales/` (lub w bundlu serwera na Edge)?

SSR i klient potrzebują tych samych payloadów `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. Sposób ich pakowania zależy od celu Nitro:

**Wyjaśnienie:**

- **Node (domyślnie):** moduł **nie** osadza tłumaczeń jako `serverAssets` Nitro / `raw:` Rollup (to rozdymało RAM builda przy dużych katalogach). Zamiast tego kopiuje premerged drzewo do `public/<apiBaseUrl>/` (domyślnie `_locales`), a SSR odczytuje te pliki przez `readFile`. Klient `$fetch`uje te same URL-e — albo jako pliki statyczne, albo przez handler Nitro.
- **Edge** (`nitro.node === false`): nie ma trwałego publicznego FS dla SSR, więc payloady są osadzane przez `serverAssets` Nitro (`assets:i18n`). Preferuj `translationPayloads.mode: 'source'`, aby osadzenie pozostało kompaktowe. Ustaw `publicAssets: true` tylko jeśli potrzebujesz także kopii CDN/statycznej.
- **`prerenderRoutes`:** opcjonalne. W trybie premerged `publicAssets` już zapisuje `\{page\}/\{locale\}/data.json`, więc prerenderowanie tych tras jest zwykle zbędne.

### ❓ Dlaczego dostaję błąd buildu odnoszący się do `@unhead/vue` lub niezdefiniowanego obiektu, szczególnie na Cloudflare Pages?

**Przyczyna:**
Niektóre projekty doświadczają konfliktów buildu lub brakujących zależności przy używaniu `nuxt-i18n-micro`. W szczególności:

- Wdrożenia na **Cloudflare Pages** lub **Cloudflare Workers** mogą wymagać dodatkowych flag kompatybilności.
- Kroki prerenderowania mogą się nie powieść, jeśli zależności takie jak `@unhead/vue` nie są prawidłowo zainstalowane.
- Niektóre moduły (np. **nuxthub**, **nitro-cloudflare-dev**) mogą wprowadzać konflikty, chyba że są skonfigurowane z prawidłowymi flagami lub zależnościami.

**Możliwe rozwiązania:**

**Rozwiązanie 1: zainstaluj `@unhead/vue` ręcznie**
Jeśli błąd buildu skarży się na brak `@unhead/vue`, zainstaluj go bezpośrednio w zależnościach projektu:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

To zapewnia jego dostępność podczas fazy prerenderowania Nitro.

**Rozwiązanie 2: dodaj flagi kompatybilności Cloudflare**
Przy używaniu Cloudflare Pages lub Cloudflare Workers kompatybilność Node.js jest często domyślnie wyłączona. Włącz ją w `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Ta flaga pozwala wielu modułom Node.js (w tym tym używanym przez `nuxt-i18n-micro`) działać płynnie.

## 🔍 SEO i `@nuxtjs/seo`

### ❓ Błąd: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Dzieje się to, gdy **`@nuxtjs/seo`** wciąga starą **`nuxt-site-config` 3.x**, która rejestruje swój plugin i18n tylko dla `@nuxtjs/i18n`, a nie dla **nuxt-i18n-micro**.

**Naprawa:**

1. Zaktualizuj do **`@nuxtjs/seo` 3+** (zawiera `nuxt-site-config` 4+ ze wsparciem micro).
2. Umieść **`nuxt-i18n-micro` przed `@nuxtjs/seo`** w `modules`.
3. Zachowaj **`i18n.meta: true`** dla tagów head świadomych lokalizacji.

Zobacz [przewodnik SEO — sekcja Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo), aby zobaczyć pełny przykład.

## 🔧 Konfiguracja i kompatybilność

### ❓ Czy `Nuxt I18n Micro` jest inspirowany przez `vue-i18n`? A modifikatory?

Podczas gdy `Nuxt I18n Micro` służy jako wydajnościowa alternatywa dla `nuxt-i18n`, jest zbudowany niezależnie od `vue-i18n`. Chociaż niektóre nazwy metod i parametry mogą być podobne, ich podstawowa funkcjonalność znacznie się różni.

**Modyfikatory**: opiekun początkowo rozważał modyfikatory, ale doszedł do wniosku, że komponenty takie jak `<i18n-t>` i `<i18n-link>` skutecznie zaspokajają te potrzeby.

Na przykład:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

To podejście jest elastyczne, więc wydawanie modyfikatorów jest obecnie niepotrzebne. Modyfikatory mogą jednak zostać dodane w przyszłych wydaniach, jeśli będzie taki popyt.
