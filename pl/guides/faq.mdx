# ❓ FAQ: częste problemy i rozwiązania

Znajdź odpowiedzi na często zadawane pytania i rozwiązania częstych problemów związanych z Nuxt I18n Micro.

## 🚀 Problemy na start

### ❓ Co, jeśli trasa się nie ładuje?

Podczas używania `Nuxt I18n Micro` niektóre trasy mogą nie ładować się zgodnie z oczekiwaniami, zwłaszcza gdy router nie przypisuje automatycznie nazwy trasie w podfolderach.

**Rozwiązanie:**
Aby temu zaradzić, ręcznie zdefiniuj nazwę trasy dla strony, dodając do odpowiedniego pliku Vue:

```javascript
definePageMeta({ name: 'pageName' })
```

Zapewni to, że trasa jest poprawnie zarejestrowana, umożliwiając płynną nawigację w aplikacji.

### ❓ Dlaczego `$t` lub inne kompozycje i18n nie działają w pluginach Nuxt?

Kompozycje Nuxt I18n (`$t`, `$getLocale`, `$localePath` itd.) mogą nie działać zgodnie z oczekiwaniami we wtyczkach Nuxt lub funkcjach narzędziowych, co skutkuje błędami runtime.

**Przyczyna i rozwiązanie:**
Kompozycje Nuxt wymagają konkretnych kontekstów (np. hooków Nuxt lub funkcji setup Vue), aby uzyskać dostęp do instancji Nuxt. Jeśli są używane poza tymi kontekstami (np. w funkcjach narzędziowych lub pluginach), w konsoli może pojawić się następujący błąd:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Rozwiązanie 1: Użyj `runWithContext`**
Aby wywołać kompozycje i18n po operacji asynchronicznej, użyj [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext), aby zachować niezbędny kontekst.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Rozwiązanie 2: Najpierw pobierz wartość**
Alternatywnie najpierw pobierz wartość tłumaczenia, a następnie przekaż ją do funkcji narzędziowej.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Rozwiązanie 3: Przekazuj klucze tłumaczeń w serwisach**
W serwisach lub funkcjach narzędziowych przekazuj klucze tłumaczeń zamiast używać `$t` bezpośrednio. Następnie pobierz tłumaczenie w komponencie.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Przełączanie locale

### ❓ Przełączyć locale bez zmiany URL-a?

Tak — ale zależy to od Twojej [strategii routingu](/guides/routing-strategies).

**Strategia `no_prefix`** — locale nie jest częścią URL-a. Użyj `$switchLocale()`, aby zmienić locale i przeładować tłumaczenia, pozostając na tej samej ścieżce:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Lub zaktualizuj tylko preferencję za pomocą `useI18nLocale().setLocale('de')`. Dla pełnego przeładowania tłumaczeń po stronie klienta preferuj `$switchLocale()`.

**Strategie z prefiksem** (`prefix`, `prefix_except_default` …) — locale i URL są powiązane. `$switchLocale()` zawsze nawiguje do zlokalizowanej trasy. Nie ma opcji `redirect: false`.

Jeśli potrzebujesz tylko docelowego URL-a (np. do linku w przełączniku języków), użyj `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Zobacz [Route & Locale Switching](/api/methods#-route-locale-switching), aby zapoznać się ze wszystkimi metodami przełączania.

### ❓ Strona przewija się na górę (lub skacze) po zmianie locale?

To oczekiwane — to **zachowanie scrolla Vue Router / Nuxt**, nie coś specyficznego dla nuxt-i18n-micro.

Ze strategiami z prefiksem (`prefix`, `prefix_except_default` …) `$switchLocale()` wykonuje normalną nawigację klienta (`/en/page` → `/de/page`). Domyślny [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) Nuxta przewija na górę przy zmianach tras (poza wstecz/naprzód przeglądarki przez `savedPosition`).

nuxt-i18n-micro nie dodaje ukrytej obsługi scrolla — użyj małego komponentu-wrappera w swojej aplikacji.

**Wrapper `SwitchLocalePreserve`**

Skopiuj [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) do swojego projektu (`components/SwitchLocalePreserve.vue`). Działające demo: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

Na stronie ustaw `scrollToTop: false` i owiń swoje UI przełącznika. Oznacz klikalne elementy `data-locale` — wrapper przechwytuje kliknięcia, wywołuje `$switchLocale` i przywraca scroll (również gdy długość tłumaczenia zmienia layout):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Komponent:

1. **Przy kliknięciu** — odczytuje `data-locale` z klikniętego elementu wewnątrz slota (przyciski, linki lub dowolny niestandardowy markup).
2. **Przed** `$switchLocale` — zapisuje `scrollY` oraz pozycję klikniętego elementu (utrzymuje go pod kursorem).
3. **Podczas** nawigacji — jednorazowo łata `router.options.scrollBehavior` i zwraca `\{ top: scrollY \}` zamiast przewijać na górę.
4. **Po** nawigacji — czeka na `page:finish`, potem ponownie stosuje scroll, podczas gdy `ResizeObserver` łapie przesunięcia layoutu wynikające z różnych długości tłumaczeń.

`scrollToTop: false` jest wymagany na stronach, na których używasz tego wrappera. Dokumentacja: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Nie wywołuj `$switchLocale` bezpośrednio na owinięstych kontrolkach — wrapper obsługuje przełączanie. Dla `<NuxtLink :to="$switchLocalePath('fr')">` poza wrapperem zachowanie scrolla podąża za normalnym routingiem Nuxt, chyba że dodasz własny `app/router.options.ts`.

## 🌐 Problemy z tłumaczeniami

### ❓ Dlaczego tłumaczenia zawodzą podczas przejść między stronami, zwłaszcza z `defineAsyncComponent`?

Podczas używania `nuxt-i18n-micro` z przejściami między stronami tłumaczenia mogą chwilowo przestać działać podczas przejścia. Ten problem wynika z tego, że trasa zmienia się przed zakończeniem przejścia, powodując, że tłumaczenia nowej strony ładują się, podczas gdy stara strona jest jeszcze widoczna.

**Główna przyczyna:**

- Przejścia między stronami powodują zmiany tras przed pełnym załadowaniem tłumaczeń
- `defineAsyncComponent` i `useAsyncData` mogą opóźnić ładowanie tłumaczeń
- Klucze tłumaczeń mogą pojawiać się jako surowe ścieżki podczas ładowania

**Rozwiązanie 1: kumulatywny merge (wbudowane, bez konfiguracji)**

W v3 moduł automatycznie używa strategii kumulatywnego mergowania. Podczas nawigacji w obrębie tego samego locale nowe tłumaczenia stron są scalane z aktywnym słownikiem zamiast go zastępować. Oznacza to, że tłumaczenia z poprzedniej strony pozostają dostępne podczas animacji przejścia. Po zakończeniu przejścia (hook `page:transition:finish`) stare klucze są automatycznie usuwane.

Nie jest wymagana konfiguracja — działa od razu.

**Rozwiązanie 2: jawny kontekst trasy**

Jeśli wolisz ręczną kontrolę, jawnie przekazuj bieżącą trasę do `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Rozwiązanie 3: stany ładowania**

Zaimplementuj stany ładowania, aby elegancko obsłużyć ładowanie tłumaczeń:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Dlaczego klucze tłumaczeń nie rozstrzygają się podczas SSR na Vercelu?

**Ograniczenia `$fetch` w SSR**
Na platformach serverless takich jak Vercel `$fetch` może pobierać tylko pliki statyczne z CDN, a nie z wewnętrznego serwera Nitro. Oznacza to, że statyczne pliki tłumaczeń mogą nie być bezpośrednio dostępne, chyba że ustawiony jest właściwy bazowy URL.

**Naprawa przez ustawienie `apiBaseClientHost` i `apiBaseServerHost`**
Jeśli tłumaczenia są hostowane zewnętrznie na CDN lub innej domenie, użyj `apiBaseClientHost` dla żądań po stronie klienta i `apiBaseServerHost` dla żądań po stronie serwera. `apiBaseUrl` powinno zawierać tylko prefiks ścieżki (np. `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Lub przez zmienne środowiskowe:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Tłumaczenia zostaną pobrane z `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` zarówno na kliencie, jak i na serwerze.

## 🔗 Routing i problemy nawigacji

### ❓ Czy mogę używać `NuxtLink` lub `<i18n-link>` bezpośrednio w ciągach tłumaczeń?

Tak, `Nuxt I18n Micro` pozwala na użycie `NuxtLink` lub `<i18n-link>` w tłumaczeniach za pomocą komponentu `<i18n-t>`, co jest szczególnie pomocne przy obsłudze wymagań gramatyki i języków RTL bez dzielenia ciągów tłumaczeń.

**Przykład:**

Plik tłumaczenia:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Szablon Vue:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Umożliwia to dynamiczne linki w tłumaczeniach, zachowując właściwą strukturę lokalizacji.

## 🏗️ Problemy z buildem i wdrożeniem

### ❓ Dlaczego payloady tłumaczeń trafiają pod `public/_locales/` (lub do bundla serwera na Edge)?

SSR i klient potrzebują tych samych payloadów `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. Sposób ich pakowania zależy od celu Nitro:

**Wyjaśnienie:**

- **Node (domyślnie):** moduł **nie** osadza tłumaczeń jako `serverAssets` Nitro / `raw:` Rollupa (co wysadzało RAM buildu przy dużych katalogach). Zamiast tego kopiuje drzewo premerged do `public/<apiBaseUrl>/` (domyślnie `_locales`), a SSR czyta te pliki przez `readFile`. Klient `$fetch`uje te same URL-e — albo jako pliki statyczne, albo przez handler Nitro.
- **Edge** (`nitro.node === false`): brak trwałego FS w public dla SSR, więc payloady są osadzone przez `serverAssets` Nitro (`assets:i18n`). Preferuj `translationPayloads.mode: 'source'`, aby osadzenie pozostało zwarte. Ustaw `publicAssets: true` tylko, jeśli potrzebujesz też kopii CDN/statycznej.
- **`prerenderRoutes`:** opcjonalne. W trybie premerged `publicAssets` już zapisuje `\{page\}/\{locale\}/data.json`, więc prerenderowanie tych tras zwykle jest nadmiarowe.

### ❓ Dlaczego otrzymuję błąd buildu odnoszący się do `@unhead/vue` lub niezdefiniowanego obiektu, szczególnie na Cloudflare Pages?

**Przyczyna:**
Niektóre projekty doświadczają konfliktów buildu lub brakujących zależności przy używaniu `nuxt-i18n-micro`. W szczególności:

- Wdrożenia na **Cloudflare Pages** lub **Cloudflare Workers** mogą wymagać dodatkowych flag kompatybilności.
- Kroki prerenderowania mogą zawieść, jeśli zależności takie jak `@unhead/vue` nie są poprawnie zainstalowane.
- Niektóre moduły (np. **nuxthub**, **nitro-cloudflare-dev**) mogą wprowadzać konflikty, chyba że są skonfigurowane z odpowiednimi flagami lub zależnościami.

**Możliwe rozwiązania:**

**Rozwiązanie 1: Zainstaluj `@unhead/vue` ręcznie**
Jeśli błąd buildu narzeka na brak `@unhead/vue`, zainstaluj go bezpośrednio w zależnościach projektu:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Zapewni to jego dostępność podczas fazy prerenderu Nitro.

**Rozwiązanie 2: Dodaj flagi kompatybilności Cloudflare**
Podczas używania Cloudflare Pages lub Cloudflare Workers kompatybilność Node.js jest często domyślnie wyłączona. Włącz ją w `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Ta flaga pozwala wielu modułom Node.js (w tym używanym przez `nuxt-i18n-micro`) działać płynnie.

## 🔍 SEO i `@nuxtjs/seo`

### ❓ Błąd: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Dzieje się to, gdy **`@nuxtjs/seo`** ciągnie stary **`nuxt-site-config` 3.x**, który rejestruje swoją wtyczkę i18n tylko dla `@nuxtjs/i18n`, nie dla **nuxt-i18n-micro**.

**Naprawa:**

1. Zaktualizuj do **`@nuxtjs/seo` 3+** (zawiera `nuxt-site-config` 4+ z obsługą micro).
2. Umieść **`nuxt-i18n-micro` przed `@nuxtjs/seo`** w `modules`.
3. Zachowaj **`i18n.meta: true`** dla świadomych locale tagów head.

Zobacz [przewodnik SEO — sekcja Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo), aby zapoznać się z pełnym przykładem.

## 🔧 Konfiguracja i kompatybilność

### ❓ Czy `Nuxt I18n Micro` jest inspirowany `vue-i18n`? Co z modyfikatorami?

Choć `Nuxt I18n Micro` służy jako wydajnościowa alternatywa dla `nuxt-i18n`, jest zbudowany niezależnie od `vue-i18n`. Choć niektóre nazwy metod i parametry mogą być podobne, leżąca u podstaw funkcjonalność znacząco się różni.

**Modyfikatory**: Opiekun początkowo rozważał modyfikatory, ale doszedł do wniosku, że komponenty takie jak `<i18n-t>` i `<i18n-link>` skutecznie odpowiadają na te potrzeby.

Na przykład:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

To podejście jest elastyczne, więc wydanie modyfikatorów jest obecnie niepotrzebne. Jednak modyfikatory mogą zostać dodane w przyszłych wydaniach, jeśli będzie na nie zapotrzebowanie.
