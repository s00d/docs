# ❓ FAQ: よくある問題と解決策

Nuxt I18n Micro に関するよくある質問への回答と、一般的な問題への解決策をまとめています。

## 🚀 導入時の問題

### ❓ ルートが読み込まれない場合は？

`Nuxt I18n Micro` を使う際、特にサブフォルダ内のルートにルーターが自動で名前を割り当てない場合、一部のルートが期待通り読み込まれないことがあります。

**解決策:**
これを解消するには、対応する Vue ファイルに以下を追加してページのルート名を明示的に定義します:

```javascript
definePageMeta({ name: 'pageName' })
```

これにより、ルートが正しく登録され、アプリケーション内でのシームレスなナビゲーションが可能になります。

### ❓ `$t` などの i18n コンポーザブルが Nuxt プラグイン内で動作しないのはなぜ？

Nuxt I18n のコンポーザブル（`$t`、`$getLocale`、`$localePath` など）は、Nuxt プラグインやユーティリティ関数内で期待通り動作せず、ランタイムエラーになることがあります。

**原因と解決策:**
Nuxt のコンポーザブルは Nuxt インスタンスにアクセスするために特定のコンテキスト（Nuxt フック、Vue の setup 関数など）を必要とします。それ以外のコンテキスト（ユーティリティ関数やプラグインなど）で利用すると、コンソールに次のようなエラーが表示されることがあります:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**解決策 1: `runWithContext` を使う**
非同期処理後に i18n コンポーザブルを呼び出したい場合は、必要なコンテキストを保持するために [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) を使用します。

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**解決策 2: 先に値を取り出す**
あるいは、翻訳値を先に取り出してからユーティリティ関数に渡します。

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**解決策 3: サービスでは翻訳キーを渡す**
サービスやユーティリティ関数内では `$t` を直接使わず、翻訳キーを渡し、コンポーネント側で翻訳を取得します。

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 ロケール切り替え

### ❓ URL を変えずにロケールを切り替えられますか？

はい — ただし [ルーティング戦略](/guides/routing-strategies) によります。

**`no_prefix` 戦略** — ロケールは URL の一部ではありません。同じパスに留まったままロケールを変更し翻訳を再読み込みするには、`$switchLocale()` を使用します:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

あるいは `useI18nLocale().setLocale('de')` で設定のみを更新することもできます。クライアント側で翻訳を完全にリロードしたい場合は `$switchLocale()` を推奨します。

**プレフィックス戦略**（`prefix`、`prefix_except_default` など） — ロケールと URL は連動します。`$switchLocale()` は常にローカライズされたルートに遷移します。`redirect: false` オプションは存在しません。

移動先の URL だけが必要な場合（例: 言語スイッチャーのリンク）は、代わりに `$switchLocalePath()` を使用してください:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

すべての切り替えメソッドについては [ルートとロケールの切り替え](/api/methods#-route-locale-switching) を参照してください。

### ❓ ロケール切り替え時にページがトップにスクロールする（またはジャンプする）

これは想定内の挙動で — nuxt-i18n-micro 固有ではなく、**Vue Router / Nuxt のスクロール挙動** です。

プレフィックス戦略（`prefix`、`prefix_except_default` など）では、`$switchLocale()` は通常のクライアントナビゲーション（`/en/page` → `/de/page`）を行います。Nuxt のデフォルト [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) は、ルート変更時にトップへスクロールします（ブラウザの戻る / 進むによる `savedPosition` を除く）。

nuxt-i18n-micro は隠れたスクロール処理を追加しません — アプリ側で小さなラッパーコンポーネントを使ってください。

**`SwitchLocalePreserve` ラッパー**

[`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) をプロジェクト（`components/SwitchLocalePreserve.vue`）にコピーしてください。動作サンプル: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue)。

ページ側では `scrollToTop: false` を設定してスイッチャー UI をラップします。クリック可能な対象要素には `data-locale` を付与します — ラッパーはクリックを横取りし、`$switchLocale` を呼び出し、スクロール位置を復元します（翻訳の文字量でレイアウトが変わる場合を含む）:

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

このコンポーネントは以下の動作を行います:

1. **クリック時** — スロット内のクリックされた要素（ボタン、リンク、任意のカスタムマークアップ）の `data-locale` を読み取ります。
2. `$switchLocale` の **前** — `scrollY` とクリックされた要素の位置を保存します（要素がカーソル下に留まるようにします）。
3. **ナビゲーション中** — `router.options.scrollBehavior` を一度パッチして、トップへのスクロールの代わりに `\{ top: scrollY \}` を返します。
4. **ナビゲーション後** — `page:finish` を待ってスクロールを再適用し、`ResizeObserver` が翻訳長の違いによるレイアウトシフトを検知します。

このラッパーを使うページでは `scrollToTop: false` が必須です。ドキュメント: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta)。

ラップされたコントロール上で直接 `$switchLocale` を呼び出さないでください — 切り替えはラッパーが担当します。ラッパー外の `<NuxtLink :to="$switchLocalePath('fr')">` のスクロール挙動は、独自の `app/router.options.ts` を追加しない限り、通常の Nuxt ルーティングに従います。

## 🌐 翻訳に関する問題

### ❓ ページ遷移中、特に `defineAsyncComponent` 使用時に翻訳が崩れるのはなぜ？

`nuxt-i18n-micro` をページ遷移とともに使うと、遷移中に翻訳が一時的に機能しなくなることがあります。これは、遷移完了前にルートが変わり、古いページがまだ表示された状態で新しいページの翻訳が読み込まれるために発生します。

**根本原因:**

- ページ遷移によって、翻訳の読み込みが完了する前にルートが変わる
- `defineAsyncComponent` や `useAsyncData` が翻訳読み込みを遅らせることがある
- 読み込み中は翻訳キーが生のパスのまま表示されることがある

**解決策 1: 累積マージ（組み込み、設定不要）**

v3 では、モジュールは自動的に累積マージ戦略を使用します。同じロケール内でナビゲーションする際、新しいページの翻訳はアクティブな辞書を置き換えるのではなくマージされます。これにより、遷移アニメーション中も前のページの翻訳が利用可能なままとなります。遷移完了後（`page:transition:finish` フック）、古いキーは自動的にクリーンアップされます。

設定は不要で — 標準で動作します。

**解決策 2: 明示的なルートコンテキスト**

手動制御したい場合は、現在のルートを明示的に `$_t` に渡します:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**解決策 3: ローディング状態**

翻訳の読み込みを穏やかに扱うローディング状態を実装します:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Vercel での SSR 中に翻訳キーが解決されないのはなぜ？

**SSR における `$fetch` の制限**
Vercel のようなサーバーレスプラットフォームでは、`$fetch` は内部の Nitro サーバーからではなく CDN 上の静的ファイルからのみ取得できます。そのため、正しいベース URL が設定されていないと、静的な翻訳ファイルに直接アクセスできない場合があります。

**`apiBaseClientHost` と `apiBaseServerHost` の設定で修正**
翻訳が CDN や別ドメイン上に外部ホストされている場合、クライアントリクエスト用に `apiBaseClientHost` を、サーバーリクエスト用に `apiBaseServerHost` を使用します。`apiBaseUrl` はパスプレフィックス（例: `_locales`）のみを含めるべきです。

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

あるいは環境変数経由で:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

翻訳は、クライアントとサーバーの両方で `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` から取得されます。

## 🔗 ルーティング / ナビゲーションの問題

### ❓ 翻訳文字列内に `NuxtLink` や `<i18n-link>` を直接使えますか？

はい。`Nuxt I18n Micro` は `<i18n-t>` コンポーネントを通じて、翻訳内での `NuxtLink` や `<i18n-link>` の利用を許可します。これは、翻訳文字列を分割せずに文法や RTL 言語の要件を扱う際に特に有用です。

**例:**

翻訳ファイル:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue テンプレート:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

これにより、翻訳内で動的なリンクを利用しつつ、適切なローカライズ構造を保てます。

## 🏗️ ビルド / デプロイの問題

### ❓ 翻訳ペイロードが `public/_locales/` 配下（あるいは Edge ではサーバーバンドル内）に配置されるのはなぜ？

SSR とクライアントは同じ `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json` ペイロードを必要とします。パッケージングの方法は Nitro のターゲットに依存します:

**解説:**

- **Node（デフォルト）:** モジュールは Nitro の `serverAssets` / Rollup の `raw:` として翻訳を埋め込み **ません**（大規模カタログでビルド RAM が破裂するため）。代わりに premerge されたツリーを `public/<apiBaseUrl>/`（デフォルトは `_locales`）にコピーし、SSR は `readFile` でそれらを読みます。クライアントは同じ URL を `$fetch` で取得します — 静的ファイルとして、あるいは Nitro ハンドラー経由で。
- **Edge**（`nitro.node === false`）: SSR 用の永続的な public FS がないため、ペイロードは Nitro の `serverAssets`（`assets:i18n`）経由で埋め込まれます。埋め込みを小さく保つため `translationPayloads.mode: 'source'` が推奨されます。CDN / 静的コピーが必要な場合のみ `publicAssets: true` を設定してください。
- **`prerenderRoutes`:** 任意。premerged モードでは `publicAssets` が既に `\{page\}/\{locale\}/data.json` を書き出しているため、これらのルートのプリレンダリングは通常冗長です。

### ❓ 特に Cloudflare Pages で `@unhead/vue` や未定義オブジェクトに関するビルドエラーが出るのはなぜ？

**原因:**
`nuxt-i18n-micro` を使う一部のプロジェクトでは、ビルド競合や依存関係欠落が発生することがあります。特に:

- **Cloudflare Pages** や **Cloudflare Workers** へのデプロイでは、追加の互換性フラグが必要な場合があります。
- `@unhead/vue` などの依存が適切にインストールされていないと、プリレンダリングステップが失敗することがあります。
- 特定のモジュール（例: **nuxthub**、**nitro-cloudflare-dev**）は、適切なフラグや依存関係で設定されていないと競合を引き起こすことがあります。

**考えられる解決策:**

**解決策 1: `@unhead/vue` を手動インストール**
ビルドエラーが `@unhead/vue` が見つからないと告げる場合、プロジェクトの依存に直接インストールしてください:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

これにより、Nitro のプリレンダリングフェーズで利用可能になります。

**解決策 2: Cloudflare 互換性フラグを追加**
Cloudflare Pages や Cloudflare Workers を利用する場合、Node.js の互換性がデフォルトで無効化されていることが多いです。`wrangler.toml` で有効化してください:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

このフラグにより、多くの Node.js モジュール（`nuxt-i18n-micro` が利用しているものを含む）が問題なく動作するようになります。

## 🔍 SEO と `@nuxtjs/seo`

### ❓ エラー: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

これは、**`@nuxtjs/seo`** が古い **`nuxt-site-config` 3.x** を引き込む場合に発生します。そのバージョンは `@nuxtjs/i18n` 向けにしか i18n プラグインを登録せず、**nuxt-i18n-micro** 向けに登録しません。

**修正方法:**

1. **`@nuxtjs/seo` 3 以上** にアップグレードします（micro をサポートする `nuxt-site-config` 4 以上を含みます）。
2. `modules` 内で **`nuxt-i18n-micro` を `@nuxtjs/seo` より前** に配置します。
3. ロケール対応の head タグのため、**`i18n.meta: true`** を維持します。

完全な例は [SEO ガイド — Nuxt SEO セクション](/guides/seo#nuxt-seo-nuxtjs-seo) を参照してください。

## 🔧 設定と互換性

### ❓ `Nuxt I18n Micro` は `vue-i18n` に着想を得たものですか？モディファイアはありますか？

`Nuxt I18n Micro` は `nuxt-i18n` のパフォーマンス代替として機能しますが、`vue-i18n` とは独立に構築されています。一部のメソッド名やパラメータが似ていることはあっても、基盤となる機能は大きく異なります。

**モディファイア**: メンテナーは当初モディファイアを検討しましたが、`<i18n-t>` や `<i18n-link>` のようなコンポーネントで同じニーズを効果的に満たせると結論づけました。

例:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

このアプローチは柔軟であるため、現時点でモディファイアをリリースする必要はないと判断しています。ただし、要望があれば将来のリリースでモディファイアが追加される可能性はあります。
