# ❓ BUJ: biežas problēmas un risinājumi

Atradiet atbildes uz biežāk uzdotajiem jautājumiem un risinājumus biežām Nuxt I18n Micro problēmām.

## 🚀 Sākuma problēmas

### ❓ Kā rīkoties, ja maršruts netiek ielādēts?

Izmantojot `Nuxt I18n Micro`, atsevišķi maršruti var neielādēties, kā paredzēts, īpaši, ja maršrutētājs automātiski nepiešķir nosaukumu apakšmapē esošam maršrutam.

**Risinājums:**
Lai to atrisinātu, manuāli definējiet lapas maršruta nosaukumu, atbilstošajā Vue failā pievienojot šo:

```javascript
definePageMeta({ name: 'pageName' })
```

Tas nodrošina, ka maršruts ir pareizi reģistrēts, ļaujot nemanāmi pārvietoties pa lietotni.

### ❓ Kāpēc `$t` vai citas i18n komponējamās funkcijas nedarbojas Nuxt spraudņos?

Nuxt I18n komponējamās funkcijas (`$t`, `$getLocale`, `$localePath` u.c.) Nuxt spraudņos vai utilītfunkcijās var nedarboties, kā paredzēts, izraisot izpildlaika kļūdas.

**Cēlonis un risinājums:**
Nuxt komponējamām funkcijām nepieciešams konkrēts konteksts (piemēram, Nuxt hooks vai Vue setup funkcijas), lai piekļūtu Nuxt instancei. Ja tās tiek izmantotas ārpus šiem kontekstiem (piemēram, utilītfunkcijās vai spraudņos), konsolē var parādīties šī kļūda:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**1. risinājums: izmantojiet `runWithContext`**
Lai i18n komponējamās funkcijas izsauktu pēc asinhronas operācijas, izmantojiet [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext), lai saglabātu nepieciešamo kontekstu.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**2. risinājums: vispirms iegūstiet vērtību**
Alternatīvi, vispirms iegūstiet tulkojuma vērtību, tad nododiet to utilītfunkcijai.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**3. risinājums: nododiet tulkojumu atslēgas pakalpojumos**
Pakalpojumos vai utilītfunkcijās nododiet tulkojumu atslēgas, nevis izmantojiet `$t` tieši. Pēc tam iegūstiet tulkojumu komponentā.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Lokāles pārslēgšana

### ❓ Pārslēgt lokāli, nemainot URL?

Jā — bet tas ir atkarīgs no jūsu [maršrutēšanas stratēģijas](/guides/routing-strategies).

**`no_prefix` stratēģija** — lokāle nav daļa no URL. Izmantojiet `$switchLocale()`, lai mainītu lokāli un pārlādētu tulkojumus, paliekot uz tā paša ceļa:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Vai atjaunināt tikai preferenci ar `useI18nLocale().setLocale('de')`. Pilnīgai klienta puses tulkojumu pārlādei labāk izmantojiet `$switchLocale()`.

**Priedēkļa stratēģijas** (`prefix`, `prefix_except_default`, …) — lokāle un URL ir saistīti. `$switchLocale()` vienmēr pārvietojas uz lokalizēto maršrutu. Nav opcijas `redirect: false`.

Ja jums nepieciešams tikai mērķa URL (piemēram, valodas pārslēdzēja saitei), tā vietā izmantojiet `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Visas pārslēgšanas metodes skatiet [Maršruts un lokāles pārslēgšana](/api/methods#-route-locale-switching).

### ❓ Lapa ritinās uz augšu (vai pārlec), pārslēdzot lokāli?

Tas ir paredzēts — tā ir **Vue Router / Nuxt ritināšanas uzvedība**, nevis kaut kas specifisks nuxt-i18n-micro.

Ar priedēkļa stratēģijām (`prefix`, `prefix_except_default`, …) `$switchLocale()` veic normālu klienta navigāciju (`/en/page` → `/de/page`). Nuxt noklusējuma [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) maršrutu izmaiņu laikā ritina uz augšu (izņemot pārlūka atpakaļ/uz priekšu ar `savedPosition`).

nuxt-i18n-micro nepievieno slēptu ritināšanas apstrādi — savā lietotnē izmantojiet mazu ietinošo komponentu.

**`SwitchLocalePreserve` ietinošais komponents**

Nokopējiet [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) savā projektā (`components/SwitchLocalePreserve.vue`). Strādājoša demonstrācija: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

Lapā iestatiet `scrollToTop: false` un ietiniet savu pārslēdzēja UI. Atzīmējiet klikšķināmos mērķus ar `data-locale` — ietinošais komponents pārtver klikšķus, izsauc `$switchLocale` un atjauno ritināšanu (arī tad, ja tulkojumu garums maina izkārtojumu):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Komponents:

1. **Klikšķa brīdī** — nolasa `data-locale` uz klikšķinātā elementa slotā (pogas, saites vai jebkurš pielāgots marķējums).
2. **Pirms** `$switchLocale` — saglabā `scrollY` un klikšķinātā elementa pozīciju (patur to zem kursora).
3. **Navigācijas laikā** — vienreiz izlabo `router.options.scrollBehavior` un atgriež `\{ top: scrollY \}`, nevis ritinot uz augšu.
4. **Pēc** navigācijas — gaida `page:finish`, tad atkārtoti piemēro ritināšanu, kamēr `ResizeObserver` uztver izkārtojuma nobīdes no atšķirīgiem tulkojumu garumiem.

`scrollToTop: false` ir nepieciešams lapās, kur izmantojat šo ietinošo komponentu. Dokumentācija: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Neizsauciet `$switchLocale` tieši uz ietinošajām vadīklām — pārslēgšanu pārvalda ietinošais komponents. `<NuxtLink :to="$switchLocalePath('fr')">` ārpus ietinošā komponenta ritināšanas uzvedība seko normālai Nuxt maršrutēšanai, ja vien nepievienojat savu `app/router.options.ts`.

## 🌐 Tulkojumu problēmas

### ❓ Kāpēc tulkojumi lapu pāreju laikā pārtrūkst, īpaši ar `defineAsyncComponent`?

Izmantojot `nuxt-i18n-micro` ar lapu pārejām, tulkojumi pārejas laikā var uz brīdi pārstāt darboties. Šī problēma rodas tāpēc, ka maršruts mainās pirms pārejas pabeigšanas, izraisot jaunās lapas tulkojumu ielādi, kamēr vecā lapa vēl ir redzama.

**Galvenais cēlonis:**

- Lapu pārejas izraisa maršrutu izmaiņas, pirms tulkojumi ir pilnībā ielādēti
- `defineAsyncComponent` un `useAsyncData` var aizkavēt tulkojumu ielādi
- Tulkojumu atslēgas ielādes laikā var parādīties kā neapstrādāti ceļi

**1. risinājums: kumulatīvā sapludināšana (iebūvēta, konfigurācija nav nepieciešama)**

Versijā v3 modulis automātiski izmanto kumulatīvās sapludināšanas stratēģiju. Pārvietojoties tās pašas lokāles ietvaros, jaunas lapas tulkojumi tiek sapludināti aktīvajā vārdnīcā, nevis to aizvieto. Tas nozīmē, ka iepriekšējās lapas tulkojumi paliek pieejami pārejas animācijas laikā. Pēc pārejas pabeigšanas (`page:transition:finish` hook) vecās atslēgas tiek automātiski notīrītas.

Nekāda konfigurācija nav nepieciešama — tas darbojas no pirmās minūtes.

**2. risinājums: skaidrs maršruta konteksts**

Ja dodat priekšroku manuālai kontrolei, skaidri nododiet pašreizējo maršrutu `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**3. risinājums: ielādes stāvokļi**

Ieviesiet ielādes stāvokļus, lai eleganti apstrādātu tulkojumu ielādi:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Kāpēc SSR laikā uz Vercel tulkojumu atslēgas netiek atrisinātas?

**`$fetch` ierobežojumi SSR**
Uz bezservera platformām, piemēram, Vercel, `$fetch` var iegūt tikai statiskos failus no CDN, nevis no iekšējā Nitro servera. Tas nozīmē, ka statiskie tulkojumu faili var nebūt tieši pieejami, ja vien nav iestatīts pareizais bāzes URL.

**Labojums, iestatot `apiBaseClientHost` un `apiBaseServerHost`**
Ja tulkojumi tiek mitināti ārēji CDN vai atšķirīgā domēnā, izmantojiet `apiBaseClientHost` klienta puses pieprasījumiem un `apiBaseServerHost` servera puses pieprasījumiem. `apiBaseUrl` jāsatur tikai ceļa priedēklis (piemēram, `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Vai ar vides mainīgajiem:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Tulkojumi tiks iegūti no `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` gan klientā, gan serverī.

## 🔗 Maršrutēšanas un navigācijas problēmas

### ❓ Vai `NuxtLink` vai `<i18n-link>` var izmantot tieši tulkojumu virknēs?

Jā, `Nuxt I18n Micro` ļauj tulkojumos izmantot `NuxtLink` vai `<i18n-link>`, izmantojot komponentu `<i18n-t>`, kas ir īpaši noderīgi gramatikas un RTL valodu prasību apstrādei, nesadalot tulkojumu virknes.

**Piemērs:**

Tulkošanas fails:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue veidne:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Tas ļauj tulkojumos izmantot dinamiskas saites, saglabājot pareizu lokalizācijas struktūru.

## 🏗️ Būvēšanas un izvietošanas problēmas

### ❓ Kāpēc tulkojumu payload nonāk mapē `public/_locales/` (vai servera pakotnē Edge)?

Gan SSR, gan klientam nepieciešami vieni un tie paši `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json` payload. Tas, kā tie tiek iepakoti, ir atkarīgs no Nitro mērķa:

**Skaidrojums:**

- **Node (noklusējums):** modulis **neiestrādā** tulkojumus kā Nitro `serverAssets` / Rollup `raw:` (tas uzspridzināja būvēšanas RAM lieliem katalogiem). Tā vietā tas kopē premerged koku uz `public/<apiBaseUrl>/` (pēc noklusējuma `_locales`), un SSR nolasa šos failus ar `readFile`. Klients `$fetch`o tos pašus URL — vai nu kā statiskus failus, vai caur Nitro apstrādātāju.
- **Edge** (`nitro.node === false`): SSR nav noturīgas publiskās FS, tāpēc payload tiek iestrādāti caur Nitro `serverAssets` (`assets:i18n`). Priekšroku dodiet `translationPayloads.mode: 'source'`, lai iestrādājums paliktu kompakts. Iestatiet `publicAssets: true` tikai tad, ja jums nepieciešama arī CDN/statiskā kopija.
- **`prerenderRoutes`:** izvēles. Premerged režīmā `publicAssets` jau raksta `\{page\}/\{locale\}/data.json`, tāpēc šo maršrutu iepriekšēja renderēšana parasti ir lieka.

### ❓ Kāpēc es saņemu būvēšanas kļūdu, kas atsaucas uz `@unhead/vue` vai nedefinētu objektu, īpaši uz Cloudflare Pages?

**Cēlonis:**
Daži projekti, izmantojot `nuxt-i18n-micro`, saskaras ar būvēšanas konfliktiem vai trūkstošām atkarībām. Jo īpaši:

- Izvietošanai uz **Cloudflare Pages** vai **Cloudflare Workers** var būt nepieciešami papildu saderības karogi.
- Iepriekšējas renderēšanas soļi var neizdoties, ja atkarības, piemēram, `@unhead/vue`, nav pareizi instalētas.
- Daži moduļi (piemēram, **nuxthub**, **nitro-cloudflare-dev**) var radīt konfliktus, ja tie nav konfigurēti ar pareiziem karogiem vai atkarībām.

**Iespējami risinājumi:**

**1. risinājums: instalējiet `@unhead/vue` manuāli**
Ja būvēšanas kļūda sūdzas, ka nevar atrast `@unhead/vue`, instalējiet to tieši sava projekta atkarībās:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Tas nodrošina, ka tas ir pieejams Nitro iepriekšējas renderēšanas fāzē.

**2. risinājums: pievienojiet Cloudflare saderības karogus**
Izmantojot Cloudflare Pages vai Cloudflare Workers, Node.js saderība bieži pēc noklusējuma ir atspējota. Iespējojiet to savā `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Šis karogs ļauj daudziem Node.js moduļiem (tostarp tiem, ko izmanto `nuxt-i18n-micro`) darboties nevainojami.

## 🔍 SEO un `@nuxtjs/seo`

### ❓ Kļūda: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Tas notiek, kad **`@nuxtjs/seo`** ievelk vecu **`nuxt-site-config` 3.x**, kas savu i18n spraudni reģistrē tikai priekš `@nuxtjs/i18n`, nevis priekš **nuxt-i18n-micro**.

**Labojums:**

1. Atjauniniet uz **`@nuxtjs/seo` 3+** (iekļauj `nuxt-site-config` 4+ ar micro atbalstu).
2. Ievietojiet **`nuxt-i18n-micro` pirms `@nuxtjs/seo`** sadaļā `modules`.
3. Saglabājiet **`i18n.meta: true`** lokāli apzinošiem head tagiem.

Pilnu piemēru skatiet [SEO ceļvedis — Nuxt SEO sadaļa](/guides/seo#nuxt-seo-nuxtjs-seo).

## 🔧 Konfigurācija un saderība

### ❓ Vai `Nuxt I18n Micro` ir iedvesmots no `vue-i18n`? Kā ar modifikatoriem?

Kaut arī `Nuxt I18n Micro` kalpo kā veiktspējas alternatīva `nuxt-i18n`, tas ir veidots neatkarīgi no `vue-i18n`. Lai gan dažu metožu nosaukumi un parametri var būt līdzīgi, pamatā esošā funkcionalitāte ievērojami atšķiras.

**Modifikatori**: uzturētājs sākotnēji apsvēra modifikatorus, bet secināja, ka komponenti, piemēram, `<i18n-t>` un `<i18n-link>`, efektīvi risina šīs vajadzības.

Piemēram:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Šī pieeja ir elastīga, tāpēc modifikatoru izlaišana pašlaik nav nepieciešama. Tomēr modifikatori var tikt pievienoti nākotnes laidienos, ja tam būs pieprasījums.
