# ❓ FAQ: bieži sastopamas problēmas un risinājumi

Atrodi atbildes uz bieži uzdotajiem jautājumiem un risinājumus izplatītām problēmām ar Nuxt I18n Micro.

## 🚀 Sākuma problēmas

### ❓ Ko darīt, ja maršruts neielādējas?

Izmantojot `Nuxt I18n Micro`, daži maršruti var neielādēties, kā gaidīts, īpaši, ja maršrutētājs automātiski nepiešķir nosaukumu maršrutam apakšmapēs.

**Risinājums:**
Lai to atrisinātu, manuāli definē maršruta nosaukumu lapai, pievienojot sekojošo attiecīgajam Vue failam:

```javascript
definePageMeta({ name: 'pageName' })
```

Tas nodrošina, ka maršruts ir pareizi reģistrēts, iespējojot vienmērīgu navigāciju lietotnē.

### ❓ Kāpēc `$t` vai citi i18n kompozīti nedarbojas Nuxt spraudņos?

Nuxt I18n kompozīti (`$t`, `$getLocale`, `$localePath` un citi) var nedarboties, kā gaidīts, Nuxt spraudņos vai utilītas funkcijās, izraisot izpildlaika kļūdas.

**Cēlonis un risinājums:**
Nuxt kompozītiem nepieciešami specifiski konteksti (piemēram, Nuxt āķi vai Vue setup funkcijas), lai piekļūtu Nuxt eksemplāram. Ja tos izmanto ārpus šiem kontekstiem (piemēram, utilītas funkcijās vai spraudņos), konsolē var parādīties šāda kļūda:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Risinājums 1: izmanto `runWithContext`**
Lai izsauktu i18n kompozītus pēc asinhronas operācijas, izmanto [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext), lai saglabātu nepieciešamo kontekstu.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Risinājums 2: vispirms iegūsti vērtību**
Kā alternatīvu vispirms iegūsti tulkojuma vērtību, tad nodod to utilītas funkcijai.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Risinājums 3: nodod tulkojuma atslēgas servisos**
Servisos vai utilītas funkcijās nodod tulkojuma atslēgas, nevis izmanto `$t` tieši. Pēc tam iegūsti tulkojumu komponentā.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Lokalizācijas maiņa

### ❓ Pārslēgt lokalizāciju, nemainot URL?

Jā — bet tas ir atkarīgs no tavas [maršrutēšanas stratēģijas](/guides/routing-strategies).

**`no_prefix` stratēģija** — lokalizācija nav URL daļa. Izmanto `$switchLocale()`, lai mainītu lokalizāciju un pārlādētu tulkojumus, paliekot uz tā paša ceļa:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Vai atjaunini tikai preferenci ar `useI18nLocale().setLocale('de')`. Pilnai klienta puses tulkojumu pārlādēšanai dod priekšroku `$switchLocale()`.

**Prefiksu stratēģijas** (`prefix`, `prefix_except_default`, …) — lokalizācija un URL ir saistīti. `$switchLocale()` vienmēr pārvieto uz lokalizēto maršrutu. Nav opcijas `redirect: false`.

Ja tev nepieciešams tikai mērķa URL (piemēram, valodas pārslēdzēja saite), izmanto `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Visas pārslēgšanas metodes skati [Maršruta un lokalizācijas maiņa](/api/methods#-route-locale-switching).

### ❓ Lapa ritinās uz augšu (vai lec), pārslēdzot lokalizāciju?

Tas ir gaidīts — tā ir **Vue Router / Nuxt ritināšanas uzvedība**, nevis kaut kas specifisks nuxt-i18n-micro.

Ar prefiksu stratēģijām (`prefix`, `prefix_except_default`, …) `$switchLocale()` veic parasto klienta navigāciju (`/en/page` → `/de/page`). Nuxt noklusējuma [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) ritinās uz augšu maršruta izmaiņām (izņemot pārlūka atpakaļ/uz priekšu caur `savedPosition`).

nuxt-i18n-micro nepievieno slēptu ritināšanas apstrādi — savā lietotnē izmanto nelielu ietinuma komponentu.

**`SwitchLocalePreserve` ietinums**

Kopē [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) savā projektā (`components/SwitchLocalePreserve.vue`). Strādājošs demo: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

Lapā iestati `scrollToTop: false` un ietin savu pārslēdzēja UI. Atzīmē klikšķināmus mērķus ar `data-locale` — ietinums pārtver klikšķus, izsauc `$switchLocale` un atjauno ritināšanu (tostarp, kad tulkojumu garums maina izkārtojumu):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Komponents:

1. **Klikšķa laikā** — nolasa `data-locale` uz noklikšķinātā elementa slotā (pogām, saitēm vai jebkurā pielāgotā marķējumā).
2. **Pirms** `$switchLocale` — saglabā `scrollY` un noklikšķinātā elementa pozīciju (paturot to zem kursora).
3. **Navigācijas laikā** — vienreiz plāksterē `router.options.scrollBehavior` un atgriež `\{ top: scrollY \}`, nevis ritina uz augšu.
4. **Pēc** navigācijas — gaida `page:finish`, tad atkārtoti pielieto ritināšanu, kamēr `ResizeObserver` uztver izkārtojuma nobīdes no dažādiem tulkojumu garumiem.

`scrollToTop: false` ir obligāts lapās, kur izmanto šo ietinumu. Dokumentācija: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Neizsauc `$switchLocale` tieši uz ietvertajām vadīklām — ietinums apstrādā pārslēgšanu. `<NuxtLink :to="$switchLocalePath('fr')">` ārpus ietinuma ritināšanas uzvedība seko normālai Nuxt maršrutēšanai, ja nepievieno savu `app/router.options.ts`.

## 🌐 Tulkojumu problēmas

### ❓ Kāpēc tulkojumi salūst lapas pāreju laikā, īpaši ar `defineAsyncComponent`?

Izmantojot `nuxt-i18n-micro` ar lapas pārejām, tulkojumi var īsi pārstāt darboties pārejas laikā. Šī problēma rodas, jo maršruts mainās pirms pārejas pabeigšanas, izraisot jaunās lapas tulkojumu ielādi, kamēr vēl ir redzama vecā lapa.

**Sakņu cēlonis:**

- Lapas pārejas izraisa maršruta izmaiņas pirms tulkojumu pilnīgas ielādes.
- `defineAsyncComponent` un `useAsyncData` var aizkavēt tulkojumu ielādi.
- Tulkojumu atslēgas ielādes laikā var parādīties kā neapstrādāti ceļi.

**Risinājums 1: kumulatīva sapludināšana (iebūvēts, konfigurācija nav nepieciešama)**

V3 modulis automātiski izmanto kumulatīvās sapludināšanas stratēģiju. Navigējot vienas lokalizācijas ietvaros, jaunās lapas tulkojumi tiek sapludināti aktīvajā vārdnīcā, nevis to aizvieto. Tas nozīmē, ka iepriekšējās lapas tulkojumi paliek pieejami pārejas animācijas laikā. Pēc pārejas pabeigšanas (`page:transition:finish` āķis) vecās atslēgas tiek automātiski iztīrītas.

Konfigurācija nav nepieciešama — tas darbojas jau no kastes.

**Risinājums 2: skaidrs maršruta konteksts**

Ja tu dod priekšroku manuālai kontrolei, skaidri nodod pašreizējo maršrutu uz `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Risinājums 3: ielādes stāvokļi**

Ievieto ielādes stāvokļus, lai eleganti apstrādātu tulkojumu ielādi:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Kāpēc tulkojumu atslēgas neatrisinās SSR laikā Vercel?

**`$fetch` ierobežojumi SSR**
Bezservera platformās, piemēram, Vercel, `$fetch` var iegūt tikai statiskus failus no CDN, nevis no iekšējā Nitro servera. Tas nozīmē, ka statiskie tulkojumu faili var nebūt tieši pieejami, ja vien nav iestatīts pareizais bāzes URL.

**Labojums, iestatot `apiBaseClientHost` un `apiBaseServerHost`**
Ja tulkojumi tiek mitināti ārēji CDN vai citā domēnā, izmanto `apiBaseClientHost` klienta puses pieprasījumiem un `apiBaseServerHost` servera puses pieprasījumiem. `apiBaseUrl` jāsatur tikai ceļa prefikss (piemēram, `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Vai caur vides mainīgajiem:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Tulkojumi tiks ielādēti no `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` gan klientā, gan serverī.

## 🔗 Maršrutēšanas un navigācijas problēmas

### ❓ Vai `NuxtLink` vai `<i18n-link>` var izmantot tieši tulkojumu virknēs?

Jā, `Nuxt I18n Micro` ļauj izmantot `NuxtLink` vai `<i18n-link>` tulkojumos caur komponentu `<i18n-t>`, kas ir īpaši noderīgi gramatikas un RTL valodu prasību apstrādei, nesadalot tulkojumu virknes.

**Piemērs:**

Tulkojumu fails:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue veidne:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Tas ļauj izmantot dinamiskas saites tulkojumos, saglabājot pareizu lokalizācijas struktūru.

## 🏗️ Būvēšanas un izvietošanas problēmas

### ❓ Kāpēc tulkojumu slodzes nonāk zem `public/_locales/` (vai servera komplektā Edge)?

SSR un klientam abiem nepieciešamas tās pašas `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json` slodzes. Tas, kā tās tiek iesaiņotas, ir atkarīgs no Nitro mērķa:

**Skaidrojums:**

- **Node (noklusējums):** modulis **neiegulda** tulkojumus kā Nitro `serverAssets` / Rollup `raw:` (tas uzspridzināja būvēšanas RAM lieliem katalogiem). Tā vietā tas kopē premerged koku uz `public/<apiBaseUrl>/` (noklusējums `_locales`), un SSR nolasa šos failus ar `readFile`. Klients `$fetch` iegūst tos pašus URL — vai nu kā statiskus failus, vai caur Nitro apstrādātāju.
- **Edge** (`nitro.node === false`): SSR nav ilgtermiņa publiskās FS, tāpēc slodzes tiek iegultas caur Nitro `serverAssets` (`assets:i18n`). Dod priekšroku `translationPayloads.mode: 'source'`, lai iegultne paliktu kompakta. Iestati `publicAssets: true` tikai tad, ja tev nepieciešama arī CDN/statiska kopija.
- **`prerenderRoutes`:** neobligāti. Premerged režīmā `publicAssets` jau ir ierakstījis `\{page\}/\{locale\}/data.json`, tāpēc šo maršrutu pirmsrenderēšana parasti ir lieka.

### ❓ Kāpēc es saņemu būvēšanas kļūdu, kas atsaucas uz `@unhead/vue` vai nedefinētu objektu, īpaši Cloudflare Pages?

**Cēlonis:**
Daži projekti piedzīvo būvēšanas konfliktus vai trūkstošas atkarības, izmantojot `nuxt-i18n-micro`. Jo īpaši:

- Izvietojumi uz **Cloudflare Pages** vai **Cloudflare Workers** var pieprasīt papildu saderības karogus.
- Pirmsrenderēšanas soļi var neizdoties, ja atkarības, piemēram, `@unhead/vue`, nav pareizi instalētas.
- Noteikti moduļi (piemēram, **nuxthub**, **nitro-cloudflare-dev**) var izraisīt konfliktus, ja tie nav konfigurēti ar pareiziem karogiem vai atkarībām.

**Iespējamie risinājumi:**

**Risinājums 1: instalē `@unhead/vue` manuāli**
Ja būvēšanas kļūda sūdzas par to, ka neatrod `@unhead/vue`, instalē to tieši sava projekta atkarībās:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Tas nodrošina, ka tas ir pieejams Nitro pirmsrenderēšanas fāzes laikā.

**Risinājums 2: pievieno Cloudflare saderības karogus**
Izmantojot Cloudflare Pages vai Cloudflare Workers, Node.js saderība bieži ir atspējota pēc noklusējuma. Iespējo to savā `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Šis karogs ļauj daudziem Node.js moduļiem (tostarp tiem, ko izmanto `nuxt-i18n-micro`) darboties vienmērīgi.

## 🔍 SEO un `@nuxtjs/seo`

### ❓ Kļūda: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Tas notiek, kad **`@nuxtjs/seo`** ievelk vecu **`nuxt-site-config` 3.x**, kas reģistrē savu i18n spraudni tikai priekš `@nuxtjs/i18n`, nevis priekš **nuxt-i18n-micro**.

**Labojums:**

1. Jaunini uz **`@nuxtjs/seo` 3+** (ietver `nuxt-site-config` 4+ ar micro atbalstu).
2. Ievieto **`nuxt-i18n-micro` pirms `@nuxtjs/seo`** iekš `modules`.
3. Paturi **`i18n.meta: true`**, lai iegūtu uz lokalizāciju vērstus galvas tagus.

Pilnu piemēru skati [SEO ceļvedis — Nuxt SEO sadaļa](/guides/seo#nuxt-seo-nuxtjs-seo).

## 🔧 Konfigurācija un saderība

### ❓ Vai `Nuxt I18n Micro` ir iedvesmots no `vue-i18n`? Ko par modifikatoriem?

Kaut arī `Nuxt I18n Micro` kalpo kā veiktspējas alternatīva `nuxt-i18n`, tas ir izveidots neatkarīgi no `vue-i18n`. Kaut arī daži metožu nosaukumi un parametri var būt līdzīgi, pamata funkcionalitāte būtiski atšķiras.

**Modifikatori**: uzturētājs sākotnēji apsvēra modifikatorus, bet secināja, ka komponenti, piemēram, `<i18n-t>` un `<i18n-link>`, efektīvi risina šīs vajadzības.

Piemēram:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Šī pieeja ir elastīga, tāpēc modifikatoru izlaišana pašlaik nav nepieciešama. Tomēr modifikatori var tikt pievienoti nākotnes laidienos, ja būs pieprasījums.
