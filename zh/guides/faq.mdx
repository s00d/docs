# ❓ FAQ：常见问题与解决方案

在此查找 Nuxt I18n Micro 常见问题的答案，以及常见问题的解决方案。

## 🚀 入门相关问题

### ❓ 如果某个路由无法加载怎么办？

在使用 `Nuxt I18n Micro` 时，某些路由可能无法按预期加载，尤其是当路由器未自动为子文件夹中的路由分配名称时。

**解决方案：**
为解决该问题，请通过在对应 Vue 文件中添加以下内容手动为页面定义路由名称：

```javascript
definePageMeta({ name: 'pageName' })
```

这样可以确保路由被正确注册，实现应用内的无缝导航。

### ❓ 为什么 `$t` 或其他 i18n 组合式函数在 Nuxt 插件中不生效？

Nuxt I18n 的组合式函数（`$t`、`$getLocale`、`$localePath` 等）在 Nuxt 插件或工具函数中可能不会按预期工作，从而导致运行时错误。

**原因与解决方案：**
Nuxt 组合式函数需要特定上下文（例如 Nuxt hooks 或 Vue setup 函数）才能访问 Nuxt 实例。在这些上下文之外使用（例如在工具函数或插件中）时，控制台可能出现以下错误：

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**方案 1：使用 `runWithContext`**
要在异步操作之后调用 i18n 组合式函数，请使用 [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) 来保留必要的上下文。

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**方案 2：先取值**
或者，先取得翻译值，再将其传给工具函数。

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**方案 3：在服务中传递翻译键**
在服务或工具函数中，传递翻译键而不是直接使用 `$t`。然后在组件中获取翻译。

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 区域切换

### ❓ 切换区域时不修改 URL？

可以 — 但这取决于你的[路由策略](/guides/routing-strategies)。

**`no_prefix` 策略** — 区域不在 URL 中。使用 `$switchLocale()` 在保持当前路径的同时切换区域并重新加载翻译：

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

或者仅通过 `useI18nLocale().setLocale('de')` 更新偏好。若需完整的客户端翻译重载，请优先使用 `$switchLocale()`。

**前缀策略**（`prefix`、`prefix_except_default` 等）— 区域与 URL 挂钩。`$switchLocale()` 始终会导航到本地化路由。没有 `redirect: false` 选项。

如果你只需要目标 URL（例如语言切换器链接），请改用 `$switchLocalePath()`：

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

请参阅[路由与区域切换](/api/methods#-route-locale-switching)以获取所有切换方法。

### ❓ 切换区域时页面滚动到顶部（或跳转）？

这是预期行为 — 它是 **Vue Router / Nuxt 滚动行为**，并非 nuxt-i18n-micro 特有。

使用前缀策略（`prefix`、`prefix_except_default` 等）时，`$switchLocale()` 会执行常规的客户端导航（`/en/page` → `/de/page`）。Nuxt 默认的 [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) 会在路由变更时滚动到顶部（浏览器前进/后退时通过 `savedPosition` 例外）。

nuxt-i18n-micro 不会添加隐藏的滚动处理 — 请在应用中使用一个小型包装组件。

**`SwitchLocalePreserve` 包装器**

将 [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) 复制到你的项目（`components/SwitchLocalePreserve.vue`）。可用示例：[`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue)。

在页面上设置 `scrollToTop: false` 并包裹你的切换 UI。为可点击元素添加 `data-locale` — 包装器会拦截点击、调用 `$switchLocale` 并恢复滚动位置（包括翻译长度导致布局变化时）：

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

该组件：

1. **点击时** — 读取插槽中被点击元素的 `data-locale`（按钮、链接或任意自定义标记）。
2. **在 `$switchLocale` 之前** — 存储 `scrollY` 与被点击元素位置（保持其位于光标下方）。
3. **导航期间** — 一次性修补 `router.options.scrollBehavior`，返回 `\{ top: scrollY \}` 而不是滚动到顶部。
4. **导航之后** — 等待 `page:finish`，然后重新应用滚动，同时使用 `ResizeObserver` 捕获不同翻译长度带来的布局变化。

在使用该包装器的页面上，`scrollToTop: false` 是必需的。文档：[Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta)。

不要在被包装的控件上直接调用 `$switchLocale` — 包装器会负责切换。对于包装器之外的 `<NuxtLink :to="$switchLocalePath('fr')">`，滚动行为遵循 Nuxt 常规路由行为，除非你添加了自己的 `app/router.options.ts`。

## 🌐 翻译问题

### ❓ 为什么翻译在页面过渡期间出现问题，特别是使用 `defineAsyncComponent` 时？

在 `nuxt-i18n-micro` 与页面过渡一起使用时，翻译可能在过渡期间短暂停止工作。这是因为路由在过渡完成前发生了变化，导致新页面翻译在旧页面仍显示时就开始加载。

**根本原因：**

- 页面过渡在翻译完全加载前就触发了路由变化
- `defineAsyncComponent` 和 `useAsyncData` 可能延迟翻译加载
- 翻译键在加载期间可能显示为原始路径

**方案 1：累积合并（内置，无需配置）**

在 v3 中，模块自动使用累积合并策略。当在同一区域内导航时，新页面翻译会被合并进入活动字典而非替换。这意味着在过渡动画期间，前一页面的翻译仍然可用。过渡结束后（`page:transition:finish` hook），旧键会自动清理。

无需任何配置 — 开箱即用。

**方案 2：显式路由上下文**

如果你更倾向手动控制，可以将当前路由显式传给 `$_t`：

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**方案 3：加载状态**

实现加载状态以优雅地处理翻译加载：

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ 为什么在 Vercel 上 SSR 期间翻译键无法解析？

**SSR 上的 `$fetch` 限制**
在 Vercel 等无服务器平台上，`$fetch` 只能从 CDN 获取静态文件，而不能访问 Nitro 内部服务器。这意味着除非设置了正确的 base URL，否则静态翻译文件可能无法直接访问。

**通过设置 `apiBaseClientHost` 和 `apiBaseServerHost` 修复**
如果翻译托管在外部 CDN 或不同域名，请对客户端请求使用 `apiBaseClientHost`，对服务端请求使用 `apiBaseServerHost`。`apiBaseUrl` 应只包含路径前缀（例如 `_locales`）。

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

或通过环境变量：

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

翻译将会在客户端与服务端均从 `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` 获取。

## 🔗 路由与导航问题

### ❓ 可以在翻译字符串中直接使用 `NuxtLink` 或 `<i18n-link>` 吗？

可以，`Nuxt I18n Micro` 允许通过 `<i18n-t>` 组件在翻译中使用 `NuxtLink` 或 `<i18n-link>`，这对于在不分割翻译字符串的情况下处理语法和 RTL 语言需求特别有用。

**示例：**

翻译文件：

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue 模板：

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

这样可以在翻译中动态嵌入链接，同时保持正确的本地化结构。

## 🏗️ 构建与部署问题

### ❓ 为什么翻译载荷最终会出现在 `public/_locales/` 下（或在 Edge 部署时出现在服务端包中）？

SSR 与客户端都需要相同的 `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json` 载荷。它们的打包方式取决于 Nitro 目标：

**说明：**

- **Node（默认）：** 模块**不会**将翻译作为 Nitro `serverAssets` / Rollup `raw:` 嵌入（这会在大词典上使构建内存爆炸）。相反，它将预合并树复制到 `public/<apiBaseUrl>/`（默认 `_locales`），SSR 会用 `readFile` 读取这些文件。客户端则以 `$fetch` 获取相同的 URL — 无论是静态文件还是通过 Nitro handler。
- **Edge**（`nitro.node === false`）：SSR 没有持久的 public 文件系统，因此载荷通过 Nitro `serverAssets`（`assets:i18n`）嵌入。请优先使用 `translationPayloads.mode: 'source'`，以使嵌入保持紧凑。仅当你还需要 CDN/静态副本时才设置 `publicAssets: true`。
- **`prerenderRoutes`：** 可选。在 premerged 模式下 `publicAssets` 已经写入了 `\{page\}/\{locale\}/data.json`，因此预渲染这些路由通常是多余的。

### ❓ 为什么会遇到与 `@unhead/vue` 相关的构建错误或未定义对象错误，尤其是在 Cloudflare Pages 上？

**原因：**
一些项目在使用 `nuxt-i18n-micro` 时会遇到构建冲突或缺少依赖。特别是：

- 在 **Cloudflare Pages** 或 **Cloudflare Workers** 上部署可能需要额外的兼容性标记。
- 如果 `@unhead/vue` 等依赖未正确安装，预渲染步骤可能失败。
- 某些模块（例如 **nuxthub**、**nitro-cloudflare-dev**）如果没有正确的标记或依赖，会引发冲突。

**可能的解决方案：**

**方案 1：手动安装 `@unhead/vue`**
如果构建错误提示找不到 `@unhead/vue`，请将其直接安装到项目依赖中：

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

这样可以确保它在 Nitro 预渲染阶段可用。

**方案 2：添加 Cloudflare 兼容性标记**
在使用 Cloudflare Pages 或 Cloudflare Workers 时，Node.js 兼容性通常默认禁用。请在 `wrangler.toml` 中启用：

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

此标记允许许多 Node.js 模块（包括 `nuxt-i18n-micro` 使用的那些）顺利运行。

## 🔍 SEO 与 `@nuxtjs/seo`

### ❓ 错误：`nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

出现该问题的原因是 **`@nuxtjs/seo`** 引入了旧版 **`nuxt-site-config` 3.x**，它只为 `@nuxtjs/i18n` 注册其 i18n 插件，而不为 **nuxt-i18n-micro** 注册。

**修复方式：**

1. 升级到 **`@nuxtjs/seo` 3+**（包含支持 micro 的 `nuxt-site-config` 4+）。
2. 在 `modules` 中将 **`nuxt-i18n-micro` 放在 `@nuxtjs/seo` 之前**。
3. 保持 **`i18n.meta: true`** 以获得基于区域的头标签。

请参见 [SEO 指南 — Nuxt SEO 部分](/guides/seo#nuxt-seo-nuxtjs-seo) 获取完整示例。

## 🔧 配置与兼容性

### ❓ `Nuxt I18n Micro` 是否受 `vue-i18n` 启发？修饰符呢？

尽管 `Nuxt I18n Micro` 作为 `nuxt-i18n` 的高性能替代方案存在，但它是独立于 `vue-i18n` 构建的。虽然部分方法名和参数可能相似，但底层功能有很大差异。

**修饰符**：维护者最初考虑过修饰符，但最终认为像 `<i18n-t>` 和 `<i18n-link>` 这样的组件已能有效满足相关需求。

例如：

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

此方案非常灵活，因此目前没必要发布修饰符。不过，如有需求，未来版本可能会加入修饰符。
