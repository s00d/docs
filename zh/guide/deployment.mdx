该模块无需额外配置即可与任何 Nitro preset 配合使用：它会根据你构建所用的 preset 决定翻译文件的存放位置。默认值适用于大多数应用；请阅读与你的平台对应的章节。本页说明：

- `.output/` 中最终包含什么，以及 payload 会获得哪些响应头；
- 针对静态托管、大型翻译目录、子路径、代理或 CDN 需要做哪些修改。

<Note>

已在真实主机上部署并验证：Cloudflare Workers 和 Pages、Vercel 和 Vercel Edge、Netlify 和 Netlify Edge、Cloud Run 和 Deno Deploy，各自按照[平台](#platforms)中列出的内容进行配置。其他 preset 已在本地构建并运行。

</Note>

## 翻译如何交付 {#how-translations-are-delivered}

在构建时，模块会将 `locales/`（合并所有层）转换为 **payload**：每个页面和 locale 各一个 JSON 文件。有两个使用方会读取它们：

- **SSR** 在进程内加载所渲染页面的 payload —— 没有 HTTP 请求，字典也不会嵌入 HTML 中。
- **浏览器**在 hydration 和导航时获取 `/_locales/<page>/<locale>/data.json?v=<dateBuild>`。

`_locales` 即 [`apiBaseUrl`](/zh/api/module-options#apibaseurl)。内置的服务器路由会响应该 URL；`public/` 中的静态副本则无需服务器即可响应。

## Node 服务器 {#node-server}

```bash
npx nuxi build
node .output/server/index.mjs
```

使用 `node-server`（默认 preset）、`node-cluster`、`bun`、`deno-server` 或任何其他从磁盘提供 `public/` 且 `public/` 与 `server/` 文件夹相邻的 preset 时：

- payload 会被复制到 `.output/public/_locales/<page>/<locale>/data.json`；
- SSR 使用 `fs` 从该文件夹读取它们（不会打包进服务器）；
- 浏览器以静态文件的形式获取它们，或从服务器路由获取。

请部署整个 `.output/` 目录。该模块需要 Node 20 或更高版本，而 Nuxt 有其自身的最低要求：Nuxt 4.5 声明为 `^22.19.0 || ^24.11.0 || >=26.0.0`。

持续负载下的进程所占用的内存可能远大于其实时堆。在设置容器内存限制之前，请参阅 [Node 服务器上的内存](/zh/guide/performance#memory-on-a-node-server)。

对于其他目录结构，模块会按照下一节所述嵌入 payload。这包括：

- 自定义的 `nitro.output.publicDir`，构建时只读取一次；
- 在将静态文件存放在别处的 preset 上设置 `serveStatic: true`。

<Warning>

如果构建读取了 `public/`，而该文件夹没有到达服务器（例如 `aws-lambda` 搭配 `serveStatic: true`），服务器会记录一条错误，页面会显示原始键。请设置 `nitro.serveStatic: false` 以嵌入 payload。

</Warning>

## Serverless 与 Edge {#serverless-and-edge}

以下 preset 无法在运行时读取 `public/`：

- 将 `public/` 发送到 CDN 或不提供它的函数 preset：`vercel`、`netlify`、`aws-lambda`、`aws-amplify`、`azure-swa`、`firebase`、`stormkit`、`zeabur`、`node-listener`；
- 没有文件系统的 Edge preset：`cloudflare-module`、`cloudflare-pages`、`vercel-edge`、`netlify-edge`、`deno_deploy`；
- `serveStatic: 'inline'`，例如 `winterjs`。

在这些环境中，模块会将 payload 作为 Nitro 服务器资源（`assets:i18n`）嵌入服务器包中，同时仍为浏览器写入公共副本。

嵌入完整的页面 × locale 矩阵会使包变得很大。超过 Edge 平台的限制时，构建会发出警告并指明该平台，参见[包体积限制](#bundle-limits-on-edge)。对于大型翻译目录，请切换到 `source` 模式，它会嵌入紧凑的源文件，并在运行时合并根翻译、页面翻译和回退翻译：

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    translationPayloads: {
      mode: 'source',
    },
  },
})
```

在 `source` 模式下，浏览器始终从服务器路由获取 payload，服务器路由会在请求时合并它们（任何公共副本存放的都是只有服务器才读取的紧凑源文件树）。这需要一个运行中的服务器，因此纯静态站点不要使用 `source`。

### Edge 上的包体积限制 {#bundle-limits-on-edge}

| 平台               | 限制                                                                                   |
| ------------------ | -------------------------------------------------------------------------------------- |
| Cloudflare Workers | 未压缩 64 MiB，Free 和 Paid 计划相同。无压缩后限制。1 s 启动时间，128 MB 内存          |
| Vercel Edge        | Hobby 计划 gzip 后 1 MB，Pro 计划 2 MB，Enterprise 计划 4 MB                           |
| Netlify Edge       | 压缩后 20 MB                                                                           |

构建会汇总其嵌入的字典大小，仅在超过平台最低限制时发出警告。它只计算字典，应用本身的体积还要另算。例如，120 个页面 × 4 个 locale，根文件 60 KB，嵌入的大小为：

| 模式 | 嵌入大小 | 适用平台 |
| --- | --- | --- |
| `premerged` | 34.9 MiB | Cloudflare；不适用于 Vercel Edge 或 Netlify Edge |
| `source` | 5.7 MiB | 在 Vercel Edge 上 gzip 后仍有 3 MB |

在 Vercel Edge 上，这种规模的翻译目录需要一个 [payload 主机](#app-baseurl-and-payload-hosts)。

`source` 会在每个 isolate 中为每个页面和 locale 付出一次合并的代价，在上述示例中约为 1 ms，冷启动的 isolate 中约为 7 ms CPU 时间。它随回退链的大小而增长：4 MB 的回退链文件约需 43 ms。Netlify Edge 允许每个请求 50 ms CPU 时间，Cloudflare 的 Free 计划为 10 ms。

### Edge 运行时上的日期 {#dates-on-edge-runtimes}

`$td` 使用运行时的 `Intl`，其 ICU 数据可能与浏览器不同。在 Netlify Edge 上，格式化后的日期可能在 Chrome 使用普通空格的位置包含 U+202F（窄不换行空格），因此 Vue 会记录一次 hydration 不匹配，文本会在 hydration 时自行修正。在那里，使用原生 `Intl` 的普通 Nuxt 也会出现同样的情况；Deno Deploy 则不会。

<Tip>

带有 `date` 或 `relativeDate` 的 `<i18n-t>` 已经允许这种不匹配。对于模板中的 `$td`，请在元素上添加 `data-allow-mismatch="text"`。

</Tip>

## 静态站点（nuxi generate） {#static-site-nuxi-generate}

```bash
npx nuxi generate
```

`nuxi build --preset <static preset>` 的效果相同。

- 默认的 `premerged` 模式会将所有 payload 写入 `.output/public/_locales/`，因此任何静态主机都能提供它们。
- 页面会为每个 locale 预渲染：在 `prefix` 下，模块会为每个本地化根路径（`/en`、`/de`）生成种子路由，而 `/` 会保留为重定向存根。
- 请保持 [`prerenderRoutes`](/zh/api/module-options#translationpayloads) 关闭：公共副本已经包含 payload 文件。
- 使用 `source` 模式或 `publicAssets: false` 时，浏览器没有可读取的内容，构建会发出警告。

<Note>

没有服务器来读取 cookie 或 `Accept-Language`，因此首次加载时，已保存的 locale 不会重定向 `/`。在 `no_prefix` 下，HTML 包含默认 locale，已保存的 cookie 不会在加载时生效：`$switchLocale` 在已打开的页面中仍然可用。

</Note>

关于 Cloudflare Pages，请参阅 [Cloudflare Pages](#cloudflare-pages)。

对于使用 [locale 域名](/zh/guide/layers#multiple-domains)的构建，请为每个域名运行一次 generate，并将 `NUXT_I18N_DOMAIN` 设置为本次运行的主机。这样每个目录树都包含该域名的页面和 payload。Nitro 没有用于输出文件夹的变量，因此请在配置中读取你自己的变量：

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: { output: { publicDir: process.env.PUBLIC_DIR } },
})
```

```bash
NUXT_I18N_DOMAIN=example.de PUBLIC_DIR=sites/example.de npx nuxi generate
NUXT_I18N_DOMAIN=example.com PUBLIC_DIR=sites/example.com npx nuxi generate
```

- 请将这些文件夹放在 `.output` 之外：每次运行都会清空它。
- 指向其他域名的绝对链接不会被爬取。
- 如果没有该变量，包含 `baseUrl` locale 的构建会发出警告并生成构建配置，其中这些 locale 只是链接，不会生成页面。
- 在 Node 服务器上，同一个变量会将进程固定到一个域名，无论 `Host` 是什么。

静态主机会对这些文件应用自己的响应头；请在主机的配置中设置缓存。模块的 `/_locales/*` 规则确实会通过 `_headers` 到达 Cloudflare Pages，通过 `config.json` 到达 Vercel，值为 `public, max-age=60`。如需提供 `.gz` / `.br` 兄弟文件，请开启 `nitro.compressPublicAssets`：模块会使用相同的设置压缩 payload 副本。

## 缓存响应头与 dateBuild {#cache-headers-and-datebuild}

| 请求                                                                                     | `Cache-Control`                                                                                                 |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Node 服务器或路由，`?v=` 等于当前 `dateBuild`，字典非空                                   | `private, max-age=<httpCacheDuration>, immutable`                                                               |
| Node 服务器或路由，没有 `?v=`、`?v=` 为旧值，或字典为空                                   | `public, max-age=0, must-revalidate`                                                                            |
| 主机上的 `public/` 副本，任意 `?v=`                                                       | `public, max-age=60`（[`httpCacheControl`](/zh/api/module-options#other)） |
| `source` 模式、`cacheTtl` 或 `apiBaseServerHost`：字典可能在不重新构建的情况下发生变化     | 始终为 `httpCacheControl` 响应头                                                                                |
| 服务器路由，无法读取字典                                                                  | `503`、`no-store`                                                                                               |
| 开发服务器                                                                                | 无                                                                                                              |

表格之所以如此，原因如下：

- 带当前 `v` 的 URL 会像带哈希的资源一样被固定，而只有能看到 query 的一方才能这样声明：服务器路由，以及会为其静态文件设置响应头的 Node 服务器。
- 它是 `private` 的，因此忽略 query 的 CDN 无法用这个响应来应答下一个 `v`。
- 主机的静态文件从 `/_locales/**` 路由规则获取适用于整个路径的响应头，该规则看不到 query，因此保持较短；重复加载仍然不会被阻塞。
- 旧的 `v` 仍然可以提供，因为缓存的 HTML 会引用它。

`httpCacheControl: false` 会让所有静态文件保持 `max-age=0, must-revalidate`。[`httpCacheDuration`](/zh/api/module-options#httpcacheduration) 默认为一年；`0` 表示不发送该响应头。`$clearCache()` 会对其下一次加载的内容进行重新验证。

当 Safari 可能无法复用响应时，它会再次请求预加载的 payload：有 `no-cache` 和 `ETag` 时，第二次请求是 `304`；既没有缓存响应头也没有验证器时，则是第二次完整下载。`max-age` 大于 `0` 时只有一次请求。只有在不添加验证器的主机上设置 `httpCacheDuration: 0` 才会付出这个代价。

[`dateBuild`](/zh/api/module-options#datebuild) 就是 `?v=` 的值。默认情况下，它是翻译文件的哈希值，因此只有翻译变化时它才会变化，浏览器会在未涉及翻译的部署之间保留已缓存的 payload。它也会随回退链变化。

- 自行设置它以固定一个值。
- 设置为 `0` 或 `''` 可完全去掉 `?v=`；此时 payload 永远不会是 `immutable`。

<Tip>

在 Node 服务器上原地替换字典后，请使用 `NUXT_I18N_DATE_BUILD=<new value>` 重启：不重新构建的话，没有其他方式能改变 `v`。

</Tip>

### 根文件与增量文件 {#root-and-delta-files}

`premerged` 会为每个 locale 写入一个根文件 `__root/<locale>/data.json`，而每个页面的文件中只包含与根文件不同的部分。

- 页面文件通过 `__i18n_root` 键标记它所基于的根文件。
- 浏览器会同时获取两者，在两者都到达之前页面不显示任何内容，SSR 会为每个翻译块合并一次。
- 没有标记的文件是完整的字典，可以独立使用：开发环境、`source` 模式、服务器路由以及仍保存旧文件的主机都会返回这种文件，无需任何设置。

因此，任何直接读取 `_locales/*/data.json` 的人读到的都是增量。设置 `translationPayloads.rootDelta: false` 可保留完整文件。

在部署前后一直打开的标签页在请求新的增量时，会发现它是基于另一个根文件生成的，并会在显示之前获取该根文件。

### 无法读取字典时 {#when-a-dictionary-cannot-be-read}

从主机获取失败（404 以外的任何情况）、文件不可读或已损坏，或者 200 响应不是 JSON 对象时，结果不会进入任何缓存，下一个请求会再次读取：

- 页面渲染会记录一条警告，为该字典显示原始键，并以 `503` 响应，带有 `Cache-Control: no-store`，所有 CDN 响应头中也是如此（`CDN-Cache-Control`、`Cloudflare-CDN-Cache-Control`、`Netlify-CDN-Cache-Control`、`Vercel-CDN-Cache-Control`、`Surrogate-Control`，覆盖路由规则中的任何值），以及 `Retry-After: 60`；
- `/_locales/...` 以 `503` 和 `no-store` 响应；
- `useTranslationServerMiddleware` 提供的 `t` 会返回键或默认值。

故障期间会发生什么：

- **访问者：**该 503 的响应体就是页面本身。在 hydration 时，浏览器会再次读取字典，一旦主机恢复，文本就会出现，同时 Vue 会在控制台输出一条关于 hydration 不匹配的错误，因为服务器的 HTML 中是键。
- **爬虫**会被告知稍后再来。
- **缓存：**`swr` 或 `cache` 路由规则不会存储状态码为 400 及以上的响应，CDN 会收到 `no-store`，因此没有缓存会保留原始键，恢复后的第一个请求就会渲染真实文本。
- **已被规则缓存的页面**保持原样：重新验证失败，不存储任何内容。在 Vercel 上，失败的 `isr` 重新验证同样会保留最后一个页面。

这涵盖了一次渲染加载的每个翻译块，包括根文件可用但页面翻译块失败的情况，以及在渲染后期合并的翻译块。字典正常的页面、重定向和错误页面会保留各自的状态码。[组件 island](/zh/guide/server-side-translations) 是例外：它保持 200，因为 503 会将它从页面中移除，所以自身字典加载成功的页面可能会保留某个 island 的原始键。故障期间的每个请求都会到达主机，除了等待响应头的 60 秒外，模块本身没有其他超时。

主机返回 404 表示它没有该文件，这不算失败。页面渲染会像浏览器一样显示根字典，`/_locales/...` 也会返回同样的 404。两者都不会被缓存，因此新出现的文件会在下一个请求时被读取，代价是此类页面每次渲染都会向主机发送一次请求。如果连根文件都没有，字典就是空的，[预渲染](/zh/guide/upgrade#server,-build-and-deployment)会失败。

服务器会将已加载的 payload 保存在进程内 LRU 缓存中，最多 `cacheMaxSize` 个条目（默认 1000），设置 `cacheTtl` 后会在到期时重新加载条目；[性能调优](/zh/guide/performance)介绍了这两项，[`cacheStorage`](/zh/guide/performance#shared-cache-for-several-instances) 可添加多个实例共享的缓存。不要再在 `/_locales/**` 上额外添加 Nitro `cache` 路由规则：它以包含 query 的完整 URL 为键，会存储第三份副本。

## 应用 baseURL 与 payload 主机 {#app-baseurl-and-payload-hosts}

**`app.baseURL`** 无需其他设置。使用 `app.baseURL: '/shop/'` 时，浏览器会获取 `/shop/_locales/...`；副本仍位于 `.output/public/_locales/`，Nitro 会在 base 下提供它（静态主机必须将输出挂载在 `/shop/`）。locale 前缀和[排除路径](/zh/guide/excluding-static-files)在匹配时不包含 base。

当 payload 是 `public/` 中的文件时，**`app.cdnURL`** 也会移动它们：浏览器会获取并预加载 `<cdnURL>/_locales/...`。

- CDN 必须在该路径下、与 `_nuxt/` 并列存放 `_locales/`。
- 由于文件通过 `fetch` 获取，CDN 必须允许你站点的来源（CORS）。
- 只有服务器路由才能响应的字典（`source` 模式、没有公共副本）仍保留在应用的来源上。

在 `cloudflare-module` 上于运行时设置 `NUXT_APP_BASE_URL` 需要 Node 兼容性（`nodejs_compat`）。当 `nitro.cloudflare.nodeCompat` 关闭时（在没有标志且日期较旧的情况下 Nitro 也会回退为关闭），它看不到该变量并会在 `/` 下提供服务（普通 Nuxt 也是如此），而 locale 重定向仍会指向 base。在这种情况下，请在构建时设置 `app.baseURL`。

要从其他来源提供 payload，请将客户端和服务器指向该来源，并关闭本地输出：

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    apiBaseClientHost: 'https://cdn.example.com',
    apiBaseServerHost: 'https://cdn.example.com',
    translationPayloads: {
      serverHandler: false,
      publicAssets: false,
      serverAssets: false,
    },
  },
})
```

- 在 Node 上，`serverAssets` 会为服务器自身的读取写入相同的副本，而该文件会响应 `/_locales`：它也必须关闭，即使你为浏览器保留了服务器路由也是如此，否则浏览器的请求永远到达不了该路由。
- 主机必须提供相同的 `<apiBaseUrl>/<page>/<locale>/data.json` 目录结构。
- 当所有本地输出都关闭且缺少主机时，构建会发出警告。

相同的值也可以在构建时来自 `NUXT_I18N_APP_BASE_URL`、`NUXT_I18N_APP_BASE_CLIENT_HOST` 和 `NUXT_I18N_APP_BASE_SERVER_HOST`。`NUXT_I18N_APP_BASE_SERVER_HOST` 在运行时同样有效，并优先于构建时的值。详情参见 [`apiBaseServerHost`](/zh/api/module-options#apibaseserverhost)。

## 平台 {#platforms}

这里只列出模块或其输出所需的内容。账户、区域和 CLI 登录请参阅各平台的文档。

### Cloudflare Workers {#cloudflare-workers}

Preset `cloudflare_module`。`wrangler deploy` 会用 esbuild 对 Nitro 的输出再打包一次，之后原始的 `defineAsyncComponent(() => import('./X.vue'))` 在服务器上会渲染为空。Nuxt 的默认错误页面就是这样一个组件，因此 404 的响应体为空，浏览器会记录一次 hydration 不匹配。随后客户端会渲染页面，状态码仍为 404，但在没有 JavaScript 的情况下页面是空白的。这就是 [nuxt#33270](https://github.com/nuxt/nuxt/issues/33270)：不使用该模块的普通 Nuxt 也会如此。页面路由不受影响。

关闭二次打包：

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: {
    preset: 'cloudflare_module',
    cloudflare: {
      deployConfig: true, // `wrangler` below applies only with it
      wrangler: {
        no_bundle: true,
        find_additional_modules: true,
        rules: [{ type: 'ESModule', globs: ['**/*.mjs'] }],
      },
    },
  },
})
```

```bash
npx nuxi build
cd .output/server && npx wrangler deploy -c wrangler.json
```

请将 `compatibilityDate` 设置为 `2024-09-19` 或更晚：更早的日期会选择旧版 preset，它不会写入 `wrangler.json`，也不会报错。这样 404 就能正常渲染，上传体积也会变小：在测试应用上 gzip 后为 190 KiB，之前为 246 KiB。你自己的 `error.vue` 是另一种解决办法，但它只覆盖错误页面。

模块本身不需要 `nodejs_compat`。有关限制，请参阅[包体积限制](#bundle-limits-on-edge)。

### Cloudflare Pages {#cloudflare-pages}

使用 `cloudflare-pages-static` preset。`nuxi generate --preset cloudflare-pages` 是一次没有 `index.html` 的服务器构建。

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: {
    preset: 'cloudflare-pages-static',
    prerender: { autoSubfolderIndex: false },
  },
})
```

```bash
npx nuxi generate
npx wrangler pages project create my-site --production-branch main --force
npx wrangler pages deploy dist --project-name my-site --branch main
```

- **输出。**该 preset 写入 `dist/`，而不是 `.output/public`。
- **`--force`。**没有它时，新版 wrangler（此处为 4.156）会把 `pages project create` 转交给 Workers。加上它，你会得到一个经典的 Pages 项目。只在创建时需要一次。
- **`autoSubfolderIndex: false`。**Pages 会对 `/de` 返回 308 重定向到 `/de/`，而 canonical 和 `hreflang` 指向的是 `/de`，因此它们指向了一个重定向。使用此选项后文件为 `de.html`，重定向随之消失。
- **404 时控制台中出现的 `NUXT_E1005`** 是正常的 404。Nuxt 之所以这样报告，是因为 `404.html` 在客户端启动，早于应用挂载。页面可以正常工作，普通 Nuxt 也会输出同样的信息。

### Vercel 与 Vercel Edge {#vercel-and-vercel-edge}

Preset `vercel` 和 `vercel_edge`，无需修改应用。标签无需 `metaBaseUrl` 即可工作，它们使用平台转发的请求头。Vercel Edge 的包体积限制较小：参见[包体积限制](#bundle-limits-on-edge)。如需共享缓存，请使用 [`upstash` 驱动](/zh/guide/performance#upstash-on-vercel-and-vercel-edge)。

### Netlify {#netlify}

Preset `netlify` 和 `netlify_edge`。

```bash
npx nuxi build --preset netlify
npx netlify deploy --prod --no-build --dir dist --functions .netlify/functions-internal
```

- **不要设置 `nitro.output`。**该 preset 会自行写入 `.netlify/` 和 `dist/`。
- **在你执行部署的文件夹中保留一个 `package.json`。**没有它时，CLI 会查找父文件夹，并且不部署任何函数，也不报错。
- **Netlify Edge** 只需 `--dir dist` 即可部署。参见 [Edge 运行时上的日期](#dates-on-edge-runtimes)。

### Cloud Run {#cloud-run}

使用默认的 `node-server` 构建。当本地没有运行 docker 时，`gcloud run deploy --source` 需要在输出文件夹中有一个 `Dockerfile`：

```dockerfile
# .output/Dockerfile
FROM node:22-slim
WORKDIR /app
COPY . .
ENV NODE_ENV=production
CMD ["node", "server/index.mjs"]
```

```bash
cd .output && gcloud run deploy my-app --source .
```

标签无需 `metaBaseUrl` 即可工作，它们使用平台转发的请求头。

### Deno Deploy {#deno-deploy}

Preset `deno_deploy`。`deno deploy` 取代了 `deployctl`。创建一个入口为 `server/index.ts` 的动态应用，并从输出文件夹进行部署。

### Firebase {#firebase}

| 产品 | 设置 |
| --- | --- |
| App Hosting | 运行 Node 构建：使用默认 preset 或 `firebase-app-hosting`，以及 Node 20+ |
| Cloud Functions | `firebase` preset 会嵌入 payload，并需要 `firebase-functions` |
| Hosting（静态） | 以文件形式提供 `.output/public`，因此 `/_locales/**` 使用 Hosting 的响应头 |

在静态 Hosting 上，如果 JSON 返回的 `Content-Type` 或缓存不正确，请在 `firebase.json` 中为 `/_locales/**` 添加 `headers` 条目。Nuxt `routeRules` 的响应头不适用于 Hosting 自行提供的文件；对于确实到达服务器的响应，payload 路由会设置自己的 `Content-Type` 和 `Cache-Control`。

### AWS Amplify {#aws-amplify}

`aws-amplify` 将静态文件存放在其计算文件夹旁边，而不是服务器旁边，因此 payload 会像在函数平台上一样被嵌入。

### 同一构建的多个实例 {#several-instances-of-one-build}

同一个构建产物可以通过环境变量，让每个实例使用不同的默认 locale 或禁用不同的 locale：参见[运行时覆盖](/zh/guide/runtime-overrides)。仅在运行时禁用的 locale 在 `public/` 中仍有其静态文件；如果这些文件不能被访问，请在构建时禁用它。

从远程主机加载字典的多个实例可以通过 Redis、Upstash、Cloudflare KV 或 D1、Deno KV 或其他 Nitro 存储共享字典，这样后端只会收到一次请求，而不是每个实例一次。它是缓存，而不是翻译的来源：参见[多个实例的共享缓存](/zh/guide/performance#shared-cache-for-several-instances)。

## 位于代理或 CDN 之后 {#behind-a-proxy-or-cdn}

应用必须从请求中得知公共主机和协议。

| 代理发送的内容                               | 普通构建                                         | locale 上带有 `baseUrl` 的构建                                                    |
| -------------------------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------- |
| 真实的 `Host`                                | 无需设置                                         | 无需设置                                                                          |
| 源站的 `Host`，加上 `X-Forwarded-Host`        | 无需设置                                         | [`trustForwardedHost: true`](/zh/api/module-options#trustforwardedhost)              |
| 两者都没有                                   | [`metaBaseUrl`](/zh/api/module-options#metabaseurl) | 没有设置能起作用：每个请求看起来都像是源站的主机，因此请修改代理                  |

- **`swr` 或 `cache` 下的路由。**上表在这里不适用：参见[缓存 HTML](#caching-html)。请设置 `metaBaseUrl` 或 `site.url`。
- **`X-Forwarded-Proto`。**请发送它，否则在 HTTPS 代理之后 canonical URL 会显示为 `http://`。`metaBaseUrl` 也能解决这个问题。
- **在域名构建中**，由域名决定标签的基础 URL。在那里 `metaTrustForwardedHost` 不会选择域名，只有 `trustForwardedHost` 会。
- **重定向是相对的，locale cookie 没有 `Domain`，**因此两者都会停留在公共主机上。

<Warning>

**当源站仍可被访问时，请固定 `metaBaseUrl`** —— 在没有 `metaBaseUrl` 或 `site.url` 的普通构建中，canonical、`hreflang` 和 `og:url` 会从请求中获取主机。[`metaTrustForwardedHost`](/zh/api/module-options#metatrustforwardedhost) 默认开启，因此带有 `X-Forwarded-Host: evil.example` 的直接请求会在这些标签中得到 `https://evil.example`，而前面的缓存会传播该页面。像 `*.workers.dev` 这样的平台主机正是这样的源站。`metaBaseUrl` 对 `Host` 同样能堵住这个漏洞。域名构建中的已知主机会保留其自己的 `baseUrl`。使用 `trustForwardedHost: true` 时，直接访问的客户端可以选择另一个域名的页面，因此只有在会覆盖该请求头的代理之后才开启它。

</Warning>

## 缓存 HTML {#caching-html}

大多数 URL 都可以安全地缓存，因为它们指明了自己的 locale。以下 URL 取决于访问者：

| 设置                           | URL                                               |
| ------------------------------ | ------------------------------------------------- |
| 默认，`autoDetectPath: '/'`    | `/`                                               |
| `prefix`                       | `/` 以及所有无前缀的 URL，它们只会重定向          |
| `autoDetectPath: '*'`          | 所有 URL                                          |
| `no_prefix`                    | 所有页面                                          |

- **`Vary`。**当设置了 [`localeCookie`](/zh/api/module-options#localecookie) 时，这些响应会带有包含 `Cookie` 的 `Vary`；当开启 `autoDetectLanguage` 时则包含 `Accept-Language`。遵循它的缓存会将这些响应区分存储。
- **忽略 `Vary` 的缓存**（例如"按 URL 缓存所有内容"）必须跳过这些 URL。否则一个访问者的 `302 /de` 会被下一个访问者收到，而存储的默认页面会让所有人都失去重定向。在 `/` 上你也可以设置 `redirects: false`。Nitro 的路由缓存以路径及其 `varies` 列表为键，因此也请将 `/` 排除在 `swr` 和 `cache` 规则之外。
- **`Set-Cookie`。**设置了 `localeCookie` 时，前缀下每个服务器渲染的页面都会带有 `Set-Cookie`，正确的 CDN 不会存储它。对于缓存的 HTML，请关闭 `localeCookie`，或在边缘去除该响应头。
- **`swr` 和 `cache` 规则需要 `metaBaseUrl` 或 `site.url`。**Nitro 渲染此类路由时只带有 `cache.varies` 中的请求头，因此 `Host`、`X-Forwarded-Host` 和 `X-Forwarded-Proto` 都不存在，请求 URL 会显示为 `http://localhost`。没有固定的源站时，这些路由上的 canonical、`hreflang` 和 `og:url` 会指向 `http://localhost`，在所有平台上都是如此。普通 Nuxt 的 `useRequestURL()` 在那里读到的也是同样的值。如果改为从访问者那里获取主机，就会把某个访问者的 `X-Forwarded-Host` 放进所有访问者都会收到的页面中。域名构建不受影响：其标签使用 locale 的 `baseUrl`。

  如果一个构建服务多个主机，且没有单一的源站适用，请让规则能看到这些请求头，并为每个值保留一份副本：`'/blog/**': { swr: 60, cache: { varies: ['host', 'x-forwarded-host', 'x-forwarded-proto'] } }`。每个不同的值都是一个新的缓存条目，因此发送伪造请求头的客户端会填满缓存：请将源站放在会设置这些请求头的代理之后。
- **域名构建中的 `swr` 和 `cache` 规则。**模块会在每条此类规则的 `cache.varies` 中添加 `host`，在使用 `trustForwardedHost` 时还会添加 `x-forwarded-host`，这样一个域名就不会把它的页面提供给另一个域名。带有 `cache: false` 的规则保持原样。`isr` 是平台的缓存：请确认它以主机为键。主机作为键的一部分时，发送伪造主机的客户端会增加缓存条目。

关于 payload 文件，请参阅[缓存响应头与 dateBuild](#cache-headers-and-datebuild)。
