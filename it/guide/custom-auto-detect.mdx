---
title: "Rilevamento personalizzato della lingua"
description: "Scegli tu la lingua — in base al dominio, a un header o al profilo utente — con un plugin server e useI18nLocale().setLocale()."
---

Il rilevamento integrato legge l'URL, un cookie e `Accept-Language`. Quando la lingua dipende da qualcos'altro — il dominio, un header geografico impostato dalla tua CDN, un profilo utente — impostala tu stesso in un plugin eseguito prima del plugin i18n. Il modulo carica quindi le traduzioni di quella lingua e la usa per i reindirizzamenti esattamente come se l'avesse rilevata. Le regole che stabiliscono quando una lingua scelta prevale sull'URL si trovano in [Rilevamento della lingua](/it/guide/locale-detection); questa pagina mostra come collegare la tua sorgente.

## Impostare la lingua in un plugin server {#set-the-locale-in-a-server-plugin}

```ts
// plugins/i18n-locale.server.ts
export default defineNuxtPlugin({
  name: 'i18n-custom-locale',
  enforce: 'pre',
  order: -10, // before the i18n plugin (order -5)
  setup() {
    const { setLocale } = useI18nLocale()
    const host = (useRequestHeaders(['host']).host ?? '').split(':')[0]! // without the port

    if (host.endsWith('.de')) setLocale('de')
    else if (host.endsWith('.fr')) setLocale('fr')
  },
})
```

`setLocale(code)` scrive lo stato della lingua (`useState('i18n-locale')`) e, quando è configurato un cookie della lingua, il cookie. Usalo invece di scrivere tu stesso `useState` o `useCookie`. Passa solo codici di lingue abilitate.

Mantieni il plugin come `.server.ts` quando legge gli header della richiesta: nel browser non esistono. Un plugin `.client.ts` è il posto giusto per sorgenti disponibili solo nel browser, come `localStorage`.

## Disattivare il passaggio integrato Accept-Language {#turn-off-the-built-in-accept-language-step}

Il tuo plugin e `Accept-Language` possono essere in disaccordo. Per lasciare decidere solo il tuo codice (più l'URL e il cookie), disattiva l'header:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    autoDetectLanguage: false,
  },
})
```

[`autoDetectLanguage`](/it/api/module-options#autodetectlanguage) controlla solo il passaggio dell'header. L'URL e un cookie valido contano comunque.

## Cosa succede dopo {#what-happens-next}

L'effetto di `setLocale` dipende dalla [strategia](/it/guide/strategy):

| Strategia | Effetto di `setLocale('de')` nel plugin |
| --- | --- |
| `no_prefix` | La pagina viene renderizzata in tedesco; l'URL non cambia. |
| `prefix`, `prefix_except_default` | Su un percorso senza prefisso in cui [`autoDetectPath`](/it/api/module-options#autodetectpath) consente i reindirizzamenti (per impostazione predefinita solo `/`), il server risponde con `302` verso l'URL tedesco. Un URL con un prefisso di lingua lo mantiene. |
| `prefix_and_default` | Nessun reindirizzamento: l'URL senza prefisso è una pagina valida della lingua predefinita. |

Con le strategie a prefisso, una lingua nell'URL è una scelta dell'utente e il tuo plugin non la sovrascrive. `autoDetectPath: '*'` è l'eccezione: in quel caso il server sposta gli URL con prefisso in base al cookie e ad `Accept-Language` e ignora lo stato, ma `setLocale()` scrive anche il cookie quando ne è configurato uno, quindi dalla richiesta successiva la scelta del tuo plugin può reindirizzare un URL con prefisso. Mantieni `'/'` o usa `'no_prefix'` quando gli URL con lingua esplicita devono prevalere. Usa il tuo plugin per scegliere dove arriva un visitatore, non per riscrivere i link che ha seguito.

## Rispettare una lingua scelta dall'utente {#respect-a-locale-the-user-picked}

Quando un utente cambia lingua, il cambio scrive il cookie. Salta il tuo rilevamento quando esiste già una preferenza valida:

```ts
// plugins/i18n-locale.server.ts
import { detectLocaleFromAcceptLanguage } from '@i18n-micro/utils/accept-language'

export default defineNuxtPlugin({
  name: 'i18n-custom-locale',
  enforce: 'pre',
  order: -10,
  setup() {
    const { getPreferredLocale, setLocale, validLocales } = useI18nLocale()
    if (getPreferredLocale()) return // valid state or cookie: keep it

    const country = useRequestHeaders(['x-country'])['x-country']
    if (country === 'JP') return setLocale('ja')

    const header = useRequestHeaders(['accept-language'])['accept-language']
    setLocale(detectLocaleFromAcceptLanguage(header, validLocales))
  },
})
```

`getPreferredLocale()` restituisce lo stato o il cookie solo quando si tratta di una lingua abilitata, quindi un cookie obsoleto non blocca il rilevamento. `detectLocaleFromAcceptLanguage` è lo stesso matcher che tiene conto dei q-value usato dal modulo (installa `@i18n-micro/utils` per importarlo); `setLocale(null)` non fa nulla.

## Un dominio per lingua {#one-domain-per-locale}

Se ogni dominio deve servire le proprie lingue, non ti serve un plugin: assegna a ogni lingua un `baseUrl`, imposta `baseDefault: true` sulla lingua predefinita di ciascun dominio ed esegui una sola build (un sito statico esegue comunque `nuxi generate` per ogni dominio). Vedi [Layer e domini](/it/guide/layers#multiple-domains).
