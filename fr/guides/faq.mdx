# ❓ FAQ : problèmes courants et solutions

Trouvez des réponses aux questions fréquentes et des solutions aux problèmes courants avec Nuxt I18n Micro.

## 🚀 Problèmes de démarrage

### ❓ Que faire si une route ne se charge pas ?

Lors de l'utilisation de `Nuxt I18n Micro`, certaines routes peuvent ne pas se charger comme prévu, en particulier si le router n'assigne pas automatiquement un nom à une route dans des sous-dossiers.

**Solution :**
Pour résoudre ce problème, définissez manuellement le nom de la route pour la page en ajoutant ce qui suit dans le fichier Vue correspondant :

```javascript
definePageMeta({ name: 'pageName' })
```

Cela garantit que la route est correctement enregistrée, permettant une navigation fluide au sein de l'application.

### ❓ Pourquoi `$t` ou d'autres composables i18n ne fonctionnent-ils pas dans les plugins Nuxt ?

Les composables Nuxt I18n (`$t`, `$getLocale`, `$localePath`, etc.) peuvent ne pas fonctionner comme prévu dans les plugins Nuxt ou les fonctions utilitaires, entraînant des erreurs d'exécution.

**Cause et solution :**
Les composables Nuxt nécessitent des contextes spécifiques (par exemple, les hooks Nuxt ou les fonctions setup Vue) pour accéder à l'instance Nuxt. S'ils sont utilisés en dehors de ces contextes (par exemple, dans des fonctions utilitaires ou des plugins), l'erreur suivante peut apparaître dans la console :

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Solution 1 : utilisez `runWithContext`**
Pour appeler des composables i18n après une opération asynchrone, utilisez [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) afin de préserver le contexte nécessaire.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Solution 2 : récupérer la valeur d'abord**
Vous pouvez aussi récupérer la valeur de la traduction d'abord, puis la passer à une fonction utilitaire.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Solution 3 : passer les clés de traduction dans les services**
Dans les services ou fonctions utilitaires, passez les clés de traduction plutôt que d'utiliser `$t` directement. Puis, récupérez la traduction dans le composant.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Changement de locale

### ❓ Changer de locale sans changer l'URL ?

Oui, mais cela dépend de votre [stratégie de routage](/guides/routing-strategies).

**Stratégie `no_prefix`** — la locale ne fait pas partie de l'URL. Utilisez `$switchLocale()` pour changer de locale et recharger les traductions tout en restant sur le même chemin :

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Ou mettez uniquement à jour la préférence avec `useI18nLocale().setLocale('de')`. Pour un rechargement complet des traductions côté client, préférez `$switchLocale()`.

**Stratégies préfixées** (`prefix`, `prefix_except_default`, …) — locale et URL sont liées. `$switchLocale()` navigue toujours vers la route localisée. Il n'y a pas d'option `redirect: false`.

Si vous n'avez besoin que de l'URL cible (par exemple pour un lien de sélecteur de langue), utilisez `$switchLocalePath()` :

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Voir [Changement de route et de locale](/api/methods#-route-locale-switching) pour toutes les méthodes de changement.

### ❓ La page défile vers le haut (ou saute) lors du changement de locale ?

C'est attendu — c'est un **comportement de défilement de Vue Router / Nuxt**, pas quelque chose de spécifique à nuxt-i18n-micro.

Avec les stratégies préfixées (`prefix`, `prefix_except_default`, …), `$switchLocale()` effectue une navigation client normale (`/en/page` → `/de/page`). Le [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) par défaut de Nuxt fait défiler vers le haut lors des changements de route (sauf pour les back/forward navigateur via `savedPosition`).

nuxt-i18n-micro n'ajoute pas de gestion de défilement cachée : utilisez un petit composant wrapper dans votre app.

**Wrapper `SwitchLocalePreserve`**

Copiez [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) dans votre projet (`components/SwitchLocalePreserve.vue`). Démo fonctionnelle : [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

Sur la page, définissez `scrollToTop: false` et enveloppez votre UI de sélecteur. Marquez les cibles cliquables avec `data-locale`. Le wrapper intercepte les clics, appelle `$switchLocale` et restaure le défilement (y compris quand la longueur de la traduction change la mise en page) :

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Le composant :

1. **Au clic** — lit `data-locale` sur l'élément cliqué à l'intérieur du slot (boutons, liens ou tout balisage personnalisé).
2. **Avant** `$switchLocale` — stocke `scrollY` et la position de l'élément cliqué (le garde sous le curseur).
3. **Pendant** la navigation — patche `router.options.scrollBehavior` une fois et renvoie `\{ top: scrollY \}` au lieu de faire défiler vers le haut.
4. **Après** la navigation — attend `page:finish`, puis réapplique le défilement pendant qu'un `ResizeObserver` capte les décalages de mise en page dus aux différentes longueurs de traduction.

`scrollToTop: false` est requis sur les pages où vous utilisez ce wrapper. Docs : [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

N'appelez pas `$switchLocale` directement sur les contrôles enveloppés — le wrapper gère le changement. Pour `<NuxtLink :to="$switchLocalePath('fr')">` en dehors du wrapper, le comportement de défilement suit le routage Nuxt normal, sauf si vous ajoutez votre propre `app/router.options.ts`.

## 🌐 Problèmes de traduction

### ❓ Pourquoi les traductions cassent-elles pendant les transitions de page, en particulier avec `defineAsyncComponent` ?

Lors de l'utilisation de `nuxt-i18n-micro` avec des transitions de page, les traductions peuvent brièvement cesser de fonctionner pendant la transition. Ce problème se produit parce que la route change avant que la transition ne se termine, ce qui provoque le chargement des traductions de la nouvelle page pendant que l'ancienne est encore visible.

**Cause racine :**

- Les transitions de page provoquent des changements de route avant que les traductions ne soient entièrement chargées
- `defineAsyncComponent` et `useAsyncData` peuvent retarder le chargement des traductions
- Les clés de traduction peuvent apparaître sous forme de chemins bruts pendant le chargement

**Solution 1 : fusion cumulative (intégrée, aucune config nécessaire)**

En v3, le module utilise automatiquement une stratégie de fusion cumulative. Lors de la navigation dans la même locale, les nouvelles traductions de page sont fusionnées dans le dictionnaire actif plutôt que de le remplacer. Cela signifie que les traductions de la page précédente restent disponibles pendant l'animation de transition. Une fois la transition terminée (hook `page:transition:finish`), les anciennes clés sont nettoyées automatiquement.

Aucune configuration n'est nécessaire — cela fonctionne d'emblée.

**Solution 2 : contexte de route explicite**

Si vous préférez un contrôle manuel, passez explicitement la route courante à `$_t` :

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Solution 3 : états de chargement**

Implémentez des états de chargement pour gérer élégamment le chargement des traductions :

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Pourquoi les clés de traduction ne se résolvent-elles pas pendant le SSR sur Vercel ?

**Limites de `$fetch` en SSR**
Sur des plateformes serverless comme Vercel, `$fetch` ne peut récupérer que des fichiers statiques depuis le CDN et non depuis le serveur Nitro interne. Cela signifie que les fichiers de traduction statiques peuvent ne pas être accessibles directement sauf si la bonne URL de base est définie.

**Correctif en définissant `apiBaseClientHost` et `apiBaseServerHost`**
Si les traductions sont hébergées en externe sur un CDN ou un domaine différent, utilisez `apiBaseClientHost` pour les requêtes côté client et `apiBaseServerHost` pour les requêtes côté serveur. `apiBaseUrl` ne doit contenir que le préfixe de chemin (par exemple, `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Ou via variables d'environnement :

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Les traductions seront récupérées depuis `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` à la fois côté client et côté serveur.

## 🔗 Problèmes de routage et de navigation

### ❓ Puis-je utiliser `NuxtLink` ou `<i18n-link>` directement dans les chaînes de traduction ?

Oui, `Nuxt I18n Micro` permet l'utilisation de `NuxtLink` ou `<i18n-link>` dans les traductions via le composant `<i18n-t>`, ce qui est particulièrement utile pour gérer la grammaire et les exigences des langues RTL sans avoir à découper les chaînes de traduction.

**Exemple :**

Fichier de traduction :

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Template Vue :

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Cela permet d'avoir des liens dynamiques dans les traductions tout en préservant une structure de localisation correcte.

## 🏗️ Problèmes de build et de déploiement

### ❓ Pourquoi les payloads de traduction se retrouvent-ils sous `public/_locales/` (ou dans le bundle serveur en Edge) ?

Le SSR et le client ont tous deux besoin des mêmes payloads `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. La façon dont ils sont conditionnés dépend de la cible Nitro :

**Explication :**

- **Node (par défaut) :** le module n'intègre **pas** les traductions comme `serverAssets` Nitro / `raw:` Rollup (cela faisait exploser la RAM de build sur les gros catalogues). À la place, il copie l'arbre premerged vers `public/<apiBaseUrl>/` (par défaut `_locales`) et le SSR lit ces fichiers avec `readFile`. Le client `$fetch` les mêmes URL — soit comme fichiers statiques, soit via le handler Nitro.
- **Edge** (`nitro.node === false`) : il n'y a pas de FS public durable pour le SSR, donc les payloads sont intégrés via les `serverAssets` Nitro (`assets:i18n`). Préférez `translationPayloads.mode: 'source'` pour que l'intégration reste compacte. Définissez `publicAssets: true` uniquement si vous avez également besoin d'une copie CDN/statique.
- **`prerenderRoutes` :** optionnel. En mode premerged, `publicAssets` écrit déjà `\{page\}/\{locale\}/data.json`, donc le prerender de ces routes est généralement redondant.

### ❓ Pourquoi ai-je une erreur de build faisant référence à `@unhead/vue` ou à un objet indéfini, en particulier sur Cloudflare Pages ?

**Cause :**
Certains projets rencontrent des conflits de build ou des dépendances manquantes lors de l'utilisation de `nuxt-i18n-micro`. En particulier :

- Les déploiements sur **Cloudflare Pages** ou **Cloudflare Workers** peuvent nécessiter des flags de compatibilité supplémentaires.
- Les étapes de prerender peuvent échouer si des dépendances comme `@unhead/vue` ne sont pas correctement installées.
- Certains modules (par exemple, **nuxthub**, **nitro-cloudflare-dev**) peuvent introduire des conflits sauf si configurés avec les bons flags ou dépendances.

**Solutions possibles :**

**Solution 1 : installer `@unhead/vue` manuellement**
Si l'erreur de build se plaint de ne pas trouver `@unhead/vue`, installez-le directement dans les dépendances de votre projet :

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Cela garantit qu'il est disponible pendant la phase de prerender Nitro.

**Solution 2 : ajouter les flags de compatibilité Cloudflare**
Lors de l'utilisation de Cloudflare Pages ou Cloudflare Workers, la compatibilité Node.js est souvent désactivée par défaut. Activez-la dans votre `wrangler.toml` :

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Ce flag permet à de nombreux modules Node.js (y compris ceux utilisés par `nuxt-i18n-micro`) de fonctionner sans problème.

## 🔍 SEO et `@nuxtjs/seo`

### ❓ Erreur : `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Cela se produit quand **`@nuxtjs/seo`** tire en dépendance une ancienne **`nuxt-site-config` 3.x** qui n'enregistre son plugin i18n que pour `@nuxtjs/i18n`, et non pour **nuxt-i18n-micro**.

**Correctif :**

1. Mettez à niveau vers **`@nuxtjs/seo` 3+** (inclut `nuxt-site-config` 4+ avec le support micro).
2. Placez **`nuxt-i18n-micro` avant `@nuxtjs/seo`** dans `modules`.
3. Conservez **`i18n.meta: true`** pour les balises head sensibles à la locale.

Voir le [guide SEO — section Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo) pour un exemple complet.

## 🔧 Configuration et compatibilité

### ❓ `Nuxt I18n Micro` est-il inspiré de `vue-i18n` ? Qu'en est-il des modificateurs ?

Bien que `Nuxt I18n Micro` serve d'alternative performante à `nuxt-i18n`, il est construit indépendamment de `vue-i18n`. Certains noms de méthodes et paramètres peuvent être similaires, mais les fonctionnalités sous-jacentes diffèrent significativement.

**Modificateurs** : le mainteneur a d'abord envisagé les modificateurs, mais a conclu que des composants comme `<i18n-t>` et `<i18n-link>` répondent efficacement à ces besoins.

Par exemple :

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Cette approche est flexible, si bien qu'il n'est actuellement pas nécessaire de publier des modificateurs. Cependant, des modificateurs pourraient être ajoutés dans les versions futures si la demande existe.
