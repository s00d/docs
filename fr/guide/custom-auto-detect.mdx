---
title: "Détection de locale personnalisée"
description: "Choisissez vous-même la locale — par domaine, en-tête ou profil utilisateur — avec un plugin serveur et useI18nLocale().setLocale()."
---

La détection intégrée lit l’URL, un cookie et `Accept-Language`. Lorsque la locale dépend d’autre chose — le domaine, un en-tête géographique défini par votre CDN, un profil utilisateur — définissez-la vous-même dans un plugin qui s’exécute avant le plugin i18n. Le module charge alors les traductions de cette locale et l’utilise pour les redirections exactement comme s’il l’avait détectée lui-même. Les règles qui déterminent quand une locale choisie l’emporte sur l’URL se trouvent sur [Détection de la locale](/fr/guide/locale-detection) ; cette page montre comment brancher votre propre source.

## Définir la locale dans un plugin serveur {#set-the-locale-in-a-server-plugin}

```ts
// plugins/i18n-locale.server.ts
export default defineNuxtPlugin({
  name: 'i18n-custom-locale',
  enforce: 'pre',
  order: -10, // before the i18n plugin (order -5)
  setup() {
    const { setLocale } = useI18nLocale()
    const host = (useRequestHeaders(['host']).host ?? '').split(':')[0]! // without the port

    if (host.endsWith('.de')) setLocale('de')
    else if (host.endsWith('.fr')) setLocale('fr')
  },
})
```

`setLocale(code)` écrit l’état de la locale (`useState('i18n-locale')`) et, lorsqu’un cookie de locale est configuré, le cookie. Utilisez-le plutôt que d’écrire vous-même `useState` ou `useCookie`. Ne passez que des codes de locales activées.

Gardez le plugin en `.server.ts` lorsqu’il lit des en-têtes de requête : ils n’existent pas dans le navigateur. Un plugin `.client.ts` est l’endroit adapté pour les sources propres au navigateur comme `localStorage`.

## Désactiver l’étape Accept-Language intégrée {#turn-off-the-built-in-accept-language-step}

Votre plugin et `Accept-Language` peuvent ne pas être d’accord. Pour laisser uniquement votre code (plus l’URL et le cookie) décider, désactivez l’en-tête :

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    autoDetectLanguage: false,
  },
})
```

[`autoDetectLanguage`](/fr/api/module-options#autodetectlanguage) ne contrôle que l’étape de l’en-tête. L’URL et un cookie valide comptent toujours.

## Ce qui se passe ensuite {#what-happens-next}

L’effet de `setLocale` dépend de la [stratégie](/fr/guide/strategy) :

| Stratégie | Effet de `setLocale('de')` dans le plugin |
| --- | --- |
| `no_prefix` | La page s’affiche en allemand ; l’URL ne change pas. |
| `prefix`, `prefix_except_default` | Sur un chemin sans préfixe où [`autoDetectPath`](/fr/api/module-options#autodetectpath) autorise les redirections (par défaut uniquement `/`), le serveur répond `302` vers l’URL allemande. Une URL avec un préfixe de locale le conserve. |
| `prefix_and_default` | Pas de redirection : l’URL sans préfixe est une page valide de la locale par défaut. |

Avec les stratégies à préfixe, une locale présente dans l’URL est le choix de l’utilisateur et votre plugin ne la remplace pas. `autoDetectPath: '*'` est l’exception : le serveur redirige alors les URL préfixées selon le cookie et `Accept-Language` et ignore l’état, mais `setLocale()` écrit aussi le cookie lorsqu’il est configuré, donc dès la requête suivante le choix de votre plugin peut rediriger une URL préfixée. Conservez `'/'` ou utilisez `'no_prefix'` lorsque les URL de locale explicites doivent l’emporter. Utilisez votre plugin pour choisir où un visiteur arrive, pas pour réécrire les liens qu’il a suivis.

## Respecter la locale choisie par l’utilisateur {#respect-a-locale-the-user-picked}

Dès qu’un utilisateur change de langue, ce changement écrit le cookie. Ignorez votre propre détection lorsqu’une préférence valide existe déjà :

```ts
// plugins/i18n-locale.server.ts
import { detectLocaleFromAcceptLanguage } from '@i18n-micro/utils/accept-language'

export default defineNuxtPlugin({
  name: 'i18n-custom-locale',
  enforce: 'pre',
  order: -10,
  setup() {
    const { getPreferredLocale, setLocale, validLocales } = useI18nLocale()
    if (getPreferredLocale()) return // valid state or cookie: keep it

    const country = useRequestHeaders(['x-country'])['x-country']
    if (country === 'JP') return setLocale('ja')

    const header = useRequestHeaders(['accept-language'])['accept-language']
    setLocale(detectLocaleFromAcceptLanguage(header, validLocales))
  },
})
```

`getPreferredLocale()` ne renvoie l’état ou le cookie que s’il s’agit d’une locale activée, de sorte qu’un cookie obsolète n’empêche pas la détection. `detectLocaleFromAcceptLanguage` est le comparateur tenant compte des valeurs q que le module utilise lui-même (installez `@i18n-micro/utils` pour l’importer) ; `setLocale(null)` ne fait rien.

## Un domaine par locale {#one-domain-per-locale}

Si chaque domaine doit servir ses propres locales, vous n’avez pas besoin de plugin : donnez à chaque locale un `baseUrl`, définissez `baseDefault: true` sur la locale par défaut de chaque domaine, et faites un seul build (un site statique exécute tout de même `nuxi generate` par domaine). Voir [Layers et domaines](/fr/guide/layers#multiple-domains).
