`@i18n-micro/node` est l’instance [runtime](/fr/integrations/runtime-package) accompagnée d’un loader qui lit un dossier de traduction depuis le disque. Utilisez-le dans un serveur Express ou Fastify, une CLI, un générateur d’e-mails ou de PDF, ou tout script qui a besoin des mêmes fichiers JSON que votre application Nuxt. Vous chargez les fichiers une seule fois et traduisez par requête sans partager d’état mutable entre les requêtes.

## Installation {#install}

<CodeGroup>

```bash pnpm
pnpm add @i18n-micro/node @i18n-micro/utils
```

```bash npm
npm install @i18n-micro/node @i18n-micro/utils
```

```bash yarn
yarn add @i18n-micro/node @i18n-micro/utils
```

</CodeGroup>

Aucune dépendance peer ; Node.js `>=20`. `@i18n-micro/utils` n’est nécessaire que pour le helper `Accept-Language` ci-dessous.

## Configuration {#setup}

Le loader lit l’[organisation des dossiers de Nuxt](/fr/guide/translations) : `locales/en.json` est un dictionnaire racine, `locales/pages/blog/post/en.json` appartient à la route `blog-post`.

```ts
import { createI18n } from '@i18n-micro/node'

const i18n = createI18n({ locale: 'en', fallbackLocale: 'en', translationDir: './locales' })
await i18n.loadTranslations()

i18n.t('greeting', { name: 'Ada' }) // 'Hello, Ada!'
i18n.t('title', undefined, undefined, 'blog-post') // from locales/pages/blog/post/en.json
```

Les options sont celles du runtime (voir [l’instance](/fr/integrations/overview#the-instance)) plus `translationDir` et `disablePageLocales` (traiter les fichiers `pages/**` comme des dictionnaires racine). `i18n.reload()` vide tous les dictionnaires et relit le dossier, pour un watcher de fichiers en développement.

`loadTranslations(dir, disablePageLocales?)` est aussi exporté séparément et renvoie `{ root, routes }` :

```ts
import { loadTranslations } from '@i18n-micro/node'

const { root, routes } = await loadTranslations('./locales')
// root:   { en: {...}, de: {...} }
// routes: { 'blog-post': { en: {...}, de: {...} } }
```

## Par requête {#per-request}

Une instance contient une locale et une route. Changer `i18n.locale` sur une instance partagée dans un gestionnaire de requête crée une concurrence avec les requêtes simultanées. `run` donne à une requête sa propre instance :

```ts
const i18n = createI18n({ locale: 'en', fallbackLocale: 'en', translationDir: './locales' })
await i18n.loadTranslations()

// `() => next()`: `run` hands its callback the fork, and Express reads an argument of `next` as an error
app.use((req, res, next) => i18n.run(pickLocale(req), () => next()))

app.get('/', (req, res) => {
  res.send(i18n.t('greeting')) // the request's locale, in everything it awaits
})
```

Dans `run`, l’instance partagée lit et définit la locale et la route de la requête (`AsyncLocalStorage`) ; le fork démarre sur la route courante, et `i18n.setRoute(...)` dans le callback modifie la route de cette requête. Le callback reçoit aussi le fork de la requête : les dictionnaires qui y sont écrits restent dans la requête, ceux écrits dans l’instance partagée atteignent tout le monde.

Sans `AsyncLocalStorage`, `i18n.fork(locale)` renvoie le même type d’instance, à faire circuler.

`reload()` relit le répertoire ; les anciens dictionnaires répondent jusqu’à ce que les nouveaux soient chargés.

## Choisir la locale {#pick-the-locale}

`detectLocaleFromAcceptLanguage(header, locales)` respecte les poids `q` et fait correspondre `de-DE` à une locale `de` (et `de` à `de-DE`). Elle renvoie `null` lorsque rien ne correspond.

```ts
import express from 'express'
import { detectLocaleFromAcceptLanguage } from '@i18n-micro/utils/accept-language'

const app = express()

app.get('/hello', (req, res) => {
  const locale = detectLocaleFromAcceptLanguage(req.headers['accept-language'], locales) ?? 'en'
  const i18n = byLocale.get(locale)!
  res.json({ message: i18n.t('greeting', { name: 'Ada' }) })
})
```

Pour combiner préfixe d’URL, cookie et en-tête, `resolveLocale({ defaultLocale, validLocales, url, cookie, acceptLanguage, autoDetectLanguage: true })` de `@i18n-micro/utils/resolve-locale` applique l’ordre de priorité du module : l’URL, puis le cookie, puis `Accept-Language`, puis la valeur par défaut. Les valeurs invalides sont ignorées.

Dans une application Nuxt, vous n’avez pas besoin de ce package côté serveur : utilisez les [traductions côté serveur](/fr/guide/server-side-translations) du module.

## API {#api}

| Export | Remarques |
| --- | --- |
| `createI18n(options)`, `I18n` | instance runtime + `translationDir`, `loadTranslations(dir?)`, `reload()` |
| `loadTranslations(dir, disablePageLocales?)` | `{ root, routes }` |
| `loadRootTranslations(dir, disablePageLocales?)` | `root` uniquement |
| `FormatService`, `interpolate` | depuis core |
| Types : `I18nOptions`, `LoadedTranslations`, `Translations`, `Locale`, `PluralFunc`, `Params` | |

Les méthodes de l’instance sont listées dans [Runtime](/fr/integrations/runtime-package#api). Signatures complètes : [référence du package](/fr/api/packages/node).
