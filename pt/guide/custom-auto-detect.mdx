---
title: "Deteção de locale personalizada"
description: "Escolha o locale por si — por domínio, cabeçalho ou perfil de utilizador — com um plugin de servidor e useI18nLocale().setLocale()."
---

A deteção incorporada lê o URL, um cookie e `Accept-Language`. Quando o locale depende de outra coisa — o domínio, um cabeçalho de geolocalização definido pela sua CDN, um perfil de utilizador — defina-o por si num plugin que corra antes do plugin de i18n. O módulo carrega então as traduções desse locale e usa-o nos redirecionamentos exatamente como se o tivesse detetado. As regras que decidem quando um locale escolhido prevalece sobre o URL estão em [Deteção de locale](/pt/guide/locale-detection); esta página mostra como ligar a sua própria fonte.

## Definir o locale num plugin de servidor {#set-the-locale-in-a-server-plugin}

```ts
// plugins/i18n-locale.server.ts
export default defineNuxtPlugin({
  name: 'i18n-custom-locale',
  enforce: 'pre',
  order: -10, // before the i18n plugin (order -5)
  setup() {
    const { setLocale } = useI18nLocale()
    const host = (useRequestHeaders(['host']).host ?? '').split(':')[0]! // without the port

    if (host.endsWith('.de')) setLocale('de')
    else if (host.endsWith('.fr')) setLocale('fr')
  },
})
```

`setLocale(code)` escreve o estado do locale (`useState('i18n-locale')`) e, quando está configurado um cookie de locale, o cookie. Use-o em vez de escrever `useState` ou `useCookie` por si. Passe apenas códigos de locales ativos.

Mantenha o plugin como `.server.ts` quando lê cabeçalhos do pedido: estes não existem no navegador. Um plugin `.client.ts` é o local para fontes exclusivas do navegador, como `localStorage`.

## Desativar o passo Accept-Language incorporado {#turn-off-the-built-in-accept-language-step}

O seu plugin e `Accept-Language` podem discordar. Para que apenas o seu código (mais o URL e o cookie) decida, desative o cabeçalho:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    autoDetectLanguage: false,
  },
})
```

[`autoDetectLanguage`](/pt/api/module-options#autodetectlanguage) controla apenas o passo do cabeçalho. O URL e um cookie válido continuam a contar.

## O que acontece a seguir {#what-happens-next}

O efeito de `setLocale` depende da [estratégia](/pt/guide/strategy):

| Estratégia | Efeito de `setLocale('de')` no plugin |
| --- | --- |
| `no_prefix` | A página é apresentada em alemão; o URL não muda. |
| `prefix`, `prefix_except_default` | Num caminho sem prefixo onde [`autoDetectPath`](/pt/api/module-options#autodetectpath) permite redirecionamentos (por omissão apenas `/`), o servidor responde `302` para o URL em alemão. Um URL com prefixo de locale mantém-no. |
| `prefix_and_default` | Sem redirecionamento: o URL sem prefixo é uma página válida do locale por omissão. |

Com as estratégias de prefixo, um locale no URL é a escolha do utilizador e o seu plugin não o substitui. `autoDetectPath: '*'` é a exceção: o servidor passa então a mover URLs com prefixo com base no cookie e em `Accept-Language` e ignora o estado, mas `setLocale()` também escreve o cookie quando há um configurado, pelo que a partir do pedido seguinte a escolha do seu plugin pode redirecionar um URL com prefixo. Mantenha `'/'` ou use `'no_prefix'` quando os URLs com locale explícito tiverem de prevalecer. Use o seu plugin para escolher onde um visitante chega, não para reescrever links que ele seguiu.

## Respeitar um locale escolhido pelo utilizador {#respect-a-locale-the-user-picked}

Quando um utilizador muda de idioma, a mudança escreve o cookie. Ignore a sua própria deteção quando já existe uma preferência válida:

```ts
// plugins/i18n-locale.server.ts
import { detectLocaleFromAcceptLanguage } from '@i18n-micro/utils/accept-language'

export default defineNuxtPlugin({
  name: 'i18n-custom-locale',
  enforce: 'pre',
  order: -10,
  setup() {
    const { getPreferredLocale, setLocale, validLocales } = useI18nLocale()
    if (getPreferredLocale()) return // valid state or cookie: keep it

    const country = useRequestHeaders(['x-country'])['x-country']
    if (country === 'JP') return setLocale('ja')

    const header = useRequestHeaders(['accept-language'])['accept-language']
    setLocale(detectLocaleFromAcceptLanguage(header, validLocales))
  },
})
```

`getPreferredLocale()` devolve o estado ou o cookie apenas quando se trata de um locale ativo, pelo que um cookie desatualizado não impede a deteção. `detectLocaleFromAcceptLanguage` é o comparador sensível a valores q que o próprio módulo usa (instale `@i18n-micro/utils` para o importar); `setLocale(null)` não faz nada.

## Um domínio por locale {#one-domain-per-locale}

Se cada domínio deve servir os seus próprios locales, não precisa de um plugin: dê a cada locale um `baseUrl`, defina `baseDefault: true` no locale por omissão de cada domínio e faça o build uma vez (um site estático continua a executar `nuxi generate` por domínio). Consulte [Camadas e domínios](/pt/guide/layers#multiple-domains).
