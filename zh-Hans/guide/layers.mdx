一个 Nuxt 层可以为多个应用承载 i18n 配置和 `locales/` 文件夹，每个应用再添加或覆盖自己需要的内容。本页演示这一做法，以及如何用一次构建服务多个域名。

## 共享配置与翻译 {#share-config-and-translations}

```ts
// base/nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    locales: [
      { code: 'en', iso: 'en-US' },
      { code: 'de', iso: 'de-DE' },
      { code: 'fr', iso: 'fr-FR' },
    ],
    defaultLocale: 'en',
  },
})
```

```ts
// shop/nuxt.config.ts
export default defineNuxtConfig({
  extends: ['../base'], // a layer directory or package, not a nuxt.config file
  i18n: {
    locales: [
      { code: 'es', iso: 'es-ES' }, // added
      { code: 'fr', disabled: true }, // the base layer's fr, switched off here
    ],
  },
})
```

- **配置：** 应用中的标量选项会替换层中的选项。所有层的 `locales` 数组会合并在一起，`code` 相同的条目会合并为一个，以应用的字段为准，因此应用可以添加 locale，或在继承的 locale 上设置 `disabled: true` 等字段。
- **翻译：** 每个层的 `locales/` 会按键合并，先合并层，最后合并应用，因此 `shop/locales/en.json` 中的键会覆盖 `base/locales/en.json` 中的同名键。页面文件（`locales/pages/<page>/`）也以同样的方式合并。
- **页面：** 会从每个层的页面中读取 `$defineI18nRoute`。

要合并不属于任何层的文件夹，请在 [`additionalTranslationDirs`](/zh-Hans/api/module-options#additionaltranslationdirs) 中列出它们。

## 多域名 {#multiple-domains}

一次构建即可服务所有域名。为每个 locale 列出其域名；`baseDefault` 会让它成为该主机的默认 locale：

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    strategy: 'prefix_except_default',
    defaultLocale: 'en',
    locales: [
      { code: 'en', iso: 'en-US', baseUrl: 'https://example.com', baseDefault: true },
      { code: 'de', iso: 'de-DE', baseUrl: 'https://example.de', baseDefault: true },
      { code: 'nl', iso: 'nl-NL', baseUrl: 'https://example.de' },
      { code: 'fr', iso: 'fr-FR' },
    ],
  },
})
```

把两个域名都指向同一台服务器。其余的由请求的主机决定：

- **默认 locale：** 该主机的 `baseDefault` locale。若没有，则在主机提供构建默认 locale 时使用它，否则使用该主机的第一个 locale。
- **提供的 locale：** 该主机的 locale，加上所有未设置 `baseUrl` 的 locale。在 `example.de` 上即 `de`、`nl` 和 `fr`。
- **其他域名的 locale** 是链接目标。`$localePath`、`$localeRoute`、`$switchLocalePath`、`<i18n-switcher>` 和 `hreflang` 会给出其 `baseUrl` 上的绝对 URL，`$switchLocale` 会导航过去。在本主机上它们的 URL 返回 404，cookie 或 `Accept-Language` 都无法选中它们。
- **指向其他域名的链接**需通过 `$localePath` 或 `<i18n-link>`：`<NuxtLink :to="$localePath('/contact', 'de')">`、`<i18n-link :to="$localeRoute('/contact', 'de')">`。路由器不接受绝对地址对象，因此 `<NuxtLink :to="$localeRoute(...)">` 和 `router.push($localeRoute(...))` 会留在当前源上。在 `localhost` 或预览主机上，每个设置了 `baseUrl` 的 locale 都是这种链接，包括当前 locale。在代码中请使用 `navigateTo($localePath('/contact', 'de'), { external: true })` 或 `$switchRoute`。
- **其他任何主机**都使用构建配置，每个设置了 `baseUrl` 的 locale 都作为链接目标。不会回显请求中的任何内容：canonical 和 `hreflang` 使用 `metaBaseUrl`，否则使用构建默认 locale 的 `baseUrl`（未设置 `baseUrl` 的默认 locale 需要 `metaBaseUrl` 或 `site.url`，参见 [SEO](/zh-Hans/guide/seo#set-the-public-origin)）。
- `public/` 中的 **payload 文件**是静态的：任何主机都会返回任何 locale 的文件。按域名[生成](/zh-Hans/guide/deployment#static-site-(nuxi-generate))只会发布该域名的文件。

各策略下的 `example.de`，其中 `de: '/kontakt'` 是 `contact` 的自定义路径：

| 策略 | `/` | 默认 locale 的页面 | 其他 URL |
| --- | --- | --- | --- |
| `prefix_except_default` | `de` | `/kontakt` | `/de/kontakt` 和 `/en/contact` 返回 404，`/contact` 重定向到 `/kontakt` |
| `prefix_and_default` | `de` | `/kontakt` 和 `/de/kontakt`，链接使用 `/kontakt` | `/en/contact` 和 `/contact` 返回 404 |
| `prefix` | 重定向到 `/de` | `/de/kontakt` | `/kontakt` 重定向到 `/de/kontakt`，`/en/contact` 返回 404 |
| `no_prefix` | `de` | `/kontakt` | 其他域名上某个 locale 的自定义路径返回 404 |

在 `prefix` 下，来自其他域名的链接会保留前缀，因为不带前缀的 URL 只会重定向。在 `no_prefix` 下，指向其他域名的链接会落在该主机的默认 locale 上：URL 无法指定第二个 locale。

需要注意的事项：

- **在代理之后**，主机来自 `Host`。如果代理把公开主机放在 `X-Forwarded-Host` 中，请设置 [`trustForwardedHost`](/zh-Hans/api/module-options#trustforwardedhost)，且仅在代理会覆盖该请求头时才这样做。两者都不发送的代理无法服务按域名构建的应用。参见[在代理或 CDN 之后](/zh-Hans/guide/deployment#behind-a-proxy-or-cdn)。
- **`app.baseURL`** 也要写进 `baseUrl`：`baseUrl: 'https://example.de/shop'` 配合 `app.baseURL: '/shop'`。
- **主机必须完全匹配。** `www.example.de` 是另一个主机：请在边缘层重定向它，或在 locale 上设置该 `baseUrl`。每个 locale 只能有一个主机。
- **缓存必须以主机为键。** CDN 通常会这样做。Nitro 的路由缓存以路径为键，因此在按域名构建中，模块会把 `host` 添加到每条 `swr` 和 `cache` 规则的 `cache.varies` 中，启用 `trustForwardedHost` 时还会添加 `x-forwarded-host`。设置了 `cache: false` 的规则保持原样。`isr` 使用平台的缓存：请确认它以主机为键。
- **两个主机默认 locale 的自定义路径不能冲突。** 不带前缀的记录共用同一个路由器，因此 `/x` 不能在 `example.de` 上是一个页面、在 `example.com` 上是另一个页面。
- **预渲染页面：** 在 `nuxt build` 中，`prerender: true` 路由规则只渲染一次，不带主机，生成的文件会响应所有域名。请把因域名而异的页面交给服务器处理，或[按域名生成](/zh-Hans/guide/deployment#static-site-(nuxi-generate))。
- **`noPrefixRedirect`** 在每个主机上都依据主机和访问者的 locale。
- **`hashMode`：** 主机按上述方式选择渲染内容，指向其他域名的链接把路由放在 hash 中（`https://example.com/#/contact`）。
- **`ssr: false`：** 浏览器从 `location.host` 读取域名，因此没有服务器的主机也能解析。
- **[运行时覆盖](/zh-Hans/guide/runtime-overrides)**最先生效。运行时 `disabledLocales` 在每个主机上都有效，但有一个例外：在 `prefix_except_default` 和 `prefix_and_default` 下，主机的默认 locale 在其主机上保持启用，因为它的页面就是不带前缀的记录。在 `prefix` 和 `no_prefix` 下，主机会退回到它提供的下一个 locale。运行时 `defaultLocale` 只对未知主机生效。

对于[静态站点](/zh-Hans/guide/deployment#static-site-(nuxi-generate))，请为每个域名生成一次。

### 每个域名一个应用 {#one-app-per-domain}

当各域名需要不同的页面或模块时，仍然可以使用一个共享层加上每个域名一个小应用的方式。每个应用在同一份 `locales` 列表之上设置自己的 `defaultLocale`。如上所述，其他域名上的 locale 在该应用中返回 404。

### 在代码中选择 locale {#choosing-the-locale-in-code}

如果要让单个实例响应所有域名，并在 SEO 标签中使用请求自身的源，请参见 [SEO](/zh-Hans/guide/seo#set-the-public-origin)；如果要在代码中根据主机选择 locale，请参见[自定义 locale 检测](/zh-Hans/guide/custom-auto-detect)。
