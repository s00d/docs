# 选项详情

本模块提供了丰富的配置选项,用以定制你的国际化方案。

### 🌍 核心语言设置

#### `locales`

{/* generated:option:locales — do not edit; run `pnpm run docs:generate` */}

**类型** `Locale[]` · **默认值** `[]`

支持的语言列表。
每个条目定义一个语言代码及可选元数据(ISO、方向、显示名等)。

{/* /generated:option:locales */}

每个 locale 对象支持:

| 属性         | 类型      | 是否必填 | 说明                                           |
| ---------------- | --------- | -------- | ----------------------------------------------------- |
| `code`           | `string`  | ✅       | 唯一标识(例如 `'en'`)                      |
| `displayName`    | `string`  | ❌       | 用于切换器的可读名称(例如 `'English'`) |
| `iso`            | `string`  | ❌       | ISO 代码(例如 `'en-US'`)                            |
| `dir`            | `string`  | ❌       | 文字方向(`'ltr'` 或 `'rtl'`)                   |
| `disabled`       | `boolean` | ❌       | 为 `true` 时在下拉框中禁用                         |
| `baseUrl`        | `string`  | ❌       | 按语言的域名基础 URL                  |
| `baseDefault`    | `boolean` | ❌       | 从 URL 中移除语言前缀                        |
| `fallbackLocale` | `string`  | ❌       | 按语言的回退(覆盖全局)                |
| `[key: string]`  | `unknown` | ❌       | 任意自定义属性(见下文)                     |

**示例**:

```typescript
locales: [
  { code: 'en', iso: 'en-US', dir: 'ltr' },
  { code: 'fr', iso: 'fr-FR', dir: 'ltr' },
  { code: 'ar', iso: 'ar-SA', dir: 'rtl', disabled: true },
  {
    code: 'de',
    iso: 'de-DE',
    dir: 'ltr',
    baseUrl: 'https://de.example.com',
    baseDefault: true,
  },
]
```

<Warning>
使用 `baseUrl` 可能导致内部路由被复制为外部链接,增加路由与维护的复杂度。可以考虑直接为特定语言创建外部链接。
</Warning>

#### 自定义 Locale 属性

你可以为 locale 对象添加任意自定义属性。这些属性会传递到运行时,并可通过 `$getLocales()` 访问:

```typescript
locales: [
  { code: 'en', iso: 'en-US', flag: '🇬🇧', currency: 'GBP' },
  { code: 'de', iso: 'de-DE', flag: '🇩🇪', currency: 'EUR' },
  { code: 'ru', iso: 'ru-RU', flag: '🇷🇺', currency: 'RUB' },
]
```

在组件中访问它们:

```vue
<template>
  <ul>
    <li v-for="locale in $getLocales()" :key="locale.code">{{ locale.flag }} {{ locale.displayName }} ({{ locale.currency }})</li>
  </ul>
</template>
```

默认情况下,自定义属性的类型为 `unknown`。若要获得完整的 TypeScript 支持,请使用**模块扩充**(module augmentation)。创建一个声明文件(例如 `app/i18n.d.ts`,或任何被 `tsconfig` 包含的 `.d.ts`):

```typescript
// app/i18n.d.ts
declare module '@i18n-micro/types' {
  interface Locale {
    flag?: string
    currency?: string
  }
}
```

此后,所有自定义属性都会拥有完整类型:

```typescript
const locales = $getLocales()
locales[0].flag // string | undefined ✅
locales[0].currency // string | undefined ✅
```

</Tip>
#### `defaultLocale`

{/* generated:option:defaultLocale — do not edit; run `pnpm run docs:generate` */}

**类型** `string` · **默认值** `'en'`

当无法从 URL 或用户偏好确定语言时使用的语言。
在未设置 `fallbackLocale` 时,也会作为缺失翻译的回退语言。

{/* /generated:option:defaultLocale */}

```typescript
defaultLocale: 'en'
```
#### `strategy`

{/* generated:option:strategy — do not edit; run `pnpm run docs:generate` */}

**类型** `Strategies` · **默认值** `'prefix_except_default'`

用于语言前缀的 URL 路由策略。

- `'no_prefix'` —— URL 中不带语言;语言存储在 Cookie 中。
- `'prefix_except_default'` —— 为除默认语言外的所有语言添加前缀。
- `'prefix'` —— 始终添加前缀,包括默认语言。
- `'prefix_and_default'` —— 与 `prefix` 类似,但默认语言也可通过无前缀方式访问。

{/* /generated:option:strategy */}

<CodeGroup>
```typescript no_prefix
strategy: 'no_prefix'
// Routes: /about, /contact
// Locale detection via browser/cookies
```

```typescript prefix_except_default
strategy: 'prefix_except_default'
// Default locale: /about, /contact
// Other locales: /fr/about, /de/contact
```

```typescript prefix
strategy: 'prefix'
// All locales: /en/about, /fr/about, /de/about
```

```typescript prefix_and_default
strategy: 'prefix_and_default'
// Both prefixed and non-prefixed versions for default locale
```
</CodeGroup>

### 📂 翻译管理
#### `translationDir`

{/* generated:option:translationDir — do not edit; run `pnpm run docs:generate` */}

**类型** `string` · **默认值** `'locales'`

相对项目根目录的翻译 JSON 文件目录路径。

{/* /generated:option:translationDir */}

```typescript
translationDir: 'i18n' // Custom directory
// Nuxt 4 colocation example:
// translationDir: 'app/locales'
```

路径从 Nuxt 的**项目根目录**(`rootDir`)开始解析,而不是从 `app/`。在 Nuxt 4 中,常见的做法是将路由放在 `app/pages/`,JSON 文件放在 `locales/`(或设置了 `translationDir` 时的 `app/locales`)。
#### `disablePageLocales`

{/* generated:option:disablePageLocales — do not edit; run `pnpm run docs:generate` */}

**类型** `boolean` · **默认值** `false`

禁用按页面的翻译文件。
当 `true` 时,只加载全局翻译(`\{locale\}.json`);
不会生成或加载页面级文件(`pages/\{page\}/\{locale\}.json`)。

{/* /generated:option:disablePageLocales */}

启用后,只会使用根级翻译文件:

```tree
locales/
├── en.json
├── fr.json
└── ar.json
```
#### `fallbackLocale`

{/* generated:option:fallbackLocale — do not edit; run `pnpm run docs:generate` */}

**类型** `string` · **默认值** `undefined(无回退;返回原始键)`

全局回退语言代码。
当活动语言中缺少某个翻译键时,模块会先在此语言中查找,再回退为返回该键本身。

{/* /generated:option:fallbackLocale */}

```typescript
fallbackLocale: 'en' // Global fallback
```
#### `types`

{/* generated:option:types — do not edit; run `pnpm run docs:generate` */}

**类型** `boolean` · **默认值** `true`

基于默认语言文件中的翻译键,为 `useI18n`、`$t` 及相关辅助函数生成 TypeScript 类型声明。

{/* /generated:option:types */}

启用后,构建期间模块会输出带有翻译键类型的 `.nuxt/i18n.d.ts`。若你偏好使用无类型的辅助函数或使用外部生成器,请设为 `false`。

此内置生成器与可选的 [`@i18n-micro/types-generator`](/integrations/types-generator) 包相互独立,后者可为 monorepo 与 CI 生成更严格或独立的类型文件。

```typescript
types: false // Disable built-in key typing
```
#### `routeLocales`

{/* generated:option:routeLocales — do not edit; run `pnpm run docs:generate` */}

**类型** `Record<string, string[]>` · **默认值** —

从 `defineI18nRoute()` 调用中提取的按路由的语言限制。
将路由路径(例如 `'/about'`)映射到允许的语言代码数组。
未列出的路由不受限制(允许所有语言)。

{/* /generated:option:routeLocales */}

将路由路径(例如 `'/about'`)映射到允许的语言代码。未列出的路由允许所有已配置的语言。

通常你会在页面中通过 [`defineI18nRoute`](/guides/custom-locale-routes) 配置此项,而不是在 `nuxt.config` 中。模块会在构建期将页面级声明合并到该映射中。
#### `routeDisableMeta`

{/* generated:option:routeDisableMeta — do not edit; run `pnpm run docs:generate` */}

**类型** `Record<string, boolean \| string[]>` · **默认值** —

从 `defineI18nRoute()` 调用中提取的按路由的 meta 禁用配置。
将路由路径映射为 `true`(禁用所有 meta),或一个用于禁用 meta 的语言代码数组。

{/* /generated:option:routeDisableMeta */}

- `true` —— 禁用该路由的所有 SEO meta
- `string[]` —— 只对列出的语言代码禁用 meta

与 `routeLocales` 类似,该项通常在页面组件中设置,而不是手动写入配置。
#### `experimental`

{/* generated:option:experimental — do not edit; run `pnpm run docs:generate` */}

**类型** `Record<string, unknown>` · **默认值** —

实验性/不稳定选项的容器。
其内容可能在小版本之间不作通知地更改或移除。

{/* /generated:option:experimental */}

在 v3 中,大多数原先的 `experimental.*` 标志已被提升为顶层选项(例如 `hmr`)。请优先使用已记录的顶层选项。只在遵循引用了特定键的发布说明或迁移指南时,才使用 `experimental`。

### 🔍 SEO 与 Meta 标签
#### `meta`

{/* generated:option:meta — do not edit; run `pnpm run docs:generate` */}

**类型** `boolean` · **默认值** `true`

自动生成 SEO 元标签(`hreflang`、`canonical`、`og:url`、`og:locale`)。

{/* /generated:option:meta */}

```typescript
meta: true // Generate alternate links, canonical URLs, etc.
```
#### `metaBaseUrl`

{/* generated:option:metaBaseUrl — do not edit; run `pnpm run docs:generate` */}

**类型** `string` · **默认值** `undefined`

用于 SEO 元标签(canonical、og:url、hreflang)的基础 URL。

- 具体的 URL 字符串(例如 `'https://example.com'`)—— 原样使用(最高优先级)。
- `undefined` —— 若存在 `nuxt-site-config`,则回退到其 `site.url`;否则回退到当前请求来源
  (服务端为 `useRequestURL().origin`,客户端为 `window.location.origin`)。

### 🔢 自定义
#### `plural`

{/* generated:option:plural — do not edit; run `pnpm run docs:generate` */}

**类型** `PluralFunc` · **默认值** `内置复数处理(按数量选择表单索引)`

自定义复数处理函数。
接收 `(key, count, params, locale, getter)`,应以字符串形式返回所选的复数形式,
或返回 `null` / `undefined` 以回退到内置的 `defaultPlural` 逻辑
(这样便可只覆盖部分语言)。

对于 Nuxt 模块,该函数会通过 `.toString()` 序列化到 `.nuxt/i18n.plural.mjs` ——
它必须是自包含的(不能有 import / 外部作用域引用)。
**不支持**传入文件路径字符串。

{/* /generated:option:plural */}

##### 工作原理

翻译使用 `|` 分隔各复数形式:

```json
{
  "apples": "no apples | one apple | {count} apples"
}
```

当某种形式需要在 `\{count\}` 之外的更多参数时,使用 `$tc('apples', count)` 或 `$tc('cart', \{ count, name \})` —— **将 `count` 与其他参数放在第二个参数的对象中传入**,不要作为第三个参数(第三个参数仅表示 `defaultValue`)。

调用 `$tc` 会触发 `plural` 函数,该函数会:

1. 调用 `t(key)` 获得原始翻译字符串(例如 `"no apples | one apple | \{count\} apples"`)
2. 以 `|` 拆分得到形式数组
3. 基于 `count` 选择某个形式
4. 用实际数字替换 `\{count\}`

**默认**实现按索引选择:`count < forms.length ? forms[count] : forms[last]`。这适用于简单情况(0 → 第一种,1 → 第二种,2+ → 最后一种)。

##### 自定义复数处理函数

对于复数规则复杂的语言(例如俄语、阿拉伯语、波兰语),请覆盖 `plural` 选项。

<Danger>
该函数会通过 `.toString()` 序列化,并在构建期注入到一个虚拟模块中。这意味着:

- **必须使用 `function` 关键字** —— 不能用方法简写形式,也不能使用带外部引用的箭头函数
- **不能有 import 或外部引用** —— 该函数必须完全自包含(**不支持**类似 `plural: '~/i18n/plural.ts'` 的文件路径)
- **不能包含无法通过 `.toString()` 保留的 TypeScript 特有语法**(在 `nuxt.config.ts` 中的类型注解没问题,Nuxt 会将其剥离)
- 返回 `null` / `undefined` 会回退到内置的 `defaultPlural`(适合按语言覆盖)
</Danger>

**示例:俄语复数**(4 种形式:zero、one、few、many):

```typescript
// nuxt.config.ts
export default defineNuxtConfig({
  i18n: {
    plural: function (key, count, _params, _locale, t) {
      const translation = t(key)
      if (!translation) return key

      const forms = translation
        .toString()
        .split('|')
        .map(function (s) {
          return s.trim()
        })
      let idx

      if (count === 0) {
        idx = 0
      } else {
        const mod10 = count % 10
        const mod100 = count % 100
        if (mod10 === 1 && mod100 !== 11) {
          idx = 1
        } else if (mod10 >= 2 && mod10 <= 4 && (mod100 < 10 || mod100 >= 20)) {
          idx = 2
        } else {
          idx = 3
        }
      }

      if (idx >= forms.length) idx = forms.length - 1
      return (forms[idx] || '').replace('{count}', String(count))
    },
  },
})
```

配合以下翻译:

```json
{
  "apples": "нет яблок | {count} яблоко | {count} яблока | {count} яблок"
}
```

结果:

- `$tc('apples', 0)` → `"нет яблок"`
- `$tc('apples', 1)` → `"1 яблоко"`
- `$tc('apples', 3)` → `"3 яблока"`
- `$tc('apples', 5)` → `"5 яблок"`
- `$tc('apples', 21)` → `"21 яблоко"`

**示例:简单的英文(默认行为)**:

```typescript
// This is the built-in default — you don't need to set it explicitly
plural: function (key, count, params, _locale, t) {
  const translation = t(key, params)
  if (!translation) return null

  const forms = translation.toString().split('|')
  if (forms.length === 0) return null
  const form = count < forms.length ? forms[count] : forms[forms.length - 1]
  if (!form) return null
  return form.trim().replace('{count}', count.toString())
}
```

#### `translationPayloads`

{/* generated:option:translationPayloads — do not edit; run `pnpm run docs:generate` */}

**类型** `TranslationPayloadOptions` · **默认值** —

控制翻译 payload 的输出方式(Node:`public/<apiBaseUrl>`;Edge:Nitro `serverAssets`)。

- **Node**:`serverAssets` 表示通过 `readFile` 从 `public/` 下进行本地 SSR(不使用 Rollup `raw:`)。
- **Edge**:`serverAssets` 会注册 Nitro 的 `serverAssets`(`assets:i18n`);它不会强制生成 public 副本。

对于常见的一体化部署,保留默认值即可。对于 Edge 上的大型词典,建议使用 `mode: 'source'`。
对于 CDN 支持的部署,请关闭本地输出并设置 `apiBaseClientHost` / `apiBaseServerHost`。

{/* /generated:option:translationPayloads */}

```typescript
{
  mode?: 'premerged' | 'source'
  serverAssets?: boolean
  serverHandler?: boolean
  publicAssets?: boolean
  prerenderRoutes?: boolean
  publicDir?: string
  warnFileCount?: number
  warnSizeBytes?: number
}
```

**默认值**(`mode: 'premerged'`):

```typescript
{
  mode: 'premerged',
  serverAssets: true,
  serverHandler: true,
  publicAssets: true,
  prerenderRoutes: false
}
```

在 **Node** 上,SSR 会读取被复制到 `public/<apiBaseUrl>/` 的同一目录树(`readFile`)。在 **Edge** 上,Nitro `serverAssets` 会将其嵌入(不会强制生成 public 副本 —— 如需 CDN,请设置 `publicAssets: true`)。`mode: 'premerged'` → 每个页面/语言对应一个 `\{page\}/\{locale\}/data.json`;`mode: 'source'` → 紧凑的源文件 + 运行时合并。

在 **Node** 上,即使 `publicAssets` 为 false,`serverAssets: true` 也会强制生成 public 副本。在 **Edge** 上,它只会注册 Nitro 嵌入。对于 Edge 上的大型词典,建议使用 `mode: 'source'`。若既没有本地 payload,也没有 `apiBaseServerHost`,构建会失败。

本地的 `/\{apiBaseUrl\}/:page/:locale/data.json` 处理器、预渲染路由与 public 资源副本都是可选输出。

若需紧凑的 **public** / Edge payload:

```typescript
i18n: {
  translationPayloads: {
    mode: 'source',
  },
}
```

`mode: 'source'` 会保持按 layer 合并后的源文件紧凑,并通过内置的 `/_locales` 路由(或 Edge 的 `assets:i18n`)在运行时合并根/页面/回退。默认情况下它会禁用 public 资源复制以及预渲染的 payload 路由。

<Warning>
在 `mode: 'source'` 下,`publicAssets` 默认为 `false`(`prerenderRoutes` 始终为 false,除非你选择启用)。因此,若没有 Nitro/边缘运行时的纯静态托管,客户端将无法加载翻译 —— 除非你启用其中一项输出,让 `serverHandler` 在运行时可用,或将 payload 托管在外部。

在默认的 `mode: 'premerged'` 与 `publicAssets: true` 下,静态文件已经落到 `public/<apiBaseUrl>/\{page\}/\{locale\}/data.json` —— 与客户端 `$fetch` 的 URL 相匹配 —— 因此静态托管可以在没有 Nitro 的情况下提供它们。
</Warning>

<Warning>
当设置了 `apiBaseServerHost` 或 `apiBaseClientHost` 时,模块会从该源获取已合并的 JSON。外部主机必须提供与内置路由一致的 `/\{apiBaseUrl\}/:page/:locale/data.json` 响应。`mode: 'source'` 只影响本地 payload 目录,而不作用于外部 CDN —— 除非该 CDN 也提供运行时合并后的 payload。
</Warning>

你也可以手动关闭重复的本地输出,并从 CDN 或对象存储提供翻译 payload:

```typescript
i18n: {
  apiBaseClientHost: 'https://cdn.example.com',
  apiBaseServerHost: 'https://cdn.example.com',
  translationPayloads: {
    serverHandler: false,
    publicAssets: false,
    prerenderRoutes: false
  }
}
```

如果你只是不想将 payload 写入 public 输出,同时保留内置服务端路由用于 SSR/运行时请求,请关闭两个 public 输出:

```typescript
i18n: {
  translationPayloads: {
    publicAssets: false,
    prerenderRoutes: false
  }
}
```

在 **Node** 上,即使 `publicAssets` 为 false,`serverAssets: true` 依然会为 SSR 强制生成 public 副本 —— 如果你不想在本地生成任何 payload 文件,请设置 `serverAssets: false` 并配置 `apiBaseServerHost`。

复制 payload 时,可使用 `publicDir` 更改 public 输出目录。它默认为 `apiBaseUrl`(`_locales`)。在 premerged 模式下,`publicAssets` 会把 `\{page\}/\{locale\}/data.json` 写到该目录(即客户端 fetch 时使用的相同路径)。`prerenderRoutes` 是对处理器路由可选的 Nitro 预渲染 —— 当该目录树已被复制时,通常是多余的。

如果你关闭所有本地 payload 输出,则必须同时配置 `apiBaseServerHost`(用于 SSR)与 `apiBaseClientHost`(用于客户端导航)。否则翻译会被解析为空对象,UI 键可能看起来未翻译。

`warnFileCount` 与 `warnSizeBytes` 用于在预合并 payload 输出规模变大时控制构建期的警告(默认:500 个文件与 10 MB)。

#### `dateBuild`

{/* generated:option:dateBuild — do not edit; run `pnpm run docs:generate` */}

**类型** `string \| number` · **默认值** —

用于翻译请求缓存 buster 的值(`?v=...`)。

未提供时,模块会回退到 `Date.now()`(非确定性)。
对于可复现/滚动部署,请将其设为稳定值
(例如 git SHA 或构建号)。

{/* /generated:option:dateBuild */}

默认情况下,模块会为你的翻译源文件计算指纹(按 layer 顺序对每个
`<layer>/<translationDir>/**/*.json` 做 SHA-256)并使用它。只有翻译发生实际变化时该值才会改变,
因此重新构建或重新部署未变化的翻译不会影响浏览器与 CDN 缓存 —— 若 `httpCacheDuration` 设为 1 年,
使用构建时间戳反而会让每个客户端在每次部署时都重新下载整个词典。

只有在没有可哈希的翻译文件时,它才会回退到 `Date.now()`。

若要显式控制(例如将 payload URL 与发布版本而非内容绑定),请显式设置:

```ts
export default defineNuxtConfig({
  i18n: {
    // Any stable string/number: git SHA, CI build number, release tag, etc.
    dateBuild: process.env.GIT_SHA ?? 'local-dev',
  },
})
```
#### `httpCacheDuration`

{/* generated:option:httpCacheDuration — do not edit; run `pnpm run docs:generate` */}

**类型** `number` · **默认值** `31536000`

`/\{apiBaseUrl\}/:page/:locale/data.json` 的 HTTP `Cache-Control` max-age(秒)。

仅当 `dateBuild` 为 URL 加上 buster(`?v=...`)时才完整生效,这是默认情况:
此时响应为 `public, max-age=…, immutable`,对浏览器与 CDN 都是安全的。

- `dateBuild: 0`/`''` —— URL 稳定,因此该时长将*不*被采用;响应会变为
  `public, max-age=0, must-revalidate`。在从不变化的 URL 上使用较长的 `max-age`
  会把浏览器最初看到的那份 payload 永久钉住。

- `0` —— 完全不设置 `Cache-Control`(在本地调试时有用)
- 在开发环境(`import.meta.dev`)下不生效,以免浏览器缓存与 HMR 冲突
- 只作用于经过 Nitro 提供的响应。被复制到 `public/` 并由托管平台提供的 payload
  会采用该平台自身的响应头 —— 请参见性能指南。

类似于 `@nuxtjs/i18n` 的实验性 `httpCacheDuration`(v10.2.0),但这是显式的响应头,
而不是 Nitro `defineCachedEventHandler` 的 maxAge。

{/* /generated:option:httpCacheDuration */}

```ts
export default defineNuxtConfig({
  i18n: {
    // Per-build fallback (Date.now()) so immutable payloads never go stale when GIT_SHA is missing.
    dateBuild: process.env.GIT_SHA ?? String(Date.now()),
    httpCacheDuration: 86400, // 24 hours
    // httpCacheDuration: 0, // disable Cache-Control header
  },
})
```

#### `cacheTtl`

{/* generated:option:cacheTtl — do not edit; run `pnpm run docs:generate` */}

**类型** `number` · **默认值** `0`

缓存翻译条目的存活时间(秒)。
`0` 表示条目永不过期。

{/* /generated:option:cacheTtl */}

```typescript
export default defineNuxtConfig({
  i18n: {
    // Limit cache to 1000 entries, each lives 10 minutes (refreshed on access)
    cacheMaxSize: 1000,
    cacheTtl: 600,
  },
})
```

<Tip>
对大多数项目而言,默认值(无限制、不过期)是合适的 —— 翻译数据小而有限。但如果你的项目有**成千上万个页面**且 `disablePageLocales: false`,并且**语言数量很多**,服务端缓存可能会显著增长。在长期运行的 Node.js 服务器中,这可能导致内存过度占用。

- **`cacheMaxSize`** —— 限制缓存条目数量。用于约束内存使用。
- **`cacheTtl`** —— 确保过期的翻译最终会从存储中重新加载。适用于 serverless 环境或翻译在运行时会变化的场景。

**估算最大条目数的公式**:`语言数 × (页面数 + 1)`。例如 10 种语言 × 500 个页面 ≈ 5010 条。
</Tip>
