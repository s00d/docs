# ❓ 常见问题解答

在这里查找关于 Nuxt I18n Micro 的常见问题与解决方案。

## 🚀 上手相关

### ❓ 如果某个路由无法加载怎么办？

使用 `Nuxt I18n Micro` 时，如果 router 没能为子目录中的路由自动分配名称，某些路由可能会无法按预期加载。

**解决方案：**
在对应的 Vue 文件里手动定义路由名称：

```javascript
definePageMeta({ name: 'pageName' })
```

这样能确保路由被正确注册，从而在应用中顺畅导航。

### ❓ 为什么 `$t` 或其他 i18n 组合式函数在 Nuxt 插件中不生效？

Nuxt I18n 组合式函数（`$t`、`$getLocale`、`$localePath` 等）在 Nuxt 插件或普通工具函数中可能无法按预期工作，甚至抛出运行时错误。

**原因与解决方案：**
Nuxt 组合式函数需要特定的上下文（例如 Nuxt hook 或 Vue setup 函数）才能访问 Nuxt 实例。在这些上下文之外使用（例如普通工具函数或插件），可能会在控制台看到如下错误：

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**方案 1：使用 `runWithContext`**
若要在异步操作之后调用 i18n 组合式函数，请使用 [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) 保留必要的上下文。

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**方案 2：先取值再传递**
或者先取出翻译值，再传给工具函数。

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**方案 3：在服务中传递翻译键**
在服务或工具函数中传递翻译键而不是直接调用 `$t`，在组件中再实际取值。

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 语言切换

### ❓ 在不改变 URL 的情况下切换语言？

可以——但取决于你使用的[路由策略](/guides/routing-strategies)。

**`no_prefix` 策略** —— 语言不出现在 URL 中。使用 `$switchLocale()` 在保持当前路径的情况下切换语言并重新加载翻译：

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

或使用 `useI18nLocale().setLocale('de')` 只更新偏好。若要在客户端完整重新加载翻译，仍推荐使用 `$switchLocale()`。

**前缀策略**（`prefix`、`prefix_except_default` 等）—— 语言与 URL 绑定。`$switchLocale()` 始终会导航到本地化路由。没有 `redirect: false` 之类的选项。

如果只需要目标 URL（例如语言切换器的链接），请改用 `$switchLocalePath()`：

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

关于所有切换方法，参见[路由与语言切换](/api/methods#-route-locale-switching)。

### ❓ 切换语言时页面滚动到顶部（或跳动）？

这是预期行为——它属于 **Vue Router / Nuxt 的滚动行为**，与 nuxt-i18n-micro 无直接关系。

在前缀策略（`prefix`、`prefix_except_default` 等）下，`$switchLocale()` 执行的是普通的客户端导航（`/en/page` → `/de/page`）。Nuxt 的默认 [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) 会在路由变化时滚动到顶部（浏览器前进/后退经由 `savedPosition` 除外）。

nuxt-i18n-micro 不会额外添加隐式的滚动处理——请在应用中使用一个小型包装组件。

**`SwitchLocalePreserve` 包装组件**

把 [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) 拷贝到项目中（`components/SwitchLocalePreserve.vue`）。可用示例：[`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue)。

在页面上设置 `scrollToTop: false` 并包裹切换器 UI。为可点击元素标记 `data-locale`——包装组件会拦截点击、调用 `$switchLocale` 并恢复滚动（即使翻译长度导致布局变化）：

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

组件工作方式：

1. **点击时** —— 读取插槽内被点击元素上的 `data-locale`（按钮、链接或任意自定义 markup 均可）。
2. **`$switchLocale` 之前** —— 记录 `scrollY` 与被点击元素的位置（让它保持在光标下）。
3. **导航期间** —— 一次性打补丁修改 `router.options.scrollBehavior`，返回 `\{ top: scrollY \}` 而非滚动到顶部。
4. **导航之后** —— 等待 `page:finish`，然后重新应用滚动；同时通过 `ResizeObserver` 捕捉因翻译长度差异带来的布局位移。

在使用该组件的页面上必须设置 `scrollToTop: false`。文档：[Nuxt —— `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta)。

请不要在被包装的控件上直接调用 `$switchLocale`——包装组件已负责切换。对于位于包装器外部的 `<NuxtLink :to="$switchLocalePath('fr')">`，滚动行为遵循普通的 Nuxt 路由，除非你添加自己的 `app/router.options.ts`。

## 🌐 翻译相关

### ❓ 为什么在页面过渡（尤其是使用 `defineAsyncComponent`）时翻译会失效？

在 `nuxt-i18n-micro` 与页面过渡一起使用时，过渡期间翻译可能会短暂停止工作。这是因为路由在过渡完成之前就发生了变化，使得新页面的翻译在旧页面仍可见时开始加载。

**根本原因：**

- 页面过渡会在翻译完全加载前触发路由变化
- `defineAsyncComponent` 与 `useAsyncData` 可能延迟翻译加载
- 加载期间翻译键可能显示为原始路径

**方案 1：累积合并（内置，无需配置）**

在 v3 中，模块会自动采用累积合并策略。当在同一语言内导航时，新页面的翻译会合并进当前字典，而不是替换它。这意味着上一页的翻译在过渡动画期间仍然可用。过渡结束（`page:transition:finish` 钩子）后会自动清理旧键。

无需任何配置——开箱即用。

**方案 2：显式路由上下文**

如果你倾向于手动控制，可以显式把当前路由传给 `$_t`：

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**方案 3：加载状态**

用加载状态优雅地处理翻译加载：

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ 为什么在 Vercel 上 SSR 时翻译键无法解析？

**SSR 上的 `$fetch` 限制**
在 Vercel 等 serverless 平台上，`$fetch` 只能从 CDN 获取静态文件，无法访问内部 Nitro 服务器。这意味着除非正确设置了 base URL，否则静态翻译文件可能不可直接访问。

**通过设置 `apiBaseClientHost` 和 `apiBaseServerHost` 修复**
如果翻译托管在外部 CDN 或不同域名，请为客户端请求设置 `apiBaseClientHost`，为服务器端请求设置 `apiBaseServerHost`。`apiBaseUrl` 只应包含路径前缀（例如 `_locales`）。

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

或通过环境变量：

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

翻译会在客户端和服务端都从 `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` 获取。

## 🔗 路由与导航相关

### ❓ 我可以在翻译字符串中直接使用 `NuxtLink` 或 `<i18n-link>` 吗？

可以，`Nuxt I18n Micro` 支持通过 `<i18n-t>` 组件在翻译中使用 `NuxtLink` 或 `<i18n-link>`。这在处理语法和 RTL 语言需求时尤其有用，可避免把翻译字符串拆分。

**示例：**

翻译文件：

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue 模板：

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

这样你就可以在翻译中动态使用链接，同时保持良好的本地化结构。

## 🏗️ 构建与部署相关

### ❓ 为什么翻译 payload 最终会出现在 `public/_locales/` 下（或者在 Edge 上进入服务器 bundle）？

SSR 与客户端都需要相同的 `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json` payload。它们的打包方式取决于 Nitro 目标：

**说明：**

- **Node（默认）：** 模块**不会**把翻译作为 Nitro `serverAssets` / Rollup `raw:` 嵌入（在大型目录下这会让构建内存爆炸）。取而代之的是把预合并后的目录复制到 `public/<apiBaseUrl>/`（默认 `_locales`），SSR 会通过 `readFile` 读取这些文件。客户端 `$fetch` 相同 URL——可能是静态文件，也可能通过 Nitro 处理器提供。
- **Edge**（`nitro.node === false`）：SSR 没有持久的 public 文件系统，因此 payload 会通过 Nitro `serverAssets`（`assets:i18n`）嵌入。建议使用 `translationPayloads.mode: 'source'` 让嵌入保持紧凑。仅当你还需要一份 CDN/静态副本时，才设置 `publicAssets: true`。
- **`prerenderRoutes`：** 可选。在 premerged 模式下 `publicAssets` 已经写出了 `\{page\}/\{locale\}/data.json`，因此对这些路由再做预渲染通常是多余的。

### ❓ 为什么会遇到与 `@unhead/vue` 或未定义对象相关的构建错误，尤其是在 Cloudflare Pages 上？

**原因：**
一些项目在使用 `nuxt-i18n-micro` 时可能遇到构建冲突或依赖缺失，尤其是：

- 部署到 **Cloudflare Pages** 或 **Cloudflare Workers** 时可能需要额外的兼容性 flag。
- 若像 `@unhead/vue` 之类的依赖未正确安装，预渲染阶段可能失败。
- 某些模块（例如 **nuxthub**、**nitro-cloudflare-dev**）如果未配置好 flag 或依赖，可能引入冲突。

**可行方案：**

**方案 1：手动安装 `@unhead/vue`**
如果构建错误提示找不到 `@unhead/vue`，请把它直接加入项目依赖：

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

这样能保证在 Nitro 预渲染阶段可用。

**方案 2：添加 Cloudflare 兼容性 flag**
使用 Cloudflare Pages 或 Workers 时，Node.js 兼容性通常默认关闭。请在 `wrangler.toml` 中启用：

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

该 flag 允许许多 Node.js 模块（包括 `nuxt-i18n-micro` 使用的）正常运行。

## 🔍 SEO 与 `@nuxtjs/seo`

### ❓ 错误：`nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

出现该错误是因为 **`@nuxtjs/seo`** 引入了旧版 **`nuxt-site-config` 3.x**，而它只为 `@nuxtjs/i18n` 注册 i18n 插件，不适配 **nuxt-i18n-micro**。

**修复方式：**

1. 升级到 **`@nuxtjs/seo` 3+**（内置支持 micro 的 `nuxt-site-config` 4+）。
2. 在 `modules` 中把 **`nuxt-i18n-micro` 放在 `@nuxtjs/seo` 之前**。
3. 保持 **`i18n.meta: true`** 以生成与语言相关的 head 标签。

完整示例参见 [SEO 指南 —— Nuxt SEO 章节](/guides/seo#nuxt-seo-nuxtjs-seo)。

## 🔧 配置与兼容性

### ❓ `Nuxt I18n Micro` 是否受 `vue-i18n` 启发？modifiers 呢？

`Nuxt I18n Micro` 是 `nuxt-i18n` 的性能替代方案，但它是独立于 `vue-i18n` 构建的。虽然某些方法名和参数可能相近，但底层实现有显著差异。

**Modifiers**：维护者最初考虑过 modifiers，但认为像 `<i18n-t>`、`<i18n-link>` 这样的组件已能有效满足这类需求。

例如：

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

这种方式足够灵活，因此目前无需引入 modifiers。不过如果社区有需求，未来版本仍可能加入。
