# ❓ FAQ:常见问题与解决方案

在此查找关于 Nuxt I18n Micro 的常见问题解答与故障排查方案。

## 🚀 上手相关问题

### ❓ 如果某个路由无法加载,该怎么办?

在使用 `Nuxt I18n Micro` 时,某些路由可能无法按预期加载,尤其是当路由器没有自动为子目录中的路由分配名称时。

**解决方案:**
可以通过在对应 Vue 文件中显式定义路由名称来解决:

```javascript
definePageMeta({ name: 'pageName' })
```

这样能确保路由被正确注册,从而在应用中实现顺畅的导航。

### ❓ 为什么 `$t` 或其他 i18n 组合式函数在 Nuxt 插件中不生效?

Nuxt I18n 的组合式函数(`$t`、`$getLocale`、`$localePath` 等)在 Nuxt 插件或工具函数中可能无法按预期工作,并导致运行时错误。

**原因与解决方案:**
Nuxt 的组合式函数需要特定上下文(例如 Nuxt hooks 或 Vue setup 函数)才能访问 Nuxt 实例。如果在这些上下文之外调用(例如工具函数或插件中),控制台可能会出现如下错误:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**方案 1:使用 `runWithContext`**
若需要在异步操作之后调用 i18n 的组合式函数,可以使用 [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) 来保留所需上下文。

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**方案 2:先取值**
或者,先获取翻译的值,再将其传给工具函数。

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**方案 3:在 Service 中传递翻译键**
在 Service 或工具函数中传递翻译键,而不是直接使用 `$t`。然后在组件中获取翻译。

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 语言切换

### ❓ 在不改变 URL 的情况下切换语言?

可以 —— 但这取决于你的[路由策略](/guides/routing-strategies)。

**`no_prefix` 策略** —— 语言不体现在 URL 中。使用 `$switchLocale()` 可以在保持当前路径不变的情况下切换语言并重新加载翻译:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

或者仅使用 `useI18nLocale().setLocale('de')` 更新偏好。若需完全在客户端重新加载翻译,建议使用 `$switchLocale()`。

**带前缀策略**(`prefix`、`prefix_except_default` 等)—— 语言与 URL 相互绑定。`$switchLocale()` 始终会导航到对应本地化的路由,不存在 `redirect: false` 选项。

如果你只需要目标 URL(例如做语言切换链接),请改用 `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

所有切换方法请参见[路由与语言切换](/api/methods#-route-locale-switching)。

### ❓ 切换语言时页面滚动到顶部(或跳动)?

这是**Vue Router / Nuxt 的滚动行为**,并非 nuxt-i18n-micro 特有的问题。

在带前缀策略(`prefix`、`prefix_except_default` 等)下,`$switchLocale()` 会执行常规的客户端导航(`/en/page` → `/de/page`)。Nuxt 默认的 [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) 会在路由变化时滚动到顶部(除通过 `savedPosition` 的浏览器前进/后退外)。

nuxt-i18n-micro 不会自行添加隐藏的滚动处理 —— 请在应用中使用一个小的包装组件。

**`SwitchLocalePreserve` 包装器**

将 [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) 复制到你的项目(`components/SwitchLocalePreserve.vue`)。可运行示例:[`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue)。

在页面上设置 `scrollToTop: false`,并用该组件包裹你的切换器 UI。为可点击目标标记 `data-locale` —— 包装器会拦截点击、调用 `$switchLocale` 并恢复滚动位置(包括翻译长度导致布局变化的情形):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

该组件:

1. **点击时** —— 从 slot 内被点击元素上读取 `data-locale`(按钮、链接或任意自定义标记均可)。
2. **在** `$switchLocale` **之前** —— 保存 `scrollY` 与被点击元素的位置(使其保持在光标下方)。
3. **导航过程中** —— 一次性打补丁到 `router.options.scrollBehavior`,返回 `\{ top: scrollY \}` 而不是滚动到顶部。
4. **导航后** —— 等待 `page:finish`,然后重新应用滚动位置,同时通过 `ResizeObserver` 捕捉因不同翻译长度带来的布局变化。

在使用该包装器的页面上必须设置 `scrollToTop: false`。文档:[Nuxt —— `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta)。

不要在被包裹的控件上直接调用 `$switchLocale` —— 包装器会处理切换逻辑。对于在包装器之外使用的 `<NuxtLink :to="$switchLocalePath('fr')">`,若未自行添加 `app/router.options.ts`,其滚动行为仍遵循 Nuxt 默认路由。

## 🌐 翻译相关问题

### ❓ 为什么在页面过渡期间(尤其是使用 `defineAsyncComponent` 时)翻译会失效?

在页面过渡中使用 `nuxt-i18n-micro` 时,过渡期间翻译可能会短暂失效。这是因为路由在过渡完成之前就已变更,导致新页面的翻译在旧页面仍可见的情况下开始加载。

**根本原因:**

- 页面过渡在翻译完全加载之前就切换了路由
- `defineAsyncComponent` 与 `useAsyncData` 可能延迟翻译加载
- 加载期间翻译键可能显示为原始路径

**方案 1:累积合并(内置,无需配置)**

在 v3 中,模块会自动使用累积合并策略。在同一语言内导航时,新页面的翻译会合并进当前词典而非替换。这样在过渡动画期间,上一个页面的翻译仍然可用。过渡结束后(`page:transition:finish` hook),旧的键会被自动清理。

无需任何配置 —— 开箱即用。

**方案 2:显式路由上下文**

如果你更希望手动控制,可以显式将当前路由传给 `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**方案 3:加载态**

实现加载态以优雅地处理翻译加载:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ 为什么在 Vercel 上 SSR 期间翻译键无法解析?

**SSR 上的 `$fetch` 限制**
在 Vercel 等 serverless 平台上,`$fetch` 只能从 CDN 获取静态文件,而无法从内部 Nitro 服务器获取。这意味着除非设置了正确的基础 URL,静态翻译文件可能无法被直接访问。

**通过设置 `apiBaseClientHost` 与 `apiBaseServerHost` 修复**
如果翻译托管在外部 CDN 或不同域名下,请为客户端请求使用 `apiBaseClientHost`,为服务端请求使用 `apiBaseServerHost`。`apiBaseUrl` 只应包含路径前缀(例如 `_locales`)。

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

也可以通过环境变量:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

翻译会在客户端与服务端都从 `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` 获取。

## 🔗 路由与导航问题

### ❓ 我可以在翻译字符串中直接使用 `NuxtLink` 或 `<i18n-link>` 吗?

可以。`Nuxt I18n Micro` 允许通过 `<i18n-t>` 组件在翻译中使用 `NuxtLink` 或 `<i18n-link>`,这在处理语法与 RTL 语言需求时非常有帮助,不必将翻译字符串拆开。

**示例:**

翻译文件:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue 模板:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

这样便可在翻译中嵌入动态链接,同时保持正确的本地化结构。

## 🏗️ 构建与部署问题

### ❓ 为什么翻译 payload 会出现在 `public/_locales/` 下(或在 Edge 上出现在服务端 bundle 中)?

SSR 与客户端都需要相同的 `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json` payload。打包方式取决于 Nitro 目标:

**说明:**

- **Node(默认):** 模块**不会**将翻译作为 Nitro 的 `serverAssets` / Rollup 的 `raw:` 嵌入(那样会让大词典的构建内存爆炸)。取而代之的是把预合并的树复制到 `public/<apiBaseUrl>/`(默认 `_locales`),SSR 通过 `readFile` 读取这些文件。客户端会 `$fetch` 同样的 URL —— 无论是作为静态文件,还是通过 Nitro 处理器。
- **Edge**(`nitro.node === false`):没有持久的 public 文件系统可供 SSR 使用,因此 payload 会通过 Nitro 的 `serverAssets`(`assets:i18n`)嵌入。建议使用 `translationPayloads.mode: 'source'` 以保持嵌入紧凑。仅当你还需要 CDN/静态副本时才设置 `publicAssets: true`。
- **`prerenderRoutes`:** 可选。在 premerged 模式下,`publicAssets` 已经写出了 `\{page\}/\{locale\}/data.json`,因此对这些路由再进行预渲染通常是多余的。

### ❓ 为什么会遇到与 `@unhead/vue` 或某个未定义对象相关的构建错误,尤其是在 Cloudflare Pages 上?

**原因:**
一些项目在使用 `nuxt-i18n-micro` 时会遇到构建冲突或依赖缺失,尤其是:

- 部署到 **Cloudflare Pages** 或 **Cloudflare Workers** 可能需要额外的兼容标志。
- 如果像 `@unhead/vue` 这样的依赖未正确安装,预渲染可能失败。
- 某些模块(如 **nuxthub**、**nitro-cloudflare-dev**)如果没有正确的标志或依赖,可能会引入冲突。

**可能的解决方案:**

**方案 1:手动安装 `@unhead/vue`**
如果构建报错找不到 `@unhead/vue`,可以直接安装到项目依赖中:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

这样可确保它在 Nitro 预渲染阶段可用。

**方案 2:添加 Cloudflare 兼容标志**
在 Cloudflare Pages 或 Cloudflare Workers 上,Node.js 兼容通常是关闭的。可在 `wrangler.toml` 中启用:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

该标志允许许多 Node.js 模块(包括 `nuxt-i18n-micro` 所使用的)正常运行。

## 🔍 SEO 与 `@nuxtjs/seo`

### ❓ 错误:`nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

出现该错误是因为 **`@nuxtjs/seo`** 引入了旧版 **`nuxt-site-config` 3.x**,后者只为 `@nuxtjs/i18n` 注册了其 i18n 插件,而不支持 **nuxt-i18n-micro**。

**修复方式:**

1. 升级到 **`@nuxtjs/seo` 3+**(内含支持 micro 的 `nuxt-site-config` 4+)。
2. 在 `modules` 中把 **`nuxt-i18n-micro` 放到 `@nuxtjs/seo` 之前**。
3. 保持 **`i18n.meta: true`**,以获得随语言变化的 head 标签。

完整示例请参见 [SEO 指南 —— Nuxt SEO 部分](/guides/seo#nuxt-seo-nuxtjs-seo)。

## 🔧 配置与兼容性

### ❓ `Nuxt I18n Micro` 是否受 `vue-i18n` 启发?那 modifier 呢?

`Nuxt I18n Micro` 是 `nuxt-i18n` 的性能替代方案,但它是独立于 `vue-i18n` 开发的。虽然某些方法名和参数看起来相似,但底层实现有明显差异。

**Modifier**:维护者最初曾考虑过 modifier,但认为像 `<i18n-t>` 和 `<i18n-link>` 这样的组件已经能有效满足这类需求。

例如:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

这种方式已足够灵活,因此目前无需发布 modifier。但如有需求,未来版本仍有可能加入。
