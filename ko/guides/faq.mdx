# ❓ FAQ: 자주 발생하는 문제 및 해결책

Nuxt I18n Micro에 대한 자주 묻는 질문과 일반적인 문제에 대한 해결책을 확인하세요.

## 🚀 시작 시 발생하는 문제

### ❓ 라우트가 로드되지 않으면 어떻게 해야 하나요?

`Nuxt I18n Micro`를 사용할 때, 특히 하위 폴더의 라우트에 라우터가 자동으로 이름을 할당하지 않는 경우 일부 라우트가 예상대로 로드되지 않을 수 있습니다.

**해결책:**
이를 해결하려면 해당 Vue 파일에 다음을 추가하여 페이지의 라우트 이름을 수동으로 정의합니다:

```javascript
definePageMeta({ name: 'pageName' })
```

이렇게 하면 라우트가 올바르게 등록되어 애플리케이션 내에서 매끄러운 내비게이션이 가능합니다.

### ❓ Nuxt 플러그인에서 `$t` 또는 다른 i18n 컴포저블이 작동하지 않는 이유는 무엇인가요?

Nuxt I18n 컴포저블(`$t`, `$getLocale`, `$localePath` 등)은 Nuxt 플러그인이나 유틸리티 함수 내에서 예상대로 작동하지 않을 수 있으며, 런타임 오류가 발생합니다.

**원인 및 해결책:**
Nuxt 컴포저블은 Nuxt 인스턴스에 접근하기 위해 특정 컨텍스트(예: Nuxt 훅 또는 Vue setup 함수)가 필요합니다. 이러한 컨텍스트 외부에서 사용되면(예: 유틸리티 함수 또는 플러그인) 콘솔에 다음 오류가 나타날 수 있습니다:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**해결책 1: `runWithContext` 사용**
비동기 작업 후에 i18n 컴포저블을 호출하려면 필요한 컨텍스트를 유지하기 위해 [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext)를 사용하세요.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**해결책 2: 값을 먼저 가져오기**
또는 번역 값을 먼저 가져온 다음 유틸리티 함수에 전달합니다.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**해결책 3: 서비스에서 번역 키 전달**
서비스나 유틸리티 함수에서 `$t`를 직접 사용하는 대신 번역 키를 전달합니다. 그런 다음 컴포넌트에서 번역을 가져옵니다.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 로케일 전환

### ❓ URL을 변경하지 않고 로케일을 전환할 수 있나요?

가능합니다 — 그러나 [라우팅 전략](/guides/routing-strategies)에 따라 다릅니다.

**`no_prefix` 전략** — 로케일이 URL의 일부가 아닙니다. `$switchLocale()`을 사용하여 동일한 경로에 머무르면서 로케일을 변경하고 번역을 다시 로드합니다:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

또는 `useI18nLocale().setLocale('de')`으로 환경 설정만 업데이트합니다. 전체 클라이언트 측 번역 재로드를 원한다면 `$switchLocale()`을 선호하세요.

**접두사 전략**(`prefix`, `prefix_except_default`, …) — 로케일과 URL이 연결되어 있습니다. `$switchLocale()`은 항상 지역화된 라우트로 내비게이션합니다. `redirect: false` 옵션은 없습니다.

대상 URL만 필요한 경우(예: 언어 스위처 링크), 대신 `$switchLocalePath()`를 사용하세요:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

모든 전환 메서드는 [Route & Locale Switching](/api/methods#-route-locale-switching)을 참조하세요.

### ❓ 로케일을 전환할 때 페이지가 맨 위로 스크롤되거나 점프하나요?

이는 예상된 동작입니다 — nuxt-i18n-micro 고유의 문제가 아니라 **Vue Router / Nuxt 스크롤 동작**입니다.

접두사 전략(`prefix`, `prefix_except_default`, …)에서 `$switchLocale()`은 일반 클라이언트 내비게이션(`/en/page` → `/de/page`)을 수행합니다. Nuxt의 기본 [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts)는 라우트 변경 시 맨 위로 스크롤합니다(`savedPosition`을 통한 브라우저 뒤로/앞으로 제외).

nuxt-i18n-micro는 숨겨진 스크롤 처리를 추가하지 않습니다 — 앱에 작은 래퍼 컴포넌트를 사용하세요.

**`SwitchLocalePreserve` 래퍼**

[`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue)를 프로젝트(`components/SwitchLocalePreserve.vue`)에 복사하세요. 작동 데모: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

페이지에서 `scrollToTop: false`를 설정하고 스위처 UI를 감쌉니다. 클릭 가능한 대상은 `data-locale`로 표시하세요 — 래퍼는 클릭을 가로채고 `$switchLocale`을 호출하며 스크롤을 복원합니다(번역 길이가 레이아웃을 변경할 때 포함):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

이 컴포넌트는:

1. **클릭 시** — 슬롯 내부의 클릭된 요소(버튼, 링크 또는 사용자 정의 마크업)에서 `data-locale`을 읽습니다.
2. **`$switchLocale` 전에** — `scrollY`와 클릭된 요소 위치를 저장합니다(커서 아래에 유지).
3. **내비게이션 중** — `router.options.scrollBehavior`를 한 번 패치하고 맨 위로 스크롤하는 대신 `\{ top: scrollY \}`를 반환합니다.
4. **내비게이션 후** — `page:finish`를 기다린 후 `ResizeObserver`가 다른 번역 길이로 인한 레이아웃 이동을 감지하는 동안 스크롤을 다시 적용합니다.

이 래퍼를 사용하는 페이지에서는 `scrollToTop: false`가 필요합니다. 문서: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

래퍼로 감싼 컨트롤에서 `$switchLocale`을 직접 호출하지 마세요 — 래퍼가 전환을 처리합니다. 래퍼 외부의 `<NuxtLink :to="$switchLocalePath('fr')">`의 경우, 자체 `app/router.options.ts`를 추가하지 않는 한 스크롤 동작은 일반 Nuxt 라우팅을 따릅니다.

## 🌐 번역 관련 문제

### ❓ 특히 `defineAsyncComponent`를 사용할 때 페이지 전환 중에 번역이 깨지는 이유는 무엇인가요?

`nuxt-i18n-micro`를 페이지 전환과 함께 사용할 때, 전환 중에 번역이 잠시 중단될 수 있습니다. 이 문제는 전환이 완료되기 전에 라우트가 변경되어 이전 페이지가 여전히 표시되는 동안 새 페이지의 번역이 로드되기 때문에 발생합니다.

**근본 원인:**

- 페이지 전환은 번역이 완전히 로드되기 전에 라우트를 변경합니다.
- `defineAsyncComponent`와 `useAsyncData`는 번역 로드를 지연시킬 수 있습니다.
- 로드 중에 번역 키가 원시 경로로 나타날 수 있습니다.

**해결책 1: 누적 병합 (기본 제공, 구성 불필요)**

v3에서는 모듈이 자동으로 누적 병합 전략을 사용합니다. 동일한 로케일 내에서 내비게이션할 때, 새 페이지 번역은 활성 사전을 대체하는 대신 병합됩니다. 즉, 전환 애니메이션 중에 이전 페이지의 번역이 계속 사용 가능합니다. 전환이 완료된 후(`page:transition:finish` 훅), 이전 키는 자동으로 정리됩니다.

구성이 필요 없습니다 — 이 기능은 기본적으로 작동합니다.

**해결책 2: 명시적 라우트 컨텍스트**

수동 제어를 선호한다면 현재 라우트를 `$_t`에 명시적으로 전달합니다:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**해결책 3: 로딩 상태**

번역 로드를 우아하게 처리하기 위한 로딩 상태를 구현합니다:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Vercel의 SSR 중에 번역 키가 해결되지 않는 이유는 무엇인가요?

**SSR에서 `$fetch`의 제한 사항**
Vercel과 같은 서버리스 플랫폼에서는 `$fetch`가 CDN에서만 정적 파일을 가져올 수 있고 내부 Nitro 서버에서는 가져올 수 없습니다. 즉, 올바른 base URL이 설정되지 않는 한 정적 번역 파일에 직접 액세스할 수 없을 수 있습니다.

**`apiBaseClientHost`와 `apiBaseServerHost` 설정으로 해결**
번역이 CDN 또는 다른 도메인에 외부적으로 호스팅되는 경우, 클라이언트 측 요청에는 `apiBaseClientHost`를, 서버 측 요청에는 `apiBaseServerHost`를 사용하세요. `apiBaseUrl`에는 경로 접두사(예: `_locales`)만 포함해야 합니다.

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

또는 환경 변수를 통해:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

번역은 클라이언트와 서버 모두에서 `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json`에서 가져오게 됩니다.

## 🔗 라우팅 및 내비게이션 문제

### ❓ 번역 문자열에 `NuxtLink` 또는 `<i18n-link>`를 직접 사용할 수 있나요?

네, `Nuxt I18n Micro`는 `<i18n-t>` 컴포넌트를 통해 번역 내에서 `NuxtLink` 또는 `<i18n-link>`를 사용할 수 있게 하며, 이는 번역 문자열을 분할하지 않고 문법 및 RTL 언어 요구 사항을 처리하는 데 특히 유용합니다.

**예제:**

번역 파일:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue 템플릿:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

이렇게 하면 적절한 지역화 구조를 유지하면서 번역 내에서 동적 링크를 사용할 수 있습니다.

## 🏗️ 빌드 및 배포 문제

### ❓ 번역 페이로드가 `public/_locales/`에 저장되거나 (Edge에서는 서버 번들에) 들어가는 이유는 무엇인가요?

SSR과 클라이언트 모두 동일한 `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json` 페이로드가 필요합니다. 패키징 방식은 Nitro 타겟에 따라 다릅니다:

**설명:**

- **Node (기본):** 모듈은 번역을 Nitro `serverAssets` / Rollup `raw:`로 임베드하지 **않습니다**(대용량 카탈로그에서 빌드 RAM이 폭발했음). 대신 premerged 트리를 `public/<apiBaseUrl>/`(기본값 `_locales`)에 복사하며 SSR은 `readFile`로 이러한 파일을 읽습니다. 클라이언트는 동일한 URL을 `$fetch`합니다 — 정적 파일 또는 Nitro 핸들러를 통해.
- **Edge** (`nitro.node === false`): SSR을 위한 지속적인 공용 FS가 없으므로 페이로드는 Nitro `serverAssets`(`assets:i18n`)를 통해 임베드됩니다. 임베드가 컴팩트하게 유지되도록 `translationPayloads.mode: 'source'`를 선호하세요. CDN/정적 사본이 필요한 경우에만 `publicAssets: true`를 설정하세요.
- **`prerenderRoutes`:** 선택 사항. premerged 모드에서는 `publicAssets`가 이미 `\{page\}/\{locale\}/data.json`을 작성하므로 이러한 라우트를 사전 렌더링하는 것은 일반적으로 중복입니다.

### ❓ 특히 Cloudflare Pages에서 `@unhead/vue` 또는 정의되지 않은 객체를 참조하는 빌드 오류가 발생하는 이유는 무엇인가요?

**원인:**
일부 프로젝트는 `nuxt-i18n-micro`를 사용할 때 빌드 충돌이나 누락된 종속성 문제를 경험합니다. 특히:

- **Cloudflare Pages** 또는 **Cloudflare Workers**에서의 배포는 추가 호환성 플래그가 필요할 수 있습니다.
- `@unhead/vue`와 같은 종속성이 올바르게 설치되지 않은 경우 사전 렌더링 단계가 실패할 수 있습니다.
- 특정 모듈(예: **nuxthub**, **nitro-cloudflare-dev**)은 올바른 플래그나 종속성으로 구성되지 않으면 충돌을 일으킬 수 있습니다.

**가능한 해결책:**

**해결책 1: `@unhead/vue` 수동 설치**
빌드 오류가 `@unhead/vue`를 찾을 수 없다고 불평하면 프로젝트의 종속성에 직접 설치하세요:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

이렇게 하면 Nitro 사전 렌더링 단계에서 사용할 수 있습니다.

**해결책 2: Cloudflare 호환성 플래그 추가**
Cloudflare Pages 또는 Cloudflare Workers를 사용할 때 Node.js 호환성은 기본적으로 비활성화되어 있는 경우가 많습니다. `wrangler.toml`에서 활성화하세요:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

이 플래그를 사용하면 많은 Node.js 모듈(`nuxt-i18n-micro`에서 사용하는 모듈 포함)이 원활하게 실행됩니다.

## 🔍 SEO 및 `@nuxtjs/seo`

### ❓ 오류: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

**`@nuxtjs/seo`**가 `@nuxtjs/i18n`용으로만 i18n 플러그인을 등록하고 **nuxt-i18n-micro**용으로는 등록하지 않는 오래된 **`nuxt-site-config` 3.x**를 가져올 때 발생합니다.

**해결책:**

1. **`@nuxtjs/seo` 3+**로 업그레이드합니다(micro 지원이 포함된 `nuxt-site-config` 4+ 포함).
2. `modules`에서 **`nuxt-i18n-micro`를 `@nuxtjs/seo` 앞에** 놓습니다.
3. 로케일 인식 헤드 태그를 위해 **`i18n.meta: true`**를 유지합니다.

전체 예제는 [SEO 가이드 — Nuxt SEO 섹션](/guides/seo#nuxt-seo-nuxtjs-seo)을 참조하세요.

## 🔧 구성 및 호환성

### ❓ `Nuxt I18n Micro`는 `vue-i18n`에서 영감을 받았나요? 수정자는 어떻게 되나요?

`Nuxt I18n Micro`는 `nuxt-i18n`의 성능 대안 역할을 하지만, `vue-i18n`과 독립적으로 개발되었습니다. 일부 메서드 이름과 매개변수가 유사할 수 있지만 기본 기능은 크게 다릅니다.

**수정자**: 관리자는 처음에 수정자를 고려했으나, `<i18n-t>` 및 `<i18n-link>`와 같은 컴포넌트가 이러한 요구를 효과적으로 해결한다고 결론지었습니다.

예를 들어:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

이 접근 방식은 유연하므로 현재 수정자를 릴리스할 필요가 없습니다. 그러나 수요가 있으면 향후 릴리스에서 수정자가 추가될 수 있습니다.
