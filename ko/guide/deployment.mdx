이 모듈은 추가 구성 없이 모든 Nitro 프리셋에서 동작합니다: 빌드 대상 프리셋에 따라 번역 파일의 위치를 선택합니다. 기본값은 대부분의 앱에 적합하므로, 사용하는 플랫폼의 섹션을 읽으세요. 이 페이지에서 설명하는 내용:

- `.output/`에 무엇이 들어가고 페이로드가 어떤 헤더를 받는지;
- 정적 호스팅, 대규모 카탈로그, 하위 경로, 프록시 또는 CDN을 위해 무엇을 변경해야 하는지.

<Note>

실제 호스트에 배포하여 확인했습니다: Cloudflare Workers 및 Pages, Vercel 및 Vercel Edge, Netlify 및 Netlify Edge, Cloud Run 및 Deno Deploy, 각각 [플랫폼](#platforms)에 나열된 설정으로. 다른 프리셋은 로컬에서 빌드하고 실행했습니다.

</Note>

## 번역이 전달되는 방식 {#how-translations-are-delivered}

빌드 시 모듈은 `locales/`(모든 레이어 병합)를 **페이로드**로 변환합니다: 페이지와 로케일당 하나의 JSON 파일. 두 소비자가 이를 읽습니다:

- **SSR**은 렌더링된 페이지의 페이로드를 프로세스 내에서 로드합니다 — HTTP 요청이 없으며, 사전은 HTML에 포함되지 않습니다.
- **브라우저**는 하이드레이션과 내비게이션 시 `/_locales/<page>/<locale>/data.json?v=<dateBuild>`를 가져옵니다.

`_locales`는 [`apiBaseUrl`](/ko/api/module-options#apibaseurl)입니다. 내장 서버 라우트가 이 URL에 응답하며, `public/`의 정적 복사본은 서버 없이 응답합니다.

## Node 서버 {#node-server}

```bash
npx nuxi build
node .output/server/index.mjs
```

`node-server`(기본 프리셋), `node-cluster`, `bun`, `deno-server` 또는 `server/` 폴더 옆에 `public/`이 있고 디스크에서 `public/`을 제공하는 다른 프리셋에서는:

- 페이로드가 `.output/public/_locales/<page>/<locale>/data.json`에 복사됩니다;
- SSR은 `fs`로 해당 폴더에서 읽습니다(서버에 아무것도 번들링되지 않음);
- 브라우저는 정적 파일 또는 서버 라우트에서 받습니다.

`.output/` 디렉터리 전체를 배포하세요. 모듈은 Node 20 이상이 필요하며, Nuxt에도 자체 최소 요구 사항이 있습니다: Nuxt 4.5는 `^22.19.0 || ^24.11.0 || >=26.0.0`을 선언합니다.

지속적인 부하를 받는 프로세스는 라이브 힙보다 훨씬 많은 메모리를 유지할 수 있습니다. 컨테이너 제한을 설정하기 전에 [Node 서버의 메모리](/ko/guide/performance#memory-on-a-node-server)를 참고하세요.

다른 레이아웃에서는 모듈이 다음 섹션에서 설명하는 대로 페이로드를 포함시킵니다. 해당하는 경우:

- 빌드가 한 번 읽는 사용자 정의 `nitro.output.publicDir`;
- 정적 파일을 다른 곳에 보관하는 프리셋에서의 `serveStatic: true`.

<Warning>

빌드가 `public/`을 읽는데 해당 폴더가 서버에 도달하지 않으면(`aws-lambda`와 `serveStatic: true`의 경우처럼), 서버는 오류를 한 번 기록하고 페이지에는 원시 키가 표시됩니다. 페이로드를 포함시키려면 `nitro.serveStatic: false`를 설정하세요.

</Warning>

## 서버리스와 Edge {#serverless-and-edge}

다음 프리셋은 런타임에 `public/`을 읽을 수 없습니다:

- `public/`을 CDN으로 보내거나 제공하지 않는 함수 프리셋: `vercel`, `netlify`, `aws-lambda`, `aws-amplify`, `azure-swa`, `firebase`, `stormkit`, `zeabur`, `node-listener`;
- 파일 시스템이 없는 Edge 프리셋: `cloudflare-module`, `cloudflare-pages`, `vercel-edge`, `netlify-edge`, `deno_deploy`;
- `winterjs` 같은 `serveStatic: 'inline'`.

이 경우 모듈은 페이로드를 Nitro 서버 에셋(`assets:i18n`)으로 서버 번들에 포함시키고, 브라우저용 공개 복사본도 여전히 작성합니다.

페이지 × 로케일 전체 매트릭스를 포함시키면 번들이 커집니다. Edge 플랫폼의 한도를 넘으면 빌드가 경고하고 해당 플랫폼을 명시합니다. [번들 한도](#bundle-limits-on-edge)를 참고하세요. 대규모 카탈로그의 경우 `source` 모드로 전환하세요. 이 모드는 압축된 소스 파일을 포함시키고 런타임에 루트, 페이지, 폴백 번역을 병합합니다:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    translationPayloads: {
      mode: 'source',
    },
  },
})
```

`source` 모드에서 브라우저는 항상 서버 라우트에서 페이로드를 가져오며, 서버 라우트가 요청 시 이를 병합합니다(공개 복사본은 서버만 읽는 압축된 소스 트리를 담고 있습니다). 실행 중인 서버가 필요하므로 순수 정적 사이트에는 `source`를 사용하지 마세요.

### Edge의 번들 한도 {#bundle-limits-on-edge}

| 플랫폼           | 한도                                                                                  |
| ------------------ | -------------------------------------------------------------------------------------- |
| Cloudflare Workers | Free 및 Paid에서 비압축 64 MiB. 압축 한도 없음. 시작 1초, 메모리 128 MB |
| Vercel Edge        | Hobby에서 gzip 1 MB, Pro에서 2 MB, Enterprise에서 4 MB                                    |
| Netlify Edge       | 압축 20 MB                                                                       |

빌드는 포함시키는 사전의 크기를 합산하고 플랫폼의 가장 낮은 한도를 넘을 때만 경고합니다. 사전만 계산하므로 앱 크기는 별도로 추가됩니다. 예를 들어 60 KB 루트 파일을 가진 120개 페이지 × 4개 로케일은 다음을 포함시킵니다:

| 모드 | 포함 크기 | 적합한 플랫폼 |
| --- | --- | --- |
| `premerged` | 34.9 MiB | Cloudflare; Vercel Edge나 Netlify Edge는 불가 |
| `source` | 5.7 MiB | Vercel Edge에서는 여전히 gzip 3 MB |

Vercel Edge에서 그 정도 크기의 카탈로그는 [페이로드 호스트](#app-baseurl-and-payload-hosts)가 필요합니다.

`source`는 각 isolate에서 페이지와 로케일마다 병합 비용을 치르며, 위 예제에서 약 1 ms, 콜드 상태에서는 CPU 7 ms입니다. 폴백 체인의 크기에 따라 증가하며, 4 MB의 체인 파일에서는 약 43 ms입니다. Netlify Edge는 요청당 CPU 50 ms를, Cloudflare의 Free 플랜은 10 ms를 허용합니다.

### Edge 런타임에서의 날짜 {#dates-on-edge-runtimes}

`$td`는 런타임의 `Intl`을 사용하며, 그 ICU 데이터는 브라우저의 것과 다를 수 있습니다. Netlify Edge에서는 포맷된 날짜에 Chrome의 일반 공백 대신 U+202F(좁은 줄바꿈 없는 공백)가 포함될 수 있어, Vue가 하이드레이션 불일치를 한 번 기록하고 텍스트는 하이드레이션 시 스스로 수정됩니다. 그곳에서는 순수 `Intl`을 사용하는 순수 Nuxt도 마찬가지이며, Deno Deploy에서는 그렇지 않습니다.

<Tip>

`date` 또는 `relativeDate`를 사용하는 `<i18n-t>`는 이미 불일치를 허용합니다. 템플릿에서 `$td`를 사용할 때는 요소에 `data-allow-mismatch="text"`를 지정하세요.

</Tip>

## 정적 사이트(nuxi generate) {#static-site-(nuxi-generate)}

```bash
npx nuxi generate
```

`nuxi build --preset <static preset>`도 같은 동작을 합니다.

- 기본 `premerged` 모드는 모든 페이로드를 `.output/public/_locales/`에 작성하므로, 모든 정적 호스트가 이를 제공할 수 있습니다.
- 페이지는 각 로케일에 대해 사전 렌더링됩니다: `prefix`에서는 모듈이 모든 현지화된 루트(`/en`, `/de`)를 시드하고, `/`는 리디렉션 스텁으로 유지됩니다.
- [`prerenderRoutes`](/ko/api/module-options#translationpayloads)는 끈 상태로 두세요: 공개 복사본에 이미 페이로드 파일이 포함되어 있습니다.
- `source` 모드나 `publicAssets: false`에서는 브라우저가 읽을 것이 없으며, 빌드가 경고합니다.

<Note>

쿠키나 `Accept-Language`를 읽을 서버가 없으므로, 저장된 로케일이 첫 로드 시 `/`를 리디렉션하지 않습니다. `no_prefix`에서는 HTML이 기본 로케일을 담고 있으며 저장된 쿠키는 로드 시 적용되지 않습니다: 열린 페이지에서 `$switchLocale`은 여전히 동작합니다.

</Note>

Cloudflare Pages는 [Cloudflare Pages](#cloudflare-pages)를 참고하세요.

[로케일 도메인](/ko/guide/layers#multiple-domains)을 사용하는 빌드에서는 도메인마다 한 번씩 generate를 실행하며, `NUXT_I18N_DOMAIN`을 해당 실행의 호스트로 지정하세요. 그러면 각 트리가 해당 도메인의 페이지와 페이로드를 담습니다. Nitro에는 출력 폴더용 변수가 없으므로 구성에서 직접 읽으세요:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: { output: { publicDir: process.env.PUBLIC_DIR } },
})
```

```bash
NUXT_I18N_DOMAIN=example.de PUBLIC_DIR=sites/example.de npx nuxi generate
NUXT_I18N_DOMAIN=example.com PUBLIC_DIR=sites/example.com npx nuxi generate
```

- 폴더는 `.output` 밖에 두세요: 각 실행이 이를 비웁니다.
- 다른 도메인으로의 절대 링크는 크롤링되지 않습니다.
- 변수가 없으면 `baseUrl` 로케일이 있는 빌드는 경고하고 빌드 구성을 생성하며, 이때 해당 로케일은 링크가 되고 페이지가 생성되지 않습니다.
- Node 서버에서는 같은 변수가 `Host`와 상관없이 프로세스를 하나의 도메인에 고정합니다.

정적 호스트는 이 파일들에 자체 헤더를 적용하므로, 캐싱은 호스트 구성에서 설정하세요. 모듈의 `/_locales/*` 규칙은 Cloudflare Pages에는 `_headers`를 통해, Vercel에는 `config.json`을 통해 `public, max-age=60`으로 전달됩니다. `.gz` / `.br` 파일을 함께 배포하려면 `nitro.compressPublicAssets`를 켜세요: 모듈이 같은 설정으로 페이로드 복사본을 압축합니다.

## 캐시 헤더와 dateBuild {#cache-headers-and-datebuild}

| 요청                                                                                  | `Cache-Control`                                                                                                 |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Node 서버 또는 라우트, `?v=`가 현재 `dateBuild`와 같고 사전이 비어 있지 않음     | `private, max-age=<httpCacheDuration>, immutable`                                                               |
| Node 서버 또는 라우트, `?v=`가 없거나 오래된 값이거나 사전이 비어 있음             | `public, max-age=0, must-revalidate`                                                                            |
| 호스트의 `public/` 복사본, 모든 `?v=`                                                    | `public, max-age=60` ([`httpCacheControl`](/ko/api/module-options#other)) |
| `source` 모드, `cacheTtl` 또는 `apiBaseServerHost`: 빌드 없이 사전이 변경될 수 있음 | 항상 `httpCacheControl` 헤더                                                                           |
| 서버 라우트, 사전을 읽을 수 없음                                           | `503`, `no-store`                                                                                               |
| 개발 서버                                                                               | 없음                                                                                                            |

표가 이렇게 생긴 이유:

- 현재 `v`가 있는 URL은 해시된 에셋처럼 고정되며, 쿼리를 볼 수 있는 쪽만 그렇게 지정할 수 있습니다: 서버 라우트, 그리고 정적 파일에 헤더를 설정하는 Node 서버.
- `private`이므로, 쿼리를 무시하는 CDN이 이 응답으로 다음 `v`에 응답할 수 없습니다.
- 호스트의 정적 파일은 `/_locales/**` 라우트 규칙에서 경로 전체에 적용되는 헤더를 받는데, 이 규칙은 쿼리를 볼 수 없으므로 짧게 유지됩니다. 반복 로드에서도 차단되는 것은 없습니다.
- 캐시된 HTML이 참조하므로, 오래된 `v`도 계속 제공 가능합니다.

`httpCacheControl: false`는 모든 정적 파일을 `max-age=0, must-revalidate`로 유지합니다. [`httpCacheDuration`](/ko/api/module-options#httpcacheduration)의 기본값은 1년이며, `0`이면 헤더를 보내지 않습니다. `$clearCache()`는 다음에 로드하는 모든 것을 재검증합니다.

Safari는 응답을 재사용할 수 없을 때 사전 로드된 페이로드를 다시 요청합니다: `no-cache`와 `ETag`가 있으면 두 번째 요청은 `304`이고, 캐시 헤더와 검증자가 모두 없으면 두 번째 전체 다운로드가 됩니다. `0`보다 큰 `max-age`는 요청을 한 번으로 만듭니다. 검증자를 추가하지 않는 호스트에서 `httpCacheDuration: 0`을 사용하는 경우에만 이 비용을 치릅니다.

[`dateBuild`](/ko/api/module-options#datebuild)는 `?v=` 값입니다. 기본적으로 번역 파일의 해시이므로 번역이 변경될 때만 바뀌며, 브라우저는 번역을 건드리지 않은 배포 간에 캐시된 페이로드를 유지합니다. 폴백 체인에 따라서도 바뀝니다.

- 값을 고정하려면 직접 설정하세요.
- `?v=`를 완전히 제거하려면 `0` 또는 `''`를 설정하세요. 그러면 페이로드는 절대 `immutable`이 되지 않습니다.

<Tip>

Node 서버에서 사전을 제자리에서 교체한 후에는 `NUXT_I18N_DATE_BUILD=<new value>`로 재시작하세요: 재빌드 없이 `v`를 바꾸는 다른 방법은 없습니다.

</Tip>

### 루트 파일과 델타 파일 {#root-and-delta-files}

`premerged`는 로케일당 하나의 루트 `__root/<locale>/data.json`을 작성하고, 각 페이지 파일에는 루트와 다른 부분만 작성합니다.

- 페이지 파일은 기준이 된 루트를 `__i18n_root` 키로 표시합니다.
- 브라우저는 둘 다 가져오며, 둘 다 도착할 때까지 페이지는 아무것도 표시하지 않고, SSR은 청크당 한 번 이를 병합합니다.
- 표시가 없는 파일은 전체 사전이며 단독으로 사용됩니다: 개발 모드, `source` 모드, 서버 라우트, 그리고 이전 파일을 여전히 보유한 호스트는 모두 설정 없이 이런 파일로 응답합니다.

따라서 `_locales/*/data.json`을 직접 읽는 사람은 델타를 읽게 됩니다. 전체 파일을 유지하려면 `translationPayloads.rootDelta: false`를 설정하세요.

배포를 거치며 열려 있던 탭이 새 델타를 요청하면, 그것이 다른 루트를 기준으로 만들어졌음을 확인하고 표시하기 전에 해당 루트를 가져옵니다.

### 사전을 읽을 수 없는 경우 {#when-a-dictionary-cannot-be-read}

호스트에서의 가져오기 실패(404 제외), 읽을 수 없거나 손상된 파일, 또는 JSON 객체가 아닌 200 응답은 어떤 캐시에도 저장되지 않으며, 다음 요청에서 다시 읽습니다:

- 페이지 렌더링은 경고를 기록하고, 해당 사전에 대해 원시 키를 표시하며, `Cache-Control: no-store`와 함께 `503`으로 응답합니다. 모든 CDN 헤더(`CDN-Cache-Control`, `Cloudflare-CDN-Cache-Control`, `Netlify-CDN-Cache-Control`, `Vercel-CDN-Cache-Control`, `Surrogate-Control`, 라우트 규칙의 값보다 우선)에도 동일하게 적용되며 `Retry-After: 60`도 포함됩니다;
- `/_locales/...`는 `no-store`와 함께 `503`으로 응답합니다;
- `useTranslationServerMiddleware`는 키 또는 기본값을 반환하는 `t`를 제공합니다.

장애 중에 일어나는 일:

- **방문자:** 해당 503의 본문은 페이지 자체입니다. 하이드레이션 시 브라우저가 사전을 다시 읽고, 호스트가 복구되면 텍스트가 나타나며, 서버의 HTML에 키가 있었으므로 하이드레이션 불일치에 대한 Vue 콘솔 오류가 한 번 발생합니다.
- **크롤러**에게는 나중에 다시 오라고 알립니다.
- **캐시:** `swr` 또는 `cache` 라우트 규칙은 상태가 400 이상인 응답을 저장하지 않으며, CDN은 `no-store`를 받으므로 어떤 캐시도 원시 키를 보관하지 않고, 복구 후 첫 요청이 실제 텍스트를 렌더링합니다.
- 규칙에 의해 **이미 캐시된 페이지**는 그대로 유지됩니다: 재검증이 실패하고 아무것도 저장하지 않습니다. Vercel에서 실패한 `isr` 재검증도 같은 방식으로 마지막 페이지를 유지합니다.

이는 렌더링이 로드하는 모든 청크에 적용되며, 루트는 있지만 실패한 페이지 청크와 렌더링 중 나중에 병합되는 청크도 포함됩니다. 정상적인 사전을 가진 페이지, 리디렉션, 오류 페이지는 상태를 유지합니다. [컴포넌트 아일랜드](/ko/guide/server-side-translations)는 예외입니다: 503이면 페이지에서 제거되므로 200으로 유지되며, 따라서 자체 사전이 로드되는 페이지에 아일랜드의 원시 키가 남을 수 있습니다. 장애 중의 요청은 각각 호스트에 도달하며, 응답 헤더에 대한 60초 외에 모듈 자체의 타임아웃은 없습니다.

호스트의 404는 해당 파일이 없다는 의미이며, 실패가 아닙니다. 페이지 렌더링은 브라우저와 마찬가지로 루트 사전을 표시하며, `/_locales/...`는 같은 404로 응답합니다. 어떤 캐시도 이를 보관하지 않으므로, 파일이 나타나면 다음 요청에서 읽히며, 그 대가로 그런 페이지를 렌더링할 때마다 호스트에 요청이 한 번 발생합니다. 루트 파일도 없으면 사전은 비어 있으며, [사전 렌더링](/ko/guide/upgrade#server,-build-and-deployment)이 실패합니다.

서버는 로드된 페이로드를 최대 `cacheMaxSize`개 항목(기본값 1000)의 프로세스 내 LRU 캐시에 보관하며, `cacheTtl`이 설정되면 그 후에 항목을 다시 로드합니다. 두 옵션 모두 [성능 튜닝](/ko/guide/performance)에서 다루며, [`cacheStorage`](/ko/guide/performance#shared-cache-for-several-instances)는 인스턴스 간 공유 캐시를 추가합니다. 그 위에 `/_locales/**`에 Nitro `cache` 라우트 규칙을 추가하지 마세요: 쿼리를 포함한 전체 URL을 키로 사용하며 세 번째 복사본을 저장합니다.

## App baseURL과 페이로드 호스트 {#app-baseurl-and-payload-hosts}

**`app.baseURL`**은 다른 설정이 필요 없습니다. `app.baseURL: '/shop/'`이면 브라우저는 `/shop/_locales/...`를 가져옵니다. 복사본은 `.output/public/_locales/`에 남으며, Nitro가 이를 base 아래에서 제공합니다(정적 호스트는 출력을 `/shop/`에 마운트해야 합니다). 로케일 접두사와 [제외된 경로](/ko/guide/excluding-static-files)는 base 없이 매칭됩니다.

**`app.cdnURL`**도 페이로드가 `public/`의 파일일 때 이를 이동시킵니다: 브라우저는 `<cdnURL>/_locales/...`를 가져오고 사전 로드합니다.

- CDN은 해당 경로에 `_nuxt/` 옆에 `_locales/`를 보유해야 합니다.
- 파일이 `fetch`로 도착하므로, 사이트의 출처를 허용해야 합니다(CORS).
- 서버 라우트만 응답하는 사전(`source` 모드, 공개 복사본 없음)은 앱의 출처에 남습니다.

`cloudflare-module`에서 런타임 `NUXT_APP_BASE_URL`은 Node 호환성(`nodejs_compat`)이 필요합니다. `nitro.cloudflare.nodeCompat`이 꺼져 있으면(플래그 없이 오래된 날짜에서는 Nitro도 이렇게 됩니다) 변수를 보지 못하고 `/`를 제공하며(순수 Nuxt 포함), 로케일 리디렉션은 여전히 base로 이동합니다. 그곳에서는 빌드 시 `app.baseURL`을 설정하세요.

다른 출처에서 페이로드를 제공하려면 클라이언트와 서버가 그곳을 가리키도록 하고 로컬 출력을 끄세요:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    apiBaseClientHost: 'https://cdn.example.com',
    apiBaseServerHost: 'https://cdn.example.com',
    translationPayloads: {
      serverHandler: false,
      publicAssets: false,
      serverAssets: false,
    },
  },
})
```

- Node에서 `serverAssets`는 서버 자체의 읽기를 위해 같은 복사본을 작성하며, 그 파일이 `/_locales`에 응답합니다: 이것도 꺼야 하며, 브라우저용으로 서버 라우트를 유지하는 경우에도 마찬가지입니다(서버 라우트에는 절대 도달하지 않기 때문입니다).
- 호스트는 같은 `<apiBaseUrl>/<page>/<locale>/data.json` 레이아웃을 제공해야 합니다.
- 모든 로컬 출력이 꺼져 있는데 호스트가 없으면 빌드가 경고합니다.

같은 값을 빌드 시 `NUXT_I18N_APP_BASE_URL`, `NUXT_I18N_APP_BASE_CLIENT_HOST`, `NUXT_I18N_APP_BASE_SERVER_HOST`에서 가져올 수도 있습니다. `NUXT_I18N_APP_BASE_SERVER_HOST`는 런타임에도 동작하며 빌드 값보다 우선합니다. 자세한 내용은 [`apiBaseServerHost`](/ko/api/module-options#apibaseserverhost)를 참고하세요.

## 플랫폼 {#platforms}

모듈이나 그 출력에 필요한 것만 다룹니다. 계정, 리전, CLI 로그인은 각 플랫폼의 문서를 참고하세요.

### Cloudflare Workers {#cloudflare-workers}

프리셋 `cloudflare_module`. `wrangler deploy`는 Nitro의 출력을 esbuild로 한 번 더 번들링하며, 그 후에는 원시 `defineAsyncComponent(() => import('./X.vue'))`가 서버에서 비어 있는 상태로 렌더링됩니다. Nuxt의 기본 오류 페이지가 이런 컴포넌트이므로, 404의 본문이 비어 있고 브라우저가 하이드레이션 불일치를 기록합니다. 그러면 클라이언트가 페이지를 렌더링하고 상태는 404로 유지되지만, JavaScript가 없으면 페이지가 비어 있습니다. 이는 [nuxt#33270](https://github.com/nuxt/nuxt/issues/33270)입니다: 모듈 없는 순수 Nuxt도 마찬가지입니다. 페이지 라우트는 영향을 받지 않습니다.

두 번째 번들링을 끄세요:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: {
    preset: 'cloudflare_module',
    cloudflare: {
      deployConfig: true, // `wrangler` below applies only with it
      wrangler: {
        no_bundle: true,
        find_additional_modules: true,
        rules: [{ type: 'ESModule', globs: ['**/*.mjs'] }],
      },
    },
  },
})
```

```bash
npx nuxi build
cd .output/server && npx wrangler deploy -c wrangler.json
```

`compatibilityDate`를 `2024-09-19` 이후로 설정하세요: 그보다 오래된 날짜는 레거시 프리셋을 선택하며, 이 프리셋은 `wrangler.json`을 작성하지 않고 오류도 표시하지 않습니다. 그러면 404가 렌더링되고 업로드 크기도 줄어듭니다: 테스트 앱에서 246 KiB 대비 190 KiB gzip. 자체 `error.vue`가 다른 해결책이지만, 오류 페이지만 다룹니다.

모듈 자체는 `nodejs_compat`이 필요하지 않습니다. 한도는 [번들 한도](#bundle-limits-on-edge)를 참고하세요.

### Cloudflare Pages {#cloudflare-pages}

`cloudflare-pages-static` 프리셋을 사용하세요. `nuxi generate --preset cloudflare-pages`는 `index.html`이 없는 서버 빌드입니다.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: {
    preset: 'cloudflare-pages-static',
    prerender: { autoSubfolderIndex: false },
  },
})
```

```bash
npx nuxi generate
npx wrangler pages project create my-site --production-branch main --force
npx wrangler pages deploy dist --project-name my-site --branch main
```

- **출력.** 프리셋은 `.output/public`이 아닌 `dist/`에 작성합니다.
- **`--force`.** 이것이 없으면 새 wrangler(여기서는 4.156)가 `pages project create`를 Workers로 넘깁니다. 이것을 사용하면 기존 방식의 Pages 프로젝트를 얻습니다. 생성 시 한 번만 필요합니다.
- **`autoSubfolderIndex: false`.** Pages는 `/de`에 `/de/`로의 308로 응답하는데 canonical과 `hreflang`은 `/de`를 지정하므로, 리디렉션을 가리키게 됩니다. 이 옵션을 사용하면 파일이 `de.html`이 되고 리디렉션이 사라집니다.
- **404 시 콘솔의 `NUXT_E1005`**는 정상적인 404입니다. `404.html`이 앱이 마운트되기 전에 클라이언트에서 시작하므로 Nuxt가 그렇게 보고합니다. 페이지는 동작하며, 순수 Nuxt도 같은 줄을 출력합니다.

### Vercel과 Vercel Edge {#vercel-and-vercel-edge}

프리셋 `vercel`과 `vercel_edge`, 앱 변경 없음. 태그는 플랫폼의 전달 헤더를 통해 `metaBaseUrl` 없이 동작합니다. Vercel Edge는 번들 한도가 작습니다: [번들 한도](#bundle-limits-on-edge)를 참고하세요. 공유 캐시에는 [`upstash` 드라이버](/ko/guide/performance#upstash-on-vercel-and-vercel-edge)를 사용하세요.

### Netlify {#netlify}

프리셋 `netlify`와 `netlify_edge`.

```bash
npx nuxi build --preset netlify
npx netlify deploy --prod --no-build --dir dist --functions .netlify/functions-internal
```

- **`nitro.output`은 설정하지 마세요.** 프리셋이 `.netlify/`와 `dist/`를 직접 작성합니다.
- **배포하는 폴더에 `package.json`을 유지하세요.** 없으면 CLI가 상위 폴더를 확인하고 함수를 배포하지 않으며, 오류도 없습니다.
- **Netlify Edge**는 `--dir dist`만으로 배포됩니다. [Edge 런타임에서의 날짜](#dates-on-edge-runtimes)를 참고하세요.

### Cloud Run {#cloud-run}

기본 `node-server` 빌드를 사용하세요. 로컬에서 docker가 실행 중이지 않으면 `gcloud run deploy --source`는 출력 폴더에 `Dockerfile`이 필요합니다:

```dockerfile
# .output/Dockerfile
FROM node:22-slim
WORKDIR /app
COPY . .
ENV NODE_ENV=production
CMD ["node", "server/index.mjs"]
```

```bash
cd .output && gcloud run deploy my-app --source .
```

태그는 플랫폼의 전달 헤더를 통해 `metaBaseUrl` 없이 동작합니다.

### Deno Deploy {#deno-deploy}

프리셋 `deno_deploy`. `deno deploy`가 `deployctl`을 대체합니다. 엔트리포인트 `server/index.ts`로 동적 앱을 만들고, 출력 폴더에서 배포하세요.

### Firebase {#firebase}

| 제품 | 설정 |
| --- | --- |
| App Hosting | Node 빌드를 실행합니다: 기본 프리셋 또는 `firebase-app-hosting`과 Node 20+를 사용하세요 |
| Cloud Functions | `firebase` 프리셋은 페이로드를 포함시키며 `firebase-functions`가 필요합니다 |
| Hosting (정적) | `.output/public`을 파일로 제공하므로, `/_locales/**`는 Hosting의 헤더를 받습니다 |

정적 Hosting에서 JSON이 잘못된 `Content-Type`이나 캐싱으로 반환되면, `firebase.json`에 `/_locales/**`에 대한 `headers` 항목을 추가하세요. Nuxt `routeRules` 헤더는 Hosting이 직접 제공하는 파일에는 적용되지 않습니다. 페이로드 라우트는 서버에 도달하는 응답에 자체 `Content-Type`과 `Cache-Control`을 설정합니다.

### AWS Amplify {#aws-amplify}

`aws-amplify`는 정적 파일을 서버 옆이 아닌 컴퓨트 폴더 옆에 보관하므로, 함수 플랫폼에서처럼 페이로드가 포함됩니다.

### 하나의 빌드로 여러 인스턴스 실행 {#several-instances-of-one-build}

하나의 아티팩트를 환경 변수를 통해 인스턴스마다 다른 기본 로케일이나 비활성화된 로케일로 실행할 수 있습니다: [런타임 재정의](/ko/guide/runtime-overrides)를 참고하세요. 런타임에만 비활성화된 로케일은 여전히 `public/`에 정적 파일이 있으므로, 접근할 수 없어야 한다면 빌드 시 비활성화하세요.

원격 호스트에서 사전을 로드하는 인스턴스는 Redis, Upstash, Cloudflare KV 또는 D1, Deno KV 또는 다른 Nitro 스토리지에서 이를 공유할 수 있으므로, 백엔드는 인스턴스당 하나가 아닌 한 번의 요청만 받습니다. 이것은 번역 소스가 아닌 캐시입니다: [여러 인스턴스를 위한 공유 캐시](/ko/guide/performance#shared-cache-for-several-instances)를 참고하세요.

## 프록시 또는 CDN 뒤에서 {#behind-a-proxy-or-cdn}

앱은 요청에서 공개 호스트와 스킴을 알아내야 합니다.

| 프록시가 보내는 것                              | 일반 빌드                                      | 로케일에 `baseUrl`이 있는 빌드                                                   |
| -------------------------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------- |
| 실제 `Host`                              | 설정할 것 없음                                   | 설정할 것 없음                                                                    |
| 원본의 `Host`와 `X-Forwarded-Host` | 설정할 것 없음                                   | [`trustForwardedHost: true`](/ko/api/module-options#trustforwardedhost)              |
| 둘 다 없음                                      | [`metaBaseUrl`](/ko/api/module-options#metabaseurl) | 도움이 되는 설정 없음: 모든 요청이 원본의 호스트처럼 보이므로 프록시를 변경하세요 |

- **`swr` 또는 `cache` 아래의 라우트.** 표가 적용되지 않습니다: [HTML 캐싱](#caching-html)을 참고하세요. `metaBaseUrl` 또는 `site.url`을 설정하세요.
- **`X-Forwarded-Proto`.** 이를 보내세요. 그렇지 않으면 HTTPS 프록시 뒤에서 canonical URL이 `http://`가 됩니다. `metaBaseUrl`도 이를 해결합니다.
- **도메인 빌드에서는** 도메인이 태그의 기본 URL을 결정합니다. 그곳에서는 `metaTrustForwardedHost`가 아닌 `trustForwardedHost`만 도메인을 선택합니다.
- **리디렉션은 상대 경로이고 로케일 쿠키에는 `Domain`이 없으므로,** 둘 다 공개 호스트에 머뭅니다.

<Warning>

**원본에 계속 접근 가능하다면 `metaBaseUrl`을 고정하세요** — `metaBaseUrl`이나 `site.url`이 없는 일반 빌드에서는 canonical, `hreflang`, `og:url`이 요청에서 호스트를 가져옵니다. [`metaTrustForwardedHost`](/ko/api/module-options#metatrustforwardedhost)는 기본적으로 켜져 있으므로, `X-Forwarded-Host: evil.example`이 포함된 직접 요청은 해당 태그에 `https://evil.example`을 받게 되고, 앞단의 캐시가 그 페이지를 퍼뜨립니다. `*.workers.dev` 같은 플랫폼 호스트가 바로 그런 원본입니다. `metaBaseUrl`은 `Host`에 대해서도 이를 막습니다. 도메인 빌드의 알려진 호스트는 자체 `baseUrl`을 유지합니다. `trustForwardedHost: true`이면 직접 접근하는 클라이언트가 다른 도메인의 페이지를 선택할 수 있으므로, 헤더를 덮어쓰는 프록시 뒤에서만 켜세요.

</Warning>

## HTML 캐싱 {#caching-html}

대부분의 URL은 로케일을 명시하므로 캐시해도 안전합니다. 다음은 방문자에 따라 달라집니다:

| 설정                          | URL                                              |
| ------------------------------ | ------------------------------------------------- |
| 기본값, `autoDetectPath: '/'` | `/`                                               |
| `prefix`                       | `/`와 리디렉션만 하는 모든 접두사 없는 URL |
| `autoDetectPath: '*'`          | 모든 URL                                         |
| `no_prefix`                    | 모든 페이지                                        |

- **`Vary`.** 이 응답들은 [`localeCookie`](/ko/api/module-options#localecookie)가 설정되면 `Cookie`를, `autoDetectLanguage`가 켜져 있으면 `Accept-Language`를 포함한 `Vary`를 가집니다. 이를 준수하는 캐시는 응답을 구분하여 보관합니다.
- **`Vary`를 무시하는 캐시**(예: "URL 기준으로 모두 캐시")는 이 URL들을 건너뛰어야 합니다. 그렇지 않으면 한 방문자의 `302 /de`가 다음 방문자에게 전달되고, 저장된 기본 페이지가 모든 사람의 리디렉션을 없앱니다. `/`에서는 `redirects: false`를 설정할 수도 있습니다. Nitro의 라우트 캐시는 경로와 `varies` 목록을 키로 사용하므로, `/`를 `swr`와 `cache` 규칙에서도 제외하세요.
- **`Set-Cookie`.** `localeCookie`가 설정되면 접두사 아래의 모든 서버 렌더링 페이지가 `Set-Cookie`를 가지며, 올바른 CDN은 이를 저장하지 않습니다. 캐시된 HTML을 위해서는 `localeCookie`를 끄거나, 엣지에서 헤더를 제거하세요.
- **`swr`와 `cache` 규칙에는 `metaBaseUrl` 또는 `site.url`이 필요합니다.** Nitro는 그런 라우트를 `cache.varies`에 있는 헤더만으로 렌더링하므로, `Host`, `X-Forwarded-Host`, `X-Forwarded-Proto`가 사라지고 요청 URL은 `http://localhost`가 됩니다. 고정된 원본이 없으면 해당 라우트의 canonical, `hreflang`, `og:url`은 모든 플랫폼에서 `http://localhost`를 가리킵니다. 순수 Nuxt의 `useRequestURL()`도 그곳에서 같은 값을 읽습니다. 대신 방문자로부터 호스트를 가져오면 한 방문자의 `X-Forwarded-Host`가 모든 방문자가 받는 페이지에 들어가게 됩니다. 도메인 빌드는 영향을 받지 않습니다: 태그가 로케일의 `baseUrl`을 사용합니다.

  하나의 빌드가 여러 호스트를 제공하고 단일 원본이 맞지 않는다면, 규칙이 헤더를 보도록 하고 값마다 하나의 복사본을 유지하세요: `'/blog/**': { swr: 60, cache: { varies: ['host', 'x-forwarded-host', 'x-forwarded-proto'] } }`. 각기 다른 값마다 새 캐시 항목이 되므로, 임의의 헤더를 보내는 클라이언트가 캐시를 채울 수 있습니다: 원본을 이 헤더를 설정하는 프록시 뒤에 두세요.
- **도메인 빌드에서의 `swr`와 `cache` 규칙.** 모듈은 그런 모든 규칙의 `cache.varies`에 `host`를, `trustForwardedHost`가 있으면 `x-forwarded-host`도 추가하므로, 한 도메인이 다른 도메인에 자신의 페이지를 제공하지 않습니다. `cache: false`인 규칙은 작성한 그대로 유지됩니다. `isr`은 플랫폼의 캐시이므로 호스트를 키로 사용하는지 확인하세요. 호스트가 키에 포함되면 임의의 호스트를 보내는 클라이언트가 캐시 항목을 추가합니다.

페이로드 파일에 대해서는 [캐시 헤더와 dateBuild](#cache-headers-and-datebuild)를 참고하세요.
