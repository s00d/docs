기본값은 일반적인 앱에 맞게 조정되어 있습니다. 페이지와 로케일마다 하나의 JSON 페이로드, HTML에서 분리된 번역, 서버의 크기 제한 캐시가 그것입니다. 이 페이지에서는 카탈로그가 크거나, 서버 메모리가 제한적이거나, 페이로드가 다른 호스트에서 올 때 바꿀 만한 몇 가지 설정을 소개합니다. `@nuxtjs/i18n` 및 일반 Nuxt와 비교한 측정 수치는 [벤치마크](/ko/guide/performance-results)를 참고하세요.

## 기본값이 이미 하는 일 {#what-the-defaults-already-do}

- **페이지당 하나의 페이로드.** 빌드는 루트, 페이지, 폴백 로케일 키를 `/_locales/<page>/<locale>/data.json`으로 병합하므로, 페이지는 파일 하나만 로드하고 `$t`는 단 한 번의 조회로 끝납니다.
- **HTML에 사전이 없음.** SSR은 번역을 서버 메모리에 유지하며, 브라우저는 `__NUXT_DATA__`에서 파싱하는 대신 페이로드를 가져옵니다.
- **브라우저 캐시.** `?v=`는 번역이 바뀔 때만 변경되므로, 번역을 건드리지 않은 배포에서는 브라우저가 페이로드를 계속 유지합니다. 호스트의 정적 사본은 60초 동안 최신 상태로 간주되고 그 후에는 재검증됩니다. 재방문 로드는 `304` 한 번만 기다립니다. 서버 라우트는 1년 동안 `immutable`로 응답합니다([배포](/ko/guide/deployment#cache-headers-and-datebuild)).
- **제한된 서버 메모리.** 서버는 기본적으로 최대 1000개의 페이로드를 캐시하며, 가장 오래전에 사용된 항목부터 제거합니다.

## 페이지별로 번역 분리 {#split-translations-by-page}

한 페이지에서만 쓰는 키는 루트 파일이 아니라 `locales/pages/<page>/<locale>.json`에 두세요. 루트 키는 모든 페이지의 페이로드에 포함되기 때문입니다. [번역 파일](/ko/guide/translations)을 참고하세요.

두 가지 설정이 이 분리 방식을 바꿉니다.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    // pages that show the same keys share one payload: /de/products/123 loads the products payload
    routesLocaleLinks: { 'products-id': 'products' },
    // or: no page files at all, every page loads only the root dictionary
    // disablePageLocales: true,
  },
})
```

[`routesLocaleLinks`](/ko/api/module-options#routeslocalelinks)는 관련 라우트의 중복 페이로드를 줄입니다. [`disablePageLocales`](/ko/api/module-options#disablepagelocales)는 로케일당 사전 하나가 더 간단한 소규모 앱에 적합합니다.

## 서버 캐시 {#server-caches}

| 설정 | 기본값 | 효과 |
| --- | --- | --- |
| [`cacheMaxSize`](/ko/api/module-options#cachemaxsize) | `0` | 페이로드 캐시의 최대 항목 수. `0` = 브라우저에서는 제한 없음, 서버에서는 1000. |
| [`cacheTtl`](/ko/api/module-options#cachettl) | `0` | 캐시된 항목을 다시 로드하기까지의 초. `0` = 다시 로드하지 않음. 페이로드가 `apiBaseServerHost`에서 오고 재배포 없이 바뀔 때 설정하세요. |
| `serverTranslationPreload` | `false` | 모든 페이지 요청에 대해 Nitro 미들웨어에서 `index` 페이로드를 로드하여, 서버 헬퍼와 홈 페이지가 이를 재사용하도록 합니다. |

페이지 × 로케일 수가 많은 작은 인스턴스에서는 `cacheMaxSize`를 낮추세요. 로컬에서 편집하는 번역에는 TTL이 필요 없습니다. 개발 모드는 파일을 실시간으로 읽고, 프로덕션 페이로드는 배포할 때만 바뀝니다.

## Node 서버의 메모리 {#memory-on-a-node-server}

꾸준한 부하에서 Node 서버는 라이브 힙의 약 12배 수준에 머무를 수 있습니다. 페이지당 10만 개 키의 스트레스 테스트에서 90 MB의 라이브 힙이 약 1.1 GB의 RSS로 동작했습니다. 이것은 메모리 누수가 아닙니다. 한 번의 과도한 GC 사이클 이후 V8은 힙 한도를 높이고, 부하가 지속되는 동안 재사용을 위해 해제된 페이지를 풀에 보관합니다. 부하가 멈추고 약 8초 후 풀이 비워지며 RSS는 약 160 MB로 떨어집니다. `global.gc()`는 이 메모리를 반환하지 않습니다. 모듈이 없는 일반 Nuxt도 더 작은 힙에 비례하여 똑같이 동작합니다.

이것은 여유 메모리를 소모합니다. 메모리 한도가 그 수준보다 낮고 힙 상한이 없으면 프로세스가 종료될 수 있습니다. 한도에 맞으면서 라이브 힙보다 충분히 큰 상한을 설정하세요.

```bash
NODE_OPTIONS=--max-old-space-size=512 node .output/server/index.mjs
```

| 10만 개 키, 12개 로케일, 5~30분 부하 | 기본값 | `--max-old-space-size=512` |
| --- | --- | --- |
| 부하 중 RSS | 약 1,150 MB | 254-287 MB |
| 초당 요청 수 | 624 | 517-572 |

즉 상한은 처리량의 8~10%를 메모리와 맞바꿉니다. 일반적인 크기의 카탈로그는 힙이 더 작고 증가 폭도 더 작습니다. 이 측정은 컨테이너가 아닌 macOS의 Node 22에서 수행되었습니다.

## 파싱 시간과 `dir` {#parse-time-and-dir}

로케일에 `dir: 'auto'`를 지정하면 브라우저가 파싱하는 동안 콘텐츠에서 방향을 판단해야 합니다. Chromium에서 요소 20,000개일 때 DOMContentLoaded는 `dir="auto"`를 사용하면 약 1.1초, 사용하지 않으면 0.1초였고, 요소 5,000개일 때는 약 130 ms 대 45 ms였습니다. `dir`을 설정하지 않거나 `ltr` 또는 `rtl`로 설정하세요([텍스트 방향](/ko/guide/seo#text-direction)).

## 여러 인스턴스를 위한 공유 캐시 {#shared-cache-for-several-instances}

하나의 빌드로 여러 인스턴스를 실행할 때, [`cacheStorage`](/ko/api/module-options#other)는 앱이 `nitro.storage`에서 구성한 연결을 사용하여 모든 Nitro 스토리지에 하나의 공유 사전 캐시를 제공합니다. 모듈은 커넥터나 의존성을 추가하지 않습니다.

**이것은 소스가 아니라 캐시입니다.** 번역은 임베드된 페이로드나 공개 페이로드, 또는 `apiBaseServerHost`에서 옵니다. 소스에서 온 것만 기록되고 키에는 빌드 정보가 포함되므로, 직접 채운 스토어는 읽히지 않습니다. KV나 데이터베이스에서 번역을 제공하려면 이를 읽는 작은 라우트를 `apiBaseServerHost`에 두세요.

**도움이 되는 경우.** 원격 `apiBaseServerHost`를 사용할 때만 해당됩니다. 39개의 사전을 순회하는 세 인스턴스는 이 옵션 없이 호스트에 117번 요청했고, 옵션을 사용하면 48번 요청했습니다. 디스크에 파일이 있는 경우 스토어 적중이 파일보다 빠르지 않으며, 12개 페이지의 첫 순회는 옵션 없이 280-296 ms, 채워진 Redis로는 308-325 ms가 걸렸으므로 설정하지 마세요. 사전을 임베드하는 프리셋에서는 호스트 없이는 아무 효과가 없으며, 빌드가 이를 알려 줍니다.

콜드 사전, 클라이언트 하나, 각각 한 번 순회한 대략적인 수치이며, 대부분은 호스트까지의 거리입니다.

| 스토어 | 호스트에서 | 스토어에서 |
| --- | --- | --- |
| Cloudflare KV | 약 300 ms | 약 110 ms |
| D1 | 약 230 ms | 약 115 ms |
| Deno KV | 약 430 ms | 약 100 ms |
| Upstash, Vercel serverless | 약 445 ms | 약 245 ms |
| Upstash, Vercel Edge | 약 505 ms | 약 235 ms |

### Redis {#redis}

프로젝트에 `ioredis`가 필요합니다.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    storage: {
      redis: { driver: 'redis', url: process.env.REDIS_URL },
    },
  },
  i18n: {
    cacheStorage: 'redis', // the mount name
    apiBaseServerHost: 'https://translations.internal',
    cacheTtl: 300,
  },
})
```

### Vercel 및 Vercel Edge의 Upstash {#upstash-on-vercel-and-vercel-edge}

두 환경 모두에서 `upstash` 드라이버를 사용하세요. `redis` 드라이버는 TCP가 필요하지만 이 드라이버는 REST로 통신합니다. 프로젝트에 `@upstash/redis`가 필요하며, 환경 변수에서 `UPSTASH_REDIS_REST_URL`과 `UPSTASH_REDIS_REST_TOKEN`을 읽습니다.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    storage: {
      upstash: { driver: 'upstash' },
    },
  },
  i18n: {
    cacheStorage: 'upstash',
    apiBaseServerHost: 'https://translations.example.com',
  },
})
```

### Cloudflare KV {#cloudflare-kv}

네임스페이스를 Worker에 `I18N_KV`로 바인딩하세요(wrangler 설정의 `kv_namespaces`).

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    storage: {
      kv: { driver: 'cloudflare-kv-binding', binding: 'I18N_KV' },
    },
  },
  i18n: {
    cacheStorage: 'kv',
    apiBaseServerHost: 'https://translations.example.com',
  },
})
```

호스트가 같은 계정의 다른 Worker라면 `global_fetch_strictly_public` 호환성 플래그가 필요합니다. 그렇지 않으면 fetch가 도달하지 않습니다.

### Cloudflare D1 {#cloudflare-d1}

`nitro.storage`는 데이터베이스 객체를 담을 수 없으므로 Nitro 플러그인이 드라이버를 마운트합니다. 마운트는 처음 사용할 때 확인되므로 이 시점이면 충분히 이릅니다. 데이터베이스를 `I18N_DB`(`d1_databases`)로 바인딩하고 프로젝트에 `unstorage`를 추가하세요.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    experimental: { database: true },
    database: {
      default: { connector: 'cloudflare-d1', options: { bindingName: 'I18N_DB' } },
    },
  },
  i18n: {
    cacheStorage: 'd1',
    apiBaseServerHost: 'https://translations.example.com',
  },
})
```

```ts
// server/plugins/i18n-storage.ts
import dbDriver from 'unstorage/drivers/db0'

export default defineNitroPlugin(() => {
  useStorage().mount('d1', dbDriver({ database: useDatabase() }))
})
```

`db0` 드라이버는 실험적 기능으로 표시되어 있으며 TTL을 무시합니다. 이전 빌드의 행은 직접 삭제할 때까지 남아 있습니다.

### Deno KV {#deno-kv}

Deno Deploy에서 데이터베이스를 프로비저닝하고(`deno deploy database provision <name> --kind denokv`), 앱에 할당한 뒤(`deno deploy database assign`), 드라이버를 사용하세요.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    storage: {
      kv: { driver: 'deno-kv' },
    },
  },
  i18n: {
    cacheStorage: 'kv',
    apiBaseServerHost: 'https://translations.example.com',
  },
})
```

### 동작 방식 {#how-it-behaves}

사전은 먼저 인스턴스 자체 캐시에서, 그다음 공유 스토리지에서, 마지막으로 소스에서 조회됩니다. `$t`는 동기식이라 트리가 메모리에 있어야 하므로 인스턴스 자체 캐시는 유지됩니다. 이 기능은 누가 가져오는지와 누가 제공하는지를 분리할 뿐, 메모리를 절약하지는 않습니다.

- **누가 가져오는가.** 원격 호스트를 사용하면 인스턴스마다가 아니라 사전마다 백엔드에서 한 번 가져옵니다. 잠금이 없기 때문에 같은 순간에 캐시 미스가 난 인스턴스는 각자 가져옵니다.
- **자체 사전이 없는 페이지**는 저장되지 않으므로, 임의로 만든 페이지 이름이 키를 추가할 수 없습니다. 각 인스턴스는 그런 페이지를 호스트에서 한 번씩 가져오며, isolate가 생겼다 사라지는 Workers에서는 이것이 꾸준히 조금씩 발생합니다.
- **호스트가 다운된 경우.** 저장된 사전이 있는 페이지는 동작합니다. 사전이 없는 페이지는 저장된 루트 사전으로 렌더링되며, 자체 키는 원시 상태로 표시되고 [어떤 캐시도 보관하지 않는 `503`](/ko/guide/deployment#when-a-dictionary-cannot-be-read)이 반환됩니다. 호스트가 복구될 때까지 `/_locales`는 해당 페이지에 대해 `503`으로 응답합니다. `useTranslationServerMiddleware`는 읽을 수 없는 사전에 대해 키를 반환합니다.
- **호스트**는 런타임의 `NUXT_I18N_APP_BASE_SERVER_HOST`이거나, 그렇지 않으면 빌드의 `apiBaseServerHost`로, 이 옵션이 없을 때와 같습니다. 사전을 임베드하는 프리셋(Cloudflare, Vercel, Netlify, [배포](/ko/guide/deployment#serverless-and-edge) 참고)에서는 호스트가 있을 때만 이 레이어가 적용됩니다. 데이터가 이미 번들에 있으므로 KV의 사본은 메모리에 있는 것을 네트워크로 읽는 셈이 됩니다.
- **키**는 `i18n-micro:<buildId>~<dateBuild>~<fallbackLocale>~<host>:<locale>:<page>`이므로, 롤링 배포 중인 두 빌드가 서로의 키를 읽지 않고, 하나의 아티팩트를 사용하는 두 백엔드도 마찬가지입니다. 각 인스턴스는 하나의 빌드(하나의 아티팩트 또는 고정된 Nuxt [`buildId`](https://nuxt.com/docs/api/nuxt-config#buildid))에서 나와야 하며, 따로 빌드된 인스턴스는 그냥 공유하지 않습니다. `buildId`를 고정하고 `dateBuild: 0`을 사용하면 서로 다른 두 빌드가 키를 공유하게 됩니다. 활성화된 로케일만 조회되며, 200자를 넘는 페이지 이름은 이 레이어를 건너뜁니다.
- **저장되는 것.** 사전은 기록되기 전에 루트 사전(`__root`)과 비교되며, 모든 루트 키를 포함하고 루트와 다를 때만 저장됩니다. 따라서 루트로 응답된 임의의 페이지는 키를 추가하지 않으며, 페이지에 대한 200 오류 본문도 마찬가지입니다. 각 인스턴스는 그런 페이지를 소스에서 한 번 읽습니다. 호스트는 알 수 없는 페이지에 루트, 빈 객체 또는 404로 응답해야 하며 `__root`를 제공해야 합니다. `__root`가 없는 호스트나 루트 키 없이 페이지를 제공하는 호스트는 아무것도 공유하지 않습니다. 호스트가 `__root` 자체를 올바른 형식의 오류로 응답하면 그것이 저장됩니다. 백엔드가 그럴 수 있다면 `cacheTtl`을 짧게 유지하세요.
- **만료.** 항목은 기록된 후 `cacheTtl`초가 지나면, `cacheTtl`이 `0`이면 하루가 지나면 만료되므로 이전 빌드의 키가 쌓이지 않습니다. 값은 인스턴스 자체 캐시에 또 한 번의 `cacheTtl` 동안, 렌더의 청크 캐시에 한 번 더 남아 있을 수 있으므로 백엔드 변경은 `cacheTtl`의 세 배 이내에 반영됩니다. 만료 기능이 없는 드라이버(`fs`)는 직접 제거할 때까지 이전 키를 유지합니다.
- **스토리지가 실패해도** 페이지는 실패하지 않습니다. 읽기는 최대 1초가 걸릴 수 있으며, 이는 연결 핸드셰이크와 해당 위치에서 콜드 상태인 Cloudflare KV 키를 감안한 값입니다. 실패 후에는 스토어가 다시 응답할 때까지 제한이 250 ms가 됩니다. 연속 세 번 실패하면 레이어가 5초 동안 닫힙니다. 닫혀 있는 동안과 방금 읽기가 실패한 동안에는 아무것도 기록되지 않습니다. 쓰기 실패는 아무것도 닫지 않으므로 읽기 전용 복제본은 계속 읽기를 제공합니다. 응답이 이 제한보다 오래 걸리는 스토어는 실패로 간주됩니다. 즉 미스로 처리되고 사전은 소스에서 옵니다. ioredis의 경우 핸드셰이크에 세 번의 왕복이 필요하므로 명령당 약 400 ms부터 그렇게 됩니다. 모듈은 분당 한 번 경고를 기록하며, ioredis는 그 위에 자체 오류를 출력합니다. 사전이 아닌 값은 미스로 간주되어 덮어쓰입니다. 알 수 없는 마운트 이름은 처음 사용할 때 한 번 경고하며, 이후 앱은 이 레이어 없이 실행됩니다.
- **소스가 실패하면** 그 실패는 어디에도 유지되지 않습니다. 실패한 fetch나 읽을 수 없는 파일은 이 캐시든 인스턴스 자체 캐시든 어떤 캐시에도 들어가지 않으며, 다음 요청에서 다시 읽습니다. [배포](/ko/guide/deployment#when-a-dictionary-cannot-be-read)를 참고하세요.
- **개발 모드와 프리렌더에서는 꺼져 있습니다.** 이들은 파일을 직접 읽으며, 프로덕션 Redis가 필요해서는 안 됩니다.
- **무효화.** 퍼지 호출은 없습니다. 새 빌드는 새 키를 사용합니다. 실행 중인 빌드를 즉시 새로 고치려면 스토리지에서 `i18n-micro:` 키를 제거하고 인스턴스를 재시작하세요. `clearCache`와 HMR은 프로세스 상태에만 영향을 줍니다.
- 런타임 변경(`$mergeTranslations`, `$defineI18nRoute`)은 이를 수행한 렌더나 브라우저에만 남으며 스토리지에는 절대 기록되지 않습니다.

## 페이로드 크기 {#payload-size}

페이로드 출력이 `translationPayloads.warnFileCount`(500개 파일) 또는 `warnSizeBytes`(10 MB)를 넘으면 빌드가 경고합니다. 그럴 때는 다음을 시도하세요.

- 페이지 전용 키를 루트 파일에서 옮기세요.
- 같은 키를 보여 주는 라우트를 연결하세요(`routesLocaleLinks`).
- 서버리스나 Edge에서는 `translationPayloads.mode: 'source'`를 사용하여 서버 번들이 모든 페이지 × 로케일 대신 압축된 소스를 임베드하도록 하세요([배포](/ko/guide/deployment#serverless-and-edge)). Edge 빌드는 플랫폼 한도를 넘으면 자체적으로 경고합니다([번들 한도](/ko/guide/deployment#bundle-limits-on-edge)).
- 정적 페이로드의 `.gz` / `.br` 사본을 위해 `nitro.compressPublicAssets`를 활성화하세요.

## 측정 {#measuring}

저장소는 `pnpm run budget:payload`로 플레이그라운드가 전송하는 내용을 추적합니다. 현재 수치는 다음과 같습니다.

`playground`의 `/`, `/de`에서 측정:

| 측정 항목 | 크기 |
| --- | --- |
| 디스크의 번역 소스 | 7.8 MB |
| 별도의 페이로드 파일로 제공 | 23.9 MB |
| 가장 큰 인라인 `__NUXT_DATA__` | 0.4 KB |
| 클라이언트 에셋 | 624.4 KB |

플레이그라운드는 최대 10만 개 키의 생성된 사전을 사용하는 테스트 벤치이므로, 이 수치는 실제
애플리케이션에서 기대할 값이 아니라 비교 측정을 위한 고정점입니다. 수치가 예상치 않게 커지면 예산 검사가 실패하며,
이를 통해 페이로드에 담기는 내용의 의도치 않은 변경을 알아챌 수 있습니다.

`pnpm test:performance`로 벤치마크 스위트를 직접 실행해 보세요. 작동 방식은 [벤치마크 방법론](https://s00d.github.io/nuxt-i18n-micro/contributing/performance-methodology)에 있습니다.
