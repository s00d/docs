# Référence de configuration

Référence complète de chaque option sous la clé `i18n` dans `nuxt.config`. Les types et valeurs par défaut correspondent à [`ModuleOptions`](https://github.com/s00d/nuxt-i18n-micro/blob/main/packages/types/src/index.ts) dans `@i18n-micro/types`.

## Référence rapide

# Détails des options

Le module offre de nombreuses options de configuration pour personnaliser votre installation d'internationalisation.

### 🌍 Paramètres de langue de base

#### `locales`

{/* generated:option:locales — do not edit; run `pnpm run docs:generate` */}

**Type** `Locale[]` · **Défaut** `[]`

Liste des langues prises en charge. Chaque entrée définit un code de langue et des métadonnées facultatives (ISO, direction, nom d'affichage, etc.).

{/* /generated:option:locales */}

Chaque objet de langue prend en charge :

| Propriété        | Type      | Requis   | Description                                           |
| ---------------- | --------- | -------- | ----------------------------------------------------- |
| `code`           | `string`  | ✅       | Identifiant unique (par exemple, `'en'`)              |
| `displayName`    | `string`  | ❌       | Nom lisible pour les sélecteurs (par exemple, `'English'`) |
| `iso`            | `string`  | ❌       | Code ISO (par exemple, `'en-US'`)                     |
| `dir`            | `string`  | ❌       | Direction du texte (`'ltr'` ou `'rtl'`)               |
| `disabled`       | `boolean` | ❌       | Désactiver dans le menu déroulant si `true`           |
| `baseUrl`        | `string`  | ❌       | URL de base pour les domaines propres à une langue    |
| `baseDefault`    | `boolean` | ❌       | Retire le préfixe de langue des URL                   |
| `fallbackLocale` | `string`  | ❌       | Repli par langue (surcharge le global)                |
| `[key: string]`  | `unknown` | ❌       | Toute propriété personnalisée (voir ci-dessous)       |

**Exemple** :

```typescript
locales: [
  { code: 'en', iso: 'en-US', dir: 'ltr' },
  { code: 'fr', iso: 'fr-FR', dir: 'ltr' },
  { code: 'ar', iso: 'ar-SA', dir: 'rtl', disabled: true },
  {
    code: 'de',
    iso: 'de-DE',
    dir: 'ltr',
    baseUrl: 'https://de.example.com',
    baseDefault: true,
  },
]
```

<Warning>
L'utilisation de `baseUrl` peut entraîner la duplication de routes internes en tant que liens externes, ce qui complique le routage et la maintenance. Envisagez plutôt de créer directement des liens externes pour certaines langues.
</Warning>

#### Propriétés personnalisées de langue

Vous pouvez ajouter n'importe quelle propriété personnalisée aux objets de langue. Elles sont transmises à l'exécution et accessibles via `$getLocales()` :

```typescript
locales: [
  { code: 'en', iso: 'en-US', flag: '🇬🇧', currency: 'GBP' },
  { code: 'de', iso: 'de-DE', flag: '🇩🇪', currency: 'EUR' },
  { code: 'ru', iso: 'ru-RU', flag: '🇷🇺', currency: 'RUB' },
]
```

Accédez-y dans les composants :

```vue
<template>
  <ul>
    <li v-for="locale in $getLocales()" :key="locale.code">{{ locale.flag }} {{ locale.displayName }} ({{ locale.currency }})</li>
  </ul>
</template>
```

Par défaut, les propriétés personnalisées sont typées comme `unknown`. Pour un support TypeScript complet, utilisez l'**augmentation de module**. Créez un fichier de déclaration (par exemple, `app/i18n.d.ts` ou tout `.d.ts` inclus dans votre `tsconfig`) :

```typescript
// app/i18n.d.ts
declare module '@i18n-micro/types' {
  interface Locale {
    flag?: string
    currency?: string
  }
}
```

Après cela, toutes les propriétés personnalisées sont entièrement typées :

```typescript
const locales = $getLocales()
locales[0].flag // string | undefined ✅
locales[0].currency // string | undefined ✅
```

#### `defaultLocale`

{/* generated:option:defaultLocale — do not edit; run `pnpm run docs:generate` */}

**Type** `string` · **Défaut** `'en'`

Langue à utiliser quand aucune langue ne peut être déterminée depuis l'URL ou les préférences de l'utilisateur. Sert aussi de langue de repli pour les traductions manquantes lorsque `fallbackLocale` n'est pas défini.

{/* /generated:option:defaultLocale */}

```typescript
defaultLocale: 'en'
```
#### `strategy`

{/* generated:option:strategy — do not edit; run `pnpm run docs:generate` */}

**Type** `Strategies` · **Défaut** `'prefix_except_default'`

Stratégie de routage d'URL pour les préfixes de langue.

- `'no_prefix'` : pas de langue dans l'URL; la langue est stockée dans un témoin.
- `'prefix_except_default'` : préfixe toutes les langues sauf la langue par défaut.
- `'prefix'` : toujours préfixer, y compris la langue par défaut.
- `'prefix_and_default'` : comme `prefix`, mais la langue par défaut est aussi accessible sans préfixe.

{/* /generated:option:strategy */}

<CodeGroup>
```typescript no_prefix
strategy: 'no_prefix'
// Routes: /about, /contact
// Locale detection via browser/cookies
```

```typescript prefix_except_default
strategy: 'prefix_except_default'
// Default locale: /about, /contact
// Other locales: /fr/about, /de/contact
```

```typescript prefix
strategy: 'prefix'
// All locales: /en/about, /fr/about, /de/about
```

```typescript prefix_and_default
strategy: 'prefix_and_default'
// Both prefixed and non-prefixed versions for default locale
```
</CodeGroup>

### 📂 Gestion des traductions
#### `translationDir`

{/* generated:option:translationDir — do not edit; run `pnpm run docs:generate` */}

**Type** `string` · **Défaut** `'locales'`

Chemin du répertoire contenant les fichiers JSON de traduction, relatif à la racine du projet.

{/* /generated:option:translationDir */}

```typescript
translationDir: 'i18n' // Custom directory
// Nuxt 4 colocation example:
// translationDir: 'app/locales'
```

Les chemins sont résolus depuis la **racine du projet** Nuxt (`rootDir`), pas depuis `app/`. Avec Nuxt 4, la configuration habituelle est `app/pages/` pour les routes et `locales/` (ou `app/locales` si vous définissez `translationDir`) pour les fichiers JSON.
#### `disablePageLocales`

{/* generated:option:disablePageLocales — do not edit; run `pnpm run docs:generate` */}

**Type** `boolean` · **Défaut** `false`

Désactive les fichiers de traduction par page. Lorsque `true`, seules les traductions globales (`\{locale\}.json`) sont chargées; les fichiers propres aux pages (`pages/\{page\}/\{locale\}.json`) ne sont ni générés ni chargés.

{/* /generated:option:disablePageLocales */}

Lorsque activé, seuls les fichiers de traduction à la racine sont utilisés :

```tree
locales/
├── en.json
├── fr.json
└── ar.json
```
#### `fallbackLocale`

{/* generated:option:fallbackLocale — do not edit; run `pnpm run docs:generate` */}

**Type** `string` · **Défaut** `undefined (aucun repli; retourne la clé brute)`

Code de langue de repli global. Lorsqu'une clé de traduction est absente dans la langue active, le module la cherche dans cette langue avant de retourner la clé elle-même.

{/* /generated:option:fallbackLocale */}

```typescript
fallbackLocale: 'en' // Global fallback
```
#### `types`

{/* generated:option:types — do not edit; run `pnpm run docs:generate` */}

**Type** `boolean` · **Défaut** `true`

Génère les déclarations de types TypeScript pour `useI18n`, `$t` et les assistants associés à partir des clés de traduction dans vos fichiers de langue par défaut.

{/* /generated:option:types */}

Lorsque activé, le module émet `.nuxt/i18n.d.ts` pendant la compilation avec des clés de traduction typées. Définissez à `false` si vous préférez des assistants non typés ou utilisez un générateur externe.

Ce générateur intégré est distinct du paquet facultatif [`@i18n-micro/types-generator`](/integrations/types-generator), qui peut produire des fichiers de types plus stricts ou autonomes pour les monorepos et l'IC.

```typescript
types: false // Disable built-in key typing
```
#### `routeLocales`

{/* generated:option:routeLocales — do not edit; run `pnpm run docs:generate` */}

**Type** `Record<string, string[]>` · **Défaut** —

Restrictions de langue par route, extraites des appels à `defineI18nRoute()`. Associe un chemin de route (par exemple `'/about'`) à un tableau de codes de langue autorisés. Les routes non listées n'ont aucune restriction (toutes les langues sont permises).

{/* /generated:option:routeLocales */}

Associe un chemin de route (par exemple `'/about'`) à des codes de langue autorisés. Les routes non listées permettent toutes les langues configurées.

Vous configurez normalement cela via [`defineI18nRoute`](/guides/custom-locale-routes) dans les pages plutôt que dans `nuxt.config`. Le module fusionne les déclarations au niveau des pages dans cette map à la compilation.
#### `routeDisableMeta`

{/* generated:option:routeDisableMeta — do not edit; run `pnpm run docs:generate` */}

**Type** `Record<string, boolean \| string[]>` · **Défaut** —

Désactivation des balises meta par route, extraite des appels à `defineI18nRoute()`. Associe un chemin de route à `true` (désactiver toutes les meta) ou à un tableau de codes de langue pour lesquels les meta doivent être désactivées.

{/* /generated:option:routeDisableMeta */}

- `true` : désactive toutes les balises meta SEO pour la route
- `string[]` : désactive les meta uniquement pour les codes de langue listés

Comme `routeLocales`, cela est généralement défini dans les composants de page, pas manuellement dans la configuration.
#### `experimental`

{/* generated:option:experimental — do not edit; run `pnpm run docs:generate` */}

**Type** `Record<string, unknown>` · **Défaut** —

Panier d'options expérimentales/instables. Le contenu peut changer ou être retiré sans préavis entre les versions mineures.

{/* /generated:option:experimental */}

La plupart des anciens drapeaux `experimental.*` ont été promus au niveau supérieur en v3 (par exemple `hmr`). Préférez les options documentées au niveau supérieur. Utilisez `experimental` uniquement en suivant une note de version ou un guide de migration qui référence une clé précise.

### 🔍 SEO et balises meta
#### `meta`

{/* generated:option:meta — do not edit; run `pnpm run docs:generate` */}

**Type** `boolean` · **Défaut** `true`

Génère automatiquement les balises meta SEO (`hreflang`, `canonical`, `og:url`, `og:locale`).

{/* /generated:option:meta */}

```typescript
meta: true // Generate alternate links, canonical URLs, etc.
```
#### `metaBaseUrl`

{/* generated:option:metaBaseUrl — do not edit; run `pnpm run docs:generate` */}

**Type** `string` · **Défaut** `undefined`

URL de base pour les balises meta SEO (canonical, og:url, hreflang).

- Une chaîne d'URL concrète (par exemple `'https://example.com'`) : utilisée telle quelle (priorité la plus haute).
- `undefined` : retombe sur `site.url` de `nuxt-site-config` quand ce module est présent, sinon l'origine de la requête courante (`useRequestURL().origin` côté serveur, `window.location.origin` côté client).

{/* /generated:option:metaBaseUrl */}

Priorité quand non défini : `site.url` de `nuxt-site-config` (si installé) → origine de la requête (`useRequestURL().origin` côté serveur avec `X-Forwarded-Host` / `X-Forwarded-Proto`, `window.location.origin` côté client). Idéal pour les **piles SEO** qui définissent déjà `site.url`, et pour les déploiements **multidomaines** quand `site.url` est omis.

- Toute autre chaîne : utilisée comme URL de base statique (l'emporte sur `site.url`).

```typescript
// Prefer sharing the SEO stack origin — omit metaBaseUrl when site.url is set
site: { url: 'https://example.com' }

// Or pin an explicit override
metaBaseUrl: 'https://example.com'
```
#### `canonicalQueryWhitelist`

{/* generated:option:canonicalQueryWhitelist — do not edit; run `pnpm run docs:generate` */}

**Type** `string[]` · **Défaut** `['page', 'sort', 'filter', 'search', 'q', 'query', 'tag']`

Liste des noms de paramètres de requête préservés dans les balises meta canonical et `og:url`. Les paramètres absents de cette liste sont retirés de l'URL canonique.

{/* /generated:option:canonicalQueryWhitelist */}

```typescript
canonicalQueryWhitelist: ['page', 'sort', 'category']
```

### 🔄 Fonctionnalités avancées
#### `globalLocaleRoutes`

{/* generated:option:globalLocaleRoutes — do not edit; run `pnpm run docs:generate` */}

**Type** `GlobalLocaleRoutes` · **Défaut** `\{\}`

Configuration globale des langues au niveau des routes. Permet de restreindre ou de personnaliser les routes de langue pour certaines pages sans modifier leurs composants.

- `false` : exclure la route de la localisation.
- `Record<LocaleCode, string>` : chemins personnalisés par langue.

{/* /generated:option:globalLocaleRoutes */}

### 🔢 Personnalisation
#### `plural`

{/* generated:option:plural — do not edit; run `pnpm run docs:generate` */}

**Type** `PluralFunc` · **Défaut** `pluralisation intégrée (index de forme selon le compte)`

Fonction de pluralisation personnalisée. Elle reçoit `(key, count, params, locale, getter)` et doit retourner la forme plurielle choisie sous forme de chaîne, ou `null`/`undefined` pour retomber sur la logique intégrée `defaultPlural` (vous pouvez ainsi ne surcharger que certaines langues).

Pour le module Nuxt, la fonction est sérialisée via `.toString()` dans `.nuxt/i18n.plural.mjs`; elle doit donc être autonome (pas d'imports ni de portée extérieure). Une chaîne de chemin de fichier n'est **pas** prise en charge.

{/* /generated:option:plural */}

##### Comment ça fonctionne

Les traductions utilisent `|` pour séparer les formes plurielles :

```json
{
  "apples": "no apples | one apple | {count} apples"
}
```

Utilisez `$tc('apples', count)` ou `$tc('cart', \{ count, name \})` quand une forme a besoin de plus que `\{count\}`. Passez **`count` et les autres params dans l'objet du deuxième argument**, pas comme troisième argument (le troisième est `defaultValue` uniquement).

L'appel `$tc` invoque la fonction `plural`, qui :

1. Appelle `t(key)` pour obtenir la chaîne de traduction brute (par exemple, `"no apples | one apple | \{count\} apples"`)
2. Sépare par `|` pour obtenir le tableau de formes
3. Sélectionne une forme selon `count`
4. Remplace `\{count\}` par le nombre réel

L'implémentation **par défaut** sélectionne par index : `count < forms.length ? forms[count] : forms[last]`. Cela fonctionne pour les cas simples (0 → première forme, 1 → deuxième, 2+ → dernière).

##### Fonction de pluralisation personnalisée

Pour les langues aux règles de pluralisation complexes (par exemple, russe, arabe, polonais), surchargez l'option `plural`.

<Danger>
La fonction est sérialisée via `.toString()` et injectée dans un module virtuel à la compilation. Cela signifie :

- **Doit utiliser le mot-clé `function`**. PAS de syntaxe raccourcie de méthode, PAS de fonctions fléchées avec des références externes.
- **Pas d'imports ni de références externes** : la fonction doit être entièrement autonome (un chemin de fichier comme `plural: '~/i18n/plural.ts'` n'est **pas** pris en charge)
- **Pas de syntaxe TypeScript uniquement** qui ne survit pas à `.toString()` (les annotations de type sont acceptables dans `nuxt.config.ts` parce que Nuxt les retire)
- Retourner `null` / `undefined` retombe sur `defaultPlural` intégré (utile pour les surcharges par langue)
</Danger>

**Exemple : pluralisation russe** (4 formes : zéro, un, quelques, plusieurs) :

```typescript
// nuxt.config.ts
export default defineNuxtConfig({
  i18n: {
    plural: function (key, count, _params, _locale, t) {
      const translation = t(key)
      if (!translation) return key

      const forms = translation
        .toString()
        .split('|')
        .map(function (s) {
          return s.trim()
        })
      let idx

      if (count === 0) {
        idx = 0
      } else {
        const mod10 = count % 10
        const mod100 = count % 100
        if (mod10 === 1 && mod100 !== 11) {
          idx = 1
        } else if (mod10 >= 2 && mod10 <= 4 && (mod100 < 10 || mod100 >= 20)) {
          idx = 2
        } else {
          idx = 3
        }
      }

      if (idx >= forms.length) idx = forms.length - 1
      return (forms[idx] || '').replace('{count}', String(count))
    },
  },
})
```

Avec cette traduction :

```json
{
  "apples": "нет яблок | {count} яблоко | {count} яблока | {count} яблок"
}
```

Résultats :

- `$tc('apples', 0)` → `"нет яблок"`
- `$tc('apples', 1)` → `"1 яблоко"`
- `$tc('apples', 3)` → `"3 яблока"`
- `$tc('apples', 5)` → `"5 яблок"`
- `$tc('apples', 21)` → `"21 яблоко"`

**Exemple : anglais simple (comportement par défaut)** :

```typescript
// This is the built-in default — you don't need to set it explicitly
plural: function (key, count, params, _locale, t) {
  const translation = t(key, params)
  if (!translation) return null

  const forms = translation.toString().split('|')
  if (forms.length === 0) return null
  const form = count < forms.length ? forms[count] : forms[forms.length - 1]
  if (!form) return null
  return form.trim().replace('{count}', count.toString())
}
```

##### Pluralisation par langue

Si différentes langues nécessitent différentes règles plurielles, branchez sur `locale` et retournez `null` pour les langues que vous ne personnalisez pas. `defaultPlural` intégré gère le reste :

```typescript
plural: function (key, count, _params, locale, t) {
  // Only override Slavic locales; en/de/… keep the built-in rules
  if (locale !== 'ru' && locale !== 'uk') return null

  const translation = t(key)
  if (!translation) return null

  const forms = translation.toString().split('|').map(function (s) { return s.trim() })
  let idx
  if (count === 0) {
    idx = 0
  } else {
    const mod10 = count % 10
    const mod100 = count % 100
    if (mod10 === 1 && mod100 !== 11) idx = 1
    else if (mod10 >= 2 && mod10 <= 4 && (mod100 < 10 || mod100 >= 20)) idx = 2
    else idx = 3
  }
  if (idx >= forms.length) idx = forms.length - 1
  return (forms[idx] || '').replace('{count}', String(count))
}
```

<Warning>
`plural: '~/i18n/plural.ts'` (ou toute chaîne de chemin) n'est **pas** pris en charge. Le module Nuxt sérialise la fonction via `.toString()` dans un fichier virtuel; les imports externes et les assistants d'un autre module sont retirés et seront `undefined` à l'exécution. Gardez la fonction entièrement en ligne dans `nuxt.config.ts` (voir la note de danger ci-dessus).
</Warning>
#### `localeCookie`

{/* generated:option:localeCookie — do not edit; run `pnpm run docs:generate` */}

**Type** `string \| null` · **Défaut** `null`

Nom du témoin pour persister la préférence linguistique de l'utilisateur entre les sessions. Définissez à `null` pour désactiver la persistance par témoin. Automatiquement défini à `'user-locale'` pour la stratégie `no_prefix` si non fourni.

{/* /generated:option:localeCookie */}

<Warning>
Bien que la valeur par défaut configurée soit `null` (désactivée), le module **surcharge automatiquement** cela à `'user-locale'` quand vous utilisez `strategy: 'no_prefix'`. Cela signifie :

- **`no_prefix`** : le témoin est **toujours activé** (`'user-locale'`), même si vous ne le définissez pas explicitement. C'est requis parce que l'URL ne contient aucune information de langue.

Si vous définissez `localeCookie` explicitement, votre valeur est toujours utilisée quelle que soit la stratégie.
</Warning>

<Warning>
En utilisant les stratégies préfixées (`prefix`, `prefix_except_default`, `prefix_and_default`) avec `redirects: true` (par défaut), vous **devez** définir `localeCookie` pour que le comportement de redirection fonctionne correctement. Sans témoin, le plugin de redirection ne peut pas se souvenir de la préférence linguistique de l'utilisateur entre les rechargements de page, et les redirections ne fonctionneront que selon l'en-tête `Accept-Language` (si `autoDetectLanguage: true`) ou `defaultLocale`.
</Warning>

```typescript
// Enable cookie (recommended when using redirects with prefix strategies)

// Enable cookie with custom name

// Disable cookie (default) - locale won't persist across reloads
localeCookie: null
```

**Ce que `localeCookie` active :**

- Persiste la préférence linguistique de l'utilisateur entre les rechargements de page
- Se souvient de la langue quand l'utilisateur revient sur votre site
- Requis pour que la stratégie `no_prefix` fonctionne correctement
- **Requis** pour le comportement de redirection dans les stratégies préfixées (quand `redirects: true`)

#### `translationPayloads`

{/* generated:option:translationPayloads — do not edit; run `pnpm run docs:generate` */}

**Type** `TranslationPayloadOptions` · **Défaut** —

Contrôle la manière dont les charges utiles de traduction sont émises (Node : `public/<apiBaseUrl>`; Edge : `serverAssets` Nitro).

- **Node** : `serverAssets` signifie SSR local via `readFile` sous `public/` (pas de `raw:` Rollup).
- **Edge** : `serverAssets` enregistre les `serverAssets` Nitro (`assets:i18n`); ne force pas une copie publique.

Conservez les valeurs par défaut pour la configuration tout-en-un habituelle. Pour les gros catalogues Edge, préférez `mode: 'source'`. Pour les déploiements adossés à un CDN, désactivez les sorties locales et définissez `apiBaseClientHost` / `apiBaseServerHost`.

{/* /generated:option:translationPayloads */}

```typescript
{
  mode?: 'premerged' | 'source'
  serverAssets?: boolean
  serverHandler?: boolean
  publicAssets?: boolean
  prerenderRoutes?: boolean
  publicDir?: string
  warnFileCount?: number
  warnSizeBytes?: number
}
```

**Défaut** (`mode: 'premerged'`) :

```typescript
{
  mode: 'premerged',
  serverAssets: true,
  serverHandler: true,
  publicAssets: true,
  prerenderRoutes: false
}
```

Le SSR sur **Node** lit le même arbre copié dans `public/<apiBaseUrl>/` (`readFile`). Sur **Edge**, les `serverAssets` Nitro l'intègrent (pas de copie publique forcée; définissez `publicAssets: true` pour un CDN). `mode: 'premerged'` → `\{page\}/\{locale\}/data.json` par page/langue; `mode: 'source'` → source compacte + fusion à l'exécution.

`serverAssets: true` sur **Node** force la copie publique même si `publicAssets` est faux. Sur **Edge**, il enregistre uniquement l'intégration Nitro. Préférez `mode: 'source'` sur Edge pour les gros catalogues. Sans charges utiles locales et sans `apiBaseServerHost`, la compilation échoue.

Le gestionnaire local `/\{apiBaseUrl\}/:page/:locale/data.json`, les routes de pré-rendu et les copies de ressources publiques restent des sorties facultatives.

Pour des charges utiles **publiques** / Edge compactes :

```typescript
i18n: {
  translationPayloads: {
    mode: 'source',
  },
}
```

`mode: 'source'` garde les fichiers de couches compacts et fusionne racine/page/repli à l'exécution via la route intégrée `/_locales` (ou `assets:i18n` Edge). Par défaut, il désactive les copies de ressources publiques et les routes de charge utile pré-rendues.

<Warning>
Avec `mode: 'source'`, `publicAssets` prend `false` par défaut (`prerenderRoutes` est toujours désactivé sauf si vous l'activez). L'hébergement purement statique sans exécution Nitro/edge ne peut donc pas charger les traductions côté client sauf si vous activez l'une de ces sorties, gardez `serverHandler` disponible à l'exécution ou hébergez les charges utiles à l'externe.

Avec `mode: 'premerged'` par défaut et `publicAssets: true`, les fichiers statiques se retrouvent déjà à `public/<apiBaseUrl>/\{page\}/\{locale\}/data.json` (correspondant aux URL `$fetch` du client), donc un hôte statique peut les servir sans Nitro.
</Warning>

<Warning>
Quand `apiBaseServerHost` ou `apiBaseClientHost` est défini, le module récupère du JSON déjà fusionné depuis cette origine. Les hôtes externes doivent servir les mêmes réponses `/\{apiBaseUrl\}/:page/:locale/data.json` que la route intégrée. `mode: 'source'` s'applique aux répertoires de charges utiles locaux, pas à un CDN externe sauf si ce CDN sert aussi des charges utiles fusionnées à l'exécution.
</Warning>

Vous pouvez aussi désactiver manuellement les sorties locales dupliquées et servir les charges utiles de traduction depuis un CDN ou un stockage d'objets :

```typescript
i18n: {
  apiBaseClientHost: 'https://cdn.example.com',
  apiBaseServerHost: 'https://cdn.example.com',
  translationPayloads: {
    serverHandler: false,
    publicAssets: false,
    prerenderRoutes: false
  }
}
```

Si vous souhaitez uniquement éviter d'écrire les charges utiles dans la sortie publique tout en gardant la route serveur intégrée pour les requêtes SSR/exécution, désactivez les deux sorties publiques :

```typescript
i18n: {
  translationPayloads: {
    publicAssets: false,
    prerenderRoutes: false
  }
}
```

Sur **Node**, `serverAssets: true` force encore une copie publique pour le SSR même quand `publicAssets` est faux. Définissez `serverAssets: false` et `apiBaseServerHost` si vous voulez zéro fichier de charge utile local.

Utilisez `publicDir` pour changer le dossier de sortie publique quand les charges utiles sont copiées. Il prend par défaut `apiBaseUrl` (`_locales`). En mode premerged, `publicAssets` écrit `\{page\}/\{locale\}/data.json` là (les mêmes chemins que le client récupère). `prerenderRoutes` est un pré-rendu Nitro facultatif des routes de gestionnaire, généralement redondant quand cet arbre a déjà été copié.

Si vous désactivez toutes les sorties de charge utile locales, vous devez configurer à la fois `apiBaseServerHost` (SSR) et `apiBaseClientHost` (navigation client). Sinon, les traductions se résoudront en objets vides et les clés de l'interface pourraient apparaître non traduites.

`warnFileCount` et `warnSizeBytes` contrôlent les avertissements à la compilation quand la sortie de charge utile préfusionnée devient volumineuse (défauts : 500 fichiers et 10 Mo).

#### `metaTrustForwardedHost`

#### `dateBuild`

{/* generated:option:dateBuild — do not edit; run `pnpm run docs:generate` */}

**Type** `string \| number` · **Défaut** —

Valeur utilisée pour invalider le cache des requêtes de traduction (`?v=...`).

En absence de valeur, le module retombe sur `Date.now()` (non déterministe). Pour des déploiements reproductibles/progressifs, définissez une valeur stable (par exemple, un SHA git ou un numéro de build).

{/* /generated:option:dateBuild */}

Par défaut, le module empreinte vos sources de traduction (SHA-256 sur chaque `<layer>/<translationDir>/**/*.json`, dans l'ordre des couches) et utilise cette valeur. Elle ne change que lorsqu'une traduction change réellement, donc recompiler ou redéployer des traductions inchangées laisse les caches navigateur et CDN intacts. Avec `httpCacheDuration` défini à un an, une empreinte de temps de compilation forcerait plutôt chaque client à retélécharger tout le dictionnaire à chaque déploiement.

Elle retombe sur `Date.now()` uniquement quand il n'y a pas de fichiers de traduction à hasher.

Définissez-la explicitement pour prendre le contrôle (par exemple, pour lier les URL de charge utile à une version plutôt qu'au contenu) :

```ts
export default defineNuxtConfig({
  i18n: {
    // Any stable string/number: git SHA, CI build number, release tag, etc.
    dateBuild: process.env.GIT_SHA ?? 'local-dev',
  },
})
```
#### `httpCacheDuration`

{/* generated:option:httpCacheDuration — do not edit; run `pnpm run docs:generate` */}

**Type** `number` · **Défaut** `31536000`

`max-age` HTTP `Cache-Control` (en secondes) pour `/\{apiBaseUrl\}/:page/:locale/data.json`.

S'applique intégralement tant que `dateBuild` invalide l'URL (`?v=...`), ce qui est la valeur par défaut : la réponse est alors `public, max-age=…, immutable` et sûre pour les navigateurs et les CDN.

- `dateBuild: 0`/`''` : l'URL est stable, donc cette durée n'est *pas* honorée; la réponse devient `public, max-age=0, must-revalidate` à la place. Un long `max-age` sur une URL invariable épingle la première charge utile qu'un navigateur a vue.

- `0` : ne définit pas du tout `Cache-Control` (utile en débogage local)
- Non appliqué en développement (`import.meta.dev`) afin que le HMR ne soit pas contrarié par le cache du navigateur
- Ne concerne que les réponses servies via Nitro. Les charges utiles copiées dans `public/` et servies par la plateforme d'hébergement prennent les en-têtes de cette plateforme. Consultez le guide de performance.

Analogue à `httpCacheDuration` expérimental de `@nuxtjs/i18n` (v10.2.0), mais en tant qu'en-tête de réponse explicite plutôt qu'en `maxAge` de `defineCachedEventHandler` Nitro.

{/* /generated:option:httpCacheDuration */}

```ts
export default defineNuxtConfig({
  i18n: {
    // Per-build fallback (Date.now()) so immutable payloads never go stale when GIT_SHA is missing.
    dateBuild: process.env.GIT_SHA ?? String(Date.now()),
    httpCacheDuration: 86400, // 24 hours
    // httpCacheDuration: 0, // disable Cache-Control header
  },
})
```

#### `cacheMaxSize`

{/* generated:option:cacheMaxSize — do not edit; run `pnpm run docs:generate` */}

**Type** `number` · **Défaut** `0`

Nombre maximal d'entrées dans le cache de traduction en mémoire. `0` signifie aucune limite.

#### `cacheTtl`

{/* generated:option:cacheTtl — do not edit; run `pnpm run docs:generate` */}

**Type** `number` · **Défaut** `0`

Durée de vie (en secondes) des entrées de cache de traduction. `0` signifie que les entrées n'expirent jamais.

{/* /generated:option:cacheTtl */}

```typescript
export default defineNuxtConfig({
  i18n: {
    // Limit cache to 1000 entries, each lives 10 minutes (refreshed on access)
    cacheMaxSize: 1000,
    cacheTtl: 600,
  },
})
```

<Tip>
Pour la plupart des projets, la valeur par défaut (illimitée, sans expiration) convient. Les traductions sont petites et finies. Toutefois, si votre projet a **des milliers de pages** avec `disablePageLocales: false` et **de nombreuses langues**, le cache serveur peut grossir considérablement. Dans les serveurs Node.js à longue durée, cela peut mener à une utilisation excessive de la mémoire.

- **`cacheMaxSize`** : limite le nombre d'entrées en cache. Utile pour borner la mémoire.
- **`cacheTtl`** : garantit que les traductions périmées seront éventuellement rechargées du stockage. Utile pour les environnements sans serveur ou quand les traductions changent à l'exécution.

**Formule pour estimer le nombre maximal d'entrées** : `nombre_de_langues × (nombre_de_pages + 1)`. Par exemple, 10 langues × 500 pages = environ 5010 entrées.
</Tip>
