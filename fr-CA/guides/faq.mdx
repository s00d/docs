# ❓ FAQ : problèmes courants et solutions

Trouvez les réponses aux questions fréquentes et les solutions aux problèmes courants avec Nuxt I18n Micro.

## 🚀 Problèmes de démarrage

### ❓ Que faire si une route ne se charge pas ?

Lorsque vous utilisez `Nuxt I18n Micro`, certaines routes peuvent ne pas se charger comme prévu, surtout si le routeur n'attribue pas automatiquement un nom à une route dans les sous-dossiers.

**Solution :**
Pour y remédier, définissez manuellement le nom de la route pour la page en ajoutant ce qui suit au fichier Vue correspondant :

```javascript
definePageMeta({ name: 'pageName' })
```

Cela garantit que la route est correctement enregistrée, permettant une navigation fluide dans l'application.

### ❓ Pourquoi `$t` ou d'autres composables i18n ne fonctionnent-ils pas dans les plugins Nuxt ?

Les composables Nuxt I18n (`$t`, `$getLocale`, `$localePath`, etc.) peuvent ne pas fonctionner comme prévu dans les plugins Nuxt ou les fonctions utilitaires, ce qui provoque des erreurs à l'exécution.

**Cause et solution :**
Les composables Nuxt nécessitent des contextes précis (par exemple, des hooks Nuxt ou des fonctions Vue setup) pour accéder à l'instance Nuxt. S'ils sont utilisés hors de ces contextes (par exemple, dans des fonctions utilitaires ou des plugins), l'erreur suivante peut apparaître dans la console :

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Solution 1 : utilisez `runWithContext`**
Pour appeler des composables i18n après une opération asynchrone, utilisez [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) pour préserver le contexte nécessaire.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Solution 2 : récupérez d'abord la valeur**
Sinon, récupérez d'abord la valeur de traduction puis passez-la à une fonction utilitaire.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Solution 3 : passez les clés de traduction dans les services**
Dans les services ou fonctions utilitaires, passez les clés de traduction plutôt que d'utiliser `$t` directement. Ensuite, récupérez la traduction dans le composant.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Changement de langue

### ❓ Changer de langue sans changer l'URL ?

Oui, mais cela dépend de votre [stratégie de routage](/guides/routing-strategies).

**Stratégie `no_prefix`** : la langue ne fait pas partie de l'URL. Utilisez `$switchLocale()` pour changer de langue et recharger les traductions tout en restant sur le même chemin :

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Vous pouvez aussi mettre à jour la préférence uniquement avec `useI18nLocale().setLocale('de')`. Pour un rechargement complet de traduction côté client, préférez `$switchLocale()`.

**Stratégies préfixées** (`prefix`, `prefix_except_default`, …) : la langue et l'URL sont liées. `$switchLocale()` navigue toujours vers la route localisée. Il n'y a pas d'option `redirect: false`.

Si vous n'avez besoin que de l'URL cible (par exemple, un lien de sélecteur de langue), utilisez plutôt `$switchLocalePath()` :

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Consultez [Changement de route et de langue](/api/methods#-route-locale-switching) pour toutes les méthodes de changement.

### ❓ La page défile jusqu'en haut (ou saute) lors du changement de langue ?

C'est attendu. C'est un comportement de défilement **Vue Router / Nuxt**, pas quelque chose de propre à nuxt-i18n-micro.

Avec les stratégies préfixées (`prefix`, `prefix_except_default`, …), `$switchLocale()` exécute une navigation client normale (`/en/page` → `/de/page`). Le [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) par défaut de Nuxt fait défiler jusqu'en haut lors des changements de route (sauf pour la navigation arrière/avant du navigateur via `savedPosition`).

nuxt-i18n-micro n'ajoute pas de gestion cachée du défilement. Utilisez un petit composant d'enveloppe dans votre application.

**Enveloppe `SwitchLocalePreserve`**

Copiez [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) dans votre projet (`components/SwitchLocalePreserve.vue`). Démo fonctionnelle : [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

Sur la page, définissez `scrollToTop: false` et enveloppez l'interface de votre sélecteur. Marquez les cibles cliquables avec `data-locale`. L'enveloppe intercepte les clics, appelle `$switchLocale` et restaure le défilement (y compris quand la longueur de la traduction modifie la mise en page) :

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Le composant :

1. **Au clic** : lit `data-locale` sur l'élément cliqué à l'intérieur de la fente (boutons, liens ou tout balisage personnalisé).
2. **Avant** `$switchLocale` : stocke `scrollY` et la position de l'élément cliqué (le garde sous le curseur).
3. **Pendant** la navigation : corrige `router.options.scrollBehavior` une seule fois et retourne `\{ top: scrollY \}` au lieu de défiler jusqu'en haut.
4. **Après** la navigation : attend `page:finish`, puis réapplique le défilement pendant qu'un `ResizeObserver` capte les changements de mise en page dus aux longueurs de traduction différentes.

`scrollToTop: false` est requis sur les pages où vous utilisez cette enveloppe. Documentation : [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

N'appelez pas `$switchLocale` directement sur des contrôles enveloppés. L'enveloppe gère le changement. Pour `<NuxtLink :to="$switchLocalePath('fr')">` hors de l'enveloppe, le comportement de défilement suit le routage Nuxt normal, sauf si vous ajoutez votre propre `app/router.options.ts`.

## 🌐 Problèmes de traduction

### ❓ Pourquoi les traductions se cassent-elles pendant les transitions de page, surtout avec `defineAsyncComponent` ?

Lorsque vous utilisez `nuxt-i18n-micro` avec des transitions de page, les traductions peuvent brièvement cesser de fonctionner pendant la transition. Ce problème survient parce que la route change avant que la transition ne se termine, ce qui fait que les traductions de la nouvelle page se chargent alors que l'ancienne page est encore visible.

**Cause principale :**

- Les transitions de page provoquent des changements de route avant que les traductions soient entièrement chargées.
- `defineAsyncComponent` et `useAsyncData` peuvent retarder le chargement des traductions.
- Les clés de traduction peuvent apparaître comme des chemins bruts pendant le chargement.

**Solution 1 : fusion cumulative (intégrée, aucune configuration requise)**

En v3, le module utilise automatiquement une stratégie de fusion cumulative. Lors de la navigation dans la même langue, les nouvelles traductions de page sont fusionnées dans le dictionnaire actif au lieu de le remplacer. Cela signifie que les traductions de la page précédente restent disponibles pendant l'animation de transition. Une fois la transition terminée (hook `page:transition:finish`), les anciennes clés sont nettoyées automatiquement.

Aucune configuration n'est nécessaire. Cela fonctionne dès la sortie de la boîte.

**Solution 2 : contexte de route explicite**

Si vous préférez un contrôle manuel, passez explicitement la route courante à `$_t` :

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Solution 3 : états de chargement**

Implémentez des états de chargement pour gérer élégamment le chargement des traductions :

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Pourquoi les clés de traduction ne se résolvent-elles pas pendant le SSR sur Vercel ?

**Limites de `$fetch` en SSR**
Sur les plateformes sans serveur comme Vercel, `$fetch` ne peut récupérer que des fichiers statiques depuis le CDN et non depuis le serveur Nitro interne. Les fichiers de traduction statiques peuvent donc ne pas être directement accessibles sans définir la bonne URL de base.

**Correctif en définissant `apiBaseClientHost` et `apiBaseServerHost`**
Si les traductions sont hébergées à l'externe sur un CDN ou un autre domaine, utilisez `apiBaseClientHost` pour les requêtes côté client et `apiBaseServerHost` pour les requêtes côté serveur. Le `apiBaseUrl` ne devrait contenir que le préfixe de chemin (par exemple, `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Ou via des variables d'environnement :

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Les traductions seront récupérées depuis `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` à la fois côté client et côté serveur.

## 🔗 Problèmes de routage et de navigation

### ❓ Puis-je utiliser `NuxtLink` ou `<i18n-link>` directement dans les chaînes de traduction ?

Oui, `Nuxt I18n Micro` permet l'utilisation de `NuxtLink` ou `<i18n-link>` dans les traductions via le composant `<i18n-t>`, ce qui est particulièrement utile pour gérer la grammaire et les exigences des langues RTL sans fractionner les chaînes de traduction.

**Exemple :**

Fichier de traduction :

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Modèle Vue :

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Cela permet des liens dynamiques dans les traductions tout en préservant une structure de localisation appropriée.

## 🏗️ Problèmes de compilation et de déploiement

### ❓ Pourquoi les charges utiles de traduction finissent-elles sous `public/_locales/` (ou dans le bundle serveur sur Edge) ?

Le SSR et le client ont tous les deux besoin des mêmes charges utiles `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. La façon dont elles sont empaquetées dépend de la cible Nitro :

**Explication :**

- **Node (par défaut) :** le module n'intègre **pas** les traductions comme `serverAssets` Nitro / `raw:` Rollup (cela faisait exploser la RAM de compilation sur les gros catalogues). Il copie plutôt l'arbre préfusionné dans `public/<apiBaseUrl>/` (par défaut `_locales`) et le SSR lit ces fichiers avec `readFile`. Le client `$fetch` les mêmes URL, soit comme fichiers statiques, soit via le gestionnaire Nitro.
- **Edge** (`nitro.node === false`) : il n'y a pas de FS public durable pour le SSR, alors les charges utiles sont intégrées via `serverAssets` Nitro (`assets:i18n`). Préférez `translationPayloads.mode: 'source'` pour que l'intégration reste compacte. Définissez `publicAssets: true` uniquement si vous avez aussi besoin d'une copie CDN/statique.
- **`prerenderRoutes` :** facultatif. En mode premerged, `publicAssets` écrit déjà `\{page\}/\{locale\}/data.json`, donc pré-rendre ces routes est habituellement redondant.

### ❓ Pourquoi ai-je une erreur de compilation référant à `@unhead/vue` ou à un objet indéfini, surtout sur Cloudflare Pages ?

**Cause :**
Certains projets subissent des conflits de compilation ou des dépendances manquantes en utilisant `nuxt-i18n-micro`. En particulier :

- Les déploiements sur **Cloudflare Pages** ou **Cloudflare Workers** peuvent nécessiter des indicateurs de compatibilité supplémentaires.
- Les étapes de pré-rendu peuvent échouer si des dépendances comme `@unhead/vue` ne sont pas correctement installées.
- Certains modules (par exemple, **nuxthub**, **nitro-cloudflare-dev**) peuvent introduire des conflits sauf s'ils sont configurés avec les bons indicateurs ou dépendances.

**Solutions possibles :**

**Solution 1 : installer `@unhead/vue` manuellement**
Si l'erreur de compilation se plaint de ne pas trouver `@unhead/vue`, installez-le directement dans les dépendances de votre projet :

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Cela garantit sa disponibilité pendant la phase de pré-rendu Nitro.

**Solution 2 : ajouter les indicateurs de compatibilité Cloudflare**
Lorsque vous utilisez Cloudflare Pages ou Cloudflare Workers, la compatibilité Node.js est souvent désactivée par défaut. Activez-la dans votre `wrangler.toml` :

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Cet indicateur permet à de nombreux modules Node.js (y compris ceux utilisés par `nuxt-i18n-micro`) de fonctionner sans heurts.

## 🔍 SEO et `@nuxtjs/seo`

### ❓ Erreur : `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Cela se produit lorsque **`@nuxtjs/seo`** entraîne l'installation d'une ancienne **`nuxt-site-config` 3.x** qui n'enregistre son plugin i18n que pour `@nuxtjs/i18n`, pas pour **nuxt-i18n-micro**.

**Correctif :**

1. Mettez à niveau vers **`@nuxtjs/seo` 3+** (inclut `nuxt-site-config` 4+ avec le support de micro).
2. Placez **`nuxt-i18n-micro` avant `@nuxtjs/seo`** dans `modules`.
3. Conservez **`i18n.meta: true`** pour des balises head sensibles à la langue.

Consultez le [guide SEO — section Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo) pour un exemple complet.

## 🔧 Configuration et compatibilité

### ❓ `Nuxt I18n Micro` s'inspire-t-il de `vue-i18n` ? Qu'en est-il des modificateurs ?

Bien que `Nuxt I18n Micro` serve d'alternative performante à `nuxt-i18n`, il est bâti indépendamment de `vue-i18n`. Bien que certains noms de méthodes et paramètres puissent être similaires, la fonctionnalité sous-jacente diffère considérablement.

**Modificateurs** : le mainteneur a initialement envisagé les modificateurs, mais a conclu que des composants comme `<i18n-t>` et `<i18n-link>` répondent efficacement à ces besoins.

Par exemple :

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Cette approche est flexible, donc publier des modificateurs n'est actuellement pas nécessaire. Toutefois, des modificateurs pourraient être ajoutés dans les versions futures s'il y a de la demande.
