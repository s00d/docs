`@i18n-micro/node` est l’instance [runtime](/fr-CA/integrations/runtime-package) assortie d’un chargeur qui lit un dossier de traductions sur le disque. Utilisez-le dans un serveur Express ou Fastify, un outil en ligne de commande, un générateur de courriels ou de PDF, ou tout script qui a besoin des mêmes fichiers JSON que votre application Nuxt. Vous chargez les fichiers une seule fois et traduisez à chaque requête sans partager d’état mutable entre les requêtes.

## Installation {#install}

<CodeGroup>

```bash pnpm
pnpm add @i18n-micro/node @i18n-micro/utils
```

```bash npm
npm install @i18n-micro/node @i18n-micro/utils
```

```bash yarn
yarn add @i18n-micro/node @i18n-micro/utils
```

</CodeGroup>

Aucune dépendance pair; Node.js `>=20`. `@i18n-micro/utils` n’est nécessaire que pour la fonction `Accept-Language` ci-dessous.

## Configuration {#setup}

Le chargeur lit l’[organisation des dossiers de Nuxt](/fr-CA/guide/translations) : `locales/en.json` est un dictionnaire racine, `locales/pages/blog/post/en.json` appartient à la route `blog-post`.

```ts
import { createI18n } from '@i18n-micro/node'

const i18n = createI18n({ locale: 'en', fallbackLocale: 'en', translationDir: './locales' })
await i18n.loadTranslations()

i18n.t('greeting', { name: 'Ada' }) // 'Hello, Ada!'
i18n.t('title', undefined, undefined, 'blog-post') // from locales/pages/blog/post/en.json
```

Les options sont celles du runtime (consultez [l’instance](/fr-CA/integrations/overview#the-instance)), plus `translationDir` et `disablePageLocales` (traiter les fichiers `pages/**` comme des dictionnaires racine). `i18n.reload()` vide tous les dictionnaires et relit le dossier, pour un observateur de fichiers en développement.

`loadTranslations(dir, disablePageLocales?)` est aussi exporté séparément et renvoie `{ root, routes }` :

```ts
import { loadTranslations } from '@i18n-micro/node'

const { root, routes } = await loadTranslations('./locales')
// root:   { en: {...}, de: {...} }
// routes: { 'blog-post': { en: {...}, de: {...} } }
```

## Par requête {#per-request}

Une instance contient une langue et une route. Changer `i18n.locale` sur une instance partagée dans un gestionnaire de requêtes crée une situation de concurrence avec les requêtes simultanées. `run` donne à une requête sa propre instance :

```ts
const i18n = createI18n({ locale: 'en', fallbackLocale: 'en', translationDir: './locales' })
await i18n.loadTranslations()

// `() => next()`: `run` hands its callback the fork, and Express reads an argument of `next` as an error
app.use((req, res, next) => i18n.run(pickLocale(req), () => next()))

app.get('/', (req, res) => {
  res.send(i18n.t('greeting')) // the request's locale, in everything it awaits
})
```

À l’intérieur de `run`, l’instance partagée lit et définit la langue et la route de la requête (`AsyncLocalStorage`); la copie démarre sur la route courante, et `i18n.setRoute(...)` dans la fonction de rappel modifie la route de cette requête. La fonction de rappel reçoit aussi la copie propre à la requête : les dictionnaires qui y sont écrits restent dans la requête, tandis que ceux écrits dans l’instance partagée atteignent tout le monde.

Sans `AsyncLocalStorage`, `i18n.fork(locale)` renvoie le même genre d’instance, à transmettre vous-même.

`reload()` relit le dossier; les anciens dictionnaires répondent jusqu’à ce que les nouveaux soient chargés.

## Choisir la langue {#pick-the-locale}

`detectLocaleFromAcceptLanguage(header, locales)` respecte les pondérations `q` et fait correspondre `de-DE` à une langue `de` (et `de` à `de-DE`). Elle renvoie `null` si rien ne correspond.

```ts
import express from 'express'
import { detectLocaleFromAcceptLanguage } from '@i18n-micro/utils/accept-language'

const app = express()

app.get('/hello', (req, res) => {
  const locale = detectLocaleFromAcceptLanguage(req.headers['accept-language'], locales) ?? 'en'
  const i18n = byLocale.get(locale)!
  res.json({ message: i18n.t('greeting', { name: 'Ada' }) })
})
```

Pour combiner préfixe d’URL, témoin et en-tête, `resolveLocale({ defaultLocale, validLocales, url, cookie, acceptLanguage, autoDetectLanguage: true })` de `@i18n-micro/utils/resolve-locale` applique l’ordre de priorité du module : l’URL, puis le témoin, puis `Accept-Language`, puis la langue par défaut. Les valeurs invalides sont ignorées.

Dans une application Nuxt, vous n’avez pas besoin de ce paquet côté serveur : utilisez les [traductions côté serveur](/fr-CA/guide/server-side-translations) du module.

## API {#api}

| Export | Remarques |
| --- | --- |
| `createI18n(options)`, `I18n` | instance runtime + `translationDir`, `loadTranslations(dir?)`, `reload()` |
| `loadTranslations(dir, disablePageLocales?)` | `{ root, routes }` |
| `loadRootTranslations(dir, disablePageLocales?)` | `root` seulement |
| `FormatService`, `interpolate` | provenant de core |
| Types : `I18nOptions`, `LoadedTranslations`, `Translations`, `Locale`, `PluralFunc`, `Params` | |

Les méthodes de l’instance sont énumérées dans [Runtime](/fr-CA/integrations/runtime-package#api). Signatures complètes : [référence du paquet](/fr-CA/api/packages/node).
