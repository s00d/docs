Les traductions sont de simples fichiers JSON : un fichier racine par locale pour les clés partagées, et un fichier par page et par locale pour les clés de cette page. Lisez cette page lorsque vous ajoutez des pages, partagez des clés entre elles ou configurez des solutions de repli. Vous apprendrez dans quel fichier une clé doit aller, ce qu'une page peut voir et quand chaque fichier est chargé.

## Organisation {#layout}

```text
locales/
├── en.json                 # root: menus, footer, buttons
├── de.json
└── pages/
    ├── index/              # pages/index.vue
    │   ├── en.json
    │   └── de.json
    ├── about/              # pages/about.vue
    │   ├── en.json
    │   └── de.json
    └── products-id/        # pages/products/[id].vue
        ├── en.json
        └── de.json
```

- Le dossier sous `locales/pages/` porte le **nom de route** Nuxt de la page : `pages/products/[id].vue` devient `products-id`, `pages/blog/[slug]/comments.vue` devient `blog-slug-comments`.
- Les clés peuvent être imbriquées à n'importe quelle profondeur; `$t('auth.form.login')` lit `{ "auth": { "form": { "login": … } } }`.
- `translationDir` déplace le dossier (`'locales'` par défaut, relatif à la racine du projet, y compris avec l'organisation `app/` de Nuxt 4).
- Les fichiers manquants sont créés sous la forme `{}` lorsque Nuxt résout les pages, sauf si [`disableWatcher`](/fr-CA/api/module-options#disablewatcher) est défini.

## Ce qu'une page voit {#what-a-page-sees}

![Ordre de recherche d'une clé sur /about en de : pages/about/de.json, de.json, pages/about/en.json, en.json. Ils sont fusionnés en un seul about/de/data.json que $t lit](/images/diagrams/page-dictionary.svg)

Le dictionnaire d'une page est son fichier racine fusionné avec son fichier de page, en profondeur (à tous les niveaux). Le fichier de page l'emporte en cas de conflit :

```json
// locales/en.json
{ "title": "My shop", "nav": { "home": "Home", "cart": "Cart" } }
```

```json
// locales/pages/about/en.json
{ "title": "About us", "nav": { "cart": "Basket" } }
```

```ts
// on /about
t('title') // 'About us'
t('nav.home') // 'Home'   (root)
t('nav.cart') // 'Basket' (page wins)
// on any other page
t('title') // 'My shop'
```

Une page sans son propre dossier ne reçoit que le dictionnaire racine. Les clés des autres pages ne sont pas visibles.

### Locales de repli {#fallback-locales}

Une clé absente dans la locale active est prise dans sa locale de repli avant que la clé elle-même ne soit affichée :

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    locales: [
      { code: 'en', iso: 'en-US' },
      { code: 'de', iso: 'de-DE' },
      { code: 'de-at', iso: 'de-AT', fallbackLocale: 'de' },
    ],
    defaultLocale: 'en',
    fallbackLocale: 'en', // global, for every locale
  },
})
```

- Le `fallbackLocale` propre à une locale est suivi jusqu'au bout : `de-at` → `de` → `en`.
- Le `fallbackLocale` global est la couche la plus faible, sous toutes les chaînes.
- Chaque locale de la chaîne ajoute son fichier racine, puis son fichier de page, de la locale de repli la plus faible jusqu'à la locale active. Ainsi, le fichier racine de la locale active l'emporte sur le fichier de page d'une locale de repli.

Sans locale de repli, une clé manquante est affichée telle quelle (`'nav.home'`) et un avertissement est journalisé dans la console du navigateur en développement ([`missingWarn`](/fr-CA/api/module-options#missingwarn)).

## Partage et autres sources {#sharing-and-other-sources}

| Besoin | Option |
| --- | --- |
| Seulement des fichiers racines, aucun dossier `pages/` | [`disablePageLocales: true`](/fr-CA/api/module-options#disablepagelocales) |
| Deux pages lisent un même dossier de page | [`routesLocaleLinks`](/fr-CA/api/module-options#routeslocalelinks) : `{ 'about-us': 'about' }` |
| Fichiers racines partagés dans un autre dossier | [`additionalTranslationDirs`](/fr-CA/api/module-options#additionaltranslationdirs) : `['common']` (le `translationDir` principal l'emporte) |
| Clés provenant d'une couche Nuxt | Les fichiers des couches sont fusionnés, ceux du projet l'emportent. Consultez [Couches](/fr-CA/guide/layers) |
| Clés ajoutées à l'exécution | le hook [`i18n:register`](/fr-CA/api/events), `$mergeTranslations`, `$setTranslation` |
| Clés intégrées dans un composant de page | `$defineI18nRoute({ locales: { en: { … } } })`, consultez [Configuration de page](/fr-CA/guide/per-component-translations) |

## Comment une page charge son dictionnaire {#how-a-page-loads-its-dictionary}

![Les fichiers JSON de locale sont compilés en une arborescence de payloads, stockée dans public/ sur Node ou dans les assets serveur sur Edge, lue par un chargeur serveur, puis utilisée par $t sur le serveur et récupérée pour $t dans le navigateur](/images/diagrams/translation-pipeline.svg)

Le module construit un payload par page et par locale : `/{apiBaseUrl}/{page}/{locale}/data.json` (`/_locales/about/de/data.json` par défaut).

1. **Rendu serveur.** Nitro détecte la locale et la page charge son payload directement à partir du chargeur serveur, sans requête HTTP. Le dictionnaire n'est pas écrit dans le payload HTML; les pages restent donc légères.
2. **Hydratation.** Le navigateur récupère le même payload. Le serveur a déjà émis un `<link rel="preload">` pour celui-ci; la récupération commence donc avec le HTML.
3. **Navigation.** Le payload de la page suivante remplace le dictionnaire. Les clés de la page quittée sont encore résolues jusqu'à sa disparition (fin de la transition de page, ou `page:finish`), de sorte qu'une page en train de s'estomper n'affiche pas brièvement des clés brutes. Un bloc dont le chargement échoue (erreur réseau, 4xx ou 5xx, corps qui n'est pas un objet) laisse le dictionnaire courant en place, et la navigation suivante le charge de nouveau. Il en va de même pour un changement de locale qui échoue : `$switchLocale` se résout à `false`, et l'appeler de nouveau, ou cliquer de nouveau sur le sélecteur, relance la tentative. Avec les stratégies à préfixe, l'URL a déjà changé à ce moment-là; `lang` et `$getLocale()` indiquent donc la locale de l'URL pendant que les anciens textes restent à l'écran.
4. **Cache.** Les payloads chargés sont mis en cache sur le serveur et dans le navigateur; [Performance](/fr-CA/guide/performance) présente les réglages de taille et de TTL.

`translationPayloads.mode` détermine la façon dont les payloads sont construits. `'premerged'` (par défaut) écrit chaque fichier page × locale au moment du build. `'source'` conserve les fichiers sources et les fusionne à chaque requête, ce qui est plus léger pour les grands catalogues sur des cibles Edge. Les deux produisent les mêmes dictionnaires. L'emplacement des fichiers pour chaque cible de déploiement est décrit dans [Déploiement](/fr-CA/guide/deployment).

## Modification en développement {#editing-in-development}

`nuxt dev` lit les fichiers en direct. L'enregistrement d'un fichier de traduction rafraîchit sur place le dictionnaire de la page ouverte : aucun rechargement, les clés supprimées disparaissent, et une modification d'un fichier racine atteint toutes les pages. Un fichier JSON invalide journalise un avertissement avec son chemin et est traité comme vide. Définissez [`hmr: false`](/fr-CA/api/module-options#hmr) pour rafraîchir manuellement à la place.
