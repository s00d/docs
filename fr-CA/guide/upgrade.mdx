Cette page énumère ce qui change pour votre application lorsque vous mettez à niveau nuxt-i18n-micro et ses paquets `@i18n-micro/*`. Lisez la section correspondant à votre version de départ avant de mettre à jour la dépendance. La plupart des applications nécessitent peu de modifications de code.

<Tip>

**Vous venez de `@nuxtjs/i18n`?** — Consultez [Migrer depuis @nuxtjs/i18n](/fr-CA/guide/migration).

</Tip>

## Après 3.30.3 : la version majeure {#after-3-30-3-the-major-release}

Les options du module, `$t`, `$localePath`, `$switchLocale` et les autres fonctions utilitaires, composants, composables et utilitaires serveur documentés conservent leur nom. Ce qui change, c'est le comportement, surtout par des correctifs de bogues. Les paquets d'adaptation et les paquets de routage comportent de véritables ruptures d'API : voir [Paquets de cadriciels](#framework-packages) et [Autres paquets](#other-packages).

### À faire en premier {#do-this-first}

1. **Vérifiez vos versions.** Le module nécessite Nuxt 3.18 ou plus récent et Node 20 ou plus récent. Nuxt a son propre minimum pour Node : Nuxt 4.5 déclare `^22.19.0 || ^24.11.0 || >=26.0.0`. `nuxt generate` sur Nuxt 3.18.0 lui-même échoue aussi avec Nuxt seul (`[unstorage] Invalid key: "/"`); la version 3.21.11 fonctionne. `@i18n-micro/react` nécessite React 18 ou plus récent.
2. **Corrigez les paquets installés.**
   - Retirez `@i18n-micro/hmr`. Le HMR des traductions est intégré au module.
   - Si vos tests importent `@i18n-micro/test-utils`, ajoutez-le : `npm install -D @i18n-micro/test-utils`. Il n'est plus installé avec le module.
   - Remplacez `nuxt-i18n-micro-cli` par `@i18n-micro/cli`. Les 28 commandes sont devenues 16, `check` en remplace trois, et les codes de sortie changent : voir [le guide de la CLI](/fr-CA/guide/cli#moving-from-nuxt-i18n-micro-cli).
3. **Cherchez dans votre code** les entrées du tableau ci-dessous.
4. **Vérifiez ce qui se trouve devant l'application.** Avec `baseUrl` sur des locales derrière un proxy, voir [Derrière un proxy ou un CDN](/fr-CA/guide/deployment#behind-a-proxy-or-cdn). Avec un CDN, comparez sa clé de cache à l'en-tête `Vary` : voir [Mise en cache du HTML](/fr-CA/guide/deployment#caching-html). Avec `apiBaseClientHost` ou une CSP stricte, autorisez le nouveau lien `preload` : voir [SEO et balises d'en-tête](#seo-and-head-tags).
5. **Mettez à jour les instantanés.** Les instantanés de l'en-tête gagnent le lien `preload`, le balisage du sélecteur a changé ([`<i18n-switcher>` et `<i18n-link>`](#&lt;i18n-switcher>-and-&lt;i18n-link>)), et les chaînes de requête dans la sortie de `$localeRoute` sont encodées différemment.
6. **Ouvrez vos pages dans chaque locale et cherchez les clés brutes.** Les mises en page qui utilisaient des clés du fichier de la page précédente les affichent maintenant brutes : déplacez ces clés dans le fichier racine.

<Warning>

**`switchLocaleRoute` de `@i18n-micro/path-strategy` a perdu son premier argument** — `switchLocaleRoute(fromLocale, toLocale, route, options)` est maintenant `switchLocaleRoute(toLocale, route, options)`. **Un ancien appel JavaScript n'échoue pas : il retourne un résultat erroné,** car `fromLocale` est lu comme la cible et `toLocale` comme la route. Seul TypeScript vous le signale. Le `$switchLocaleRoute` de Nuxt n'est pas touché.

</Warning>

### URL et redirections {#urls-and-redirects}

- **`/en` et `/en/...` donnent une erreur 404 avec `prefix_except_default`** (`en` étant la locale par défaut), comme documenté.
- **Un préfixe de locale avec une autre casse ou une autre graphie donne une erreur 404.** `/DE/about` affichait auparavant la route allemande dans la locale par défaut, ou redirigeait vers `/en/DE/about`. Une page propre à cette URL reste une page. Une page attrape-tout ou une page `[slug]` n'en est pas une : `/DE/x` sous `[...slug]` et `/DE` à côté de `[slug]` donnent aussi une erreur 404; un slug de CMS identique à un code de locale dans une autre casse perd donc sa page. Avec `ssr: false`, aucun serveur ne répond, donc `/DE/about` affiche la page allemande.
- **Un chemin de page dans une autre casse redirige vers sa propre graphie.** `/T/BASIC` donnait un 200 et donne maintenant un `302` vers `/t/basic`.
- **Une URL inconnue reste une erreur 404.** Avec `autoDetectPath: '*'` ou `'no_prefix'`, `/nope` ne redirige plus d'abord vers `/de/nope`. `prefix` conserve la redirection (rien n'y est servi sans préfixe), tout comme `/` partout.
- **Le chemin personnalisé d'une autre locale, sans préfixe, trouve sa page avec `prefix_except_default`.** `/a-propos` donnait une erreur 404 et donne maintenant un `302` vers l'URL de la locale par défaut (`/about`). Avec `prefix`, la même redirection atteint maintenant une page existante (`/en/about`; c'était `/en/a-propos`, une erreur 404). `prefix_and_default` reste une erreur 404.
- **`prefix` avec `redirects: false` répond par une erreur 404 sur une URL sans préfixe** (`/about` donnait un `302`), y compris l'URL d'origine d'une page ayant un chemin personnalisé par défaut. `$localePath('/about')` trouve toujours cette page.
- **Avec `prefix_except_default`, l'URL d'origine d'une page ayant un chemin personnalisé par défaut redirige vers celui-ci,** pages dynamiques comprises. `/dir/one` donnait une erreur 404 et donne maintenant un `302` vers `/dir-one/one`.
- **`autoDetectPath: '*'` applique maintenant le témoin et `Accept-Language` aux chemins sans préfixe aussi** (`/about` → `/de/about`).
- **Avec `prefix`, une URL sans préfixe conserve la locale du visiteur.** Avec le témoin `de`, `/about` et un simple `<NuxtLink to="/about">` mènent à `/de/about`, sur tous les chemins, peu importe ce que dit `autoDetectPath`.
- **Avec `prefix_and_default`, une URL sans préfixe correspond à la locale par défaut.** `/contact` avec `Accept-Language: de` s'affichait auparavant en allemand, puis s'hydratait en anglais. Elle s'affiche maintenant dans la locale par défaut; les visiteurs accèdent à l'allemand par `/de/...`.
- **Avec `no_prefix`, un chemin personnalisé s'affiche dans sa propre locale** (`/ueber-uns` est en allemand, quelle que soit la préférence), et une page restreinte s'affiche dans une locale qu'elle sert. Un chemin que plusieurs locales partagent s'affiche dans la locale préférée lorsqu'elle en fait partie et, avec `baseUrl`, constitue une page sur chacun de leurs domaines. Ces locales partagent un même enregistrement, `localized-<page>-<first locale>`.
- **`noPrefixRedirect` se fie à la locale du visiteur.** Avec le témoin `de`, `/about` mène à `/ueber-uns`, et s'affiche en allemand, et non au `/about-us` de la locale par défaut. Une locale sans chemin personnalisé propre reste sur `/about`.
- **Une redirection `routeRules` sans page n'est pas localisée.** `/de/old` donnait un 200 vide; c'est maintenant une erreur 404 : ajoutez une règle pour le chemin avec préfixe si vous en avez besoin. Un lien depuis une autre locale vers une telle règle conserve le chemin tel qu'écrit et aboutit à la cible de la règle.
- **Les règles de route atteignent les chemins personnalisés.** `/blog/**` s'applique aussi à `/de/artikel/:slug` lorsque `blog/[slug]` a ce chemin, et les règles sont aussi copiées avec `no_prefix`. Une route sœur statique comme `/de/artikel/news` correspond elle aussi à ce motif. Une règle déjà écrite sous un préfixe de locale reste telle qu'écrite.
- **Une locale avec `disabled: true` répond immédiatement par une erreur 404 sur son préfixe**, et les liens vers celle-ci restent sur la page. Une locale désactivée à l'exécution fait de même : elle s'affichait auparavant dans la locale de repli.
- **La page 404 du module affiche `Page Not Found`** sur le préfixe d'une locale désactivée et sur le préfixe propre à un hôte, là où Nuxt affichait `Page not found: /de/about`. Le statut est le même.
- **`customRegexMatcher` ne donne plus d'erreur 404 pour une vraie page** dont le premier segment ressemble à une locale.
- **Les noms de route localisés sont cohérents.** Un enfant sous un enregistrement de locale partagé conserve le nom de la page, `no_prefix` respecte `localizedRouteNamePrefix`, et un parent ayant un enfant index reste sans nom.
- **Les pages qu'un module ajoute sans `name`** (`extendPages`) sont localisées et reçoivent un nom, avec des variantes de locale et `hreflang`. Elles restaient auparavant non localisées.
- **Une entrée de `nuxt.config` l'emporte sur `$defineI18nRoute`,** quelle que soit la forme de la clé (`about/team`, `/about/team`, `about-team`). Auparavant, celle qui l'emportait dépendait de la graphie.
- **Nouveaux avertissements de compilation :** une valeur de `localeRoutes` qui commence par son propre code de locale (`fr: '/fr/article'`), et le chemin personnalisé d'un enfant situé hors de son parent.
- **Le mode hash fonctionne avec `prefix`.** Le document est `/`, et `/en` ou `/about` redirigent vers le fragment.
- **`/#/de/x` s'affiche en allemand** avec `prefix_except_default` et `prefix_and_default`. Il s'affichait en anglais avec une incohérence d'hydratation.

### Liens et objets de route {#links-and-route-objects}

- **Une locale qui ne sert pas une page pointe vers son accueil.** `$localeRoute`, `$switchLocalePath` et le sélecteur ne retournent plus la page d'une autre locale.
- **Un code de locale inconnu mène à la locale par défaut.** `$localePath(path, 'xx')` et `$localeRoute` donnaient auparavant `/xx`.
- **`$localePath` retourne telle quelle une chaîne avec un schéma `http(s):`, `mailto:` ou `tel:`, et le `path` et le `fullPath` de `$localeRoute` la conservent inchangée**; ne leur passez donc pas une valeur non vérifiée (un paramètre `?next=`) comme cible de lien. `//host` et les noms nus comme `x.com` restent des chemins, sur cette origine dans chaque locale, et aucun lien qu'ils produisent n'en sort : `/de//x.com` vers la locale par défaut donne `/x.com`. Les barres obliques inverses comptent comme des barres obliques.
- **`$localePath` encode un chemin :** `/a b` donne `/a%20b`.
- **`$localeRoute` et `$switchLocaleRoute` retournent des objets simples,** utilisables sans risque dans `ref`, `reactive`, `useState`, en JSON et dans des décompositions. Lorsqu'un paramètre doit être échappé, l'objet est `{ path, fullPath, query, hash }` (`$localeRoute` ajoute `href`), sans `name` ni `params`, et l'URL reste la même avant et après un rechargement. Une URL simple a les deux. `name` est nouveau : les anciens objets ne l'avaient jamais. Le code qui lit `.name` ou `.params` doit gérer leur absence, et la forme obtenue dépend de la valeur.
- **Avec `trailingSlash`, `$switchLocaleRoute` retourne toujours cette forme de chemin,** y compris pour les slugs simples, et les redirections serveur suivent `trailingSlash`. Les résultats et les en-têtes `Location` peuvent changer avec cette option.
- **Les valeurs de requête dans la sortie de `$localeRoute` utilisent l'encodage de vue-router :** `/` reste littéral et une espace devient `+` (`?redirect=/v2`; c'était `%2Fv2`). La valeur décodée est la même, mais un instantané d'un tel `href` change.
- **Un lien sans chemin reste sur la page actuelle.** `$localePath('#top')`, `'?p=2'`, `''` et `{ query }` conservent la page où ils se trouvent; `'#top'` se lisait auparavant à partir de la racine du site. Un `'about'` nu signifie toujours `/about`.
- **Décompositions.** `{ ...route, query }` et `{ ...route, hash }` conservent la modification, y compris par `$switchRoute`. Un nouveau `path` l'emporte dans `$localeRoute`, `$localePath` et `$switchRoute`. `{ ...route, params }` fonctionne sur une route nommée; sur une route sous forme de chemin, le chemin l'emporte et les paramètres sont ignorés, avec l'avertissement de développement de vue-router. Utilisez `$localeRoute({ name, params })`.
- **`$switchRoute` reste dans l'application.** Le `baseUrl` propre à une locale, `mailto:` et `tel:` en sortent; toute autre chaîne est un chemin.
- **`excludePatterns`** correspond à des segments complets (`'/admin'` ne correspond plus à `/administrator`), et les globs sont ancrés (`/docs/*` ne correspond plus à `/en/docs/x`). Les motifs `RegExp` atteignent maintenant l'exécution; ils y étaient auparavant perdus. Une page à laquelle ils correspondent n'est pas localisée : aucun `hreflang`, et la locale par défaut avec `prefix_except_default`. Vérifiez vos motifs à l'aide de [Exclure des chemins](/fr-CA/guide/excluding-static-files).

Un `%` ou un `?` dans un paramètre ne survit pas à un rechargement rendu par le serveur sur Nuxt 4.5.2, dans n'importe quelle application : cela relève du projet en amont, et non du module.

### Domaines de locale {#locale-domains}

- **`locales[].baseUrl` achemine maintenant les requêtes.** Une seule compilation sert tous les domaines : voir [Couches et domaines](/fr-CA/guide/layers#multiple-domains). Avec `baseUrl` défini, une locale d'un autre domaine donne une erreur 404 sur cet hôte (`/en/about` sur `example.de`), et les liens vers une locale sur le même hôte sont relatifs. Les requêtes sur tout autre hôte, `localhost` compris, se comportent comme avant, sauf que les balises canonical et `hreflang` utilisent `metaBaseUrl` s'il est défini, sinon le `baseUrl` de la locale par défaut, et non l'origine de la requête.
- **Derrière un proxy qui réécrit `Host`,** chaque requête retombe sur la configuration de compilation jusqu'à ce que vous définissiez [`trustForwardedHost`](/fr-CA/api/module-options#trustforwardedhost). Sa valeur par défaut est `false`, contrairement à `metaTrustForwardedHost`. Voir [Derrière un proxy ou un CDN](/fr-CA/guide/deployment#behind-a-proxy-or-cdn).
- **`nuxi generate` avec `baseUrl` nécessite `NUXT_I18N_DOMAIN`, une fois par domaine.** Sans cela, la compilation émet un avertissement, et ces locales sont des liens sans pages. Voir [Site statique](/fr-CA/guide/deployment#static-site-(nuxi-generate)).
- **Un lien vers une locale ayant un `baseUrl` passe par `$localePath` ou `<i18n-link>`.** `<NuxtLink :to="$localePath(x, 'fr')">` et `<i18n-link :to="$localeRoute(x, 'fr')">` correspondent à cette URL absolue, et un clic y mène. Le routeur n'accepte aucun objet absolu : `<NuxtLink :to="$localeRoute(x, 'fr')">` et `router.push($localeRoute(x, 'fr'))` restent `/https://fr.example.com/...`, un chemin de cette application. Sur `localhost` ou un hôte de prévisualisation, chaque locale ayant un `baseUrl` est un tel lien, y compris la locale actuelle. Dans le code, utilisez `navigateTo($localePath(x, 'fr'), { external: true })`.
- **L'accueil d'un domaine s'écrit partout sans barre oblique finale** (`https://example.de`), dans les liens, la balise canonical et `hreflang`.
- **Avec `prefix`, un lien vers un autre domaine conserve le préfixe de locale, avec ou sans `baseDefault`.** `https://example.de/de/about`, et non `https://example.de/about`, qui ne fait que rediriger.
- **Avec `prefix_except_default` et `baseDefault` sur une locale autre que celle par défaut de la compilation, les routes conservent tous les préfixes** afin que d'autres domaines puissent y faire référence. `/en` donne toujours une erreur 404. Seul le code qui lit `router.getRoutes()` voit la différence.
- **Avec `prefix_except_default`, le préfixe propre à un hôte donne une erreur 404 sur son hôte `baseDefault`.** `/de/x` sur l'hôte `de` donnait un 200.
- **`$getI18nConfig().locales` contient seulement ce que l'hôte sert.** `linkLocales` les contient toutes, et `$getLocales()` reste complet.

### Navigation et `$switchLocale` {#navigation-and-$switchlocale}

- **Une navigation s'applique lorsqu'elle est validée.** Le dictionnaire, la locale, les paramètres et l'en-tête changent dans `router.afterEach`; une navigation annulée ou bloquée ne change donc rien, et les liens de l'ancienne page restent valides pendant le chargement du bloc suivant. Un `beforeResolve`, un `beforeRouteEnter` ou une garde globale ultérieure voit maintenant l'ancien dictionnaire et l'ancienne locale. Le middleware de route n'est pas touché.
- **Un bloc dont le chargement échoue conserve le dictionnaire actuel.** Une erreur 5xx, une erreur réseau ou un corps invalide pour le fichier racine affichait auparavant des clés brutes. La nouvelle page s'affiche maintenant avec les anciennes chaînes, et la navigation suivante réessaie. Une erreur 404, ou la coquille SPA d'un hôte statique à la place du fichier, donne le dictionnaire racine jusqu'au prochain rechargement.
- **`$switchLocale` se résout par `true` ou `false`** (il ne se résolvait en rien), `false` lorsque le dictionnaire de la locale ne s'est pas appliqué. Il est typé `Promise<boolean>`, et `$switchRoute` `Promise<void>`.
- **`$switchLocale` est un choix explicite.** À l'arrivée, il enregistre la locale, y compris sur une erreur 404. Si la navigation est bloquée, annulée ou lève une exception, la préférence enregistrée et l'état restent tels quels, et l'exception est relancée. Un déplacement vers un autre hôte l'enregistre d'abord. Avec `no_prefix` et en mode hash, le changement tient, quoi que fasse la navigation. Sur une page ayant une seule URL pour toutes les locales (`excludePatterns`), le choix n'est pas annulé, et c'est l'URL de la page suivante qui décide : avec `prefix_except_default`, un lien sans préfixe revient à la locale par défaut.
- **Avec `no_prefix`, `$switchLocale` conserve sa page lorsque deux pages partagent un chemin personnalisé,** y compris avec des paramètres échappés. Un rechargement d'une telle URL, et un `$localeRoute` avec un paramètre échappé, aboutissent au premier enregistrement.
- **Une redirection côté client conserve le mode de sa navigation.** Un simple `<NuxtLink to="/about">` avec `prefix` ajoute une entrée à l'historique au lieu de remplacer l'entrée actuelle; `router.replace` remplace toujours.
- **`$setI18nRouteParams` et `useI18nHead` provenant du serveur survivent à l'hydratation.** Après l'arrivée sur `/news/2`, le sélecteur pointe vers le slug traduit (`/de/news/2-zwei`), et non vers `/de/news/2`, y compris dans le HTML du serveur, peu importe où se trouve le sélecteur, lorsque la page définit les paramètres pendant le SSR. Ils sont abandonnés lorsqu'une navigation vers un autre chemin est validée, y compris de `/news/1` à `/news/4` : définissez-les de nouveau sur la nouvelle page.
- **`$setI18nRouteParams` lu dans le setup est lié à cette page.** Un appel tardif depuis une page déjà quittée ne fait rien. `useNuxtApp().$setI18nRouteParams` est maintenant un accesseur, et deux lectures donnent deux fonctions. Il n'a pas de mutateur : `useI18n().$setI18nRouteParams = fn`, comme pourrait le faire une simulation de test, lève une exception en mode strict; simulez donc `useI18n` lui-même. Dans une mise en page ou dans `app.vue`, c'est la fonction simple, puisque rien n'y est quitté.
- **Le serveur réécrit les liens de `<i18n-switcher>` à la fin du rendu**, sur les pages avec paramètres, car un sélecteur dans la mise en page s'affiche avant le setup asynchrone de la page. Un lien `$switchLocalePath` écrit à la main n'est pas réécrit : voir [routes de locale personnalisées](/fr-CA/guide/custom-locale-routes). Avec la diffusion en continu SSR de Nuxt, le premier HTML conserve les paramètres de l'URL.
- **Une prop nommée `locale` sur un composant serveur définit sa locale de rendu**, de sorte que `<Greeting :locale="$getLocale()" />` suit l'URL et les changements de locale. `$getLocale()`, `$localePath` et `$getLocaleName` à l'intérieur suivent aussi la prop. Voir [traductions côté serveur](/fr-CA/guide/server-side-translations). Sans la prop, il utilise toujours le témoin ou la valeur par défaut.
- **Les pages `keepalive` récupèrent leurs paramètres et leur en-tête** au retour.
- **Une page imbriquée définie à `false` avec `prefix_except_default` n'a pas d'URL de locale.** `/de/parent/kid` avec `globalLocaleRoutes: { 'parent-kid': false }` était servie et donne maintenant une erreur 404 : la page reste sur `/parent/kid`.

### Détection de la locale et témoin {#locale-detection-and-the-cookie}

Un seul ordre de priorité partout, décrit dans [Détection de la locale](/fr-CA/guide/locale-detection).

- **`?locale=` ne compte sur les pages qu'avec `no_prefix`.** Avec les stratégies à préfixe, l'URL décide; `/about?locale=de` ne s'affiche plus en allemand sous `lang="en"`. `?locale=de&locale=fr` lit la première valeur; c'était `"de,fr"`.
- **`Accept-Language` respecte les valeurs `q`** (`fr;q=0.1, de;q=0.9` → `de`; `q=0` exclut une langue). La correspondance régionale ne dépend plus de l'ordre de `locales` et ne mélange jamais les écritures chinoises.
- **Une navigation côté client vers une page enregistre sa locale dans le témoin, y compris sur une page sans préfixe de la locale par défaut.** Avec `localeCookie` défini, un visiteur qui clique sur un lien vers `/about` a maintenant `user-locale=en`, et un changement ultérieur de la langue du navigateur ne redirige plus `/`. Un premier chargement de cette URL n'enregistre rien. Avec `no_prefix` et en mode hash, une navigation n'enregistre qu'un changement.
- **Une erreur 404 n'écrit aucun témoin :** ni la réponse, ni une simple navigation côté client vers celle-ci, dans aucun mode. Avec `no_prefix`, une URL qui semble avoir un préfixe n'en écrit pas non plus.
- **Avec `no_prefix`, un `localeCookie: null` explicite est respecté.** Il devenait auparavant `user-locale`. Définissez-le dans le bloc `i18n` de `nuxt.config` : un `null` dans `modules: [[name, opts]]` ou dans une couche est toujours perdu.
- **Le mode hash lit uniquement le témoin `hash-locale`.** Un `user-locale=de` seul ne compte plus.
- **Un témoin de locale mal formé est ignoré et reste tel quel,** au lieu de faire échouer chaque page SSR avec une erreur 500. Il n'est plus supprimé à chaque requête, ce qui empêchait aussi une page avec préfixe d'enregistrer sa locale.
- **La locale de l'URL passe en premier.** Un `setLocale('de')` dans un plugin sur `/en/...` ne charge plus le dictionnaire `de`, et un code inconnu dans l'état est ignoré.
- **Les fonctions utilitaires de l'API serveur** (`useLocaleServerMiddleware`, `useTranslationServerMiddleware`) utilisent un seul ordre sur chaque route : `?locale` → paramètre `[locale]` ou préfixe → témoin → en-tête → valeur par défaut. Elles respectent maintenant `localeCookie: null` et `autoDetectLanguage: false`, et mettent en cache un dictionnaire par locale.
- **Les substitutions à l'exécution atteignent le routage.** `NUXT_I18N_DEFAULT_LOCALE` et les `disabledLocales` définies à l'exécution modifient maintenant la stratégie générée (une locale désactivée cesse d'être routée), et les `disabledLocales` d'exécution s'ajoutent à celles de la compilation. Avec `prefix_except_default` et `prefix_and_default`, une `defaultLocale` définie à l'exécution est ignorée avec un avertissement, car les routes sans préfixe de cette locale sont générées à la compilation. Une `fallbackLocale` définie à l'exécution doit être une locale activée : sinon, elle est abandonnée avec un avertissement et la valeur de la compilation s'applique si celle-ci est activée. Voir [Substitutions à l'exécution](/fr-CA/guide/runtime-overrides).

### SEO et balises d'en-tête {#seo-and-head-tags}

- **`dir="auto"` n'est plus la valeur par défaut.** Une locale sans `dir` recevait auparavant `dir="auto"`, ce qui ralentit l'analyse des grandes pages. Désormais, une langue RTL connue reçoit `dir="rtl"`, et toute autre locale ne reçoit aucun attribut. Cela s'applique à Nuxt, à `@i18n-micro/vue`, à `astro` et à `vitepress`. Si vous définissez `dir: 'auto'` sur une locale pour conserver l'ancienne sortie, cela coûte environ 1 s d'analyse à 20 000 éléments : voir [Sens du texte](/fr-CA/guide/seo#text-direction).
- **Chaque page SSR a une nouvelle balise :** `<link rel="preload" as="fetch" crossorigin="anonymous" href="/_locales/...">`, y compris les pages 404. Avec `apiBaseClientHost`, le `href` est sur cet hôte, ce qui nécessite CORS. Une CSP stricte doit l'autoriser.
- **`hreflang` énumère seulement les locales qui servent la page**; `x-default` n'est émis que lorsque la locale par défaut la sert.
- **Une page non localisée n'a ni `hreflang` ni `og:locale:alternate`.**
- **Les balises canonical et `hreflang` incluent `app.baseURL`** lorsque l'origine provient de la requête. `metaBaseUrl` et `site.url` restent tels qu'écrits.
- **Les pages 404 portent `<html lang dir>`**, dans la locale de l'URL. Elles n'ont ni canonical, ni `hreflang`, ni `og:url`, ni `og:locale`, ni alternatives, y compris lorsque le module lui-même répond par l'erreur 404 sur un enregistrement correspondant (`/en/...`). Les balises que vous passez par `replace` de `useI18nHead` restent; omettez-les donc sur les pages d'erreur.
- **Les balises canonical, `og:url` et `hreflang` conservent une chaîne de requête figurant dans la liste blanche** (`/about?page=2`), y compris sur le serveur : elle était abandonnée pendant le SSR. `page`, `sort`, `filter`, `search`, `q`, `query` et `tag` figurent dans la liste blanche par défaut; voir [`canonicalQueryWhitelist`](/fr-CA/api/module-options#canonicalquerywhitelist).
- **Un `X-Forwarded-Host` qui ne peut pas être analysé est ignoré** au lieu de causer une erreur 500 sur chaque page. Sans hôte utilisable, et sans `metaBaseUrl` ni `site.url`, les URL canonical et `hreflang` de cette réponse sont relatives. Un `Host` qui ne peut pas être analysé donne toujours une erreur 500, comme dans une application Nuxt simple.
- **`disableMeta` fonctionne maintenant,** autant dans `$defineI18nRoute` que dans `routeDisableMeta`, y compris lorsqu'il est défini dans `nuxt.config` : la page n'a ni `hreflang`, ni canonical, ni `og:locale`. `lang` et `dir` restent.
- `useLocaleHead()` retourne aussi `build()`, un accesseur pour `useHead(() => build())`.
- Dans une compilation simple sans `metaBaseUrl`, `X-Forwarded-Host` choisit toujours l'hôte dans ces balises, comme avant. Fixez `metaBaseUrl` si l'origine est accessible directement : voir [Derrière un proxy ou un CDN](/fr-CA/guide/deployment#behind-a-proxy-or-cdn).

### Traductions {#translations}

- **Les fusions sont profondes à tous les niveaux.** Les fichiers racine, de page et de repli utilisaient une fusion sur 2 niveaux, de sorte que `a.b.c` provenant d'un fichier de repli ou de la racine était perdu en mode source et en développement. Tous les modes donnent maintenant le même dictionnaire.
- **Les chaînes de repli sont suivies jusqu'au bout** (`fr` → `de` → `en`) dans tous les modes.
- **La fusion se fait par locale, et non par type de fichier.** Le fichier racine de la locale active l'emporte maintenant sur le fichier de page d'une locale de repli. Voir [Locales de repli](/fr-CA/guide/translations#fallback-locales).
- **L'entrée `locales` d'un projet l'emporte sur celle d'une couche** pour le même `code`; une couche ne fait que combler les manques.
- **Une page sans son propre dossier `pages/<name>/` lit le dictionnaire racine,** y compris les pages enfants. Elle recevait auparavant `{}` et affichait des clés brutes. La sortie gagne un fichier par page de ce type, et `__root/<locale>/data.json` par locale : `/_locales/<any name>/en/data.json` donne un 200 avec les clés racine; c'était `{}`. Cela importe pour la surveillance, pour les listes d'autorisation sur les hôtes statiques et pour les outils qui lisent l'arborescence.
- **`disablePageLocales: true` lit uniquement les fichiers racine;** `pages/index` n'y est plus fusionné.
- **Les clés de la page quittée cessent d'être résolues lorsque son élément quitte le document.** Si une mise en page utilisait des clés que seul le fichier de la page précédente contenait, déplacez-les dans le fichier racine. Les clés d'un parent restent pendant que son enfant est affiché, y compris pour un parent ayant un enfant `index`, jusqu'à la navigation suivante. Entre deux enfants d'un même parent, les clés propres au parent nécessitent le dictionnaire de l'enfant ou le dictionnaire racine.
- **`$clearCache()` recharge le dictionnaire de la page actuelle** et garde l'ancien à l'écran jusqu'à l'arrivée du nouveau. Un rechargement qui échoue conserve l'ancien dictionnaire, une réponse demandée avant le vidage est rejetée, et une page en transition de sortie reste traduite.
- **`$has(key, route)` respecte la route.**
- **`$loadPageTranslations` sur une page pas encore visitée n'empêche plus le chargement de son fichier.** Le fichier se charge à la première visite et vos clés restent par-dessus. La page affichait auparavant des clés brutes jusqu'à un rechargement.
- **Le HMR des traductions applique les modifications sur place**, sans recharger la page; les clés retirées disparaissent et les modifications de la racine atteignent toutes les pages.
- **Un fichier de locale corrompu émet un avertissement une seule fois avec son chemin, dans tous les modes.** Le mode développement levait auparavant une exception et le mode premerged l'ignorait silencieusement; une application qui comptait sur un échec brutal en développement ne le voit donc plus.

### Pluriels et formatage {#plurals-and-formatting}

- `$tc` avec un nombre négatif, fractionnaire ou très grand prend la dernière forme avec le nombre réel; `{ count: null }` ne lève plus d'exception; une clé de pluriel manquante atteint le gestionnaire des clés manquantes.
- `$tdr` donne de vraies dates futures (`in 3 days`, ou `tomorrow` avec `numeric: 'auto'`) et `Invalid Date` pour une entrée invalide. Moins d'une seconde dans le passé donne `0 seconds ago`.
- **`$tn`, `$td` et `$tdr` se fient à `iso`**, comme les pluriels : `{ code: 'en', iso: 'en-GB' }` formate maintenant les dates comme `31/10/2026`. Dans un code de locale, `_` se lit comme `-`; `en_US` ne lève donc plus d'exception, et un code inconnu d'`Intl` est formaté comme `en` plutôt que de suivre la locale de la machine. Les formats nommés sont toujours recherchés par `code`.
- Un espace réservé `{param}` lit uniquement les paramètres que vous passez (`{constructor}` reste tel qu'écrit).
- Les noms d'`{placeholder}` peuvent contenir n'importe quel caractère sauf les accolades et les espaces : `{firstName}`, `{first-name}` et `{user.name}` sont lus dans `params`. Sans un tel paramètre, ils restent tels qu'écrits, comme avant.
- Une `defaultValue` est interpolée, dans `$t` et `$tc` : `$t('missing', { n: 1 }, 'Got {n}')` donne `Got 1`; cela donnait auparavant `Got {n}`. Une valeur par défaut qui n'est pas une chaîne est retournée telle quelle.
- `$tc` sur une traduction vide répond `''`, comme `$t`. Il répondait auparavant la valeur par défaut ou la clé.
- **Les gabarits de pluriel conservent leur sens, à une exception près.** Le tableau énumère toutes les formes. Pour obtenir les catégories d'`Intl.PluralRules`, indiquez-le avec le nouveau [marqueur `=0 `](/fr-CA/api/methods#$tc) : `=0 no apples | one apple | {count} apples`.

  | Forme | Exemple (en `uk`) | Avant | Maintenant |
  | --- | --- | --- | --- |
  | N'importe quel gabarit dans une locale ayant une ou deux catégories d'entiers (`en`, `de`, `fr`, `es`, `ja`...) | `none \| one \| {count} many` | par indice | **inchangé** |
  | Une forme par catégorie | `one \| few \| many` | par indice : 21 → `many` | **inchangé**. Ajoutez le marqueur pour 21 → `one` |
  | Forme zéro en premier, trois formes | `none \| one \| many` | par indice | **inchangé** |
  | Autres espaces réservés | `no items \| {n} item \| {n} items` | par indice | **inchangé** |
  | `{count}` dans chaque forme | `{count} many \| {count} one \| {count} few` | par indice | **inchangé** |
  | Moins ou plus de formes que ci-dessous | `a \| b`, `none \| one \| two \| {count} many` | par indice | **inchangé** |
  | En `lv`, `prg`, `blo`, `cv`, `ksh`, `lag` | `none \| one \| {count} many` | par indice | **inchangé** |
  | Marqué avec `=0 ` | `=0 none \| one \| many` | le marqueur s'affichait comme du texte | forme zéro, puis catégories |
  | **Une forme zéro sans espace réservé, puis une forme par catégorie, avec `{count}` dans chaque forme que plusieurs nombres partagent** | `none \| {count} one \| {count} few \| {count} many` | par indice : 3 → `3 many`, 21 → `21 many` | **par catégorie** : 3 → `3 few`, 21 → `21 one`. 0, 1, 2 et tout nombre qui reste dans `many` donnent le même résultat |

  La dernière forme nécessite trois catégories ou plus (`ru`, `uk`, `pl`, `cs`, `sk`, `hr`, `sr`, `lt`, `ro`, `sl`, `he`, `ar`, `cy`...). En `ar`, `one` et `two` correspondent à des nombres uniques; ces deux formes n'ont donc besoin d'aucun nombre.
- **Un code de locale inconnu d'`Intl` reçoit la règle par indice**, avec ou sans les catégories du marqueur : `ua` ne suit plus la locale de la machine. Définissez `iso` : `{ code: 'ua', iso: 'uk-UA' }` applique les pluriels de l'ukrainien, dans le module et dans `@i18n-micro/vue`.
- **Une règle `plural` personnalisée conserve sa signature** et reçoit toujours le code de locale. Elle lit la valeur brute, de sorte qu'un gabarit marqué lui parvient avec `=0 ` en place, et elle reçoit le nombre sous forme de `Number` : `1.5` là où elle recevait `1`. Retourner `null` revient à la règle intégrée, qui respecte le marqueur.
- **Option `timeZone`.** Définissez-la (`Europe/Berlin`) pour afficher une même date de calendrier sur le serveur et dans tous les navigateurs. Elle n'a aucun effet sur `relativeDate`, qui dépend de l'horloge.

### `<i18n-t>` {#&lt;i18n-t>}

Cette section couvre `<i18n-t>` dans le module et `I18nT` dans `@i18n-micro/vue`. Pour les autres cadriciels, voir [Paquets de cadriciels](#framework-packages).

- **`html` échappe `params`, dans tous les cas, et ignore tous les slots.** Seule la traduction est considérée comme un balisage fiable. Un paramètre qui contenait volontairement du balisage s'affiche maintenant comme du texte : placez le balisage dans la traduction et passez les données en paramètres, ou utilisez des slots sans `html`.
- **Les slots fonctionnent avec `plural`, `number`, `date` et `relativeDate`,** et un slot `default` reçoit aussi `{ translation }` dans ces cas. Chaque `{name}` est rempli, et non seulement le premier.
- **Un slot l'emporte sur un paramètre du même nom.** Une valeur de paramètre qui ressemble à un espace réservé reste du texte. Avec un `customPluralRule` ou un `plural` personnalisé, la règle retourne une chaîne finale; un paramètre qu'elle a interpolé peut donc y être pris pour un espace réservé.
- **`null` signifie non défini** pour `plural`, `number`, `date` et `relativeDate`. `:plural="null"` faisait auparavant échouer le rendu, et `:date="null"` affichait 1970.
- `plural` compte comme `$tc`, avec `Number` : `1.5` reste `1.5` et prend la dernière forme (il était auparavant tronqué à `1`); `"2 items"` donne `NaN` (c'était `2`); `""` donne `0`. Un `customPluralRule` voit aussi `1.5`. Son autre contrat est inchangé : mêmes arguments, sa réponse est utilisée telle quelle, `null` affiche un rendu vide.
- `hideIfEmpty` s'applique à `plural`, `number`, `date` et `relativeDate`. Une valeur masquée affiche un commentaire, et non un nœud de texte vide; un test qui lisait `''` voit donc `<!---->`.
- **Une clé manquante avec `html` est du texte.** La clé est échappée, car seule une traduction est fiable et une clé peut provenir d'une requête. Une `defaultValue` vous appartient et reste du balisage.
- Avec `plural`, une `defaultValue` ou la clé reste entière en cas d'absence, comme dans `$tc` : `a | b` n'est plus divisé.
- `defaultValue` remplace une clé manquante dans chaque branche, et non la clé elle-même, et un `customPluralRule` la reçoit par son accesseur en cas d'absence. Elle n'avait auparavant d'effet qu'après `hideIfEmpty`.
- `<i18n-t>` avec `number`, `date` ou `relativeDate` conserve `params`; ils y sont fusionnés.
- La sortie de `date` et de `relativeDate` porte `data-allow-mismatch="text"` : une horloge ou un fuseau horaire qui diffère entre le serveur et le navigateur ne provoque plus d'avertissement pendant l'hydratation. À côté d'un slot nommé, le texte autour du slot est placé dans son propre `<span>`, car Vue vérifie l'attribut seulement sur le texte unique d'un élément.
- Les attributs `.innerHTML` et `textContent` sont abandonnés en même temps qu'`innerHTML`.
- `<i18n-t>` et `<i18n-group>` lisent le dictionnaire actif, comme `$t`, et non le bloc de la route. Les blocs évincés (`cacheMaxSize`) n'affichent plus de clés brutes. Une page en transition de sortie lit maintenant ce que `$t` y lit : le dictionnaire de la nouvelle page, avec repli sur le sien en cas d'absence; une clé définie par les deux pages affiche donc le nouveau texte et, après un changement de locale, ses propres clés s'affichent brutes jusqu'à son démontage.

### `<i18n-switcher>` et `<i18n-link>` {#&lt;i18n-switcher>-and-&lt;i18n-link>}

- **Un clic sur un lien du sélecteur correspond à une seule navigation.** C'est un simple `<a>` qui appelle `$switchLocale`, et non un `NuxtLink` accompagné d'un gestionnaire de clic; les classes `router-link-active` ont donc disparu. Le `href` porte toujours `app.baseURL`, et le lien de la locale actuelle a toujours `aria-current="page"`. Ctrl/Cmd-clic ouvre un nouvel onglet et ne touche pas à l'onglet actuel. Les liens conservent la chaîne de requête et le fragment.
- Le bouton est `type="button"`, il ne soumet donc plus un formulaire englobant, et il a `aria-expanded`. `aria-haspopup` a disparu, dans le module, dans `@i18n-micro/vue` et dans `@i18n-micro/astro` : il promettait un menu, alors que la liste est composée de liens. Échap et un clic à l'extérieur ferment le menu déroulant; deux sélecteurs ne restent plus ouverts en même temps.
- L'enveloppe et le menu déroulant ont les classes `i18n-switcher-wrapper` et `i18n-switcher-dropdown`; le bouton a `i18n-switcher-button` en plus de `language-switcher`, et son libellé se trouve dans un `<span>`. Les styles par défaut utilisent des propriétés CSS logiques (`inset-inline-start`, `margin-inline-start`), et le chevron est `▾`. Le menu déroulant a `z-index: 1000` (c'était 10), `min-width: 150px` et un `box-shadow`, et l'enveloppe `vertical-align: middle`. Chaque lien a `lang`, et `dir` lorsque la locale le définit.
- `<i18n-link>` : `https://`, `mailto:` et `tel:` sont reconnus quelle que soit la casse (`HTTPS://x.com`, `Mailto:`). Un `report.pdf` ou un `index.html` nu est une route, et non `https://report.pdf`; `example.com` et `example.com:8080` restent externes. Une terminaison de fichier qui est aussi un domaine de premier niveau (`example.md`, `x.zip`) compte comme un fichier : écrivez `https://`. `activeStyle` ignore une barre oblique finale, la chaîne de requête et le fragment. Il est maintenant typé `CSSProperties`; certaines valeurs typées pourraient donc devoir être modifiées.

### Hooks, plugins et types {#hooks-plugins-and-types}

- **`i18n:register` s'exécute à `app:created` au démarrage,** après tous les plugins plutôt qu'entre eux. Un plugin dont l'`order` est supérieur à 1 ou avec `enforce: 'post'` voit maintenant son abonné appelé au démarrage aussi, mais ne lit plus les clés enregistrées dans son propre `setup`. Lors d'une navigation, le hook s'exécute maintenant avant les gardes `router.beforeEach` des autres plugins.
- **`i18n:register` reçoit la locale de la page qu'il remplit.** Avec `hashMode`, une navigation qui change la locale passait auparavant l'ancienne, et les clés aboutissaient dans le mauvais bloc.
- **`i18n:register` est un hook d'exécution :** enregistrez-le avec `nuxtApp.hook('i18n:register', …)` dans un plugin, sans `@ts-expect-error`. Voir [Hooks](/fr-CA/api/events).
- **`hooks: false` et `define: false`** désactivent toujours leurs parties.
- **Avec `plugin: false`, `$defineI18nRoute` reste appelable** et ne fait rien à l'exécution. Il faisait auparavant planter la page.
- L'option `hooks` ne documente plus `i18n:beforeLocaleSwitch` / `i18n:afterLocaleSwitch`; ils n'ont jamais été émis.
- `const { $defineI18nRoute } = useNuxtApp()` dans une page fonctionne maintenant avec des configurations qui utilisent des variables.
- `useI18n()` a plus de clés : `clearCache`, `pluralFunc`, `pluralLocale`. `clearCache` figure dans son type.
- `$getRouteName(route)` répond pour la route qui lui est donnée. Il retournait une chaîne vide.
- `useI18nLocale()` abandonne `getLocaleWithServerFallback(serverLocale)` : écrivez `getPreferredLocale() ?? serverLocale ?? null`.
- **`$getI18nConfig()` est en lecture seule sur le serveur en développement.** Une écriture y lève une exception, et en production elle atteindrait chaque requête.

### Serveur, compilation et déploiement {#server-build-and-deployment}

- **Le fichier de données d'une page contient seulement ce qui diffère de la racine de la locale.** Le client charge la racine une seule fois et fusionne chaque page par-dessus; le disque et les paquets Edge diminuent donc, et une deuxième page coûte une fraction de la première. `premerged` écrit maintenant `__root/<locale>/data.json`, et `/_locales/<page>/<locale>/data.json` contient seulement la différence : tout ce qui lit ces fichiers directement doit fusionner les deux. Un dictionnaire complet reste un fichier valide; un hôte ou le mode `source` qui en sert un continue donc de fonctionner.
- **Les fichiers de dictionnaire sont mis en cache par version.** Une URL avec le `?v=` actuel est fixée pour un an sur un serveur Node, les autres URL sont revalidées, et la copie statique d'un hôte répond `max-age=60` : voir [En-têtes de cache](/fr-CA/guide/deployment#cache-headers-and-datebuild). `httpCacheControl: false` conserve `max-age=0`. Une traduction modifiée sans recompilation n'atteint un navigateur que lorsque `v` change : définissez `NUXT_I18N_DATE_BUILD`.
- **Les dictionnaires suivent `app.cdnURL`.** Le navigateur récupère les fichiers de données publics depuis `<cdnURL>/_locales/...`, là où il utilisait `app.baseURL` : le CDN doit contenir `_locales/` et autoriser l'origine de votre site (CORS). Voir [baseURL de l'application et hôtes des données](/fr-CA/guide/deployment#app-baseurl-and-payload-hosts).
- **Le SSR ne demande plus `/_locales` par HTTP,** de sorte qu'un middleware serveur ou un journal sur cette route ne voit plus les lectures du rendu. Un `apiBaseServerHost` externe passe toujours par HTTP.
- **Une lecture qui échoue ne reste plus en mémoire, pas plus qu'une erreur 404.** Une erreur 404 provenant d'un hôte signifie qu'il n'a pas ce fichier : le rendu affiche le dictionnaire racine, comme le navigateur, rien n'est conservé, et le fichier est lu dès qu'il apparaît. Tout autre échec, un 200 qui n'est pas un objet JSON, ou un fichier local illisible ou corrompu n'atteint aucun cache, et la requête suivante relit : un rendu de page journalise un avertissement, affiche des clés brutes et répond `503` avec `no-store` et `Retry-After`, de sorte qu'une règle de route ou un CDN n'en conserve rien pendant que le navigateur lit quand même le dictionnaire à l'hydratation; `/_locales/...` répond `503` avec `no-store`, et `useTranslationServerMiddleware` donne un `t` qui répond la clé ou la valeur par défaut. Pendant une panne, chaque requête atteint l'hôte, et un hôte qui n'envoie aucun en-tête de réponse pendant 60 secondes fait échouer la lecture. Le téléchargement lent d'un gros fichier n'a aucune limite. Voir [Quand un dictionnaire ne peut pas être lu](/fr-CA/guide/deployment#when-a-dictionary-cannot-be-read). `/_locales` transmet aussi cette erreur 404, là où il répondait `200 {}`.
- **Un prérendu qui ne peut pas charger son dictionnaire échoue,** tout comme un prérendu dont l'hôte n'a ni le fichier de la page ni le fichier racine. La route donne une erreur 500, un avertissement nomme la locale et la page, et aucun fichier n'est écrit; avec le `failOnError` par défaut de Nuxt, la compilation se termine avec le code 1. Une page sans fichier propre, mais avec un fichier racine, est prérendue avec la racine.
- **Un hôte défini à la compilation répond au SSR,** y compris avec la copie publique par défaut, et sur une page d'erreur d'un chemin interne. C'était auparavant le fichier public qui répondait. `NUXT_I18N_APP_BASE_SERVER_HOST` à l'exécution atteint maintenant `/_locales` et le chargeur serveur, et le rendu lit l'un ou l'autre hôte par ce chargeur.
- **Un `nitro.output.publicDir` personnalisé, et toute autre disposition où `public/` n'est pas à côté du serveur, intègre les fichiers de données.**
- **`nuxi build --preset <static preset>` effectue le prérendu comme `nuxi generate`,** il peut donc écrire plus de fichiers. `nuxi generate` prérend chaque page statique dans chaque locale qui la sert, qu'elle soit liée ou non, sauf si une règle de route définit `prerender: false`.
- **`source` ou `publicAssets: false` avec une sortie statique émet un avertissement.** Il n'y a rien à lire pour le navigateur.
- **L'avertissement sur l'intégration est maintenant une vérification de taille.** La compilation émet un avertissement seulement au-delà de la limite d'une plateforme : voir [Limites des paquets](/fr-CA/guide/deployment#bundle-limits-on-edge).
- **`Vary` est défini partout où le visiteur décide :** sur chaque page avec `no_prefix`, et sur `/` et toute autre URL qui peut rediriger selon la préférence. Il contient `Cookie` lorsqu'un témoin est utilisé et, avec `autoDetectLanguage`, `Accept-Language`. Vérifiez la clé de cache de votre CDN : voir [Mise en cache du HTML](/fr-CA/guide/deployment#caching-html).
- **La mise en cache de `/_locales` a changé.** Il n'y a plus de cache de route Nitro sur `/{apiBaseUrl}/**`, et l'en-tête `s-maxage=60, stale-while-revalidate` a disparu. Si vous comptiez sur ce cache, placez un CDN devant la route des données. Un dictionnaire vide n'est jamais `immutable`.
- **Le cache serveur est limité par défaut :** au plus 1000 entrées lorsque `cacheMaxSize` n'est pas défini. `cacheTtl` compte à partir du moment où une entrée a été stockée; les lectures ne le prolongent plus.
- **Nouveau [`cacheStorage`](/fr-CA/guide/performance#shared-cache-for-several-instances) facultatif :** un cache de dictionnaires partagé par plusieurs instances. S'il n'est pas défini, rien ne change.

## De v2 à v3 {#from-v2-to-v3}

### Options retirées {#removed-options}

```diff
 i18n: {
-  includeDefaultLocaleRoute: true,
+  strategy: 'prefix',
-  fallbackRedirectComponentPath: '~/components/MyRedirect.vue',
-  experimental: { hmr: true, previousPageFallback: true },
+  hmr: true,
 }
```

- `includeDefaultLocaleRoute: true` correspond à `strategy: 'prefix'`; `false` correspond au `prefix_except_default` par défaut.
- `fallbackRedirectComponentPath` a disparu : les redirections ont lieu sur le serveur avant le rendu et dans un middleware de route côté client. La logique de redirection personnalisée va dans un plugin qui définit la locale; voir [Détection personnalisée de la locale](/fr-CA/guide/custom-auto-detect).
- `experimental.hmr` devient l'option racine `hmr` (activée par défaut).
- `previousPageFallback` a disparu : les clés de la page quittée sont résolues jusqu'à la fin de sa transition, sans option.

### État de la locale {#locale-state}

Utilisez `useI18nLocale()` au lieu de `useState('i18n-locale')` et de `useCookie('user-locale')` :

```diff
- useState('i18n-locale').value = 'fr'
- useCookie('user-locale').value = 'fr'
+ useI18nLocale().setLocale('fr') // state and cookie together
```

### Configuration à l'exécution {#config-at-runtime}

Lisez la configuration, substitutions à l'exécution comprises, avec `$getI18nConfig()` :

```diff
- const cookieName = useRuntimeConfig().public.i18nConfig?.localeCookie
+ const { $getI18nConfig } = useNuxtApp()
+ const cookieName = $getI18nConfig().localeCookie
```

### Alias de types internes {#internal-type-aliases}

Si votre IDE ou `vue-tsc` ne parvient pas à résoudre les importations `#i18n-internal/*`, associez-les dans votre `package.json`. Nuxt les résout à la compilation, donc c'est rarement nécessaire :

```json
{
  "imports": {
    "#i18n-internal/plural": "nuxt-i18n-micro/internals",
    "#i18n-internal/strategy": "nuxt-i18n-micro/internals",
    "#i18n-internal/config": "nuxt-i18n-micro/internals"
  }
}
```
