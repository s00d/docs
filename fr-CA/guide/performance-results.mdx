### Description {#description}

Compare **Nuxt sans i18n**, **i18n-micro** et **`@nuxtjs/i18n`** avec un même profil de dictionnaire partagé, au moyen de `untestutils/perf`.

Points d'attention : temps de compilation, pic de RSS, **code vs traductions (asset) vs total** déployables, et charge (Artillery).

### Notes sur la méthodologie {#methodology-notes}

- Les métriques sont des **moyennes de 3 exécutions consécutives par projet de test** (non entrelacées).
- **Artefact** : `.output/server/index.mjs` du node-server Nitro après un `nuxi build` forcé; `nuxt-i18n-micro` est le **dist compilé du module** (pas le stub jiti de `dev:prepare`). Voir la [méthodologie des bancs d'essai](https://s00d.github.io/nuxt-i18n-micro/contributing/performance-methodology).
- **Traductions** = `bundle.asset` (JSON des locales, `chunks/raw/`, chunks de locales correspondants via `isTranslationFile`).
- **Code** exclut les source maps (`*.map`) : les projets de test lient le module depuis le dépôt, donc Nitro écrit des maps complètes pour celui-ci et aucune pour les dépendances npm.
- **plain-nuxt** sert le même volume de feuilles en JSON statique — gourmand en E/S sous charge, et non une « surcharge i18n ».
- Profil de charge `--load full` : préchauffage 6s@6 + principal 60s@60 sans plafond (historique).
- Temps de refroidissement `--cool fast` (voir le document de méthodologie).
- Chacune des compilations de `runs` est **forcée** (pas de mise à zéro du temps de compilation par un cache chaud).
- Le **taux d'erreur** Artillery dans les tableaux correspond aux erreurs de statut HTTP des métriques de charge. Les graphiques tracent aussi `vusers.failed` (délais d'attente côté client en saturation); ceux-ci peuvent être élevés alors que le taux d'erreur HTTP reste à 0 %.

## Remarques {#notes}

- Profil partagé : 4 locales × 2 pages × ~16.8k feuilles dans l'index.
- Charge : Artillery programmatique uniquement — préchauffage **6s@6** + principal **60s@60**, VU sans plafond (méthodologie YAML historique). Chemins tirés du profil d'exécution — voir `scripts/src/perf/load.ts`.
- Temps de refroidissement : 2 s après la compilation, 3 s entre les exécutions, 5 s entre les projets de test. Les compilations sont forcées à chaque exécution pour que les moyennes ne soient pas faussées par des succès de cache.
- Relancer au quotidien : `pnpm test:performance` (`--load short --cool fast`).
- Régénérer cette page : `pnpm -C scripts cli performance --load full --only all --runs 3`.
- Options : `--locales N --keys K --only all|micro|i18n|plain --runs N --skip-load --cool fast|strict`.
