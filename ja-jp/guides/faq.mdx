# ❓ FAQ: よくある問題と解決策

Nuxt I18n Micro に関するよくある質問と一般的な問題への解決策を紹介します。

## 🚀 導入時の問題

### ❓ ルートが読み込まれない場合はどうすればよいですか?

`Nuxt I18n Micro` を使う場合、特にルーターがサブフォルダー内のルートに名前を自動的に割り当てない場合、一部のルートが期待通りに読み込まれないことがあります。

**解決策:**
これに対処するには、対応する Vue ファイルに以下を追加してページのルート名を手動で定義します:

```javascript
definePageMeta({ name: 'pageName' })
```

これにより、ルートが正しく登録され、アプリケーション内でシームレスなナビゲーションが可能になります。

### ❓ なぜ `$t` などの i18n コンポーザブルが Nuxt プラグイン内で動作しないのですか?

Nuxt I18n のコンポーザブル(`$t`、`$getLocale`、`$localePath` など)は、Nuxt プラグインやユーティリティ関数内では期待通りに動作せず、ランタイムエラーが発生する場合があります。

**原因と解決策:**
Nuxt のコンポーザブルは、Nuxt インスタンスにアクセスするために特定のコンテキスト(例: Nuxt フックや Vue の setup 関数)が必要です。これらのコンテキスト外(例: ユーティリティ関数やプラグイン)で使用すると、コンソールに次のようなエラーが表示されることがあります:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**解決策 1: `runWithContext` を使う**
非同期処理の後で i18n コンポーザブルを呼び出すには、必要なコンテキストを維持するために [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) を使用します。

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**解決策 2: 先に値を取得する**
または、翻訳の値を先に取得してから、ユーティリティ関数に渡します。

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**解決策 3: サービスでは翻訳キーを渡す**
サービスやユーティリティ関数では、`$t` を直接使わずに翻訳キーを渡します。そして、コンポーネント側で翻訳を取得します。

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 ロケール切り替え

### ❓ URL を変更せずにロケールを切り替えられますか?

はい — ただし、[ルーティング戦略](/guides/routing-strategies) によります。

**`no_prefix` 戦略** — ロケールは URL の一部ではありません。同じパスを維持したままロケールを変更して翻訳を再読み込みするには、`$switchLocale()` を使用します:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

または、設定のみを更新するには `useI18nLocale().setLocale('de')` を使います。クライアントサイドで翻訳を完全に再読み込みしたい場合は `$switchLocale()` の方が推奨されます。

**プレフィックス戦略**(`prefix`、`prefix_except_default` など) — ロケールと URL がリンクしています。`$switchLocale()` は常にローカライズされたルートへナビゲートします。`redirect: false` オプションはありません。

対象の URL のみが必要な場合(例: 言語スイッチャーのリンク)、代わりに `$switchLocalePath()` を使用してください:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

すべての切り替え関連メソッドについては [ルートとロケールの切り替え](/api/methods#-route-locale-switching) を参照してください。

### ❓ ロケール切り替え時にページがトップにスクロール(またはジャンプ)します

これは想定される挙動です — **Vue Router / Nuxt のスクロール動作**であり、nuxt-i18n-micro 固有のものではありません。

プレフィックス戦略(`prefix`、`prefix_except_default` など)では、`$switchLocale()` は通常のクライアントナビゲーション(`/en/page` → `/de/page`)を実行します。Nuxt のデフォルトの [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) はルート変更時に先頭までスクロールします(ブラウザの戻る/進むによる `savedPosition` は例外)。

nuxt-i18n-micro は隠れたスクロール処理を追加しません — アプリで小さなラッパーコンポーネントを使ってください。

**`SwitchLocalePreserve` ラッパー**

[`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) をプロジェクトの `components/SwitchLocalePreserve.vue` にコピーしてください。動作するデモ: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue)。

ページで `scrollToTop: false` を設定し、スイッチャー UI をラップします。クリック可能なターゲットに `data-locale` を付けてください。ラッパーはクリックをインターセプトし、`$switchLocale` を呼び出してスクロールを復元します(翻訳の長さでレイアウトが変わる場合も含む):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

このコンポーネントは:

1. **クリック時** — スロット内でクリックされた要素の `data-locale` を読み取ります(ボタン、リンク、任意のカスタムマークアップ)。
2. **`$switchLocale` の前** — `scrollY` とクリック要素の位置を保存します(カーソル位置を保つため)。
3. **ナビゲーション中** — `router.options.scrollBehavior` を一度だけパッチし、トップへのスクロールの代わりに `\{ top: scrollY \}` を返します。
4. **ナビゲーション後** — `page:finish` を待ち、`ResizeObserver` が異なる翻訳長によるレイアウトシフトを検知しつつスクロールを再適用します。

このラッパーを使うページでは `scrollToTop: false` が必要です。ドキュメント: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta)。

ラップされたコントロール上で直接 `$switchLocale` を呼び出さないでください — ラッパーが切り替えを処理します。ラッパー外の `<NuxtLink :to="$switchLocalePath('fr')">` は、独自の `app/router.options.ts` を追加しない限り、通常の Nuxt ルーティングのスクロール挙動に従います。

## 🌐 翻訳の問題

### ❓ 特に `defineAsyncComponent` を使う場合、ページ遷移時に翻訳が壊れるのはなぜですか?

`nuxt-i18n-micro` をページ遷移と一緒に使う場合、遷移中に翻訳が一瞬機能しなくなることがあります。これは、遷移が完了する前にルートが変わり、旧ページがまだ表示されている間に新ページ用の翻訳が読み込まれるために発生します。

**原因:**

- ページ遷移により、翻訳が完全に読み込まれる前にルートが変わる
- `defineAsyncComponent` と `useAsyncData` が翻訳の読み込みを遅らせる可能性がある
- 読み込み中に翻訳キーがそのままのパスとして表示されることがある

**解決策 1: 累積マージ(組み込み、設定不要)**

v3 では、モジュールが自動的に累積マージ戦略を使用します。同じロケール内でナビゲーションする場合、新ページの翻訳はアクティブな辞書を置き換えるのではなく、そこにマージされます。これにより、遷移アニメーション中は前ページの翻訳が引き続き利用できます。遷移完了後(`page:transition:finish` フック)、古いキーは自動的にクリーンアップされます。

設定は不要 — これは箱から出してすぐに動作します。

**解決策 2: 明示的なルートコンテキスト**

手動での制御を好む場合、`$_t` に現在のルートを明示的に渡します:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**解決策 3: 読み込み状態**

翻訳の読み込みを適切に扱うため、読み込み状態を実装します:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Vercel の SSR で翻訳キーが解決されないのはなぜですか?

**SSR での `$fetch` の制限**
Vercel のようなサーバーレスプラットフォームでは、`$fetch` は CDN から静的ファイルしか取得できず、内部の Nitro サーバーからは取得できません。つまり、正しいベース URL を設定しない限り、静的な翻訳ファイルへ直接アクセスできない可能性があります。

**`apiBaseClientHost` と `apiBaseServerHost` を設定して修正する**
翻訳が CDN または別ドメインで外部ホストされている場合、クライアント側リクエスト用に `apiBaseClientHost`、サーバー側リクエスト用に `apiBaseServerHost` を使用します。`apiBaseUrl` はパスプレフィックス(例: `_locales`)のみにするべきです。

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

または環境変数経由で:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

翻訳はクライアントとサーバーの両方で `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` から取得されます。

## 🔗 ルーティングとナビゲーションの問題

### ❓ 翻訳文字列内で `NuxtLink` や `<i18n-link>` を直接使えますか?

はい、`Nuxt I18n Micro` は `<i18n-t>` コンポーネントを通じて翻訳内で `NuxtLink` または `<i18n-link>` の使用を許可しています。特に翻訳文字列を分割せずに文法や RTL 言語の要件を扱うのに便利です。

**例:**

翻訳ファイル:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue テンプレート:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

これにより、適切なローカライズ構造を維持しつつ、翻訳内で動的リンクを扱えます。

## 🏗️ ビルドとデプロイの問題

### ❓ 翻訳ペイロードが `public/_locales/` 配下(または Edge のサーバーバンドル内)に配置されるのはなぜですか?

SSR とクライアントの両方で、同じ `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json` ペイロードが必要になります。それらがどうパッケージ化されるかは Nitro のターゲット次第です:

**解説:**

- **Node(デフォルト):** モジュールは翻訳を Nitro `serverAssets` / Rollup `raw:` として**埋め込みません**(大きなカタログではビルド時の RAM が破綻するため)。代わりにプリマージされたツリーを `public/<apiBaseUrl>/`(デフォルト `_locales`)へコピーし、SSR は `readFile` でそれらを読み込みます。クライアントは同じ URL に `$fetch` します(静的ファイル、または Nitro ハンドラー経由)。
- **Edge**(`nitro.node === false`): SSR 用の永続的なパブリック FS が存在しないため、ペイロードは Nitro `serverAssets`(`assets:i18n`)を通じて埋め込まれます。埋め込みをコンパクトに保つため `translationPayloads.mode: 'source'` を推奨します。CDN や静的コピーが必要な場合のみ `publicAssets: true` を設定してください。
- **`prerenderRoutes`:** 任意。プリマージモードでは `publicAssets` が既に `\{page\}/\{locale\}/data.json` を書き込むため、それらのルートのプリレンダリングは通常冗長です。

### ❓ 特に Cloudflare Pages で、`@unhead/vue` や未定義オブジェクトを参照するビルドエラーが発生するのはなぜですか?

**原因:**
一部のプロジェクトでは、`nuxt-i18n-micro` の使用時にビルド競合や依存関係不足が発生することがあります。特に:

- **Cloudflare Pages** や **Cloudflare Workers** 上のデプロイでは、追加の互換性フラグが必要になる場合があります。
- `@unhead/vue` などの依存関係が正しくインストールされていないと、プリレンダリング段階で失敗することがあります。
- 一部のモジュール(例: **nuxthub**、**nitro-cloudflare-dev**)は、正しいフラグや依存関係が設定されていないと競合を引き起こす可能性があります。

**考えられる解決策:**

**解決策 1: `@unhead/vue` を手動でインストール**
ビルドエラーで `@unhead/vue` が見つからないと表示される場合、プロジェクトの依存関係に直接インストールします:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

これにより、Nitro のプリレンダリング段階で利用可能になります。

**解決策 2: Cloudflare の互換性フラグを追加**
Cloudflare Pages や Cloudflare Workers を使う場合、Node.js 互換性はデフォルトで無効なことが多いです。`wrangler.toml` で有効化します:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

このフラグにより、多くの Node.js モジュール(`nuxt-i18n-micro` が使うものを含む)がスムーズに動作するようになります。

## 🔍 SEO と `@nuxtjs/seo`

### ❓ エラー: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

これは、**`@nuxtjs/seo`** が古い **`nuxt-site-config` 3.x** を引き込む場合に発生します。このバージョンは i18n プラグインを `@nuxtjs/i18n` 用にしか登録せず、**nuxt-i18n-micro** 向けには登録しないためです。

**修正方法:**

1. **`@nuxtjs/seo` 3+** にアップグレードします(micro サポート付きの `nuxt-site-config` 4+ を含みます)。
2. `modules` 内で **`nuxt-i18n-micro` を `@nuxtjs/seo` の前**に配置します。
3. ロケール対応の head タグのため **`i18n.meta: true`** を維持します。

完全な例は [SEO ガイド — Nuxt SEO セクション](/guides/seo#nuxt-seo-nuxtjs-seo) を参照してください。

## 🔧 設定と互換性

### ❓ `Nuxt I18n Micro` は `vue-i18n` にインスパイアされていますか? 修飾子はどうですか?

`Nuxt I18n Micro` は `nuxt-i18n` のパフォーマンス代替として提供されていますが、`vue-i18n` とは独立して構築されています。メソッド名やパラメーターが似ている場合もありますが、内部の機能は大きく異なります。

**修飾子(modifiers)**: メンテナーは当初、修飾子を検討しましたが、`<i18n-t>` や `<i18n-link>` のようなコンポーネントで実質的にニーズをカバーできると結論しました。

例:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

このアプローチは柔軟であるため、現時点で修飾子をリリースする必要はありません。ただし、需要があれば将来のリリースで追加される可能性があります。
