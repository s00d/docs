# ❓ FAQ: Probleme comune și soluții

Găsește răspunsuri la întrebări frecvente și soluții la probleme comune ale Nuxt I18n Micro.

## 🚀 Probleme la începere

### ❓ Ce facem dacă o rută nu se încarcă?

La folosirea `Nuxt I18n Micro`, anumite rute s-ar putea să nu se încarce așa cum e așteptat, mai ales dacă router-ul nu atribuie automat un nume unei rute din subfoldere.

**Soluție:**
Pentru a rezolva acest lucru, definește manual numele rutei pentru pagină, adăugând următoarele în fișierul Vue corespunzător:

```javascript
definePageMeta({ name: 'pageName' })
```

Astfel se asigură că ruta este înregistrată corect, permițând o navigare fluidă în aplicație.

### ❓ De ce `$t` sau alte composable-uri i18n nu funcționează în plugin-urile Nuxt?

Composable-urile Nuxt I18n (`$t`, `$getLocale`, `$localePath` etc.) pot să nu funcționeze așa cum e așteptat în plugin-urile Nuxt sau în funcțiile utilitare, provocând erori la runtime.

**Cauză și soluție:**
Composable-urile Nuxt necesită contexte specifice (de ex., hook-uri Nuxt sau funcții setup Vue) pentru a accesa instanța Nuxt. Dacă sunt folosite în afara acestor contexte (de ex., în funcții utilitare sau plugin-uri), în consolă poate apărea următoarea eroare:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Soluția 1: Folosește `runWithContext`**
Pentru a apela composable-uri i18n după o operațiune asincronă, folosește [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) pentru a păstra contextul necesar.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Soluția 2: Obține mai întâi valoarea**
Alternativ, obține mai întâi valoarea traducerii, apoi transmite-o unei funcții utilitare.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Soluția 3: Transmite cheile de traducere în servicii**
În servicii sau funcții utilitare, transmite cheile de traducere în loc să folosești direct `$t`. Apoi obține traducerea în componentă.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Comutarea locale-urilor

### ❓ Schimbă locale-ul fără să schimbi URL-ul?

Da — dar depinde de [strategia ta de rutare](/guides/routing-strategies).

**Strategia `no_prefix`** — locale-ul nu face parte din URL. Folosește `$switchLocale()` pentru a schimba locale-ul și a reîncărca traducerile rămânând pe aceeași cale:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Sau actualizează doar preferința cu `useI18nLocale().setLocale('de')`. Pentru o reîncărcare completă a traducerilor pe client, preferă `$switchLocale()`.

**Strategii cu prefix** (`prefix`, `prefix_except_default`, …) — locale-ul și URL-ul sunt legate. `$switchLocale()` navighează întotdeauna către ruta localizată. Nu există o opțiune `redirect: false`.

Dacă ai nevoie doar de URL-ul țintă (de exemplu, un link de comutare a limbii), folosește în schimb `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Vezi [Route & Locale Switching](/api/methods#-route-locale-switching) pentru toate metodele de comutare.

### ❓ Pagina derulează sus (sau sare) la schimbarea locale-ului?

Aceasta este de așteptat — este **comportamentul de scroll al Vue Router / Nuxt**, nu ceva specific nuxt-i18n-micro.

Cu strategii de prefix (`prefix`, `prefix_except_default`, …), `$switchLocale()` efectuează o navigare normală pe client (`/en/page` → `/de/page`). [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) implicit al Nuxt derulează în sus la schimbările de rută (cu excepția navigării înapoi/înainte în browser prin `savedPosition`).

nuxt-i18n-micro nu adaugă gestionare ascunsă a scroll-ului — folosește o componentă wrapper mică în aplicația ta.

**Wrapper-ul `SwitchLocalePreserve`**

Copiază [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) în proiectul tău (`components/SwitchLocalePreserve.vue`). Demo funcțional: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

Pe pagină, setează `scrollToTop: false` și înfășoară UI-ul comutatorului. Marchează țintele clicabile cu `data-locale` — wrapper-ul interceptează click-urile, apelează `$switchLocale` și restabilește scroll-ul (inclusiv când lungimea traducerii schimbă layout-ul):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Componenta:

1. **La click** — citește `data-locale` de pe elementul clicat din interiorul slot-ului (butoane, link-uri sau orice markup personalizat).
2. **Înainte de** `$switchLocale` — stochează `scrollY` și poziția elementului clicat (îl păstrează sub cursor).
3. **În timpul** navigării — modifică `router.options.scrollBehavior` o dată și returnează `\{ top: scrollY \}` în loc să deruleze sus.
4. **După** navigare — așteaptă `page:finish`, apoi reaplică scroll-ul, iar un `ResizeObserver` captează schimbările de layout provocate de lungimile diferite ale traducerilor.

`scrollToTop: false` este obligatoriu pe paginile unde folosești acest wrapper. Docs: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Nu apela `$switchLocale` direct pe controalele înfășurate — wrapper-ul se ocupă de comutare. Pentru `<NuxtLink :to="$switchLocalePath('fr')">` în afara wrapper-ului, comportamentul de scroll urmează rutarea normală Nuxt, dacă nu adaugi propriul `app/router.options.ts`.

## 🌐 Probleme cu traducerile

### ❓ De ce se strică traducerile în timpul tranzițiilor de pagină, în special cu `defineAsyncComponent`?

Când folosești `nuxt-i18n-micro` cu tranziții de pagină, traducerile pot să nu funcționeze pentru scurt timp în timpul tranziției. Această problemă apare pentru că ruta se schimbă înainte ca tranziția să se finalizeze, cauzând încărcarea traducerilor pentru pagina nouă în timp ce pagina veche este încă vizibilă.

**Cauza principală:**

- Tranzițiile de pagină provoacă schimbări de rută înainte ca traducerile să fie complet încărcate
- `defineAsyncComponent` și `useAsyncData` pot întârzia încărcarea traducerilor
- Cheile de traducere pot apărea ca căi brute în timpul încărcării

**Soluția 1: Îmbinare cumulativă (încorporată, fără configurare)**

În v3, modulul folosește automat o strategie de îmbinare cumulativă. La navigarea în cadrul aceluiași locale, traducerile noii pagini sunt îmbinate în dicționarul activ în loc să îl înlocuiască. Aceasta înseamnă că traducerile din pagina anterioară rămân disponibile în timpul animației tranziției. După ce tranziția se termină (hook-ul `page:transition:finish`), cheile vechi sunt curățate automat.

Nu este necesară nicio configurare — funcționează din start.

**Soluția 2: Context explicit al rutei**

Dacă preferi controlul manual, transmite explicit ruta curentă lui `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Soluția 3: Stări de încărcare**

Implementează stări de încărcare pentru a gestiona elegant încărcarea traducerilor:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ De ce cheile de traducere nu se rezolvă în SSR pe Vercel?

**Limitări `$fetch` la SSR**
Pe platforme serverless precum Vercel, `$fetch` poate obține doar fișiere statice din CDN, nu de pe serverul Nitro intern. Aceasta înseamnă că fișierele statice de traducere pot să nu fie direct accesibile decât dacă URL-ul de bază corect este setat.

**Remediu prin setarea `apiBaseClientHost` și `apiBaseServerHost`**
Dacă traducerile sunt găzduite extern pe un CDN sau pe un domeniu diferit, folosește `apiBaseClientHost` pentru cererile de pe client și `apiBaseServerHost` pentru cererile de pe server. `apiBaseUrl` ar trebui să conțină doar prefixul de cale (de ex., `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Sau prin variabile de mediu:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Traducerile vor fi preluate de la `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` atât pe client, cât și pe server.

## 🔗 Probleme de rutare și navigare

### ❓ Pot folosi `NuxtLink` sau `<i18n-link>` direct în șirurile de traducere?

Da, `Nuxt I18n Micro` permite utilizarea `NuxtLink` sau `<i18n-link>` în cadrul traducerilor prin componenta `<i18n-t>`, ceea ce este util în special pentru gestionarea cerințelor gramaticale și RTL, fără a împărți șirurile de traducere.

**Exemplu:**

Fișierul de traducere:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Template Vue:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Aceasta permite link-uri dinamice în traduceri, păstrând structura corectă de localizare.

## 🏗️ Probleme de build și deployment

### ❓ De ce ajung payloadurile de traducere sub `public/_locales/` (sau în bundle-ul de server pe Edge)?

Atât SSR, cât și clientul au nevoie de aceleași payload-uri `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. Modul în care sunt împachetate depinde de target-ul Nitro:

**Explicație:**

- **Node (implicit):** modulul **nu** integrează traducerile ca Nitro `serverAssets` / Rollup `raw:` (asta a explodat RAM-ul de build pe cataloage mari). În schimb copiază arborele premerged în `public/<apiBaseUrl>/` (implicit `_locales`), iar SSR citește acele fișiere cu `readFile`. Clientul face `$fetch` pentru aceleași URL-uri — fie ca fișiere statice, fie prin handler-ul Nitro.
- **Edge** (`nitro.node === false`): nu există un FS public durabil pentru SSR, așa că payload-urile sunt integrate prin Nitro `serverAssets` (`assets:i18n`). Preferă `translationPayloads.mode: 'source'` pentru ca integrarea să rămână compactă. Setează `publicAssets: true` doar dacă ai nevoie și de o copie CDN/statică.
- **`prerenderRoutes`:** opțional. În modul premerged, `publicAssets` scrie deja `\{page\}/\{locale\}/data.json`, așa că prerandarea acelor rute este de obicei redundantă.

### ❓ De ce primesc o eroare de build care se referă la `@unhead/vue` sau un obiect nedefinit, în special pe Cloudflare Pages?

**Cauză:**
Unele proiecte experimentează conflicte de build sau dependențe lipsă atunci când folosesc `nuxt-i18n-micro`. În special:

- Deploymenturile pe **Cloudflare Pages** sau **Cloudflare Workers** pot necesita flag-uri de compatibilitate suplimentare.
- Pașii de prerandare pot eșua dacă dependențe precum `@unhead/vue` nu sunt instalate corect.
- Anumite module (de ex., **nuxthub**, **nitro-cloudflare-dev**) pot introduce conflicte dacă nu sunt configurate cu flag-urile sau dependențele corecte.

**Soluții posibile:**

**Soluția 1: Instalează `@unhead/vue` manual**
Dacă eroarea de build se plânge că nu găsește `@unhead/vue`, instalează-l direct în dependențele proiectului tău:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Astfel se asigură că este disponibil în timpul fazei de prerender Nitro.

**Soluția 2: Adaugă flag-uri de compatibilitate Cloudflare**
Când folosești Cloudflare Pages sau Cloudflare Workers, compatibilitatea Node.js este adesea dezactivată implicit. Activează-o în `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Acest flag permite ca multe module Node.js (inclusiv cele folosite de `nuxt-i18n-micro`) să ruleze fluid.

## 🔍 SEO și `@nuxtjs/seo`

### ❓ Eroare: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Acest lucru se întâmplă când **`@nuxtjs/seo`** trage un **`nuxt-site-config` 3.x** vechi care înregistrează pluginul său i18n doar pentru `@nuxtjs/i18n`, nu pentru **nuxt-i18n-micro**.

**Remediu:**

1. Actualizează la **`@nuxtjs/seo` 3+** (include `nuxt-site-config` 4+ cu suport micro).
2. Pune **`nuxt-i18n-micro` înainte de `@nuxtjs/seo`** în `modules`.
3. Păstrează **`i18n.meta: true`** pentru tag-uri head conștiente de locale.

Vezi [ghidul SEO — secțiunea Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo) pentru un exemplu complet.

## 🔧 Configurare și compatibilitate

### ❓ Este `Nuxt I18n Micro` inspirat din `vue-i18n`? Ce facem cu modificatorii?

Deși `Nuxt I18n Micro` servește ca alternativă de performanță la `nuxt-i18n`, este construit independent de `vue-i18n`. Deși unele nume de metode și parametri pot fi similare, funcționalitatea de bază diferă semnificativ.

**Modificatori**: Mentenantul a luat inițial în considerare modificatorii, dar a concluzionat că componentele precum `<i18n-t>` și `<i18n-link>` abordează efectiv aceste nevoi.

De exemplu:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Această abordare este flexibilă, așa că lansarea modificatorilor este momentan inutilă. Cu toate acestea, modificatorii pot fi adăugați în viitoarele versiuni, dacă va exista cerere.
