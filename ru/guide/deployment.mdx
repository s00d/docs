Модуль работает с любым пресетом Nitro без дополнительной настройки: он выбирает, где хранить файлы переводов, исходя из пресета, под который выполняется сборка. Значения по умолчанию подходят большинству приложений; прочитайте раздел для своей платформы. На этой странице объясняется:

- что попадает в `.output/` и какие заголовки получают payload;
- что менять для статического хостинга, больших каталогов, подпути, прокси или CDN.

<Note>

Развёрнуто и проверено на реальных хостингах: Cloudflare Workers и Pages, Vercel и Vercel Edge, Netlify и Netlify Edge, Cloud Run и Deno Deploy, каждый с тем, что перечислено в разделе [Платформы](#platforms). Остальные пресеты собирались и запускались локально.

</Note>

## Как доставляются переводы {#how-translations-are-delivered}

Во время сборки модуль превращает `locales/` (с объединением всех слоёв) в **payload**: по одному JSON-файлу на страницу и локаль. Их читают два потребителя:

- **SSR** загружает payload отображаемой страницы внутри процесса — без HTTP-запроса, и словарь не встраивается в HTML.
- **Браузер** запрашивает `/_locales/<page>/<locale>/data.json?v=<dateBuild>` при гидратации и при навигации.

`_locales` — это [`apiBaseUrl`](/ru/api/module-options#apibaseurl). На этот URL отвечает встроенный серверный маршрут; статическая копия в `public/` отвечает на него без сервера.

## Node-сервер {#node-server}

```bash
npx nuxi build
node .output/server/index.mjs
```

С `node-server` (пресет по умолчанию), `node-cluster`, `bun`, `deno-server` или любым другим пресетом, который отдаёт `public/` с диска, когда `public/` лежит рядом с папкой `server/`:

- payload копируются в `.output/public/_locales/<page>/<locale>/data.json`;
- SSR читает их из этой папки через `fs` (в сервер ничего не встраивается);
- браузер получает их как статические файлы или от серверного маршрута.

Развёртывайте весь каталог `.output/`. Модулю нужен Node 20 или новее, а у Nuxt есть свой минимум: Nuxt 4.5 объявляет `^22.19.0 || ^24.11.0 || >=26.0.0`.

Процесс под постоянной нагрузкой может удерживать гораздо больше памяти, чем его живая куча. Прочитайте [Память на Node-сервере](/ru/guide/performance#memory-on-a-node-server), прежде чем задавать лимит контейнера.

При другой структуре модуль встраивает payload, как описано в следующем разделе. Это относится к:

- пользовательскому `nitro.output.publicDir`, который сборка читает один раз;
- `serveStatic: true` в пресете, который хранит статические файлы в другом месте.

<Warning>

Если сборка читает `public/`, а папка не попадает на сервер, как с `aws-lambda` и `serveStatic: true`, сервер записывает в лог одну ошибку, а страницы показывают необработанные ключи. Установите `nitro.serveStatic: false`, чтобы встроить payload.

</Warning>

## Serverless и Edge {#serverless-and-edge}

Эти пресеты не могут читать `public/` во время выполнения:

- пресеты функций, которые отправляют `public/` на CDN или не отдают её: `vercel`, `netlify`, `aws-lambda`, `aws-amplify`, `azure-swa`, `firebase`, `stormkit`, `zeabur`, `node-listener`;
- пресеты Edge без файловой системы: `cloudflare-module`, `cloudflare-pages`, `vercel-edge`, `netlify-edge`, `deno_deploy`;
- `serveStatic: 'inline'`, например `winterjs`.

В этом случае модуль встраивает payload в серверный бандл как серверные ресурсы Nitro (`assets:i18n`) и по-прежнему записывает публичную копию для браузера.

Встраивание полной матрицы страница × локаль делает бандл большим. При превышении лимита Edge-платформы сборка выдаёт предупреждение и называет его, см. [Лимиты бандла](#bundle-limits-on-edge). Для больших каталогов переключитесь на режим `source`, который встраивает компактные исходные файлы и объединяет корневые, страничные и резервные переводы во время выполнения:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    translationPayloads: {
      mode: 'source',
    },
  },
})
```

В режиме `source` браузер всегда запрашивает payload у серверного маршрута, который объединяет их по запросу (любая публичная копия содержит компактное исходное дерево, которое читает только сервер). Для этого нужен работающий сервер, поэтому не используйте `source` для чисто статического сайта.

### Лимиты бандла на Edge {#bundle-limits-on-edge}

| Платформа          | Лимит                                                                                  |
| ------------------ | -------------------------------------------------------------------------------------- |
| Cloudflare Workers | 64 MiB без сжатия, на тарифах Free и Paid. Без лимита на сжатый размер. Запуск 1 с, память 128 MB |
| Vercel Edge        | 1 MB gzip на Hobby, 2 MB на Pro, 4 MB на Enterprise                                    |
| Netlify Edge       | 20 MB в сжатом виде                                                                    |

Сборка суммирует встраиваемые словари и предупреждает только при превышении наименьшего лимита платформы. Она учитывает только словари, поэтому приложение добавляется сверху. Например, 120 страниц × 4 локали с корневым файлом 60 KB встраивают:

| Режим | Встроено | Помещается |
| --- | --- | --- |
| `premerged` | 34.9 MiB | Cloudflare; не Vercel Edge и не Netlify Edge |
| `source` | 5.7 MiB | Всё ещё 3 MB gzip на Vercel Edge |

Каталогу такого размера на Vercel Edge нужен [хост для payload](#app-baseurl-and-payload-hosts).

`source` платит за слияние для каждой страницы и локали в каждом изоляте: около 1 ms в этом примере и 7 ms CPU в холодном. Это растёт с размером цепочки резервных локалей: около 43 ms для 4 MB файлов цепочки. Netlify Edge допускает 50 ms CPU на запрос, а бесплатный тариф Cloudflare — 10 ms.

### Даты в Edge-средах выполнения {#dates-on-edge-runtimes}

`$td` использует `Intl` среды выполнения, и его данные ICU могут отличаться от браузерных. На Netlify Edge отформатированная дата может содержать U+202F (узкий неразрывный пробел) там, где в Chrome обычный пробел, поэтому Vue выводит одно предупреждение о несовпадении гидратации, а текст исправляется при гидратации. Чистый Nuxt с обычным `Intl` ведёт себя там так же; Deno Deploy — нет.

<Tip>

`<i18n-t>` с `date` или `relativeDate` уже допускает это несовпадение. Для `$td` в шаблоне добавьте элементу `data-allow-mismatch="text"`.

</Tip>

## Статический сайт (nuxi generate) {#static-site-nuxi-generate}

```bash
npx nuxi generate
```

`nuxi build --preset <static preset>` делает то же самое.

- Режим `premerged` по умолчанию записывает каждый payload в `.output/public/_locales/`, поэтому их может отдавать любой статический хостинг.
- Страницы пререндерятся для каждой локали: в режиме `prefix` модуль добавляет каждый локализованный корень (`/en`, `/de`), а `/` сохраняется как заглушка-редирект.
- Оставьте [`prerenderRoutes`](/ru/api/module-options#translationpayloads) выключенным: публичная копия уже содержит файлы payload.
- В режиме `source` или с `publicAssets: false` браузеру нечего читать, и сборка выдаёт предупреждение.

<Note>

Нет сервера, который прочитал бы cookie или `Accept-Language`, поэтому сохранённая локаль не перенаправляет `/` при первой загрузке. В режиме `no_prefix` HTML содержит локаль по умолчанию, а сохранённый cookie при загрузке не применяется: `$switchLocale` по-прежнему работает на открытой странице.

</Note>

Для Cloudflare Pages см. [Cloudflare Pages](#cloudflare-pages).

Для сборки с [доменами локалей](/ru/guide/layers#multiple-domains) запускайте generate по одному разу на домен, с `NUXT_I18N_DOMAIN` в качестве хоста запуска. Тогда каждое дерево содержит страницы и payload этого домена. У Nitro нет переменной для выходной папки, поэтому читайте собственную в конфигурации:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: { output: { publicDir: process.env.PUBLIC_DIR } },
})
```

```bash
NUXT_I18N_DOMAIN=example.de PUBLIC_DIR=sites/example.de npx nuxi generate
NUXT_I18N_DOMAIN=example.com PUBLIC_DIR=sites/example.com npx nuxi generate
```

- Держите папки вне `.output`: каждый запуск её очищает.
- Абсолютные ссылки на другие домены не обходятся краулером.
- Без переменной сборка с локалью, имеющей `baseUrl`, выдаёт предупреждение и генерирует конфигурацию сборки, где такие локали являются ссылками и не получают страниц.
- На Node-сервере та же переменная закрепляет процесс за одним доменом, что бы ни говорил `Host`.

Статический хостинг применяет к этим файлам собственные заголовки; настраивайте кэширование в конфигурации хостинга. Правило модуля для `/_locales/*` всё же доходит до Cloudflare Pages через `_headers` и до Vercel через `config.json` в виде `public, max-age=60`. Чтобы поставлять рядом файлы `.gz` / `.br`, включите `nitro.compressPublicAssets`: модуль сжимает копию payload с теми же настройками.

## Заголовки кэша и dateBuild {#cache-headers-and-datebuild}

| Запрос                                                                                   | `Cache-Control`                                                                                                 |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Node-сервер или маршрут, `?v=` равен текущему `dateBuild`, непустой словарь              | `private, max-age=<httpCacheDuration>, immutable`                                                               |
| Node-сервер или маршрут, без `?v=`, со старым значением или пустой словарь               | `public, max-age=0, must-revalidate`                                                                            |
| Копия `public/` на хостинге, любой `?v=`                                                 | `public, max-age=60` ([`httpCacheControl`](/ru/api/module-options#other)) |
| Режим `source`, `cacheTtl` или `apiBaseServerHost`: словарь может измениться без сборки  | заголовок `httpCacheControl`, всегда                                                                            |
| Серверный маршрут, словарь не удалось прочитать                                          | `503`, `no-store`                                                                                               |
| dev-сервер                                                                               | нет                                                                                                             |

Почему таблица выглядит именно так:

- URL с текущим `v` закрепляется как хэшированный ресурс, и сообщить об этом может только тот, кто видит query: серверный маршрут и Node-сервер, который выставляет заголовок для своих статических файлов.
- Он `private`, поэтому CDN, игнорирующий query, не сможет ответить на следующий `v` этим ответом.
- Статические файлы хостинга получают общий для пути заголовок из правила маршрута `/_locales/**`, которое не видит query, поэтому он остаётся коротким; повторная загрузка всё равно ничего не блокирует.
- Старый `v` по-прежнему можно отдавать, так как на него ссылается закэшированный HTML.

`httpCacheControl: false` оставляет все статические файлы на `max-age=0, must-revalidate`. [`httpCacheDuration`](/ru/api/module-options#httpcacheduration) по умолчанию равен одному году; `0` не отправляет заголовок. `$clearCache()` перепроверяет всё, что загружает следующим.

Safari запрашивает предзагруженный payload повторно, если не может переиспользовать ответ: с `no-cache` и `ETag` второй запрос — это `304`, а без заголовка кэша и без валидатора — второе полное скачивание. `max-age` больше `0` даёт один запрос. Платит за это только `httpCacheDuration: 0` на хостинге, который не добавляет валидатор.

[`dateBuild`](/ru/api/module-options#datebuild) — это значение `?v=`. По умолчанию это хэш ваших файлов переводов, поэтому он меняется только при изменении переводов, и браузеры сохраняют закэшированные payload между развёртываниями, которые их не затрагивали. Он также меняется вместе с цепочкой резервных локалей.

- Задайте его сами, чтобы закрепить значение.
- Задайте `0` или `''`, чтобы полностью убрать `?v=`; тогда payload никогда не будут `immutable`.

<Tip>

После замены словаря на месте на Node-сервере перезапустите его с `NUXT_I18N_DATE_BUILD=<new value>`: ничто другое не меняет `v` без пересборки.

</Tip>

### Корневые и дельта-файлы {#root-and-delta-files}

`premerged` записывает один корень на локаль, `__root/<locale>/data.json`, а в файл каждой страницы — только то, что от него отличается.

- Файл страницы отмечает корень, относительно которого он создан, ключом `__i18n_root`.
- Браузер запрашивает оба, страница ничего не показывает, пока не получены оба, а SSR объединяет их один раз на чанк.
- Файл без отметки — это целый словарь, и он самодостаточен: dev, режим `source`, серверный маршрут и хостинг, на котором ещё лежат старые файлы, — все отдают именно такой, без каких-либо настроек.

Поэтому тот, кто читает `_locales/*/data.json` напрямую, читает дельту. Установите `translationPayloads.rootDelta: false`, чтобы сохранять целые файлы.

Вкладка, открытая во время развёртывания и запросившая новую дельту, видит, что она создана относительно другого корня, и запрашивает этот корень, прежде чем показать её.

### Когда словарь не удаётся прочитать {#when-a-dictionary-cannot-be-read}

Неудачный запрос к хосту (всё, кроме 404), нечитаемый или повреждённый файл либо ответ 200, который не является JSON-объектом, не попадают ни в какой кэш, и следующий запрос читает заново:

- рендер страницы записывает предупреждение, показывает необработанные ключи для этого словаря и отвечает `503` с `Cache-Control: no-store`, одинаково во всех заголовках CDN (`CDN-Cache-Control`, `Cloudflare-CDN-Cache-Control`, `Netlify-CDN-Cache-Control`, `Vercel-CDN-Cache-Control`, `Surrogate-Control`, поверх любых из правила маршрута) и `Retry-After: 60`;
- `/_locales/...` отвечает `503` с `no-store`;
- `useTranslationServerMiddleware` даёт `t`, который возвращает ключ или значение по умолчанию.

Что происходит во время сбоя:

- **Посетители:** тело этого 503 — сама страница. При гидратации браузер снова читает словарь, и текст появляется, как только хост снова доступен, с одной ошибкой Vue в консоли о несовпадении гидратации, так как HTML сервера содержал ключи.
- **Краулерам** сообщается, что нужно вернуться позже.
- **Кэши:** правило маршрута `swr` или `cache` ничего не сохраняет со статусом 400 и выше, а CDN получает `no-store`, поэтому ни один кэш не сохраняет необработанные ключи, и первый запрос после восстановления отображает настоящий текст.
- **Страницы, уже закэшированные** правилом, остаются как есть: перепроверка не удаётся и ничего не сохраняет. На Vercel неудачная перепроверка `isr` так же сохраняет последнюю страницу.

Это касается каждого чанка, который загружает рендер, включая неудачный чанк страницы при доступном корне и чанк, объединённый позже в ходе рендера. Страница со здоровым словарём, редирект и страница ошибки сохраняют свой статус. Исключение — [компонент-остров](/ru/guide/server-side-translations): он остаётся 200, так как 503 убрал бы его со страницы, поэтому страница, собственный словарь которой загружается, может сохраниться с необработанными ключами острова. Каждый запрос во время сбоя доходит до хоста, без собственного таймаута модуля, кроме 60 секунд на заголовки ответа.

Ответ 404 от хоста означает, что такого файла нет, и это не сбой. Рендер страницы показывает корневой словарь, как и браузер, а `/_locales/...` отвечает тем же 404. Ни один кэш не сохраняет ни то, ни другое, поэтому появившийся файл читается при следующем запросе — ценой одного запроса к хосту на каждый рендер такой страницы. Если нет и корневого файла, словарь пуст, а [пререндер](/ru/guide/upgrade#server,-build-and-deployment) завершается ошибкой.

Сервер хранит загруженные payload во внутрипроцессном LRU-кэше размером до `cacheMaxSize` записей (по умолчанию 1000), который перезагружает запись по истечении `cacheTtl`, если он задан; оба параметра описаны в разделе [Настройка производительности](/ru/guide/performance), а [`cacheStorage`](/ru/guide/performance#shared-cache-for-several-instances) добавляет кэш, общий для нескольких экземпляров. Не добавляйте поверх правило маршрута Nitro `cache` для `/_locales/**`: оно использует в качестве ключа полный URL вместе с query и хранит третью копию.

## App baseURL и хосты для payload {#app-baseurl-and-payload-hosts}

**`app.baseURL`** больше ничего не требует. С `app.baseURL: '/shop/'` браузер запрашивает `/shop/_locales/...`; копия остаётся в `.output/public/_locales/`, которую Nitro отдаёт под базовым путём (статический хостинг должен смонтировать вывод по пути `/shop/`). Префиксы локалей и [исключённые пути](/ru/guide/excluding-static-files) сопоставляются без базового пути.

**`app.cdnURL`** тоже переносит payload, если они являются файлами в `public/`: браузер запрашивает и предзагружает `<cdnURL>/_locales/...`.

- CDN должен хранить `_locales/` рядом с `_nuxt/` по этому пути.
- Он должен разрешать источник вашего сайта (CORS), так как файл приходит через `fetch`.
- Словарь, на который отвечает только серверный маршрут (режим `source`, без публичной копии), остаётся на источнике приложения.

Runtime-переменной `NUXT_APP_BASE_URL` на `cloudflare-module` нужна совместимость с Node (`nodejs_compat`). Когда `nitro.cloudflare.nodeCompat` выключен (Nitro выключает его и при старой дате без флага), переменная не видна и отдаётся `/`, в том числе в чистом Nuxt, тогда как редирект локали всё равно ведёт на базовый путь. Задавайте там `app.baseURL` во время сборки.

Чтобы отдавать payload с другого источника, направьте на него клиент и сервер и отключите локальные выходные данные:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    apiBaseClientHost: 'https://cdn.example.com',
    apiBaseServerHost: 'https://cdn.example.com',
    translationPayloads: {
      serverHandler: false,
      publicAssets: false,
      serverAssets: false,
    },
  },
})
```

- На Node `serverAssets` записывает ту же копию для собственного чтения сервером, и этот файл отвечает на `/_locales`: его тоже нужно выключить, даже если вы оставляете серверный маршрут для браузера, до которого тот никогда не дойдёт.
- Хост должен отдавать ту же структуру `<apiBaseUrl>/<page>/<locale>/data.json`.
- Сборка предупреждает, если все локальные выходные данные выключены, а хост не указан.

Те же значения можно передать через `NUXT_I18N_APP_BASE_URL`, `NUXT_I18N_APP_BASE_CLIENT_HOST` и `NUXT_I18N_APP_BASE_SERVER_HOST` во время сборки. `NUXT_I18N_APP_BASE_SERVER_HOST` также работает во время выполнения и имеет приоритет над значением сборки. Подробности см. в [`apiBaseServerHost`](/ru/api/module-options#apibaseserverhost).

## Платформы {#platforms}

Только то, что нужно модулю или его выходным данным. Аккаунты, регионы и вход в CLI описаны в документации платформы.

### Cloudflare Workers {#cloudflare-workers}

Пресет `cloudflare_module`. `wrangler deploy` повторно собирает вывод Nitro с помощью esbuild, и после этого необработанный `defineAsyncComponent(() => import('./X.vue'))` на сервере рендерится пустым. Страница ошибки Nuxt по умолчанию — именно такой компонент, поэтому у 404 пустое тело, а браузер сообщает о несовпадении гидратации. Затем клиент отображает страницу, и статус остаётся 404, но без JavaScript страница пустая. Это [nuxt#33270](https://github.com/nuxt/nuxt/issues/33270): чистый Nuxt без модуля ведёт себя так же. Маршруты страниц не затрагиваются.

Отключите повторную сборку:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: {
    preset: 'cloudflare_module',
    cloudflare: {
      deployConfig: true, // `wrangler` below applies only with it
      wrangler: {
        no_bundle: true,
        find_additional_modules: true,
        rules: [{ type: 'ESModule', globs: ['**/*.mjs'] }],
      },
    },
  },
})
```

```bash
npx nuxi build
cd .output/server && npx wrangler deploy -c wrangler.json
```

Установите `compatibilityDate` на `2024-09-19` или позже: более старая дата выбирает устаревший пресет, который не записывает `wrangler.json` и не выдаёт ошибки. Тогда 404 отображается, а загружаемый пакет становится меньше: 190 KiB gzip против 246 KiB в тестовом приложении. Другой выход — собственный `error.vue`, но он покрывает только страницу ошибки.

Самому модулю `nodejs_compat` не нужен. Лимиты см. в разделе [Лимиты бандла](#bundle-limits-on-edge).

### Cloudflare Pages {#cloudflare-pages}

Используйте пресет `cloudflare-pages-static`. `nuxi generate --preset cloudflare-pages` — это серверная сборка без `index.html`.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: {
    preset: 'cloudflare-pages-static',
    prerender: { autoSubfolderIndex: false },
  },
})
```

```bash
npx nuxi generate
npx wrangler pages project create my-site --production-branch main --force
npx wrangler pages deploy dist --project-name my-site --branch main
```

- **Вывод.** Пресет пишет в `dist/`, а не в `.output/public`.
- **`--force`.** Без него новый wrangler (здесь 4.156) передаёт `pages project create` в Workers. С ним вы получаете классический проект Pages. Он нужен один раз, при создании.
- **`autoSubfolderIndex: false`.** Pages отвечает на `/de` редиректом 308 на `/de/`, тогда как canonical и `hreflang` указывают `/de`, то есть ведут на редирект. С этим параметром файл называется `de.html`, и редиректа нет.
- **`NUXT_E1005` в консоли при 404** — это обычный 404. Nuxt сообщает о нём так, потому что `404.html` запускается на клиенте до монтирования приложения. Страница работает, а чистый Nuxt выводит ту же строку.

### Vercel и Vercel Edge {#vercel-and-vercel-edge}

Пресеты `vercel` и `vercel_edge`, без изменений в приложении. Теги работают без `metaBaseUrl` благодаря перенаправленным заголовкам платформы. У Vercel Edge небольшой лимит бандла: см. [Лимиты бандла](#bundle-limits-on-edge). Для общего кэша используйте [драйвер `upstash`](/ru/guide/performance#upstash-on-vercel-and-vercel-edge).

### Netlify {#netlify}

Пресеты `netlify` и `netlify_edge`.

```bash
npx nuxi build --preset netlify
npx netlify deploy --prod --no-build --dir dist --functions .netlify/functions-internal
```

- **Не задавайте `nitro.output`.** Пресет сам записывает `.netlify/` и `dist/`.
- **Держите `package.json` в папке, из которой выполняется развёртывание.** Без него CLI смотрит в родительскую папку и не развёртывает ни одной функции, не выдавая ошибки.
- **Netlify Edge** развёртывается только с `--dir dist`. См. [Даты в Edge-средах выполнения](#dates-on-edge-runtimes).

### Cloud Run {#cloud-run}

Используйте сборку `node-server` по умолчанию. `gcloud run deploy --source` требует `Dockerfile` в выходной папке, если docker не запущен локально:

```dockerfile
# .output/Dockerfile
FROM node:22-slim
WORKDIR /app
COPY . .
ENV NODE_ENV=production
CMD ["node", "server/index.mjs"]
```

```bash
cd .output && gcloud run deploy my-app --source .
```

Теги работают без `metaBaseUrl` благодаря перенаправленным заголовкам платформы.

### Deno Deploy {#deno-deploy}

Пресет `deno_deploy`. `deno deploy` заменяет `deployctl`. Создайте динамическое приложение с точкой входа `server/index.ts` и выполняйте развёртывание из выходной папки.

### Firebase {#firebase}

| Продукт | Настройка |
| --- | --- |
| App Hosting | Запускает сборку для Node: используйте пресет по умолчанию или `firebase-app-hosting` и Node 20+ |
| Cloud Functions | Пресет `firebase` встраивает payload и требует `firebase-functions` |
| Hosting (статический) | Отдаёт `.output/public` как файлы, поэтому `/_locales/**` получает заголовки Hosting |

Если на статическом Hosting JSON возвращается с неправильным `Content-Type` или кэшированием, добавьте запись `headers` для `/_locales/**` в `firebase.json`. Заголовки Nuxt `routeRules` не применяются к файлам, которые Hosting отдаёт сам; маршрут payload выставляет собственные `Content-Type` и `Cache-Control` для ответов, которые доходят до сервера.

### AWS Amplify {#aws-amplify}

`aws-amplify` хранит статические файлы рядом со своей вычислительной папкой, а не рядом с сервером, поэтому payload встраиваются, как на платформе функций.

### Несколько экземпляров одной сборки {#several-instances-of-one-build}

Один артефакт может работать с разными локалями по умолчанию или отключёнными локалями в каждом экземпляре через переменные окружения: см. [Переопределения во время выполнения](/ru/guide/runtime-overrides). У локали, отключённой только во время выполнения, статические файлы по-прежнему лежат в `public/`; отключайте её во время сборки, если они не должны быть доступны.

Экземпляры, загружающие словари с удалённого хоста, могут делить их в Redis, Upstash, Cloudflare KV или D1, Deno KV или другом хранилище Nitro, так что бэкенд получает один запрос вместо одного на каждый экземпляр. Это кэш, а не источник переводов: см. [Общий кэш для нескольких экземпляров](/ru/guide/performance#shared-cache-for-several-instances).

## За прокси или CDN {#behind-a-proxy-or-cdn}

Приложение должно узнать публичный хост и схему из запроса.

| Прокси отправляет                            | Обычная сборка                                   | Сборка с `baseUrl` у локалей                                                      |
| -------------------------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------- |
| Настоящий `Host`                             | Ничего задавать не нужно                         | Ничего задавать не нужно                                                          |
| `Host` источника плюс `X-Forwarded-Host`     | Ничего задавать не нужно                         | [`trustForwardedHost: true`](/ru/api/module-options#trustforwardedhost)           |
| Ни того, ни другого                          | [`metaBaseUrl`](/ru/api/module-options#metabaseurl) | Никакая настройка не поможет: каждый запрос выглядит как хост источника, поэтому измените прокси |

- **Маршруты под `swr` или `cache`.** Там таблица не действует: см. [Кэширование HTML](#caching-html). Задайте `metaBaseUrl` или `site.url`.
- **`X-Forwarded-Proto`.** Отправляйте его, иначе canonical URL за HTTPS-прокси будут начинаться с `http://`. `metaBaseUrl` тоже это исправляет.
- **В доменной сборке** домен выбирает базовый URL тегов. `metaTrustForwardedHost` там не выбирает домен, это делает только `trustForwardedHost`.
- **Редиректы относительные, а у cookie локали нет `Domain`,** поэтому оба остаются на публичном хосте.

<Warning>

**Закрепите `metaBaseUrl`, если источник остаётся доступным** — В обычной сборке без `metaBaseUrl` или `site.url` canonical, `hreflang` и `og:url` берут хост из запроса. [`metaTrustForwardedHost`](/ru/api/module-options#metatrustforwardedhost) включён по умолчанию, поэтому прямой запрос с `X-Forwarded-Host: evil.example` получает `https://evil.example` в этих тегах, а кэш перед приложением распространяет такую страницу. Хост платформы, например `*.workers.dev`, — именно такой источник. `metaBaseUrl` закрывает эту проблему и для `Host`. Известный хост доменной сборки сохраняет собственный `baseUrl`. С `trustForwardedHost: true` прямой клиент может выбрать страницу другого домена, поэтому включайте его только за прокси, который перезаписывает этот заголовок.

</Warning>

## Кэширование HTML {#caching-html}

Большинство URL безопасно кэшировать, потому что они называют свою локаль. Эти зависят от посетителя:

| Настройка                      | URL                                               |
| ------------------------------ | ------------------------------------------------- |
| По умолчанию, `autoDetectPath: '/'` | `/`                                          |
| `prefix`                       | `/` и каждый URL без префикса, которые только перенаправляют |
| `autoDetectPath: '*'`          | Каждый URL                                        |
| `no_prefix`                    | Каждая страница                                   |

- **`Vary`.** Эти ответы содержат `Vary` с `Cookie`, когда задан [`localeCookie`](/ru/api/module-options#localecookie), и с `Accept-Language`, когда включён `autoDetectLanguage`. Кэш, который его учитывает, хранит ответы раздельно.
- **Кэш, игнорирующий `Vary`,** например «кэшировать всё по URL», должен пропускать эти URL. Иначе `302 /de` одного посетителя дойдёт до следующего, а сохранённая страница по умолчанию отменит редирект для всех. Для `/` можно также задать `redirects: false`. Кэш маршрутов Nitro использует в качестве ключа путь и свой список `varies`, поэтому не включайте `/` и в правила `swr` и `cache`.
- **`Set-Cookie`.** Если задан `localeCookie`, каждая страница с серверным рендерингом под префиксом содержит `Set-Cookie`, и корректный CDN её не сохранит. Для кэшируемого HTML оставьте `localeCookie` выключенным или удаляйте заголовок на edge.
- **Правилам `swr` и `cache` нужен `metaBaseUrl` или `site.url`.** Nitro рендерит такой маршрут только с заголовками из `cache.varies`, поэтому `Host`, `X-Forwarded-Host` и `X-Forwarded-Proto` пропадают, а URL запроса выглядит как `http://localhost`. Без фиксированного источника canonical, `hreflang` и `og:url` на этих маршрутах указывают на `http://localhost` на любой платформе. `useRequestURL()` в чистом Nuxt там читает то же самое. Если бы хост брался от посетителя, `X-Forwarded-Host` одного посетителя попадал бы на страницу, которую получают все. Доменной сборки это не касается: её теги используют `baseUrl` локалей.

  Если одна сборка обслуживает несколько хостов и ни один источник не подходит, позвольте правилу видеть заголовки и хранить по одной копии на значение: `'/blog/**': { swr: 60, cache: { varies: ['host', 'x-forwarded-host', 'x-forwarded-proto'] } }`. Каждое отдельное значение — это новая запись кэша, поэтому клиент, отправляющий выдуманные заголовки, заполняет кэш: поставьте источник за прокси, который их выставляет.
- **Правила `swr` и `cache` в доменной сборке.** Модуль добавляет `host` в `cache.varies` каждого такого правила, а с `trustForwardedHost` — и `x-forwarded-host`, чтобы один домен не отдавал свою страницу другому. Правило с `cache: false` остаётся как написано. `isr` — это кэш платформы: проверьте, что он использует хост в ключе. Когда хост входит в ключ, клиент, отправляющий выдуманные хосты, добавляет записи в кэш.

Про файлы payload см. [Заголовки кэша и dateBuild](#cache-headers-and-datebuild).
