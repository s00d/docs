Значения по умолчанию настроены для типичного приложения: один JSON-payload на страницу и локаль, переводы не попадают в HTML, кэши на сервере ограничены. На этой странице перечислены немногие настройки, которые стоит менять, когда каталог большой, у сервера мало памяти или payload приходят с другого хоста. Результаты измерений в сравнении с `@nuxtjs/i18n` и чистым Nuxt см. в разделе [Бенчмарки](/ru/guide/performance-results).

## Что уже делают значения по умолчанию {#what-the-defaults-already-do}

- **Один payload на страницу.** Сборка объединяет корневые ключи, ключи страницы и резервной локали в `/_locales/<page>/<locale>/data.json`, поэтому страница загружает один файл, а `$t` — это один поиск.
- **Никаких словарей в HTML.** SSR хранит переводы в памяти сервера; браузер загружает payload, а не разбирает его из `__NUXT_DATA__`.
- **Кэш браузера.** `?v=` меняется только при изменении переводов, поэтому браузер сохраняет свои payload между деплоями, которые их не затрагивали. Статическая копия на хостинге свежая в течение 60 секунд и после этого перепроверяется: повторная загрузка ждёт один ответ `304`. Серверный маршрут отвечает с `immutable` на год ([Деплой](/ru/guide/deployment#cache-headers-and-datebuild)).
- **Ограниченная память сервера.** По умолчанию сервер кэширует не более 1000 payload и вытесняет давно не использовавшиеся.

## Разделение переводов по страницам {#split-translations-by-page}

Ключи, используемые на одной странице, должны находиться в `locales/pages/<page>/<locale>.json`, а не в корневых файлах: корневые ключи входят в payload каждой страницы. См. [Файлы переводов](/ru/guide/translations).

Это разделение меняют две настройки:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    // pages that show the same keys share one payload: /de/products/123 loads the products payload
    routesLocaleLinks: { 'products-id': 'products' },
    // or: no page files at all, every page loads only the root dictionary
    // disablePageLocales: true,
  },
})
```

[`routesLocaleLinks`](/ru/api/module-options#routeslocalelinks) убирает дублирующиеся payload для связанных маршрутов. [`disablePageLocales`](/ru/api/module-options#disablepagelocales) подходит для небольших приложений, где проще один словарь на локаль.

## Серверные кэши {#server-caches}

| Настройка | По умолчанию | Эффект |
| --- | --- | --- |
| [`cacheMaxSize`](/ru/api/module-options#cachemaxsize) | `0` | Максимальное число записей в кэшах payload. `0` = без ограничения в браузере, 1000 на сервере. |
| [`cacheTtl`](/ru/api/module-options#cachettl) | `0` | Число секунд до перезагрузки закэшированной записи. `0` = никогда; задайте, если payload приходят из `apiBaseServerHost` и меняются без повторного деплоя. |
| `serverTranslationPreload` | `false` | Загружать payload `index` в middleware Nitro при каждом запросе страницы, чтобы серверные хелперы и главная страница использовали его повторно. |

Уменьшайте `cacheMaxSize` на небольшом инстансе с большим числом страниц × локалей. Локально редактируемым переводам TTL не нужен: в режиме разработки файлы читаются напрямую, а продакшен-payload меняются только с деплоем.

## Память на сервере Node {#memory-on-a-node-server}

При постоянной нагрузке сервер Node может занимать примерно в 12 раз больше своей живой кучи и оставаться на этом уровне. В стресс-тесте со 100 тыс. ключей на страницу живая куча в 90 МБ давала около 1,1 ГБ RSS. Это не утечка. После одного чрезмерно большого цикла GC V8 повышает лимит кучи и, пока длится нагрузка, держит освобождённые страницы в пуле для повторного использования. Примерно через 8 секунд после прекращения нагрузки пул опустошается, и RSS падает примерно до 160 МБ. `global.gc()` эту память не возвращает. Чистый Nuxt без модуля ведёт себя так же, пропорционально своей меньшей куче.

Это съедает запас: при лимите памяти ниже этого уровня и без ограничения кучи процесс может быть убит. Задайте ограничение, которое укладывается в ваш лимит и находится заметно выше живой кучи:

```bash
NODE_OPTIONS=--max-old-space-size=512 node .output/server/index.mjs
```

| 100 тыс. ключей, 12 локалей, от 5 до 30 минут нагрузки | По умолчанию | `--max-old-space-size=512` |
| --- | --- | --- |
| RSS под нагрузкой | около 1150 МБ | 254–287 МБ |
| Запросов в секунду | 624 | 517–572 |

Таким образом, ограничение обменивает 8–10 % пропускной способности на память. У каталога обычного размера куча меньше, и скачок тоже меньше. Эти запуски проводились на macOS с Node 22, не в контейнере.

## Время разбора и `dir` {#parse-time-and-dir}

`dir: 'auto'` у локали заставляет браузер определять направление по содержимому во время разбора. В Chromium DOMContentLoaded при 20 000 элементов составлял около 1,1 с с `dir="auto"` и 0,1 с без него, а при 5000 элементов — около 130 мс против 45 мс. Не задавайте `dir` или задайте `ltr` либо `rtl` ([Направление текста](/ru/guide/seo#text-direction)).

## Общий кэш для нескольких инстансов {#shared-cache-for-several-instances}

При нескольких инстансах одной сборки [`cacheStorage`](/ru/api/module-options#other) даёт им общий кэш словарей в любом хранилище Nitro через подключение, которое ваше приложение настраивает в `nitro.storage`. Модуль не добавляет ни коннекторов, ни зависимостей.

**Это кэш, а не источник.** Переводы берутся из встроенных или публичных payload либо из `apiBaseServerHost`. Записывается только то, что пришло из источника, а ключи содержат идентификатор сборки, поэтому хранилище, заполненное вручную, не читается. Чтобы отдавать переводы из KV или базы данных, разместите на `apiBaseServerHost` небольшой маршрут, который их читает.

**Когда это помогает.** Только с удалённым `apiBaseServerHost`. Три инстанса, обходившие 39 словарей, сделали 117 запросов к хосту без кэша и 48 с ним. Когда файлы лежат на диске, попадание в хранилище не быстрее чтения файла: первый проход по 12 страницам занял 280–296 мс без опции и 308–325 мс с заполненным Redis, поэтому не задавайте её. На пресете, встраивающем словари, без хоста она ничего не делает, о чём сообщает сборка.

Холодный словарь, один клиент, по одному проходу — так что цифры приблизительные, и бо́льшая их часть — это расстояние до хоста:

| Хранилище | С хоста | Из хранилища |
| --- | --- | --- |
| Cloudflare KV | около 300 мс | около 110 мс |
| D1 | около 230 мс | около 115 мс |
| Deno KV | около 430 мс | около 100 мс |
| Upstash, Vercel serverless | около 445 мс | около 245 мс |
| Upstash, Vercel Edge | около 505 мс | около 235 мс |

### Redis {#redis}

Требует `ioredis` в вашем проекте.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    storage: {
      redis: { driver: 'redis', url: process.env.REDIS_URL },
    },
  },
  i18n: {
    cacheStorage: 'redis', // the mount name
    apiBaseServerHost: 'https://translations.internal',
    cacheTtl: 300,
  },
})
```

### Upstash на Vercel и Vercel Edge {#upstash-on-vercel-and-vercel-edge}

Используйте драйвер `upstash` в обоих случаях: он работает через REST, тогда как драйверу `redis` нужен TCP. Ему требуется `@upstash/redis` в вашем проекте, а `UPSTASH_REDIS_REST_URL` и `UPSTASH_REDIS_REST_TOKEN` он читает из окружения.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    storage: {
      upstash: { driver: 'upstash' },
    },
  },
  i18n: {
    cacheStorage: 'upstash',
    apiBaseServerHost: 'https://translations.example.com',
  },
})
```

### Cloudflare KV {#cloudflare-kv}

Привяжите пространство имён к Worker как `I18N_KV` (`kv_namespaces` в его конфигурации wrangler).

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    storage: {
      kv: { driver: 'cloudflare-kv-binding', binding: 'I18N_KV' },
    },
  },
  i18n: {
    cacheStorage: 'kv',
    apiBaseServerHost: 'https://translations.example.com',
  },
})
```

Если хост — это другой Worker в том же аккаунте, нужен флаг совместимости `global_fetch_strictly_public`, иначе запрос до него не дойдёт.

### Cloudflare D1 {#cloudflare-d1}

`nitro.storage` не может содержать объект базы данных, поэтому драйвер монтирует плагин Nitro. Точка монтирования проверяется при первом использовании, так что этого достаточно рано. Привяжите базу данных как `I18N_DB` (`d1_databases`) и добавьте `unstorage` в проект.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    experimental: { database: true },
    database: {
      default: { connector: 'cloudflare-d1', options: { bindingName: 'I18N_DB' } },
    },
  },
  i18n: {
    cacheStorage: 'd1',
    apiBaseServerHost: 'https://translations.example.com',
  },
})
```

```ts
// server/plugins/i18n-storage.ts
import dbDriver from 'unstorage/drivers/db0'

export default defineNitroPlugin(() => {
  useStorage().mount('d1', dbDriver({ database: useDatabase() }))
})
```

Драйвер `db0` помечен как экспериментальный и игнорирует TTL: строки старых сборок остаются, пока вы их не удалите.

### Deno KV {#deno-kv}

В Deno Deploy создайте базу данных (`deno deploy database provision <name> --kind denokv`), назначьте её приложению (`deno deploy database assign`) и используйте драйвер:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    storage: {
      kv: { driver: 'deno-kv' },
    },
  },
  i18n: {
    cacheStorage: 'kv',
    apiBaseServerHost: 'https://translations.example.com',
  },
})
```

### Как это работает {#how-it-behaves}

Словарь ищется сначала в собственном кэше инстанса, затем в общем хранилище, затем в источнике. Собственный кэш инстанса остаётся, потому что `$t` синхронный и ему нужно дерево в памяти: это разделяет того, кто загружает, и того, кто отдаёт, но не экономит память.

- **Кто загружает.** С удалённым хостом — один запрос к бэкенду на словарь вместо одного на инстанс. Инстансы, промахнувшиеся одновременно, загружают его каждый сам, потому что блокировки нет.
- **Страницы без собственного словаря** не сохраняются, чтобы выдуманные имена страниц не могли добавлять ключи. Каждый инстанс загружает такую страницу с хоста один раз, а на Workers, где изоляты появляются и исчезают, это постоянный небольшой поток запросов.
- **Хост недоступен.** Страницы с сохранённым словарём работают. Страница без него отображается по сохранённому корневому словарю, её собственные ключи выводятся как есть, с [кодом `503`, который не сохраняет ни один кэш](/ru/guide/deployment#when-a-dictionary-cannot-be-read), а `/_locales` отвечает для неё `503`, пока хост не вернётся. `useTranslationServerMiddleware` возвращает ключи для словаря, который не может прочитать.
- **Хост** — это `NUXT_I18N_APP_BASE_SERVER_HOST` во время выполнения, а иначе `apiBaseServerHost` из сборки, так же как и без опции. На пресете, встраивающем словари (Cloudflare, Vercel, Netlify, см. [Деплой](/ru/guide/deployment#serverless-and-edge)), слой применяется только при наличии хоста: данные уже в бандле, и копия в KV означала бы сетевое чтение того, что и так есть в памяти.
- **Ключи** имеют вид `i18n-micro:<buildId>~<dateBuild>~<fallbackLocale>~<host>:<locale>:<page>`, поэтому две сборки при поэтапном деплое никогда не читают данные друг друга, как и два бэкенда одного артефакта. Все инстансы должны происходить из одной сборки (один артефакт или закреплённый в Nuxt [`buildId`](https://nuxt.com/docs/api/nuxt-config#buildid)); инстансы, собранные отдельно, просто не делят кэш. При закреплённом `buildId` и `dateBuild: 0` две разные сборки всё же делят ключи. Ищутся только включённые локали, а имена страниц длиннее 200 символов обходят слой.
- **Что сохраняется.** Перед записью словарь сравнивается с корневым (`__root`) и записывается, только если содержит все корневые ключи и отличается от корневого. Поэтому выдуманная страница, на которую ответили корневым словарём, не добавляет ключ, как и тело ошибки с кодом 200 для страницы. Каждый инстанс читает такую страницу из источника один раз. Хост должен отвечать на неизвестные страницы корневым словарём, пустым объектом или 404 и отдавать `__root`. Хост без `__root` или отдающий страницы без корневых ключей ничего не разделяет. Если хост отвечает на сам `__root` корректно оформленной ошибкой, она сохраняется: держите `cacheTtl` коротким, если бэкенд на такое способен.
- **Истечение срока.** Запись истекает через `cacheTtl` секунд после записи или через один день, если `cacheTtl` равен `0`, поэтому ключи старых сборок не накапливаются. Значение может оставаться в собственном кэше инстанса ещё `cacheTtl` и в кэше чанков рендера ещё столько же: изменения на бэкенде становятся видны в пределах трёх `cacheTtl`. Драйверы без истечения срока (`fs`) хранят старые ключи, пока вы их не удалите.
- **Когда отказывает хранилище**, страница не отказывает. Чтение может занимать 1 секунду, чего хватает на установку соединения и холодный в этой локации ключ Cloudflare KV. После сбоя лимит составляет 250 мс, пока хранилище снова не ответит. Три сбоя подряд закрывают слой на 5 секунд. Пока он закрыт, а также сразу после неудачного чтения ничего не записывается. Неудачная запись ничего не закрывает, поэтому реплика только для чтения продолжает обслуживать чтения. Хранилище, ответы которого превышают эти лимиты, считается отказавшим: это промах, и словарь берётся из источника. С ioredis это начинается примерно с 400 мс на команду, потому что его установка соединения занимает три круговых обхода. Модуль пишет одно предупреждение в минуту; ioredis сверх этого выводит собственные ошибки. Значение, не являющееся словарём, считается промахом и перезаписывается. Неизвестное имя точки монтирования вызывает одно предупреждение при первом использовании; после этого приложение работает без слоя.
- **Когда отказывает источник**, сбой нигде не сохраняется. Неудачный запрос или нечитаемый файл не попадает ни в один кэш — ни в этот, ни в собственный кэш инстанса, — и следующий запрос читает заново. См. [Деплой](/ru/guide/deployment#when-a-dictionary-cannot-be-read).
- **Отключено в режиме разработки и при пререндеринге**: они читают свои файлы и не должны зависеть от вашего продакшен-Redis.
- **Инвалидация.** Вызова очистки нет: новая сборка использует новые ключи. Чтобы сразу обновить работающую сборку, удалите ключи `i18n-micro:` из хранилища и перезапустите инстансы. `clearCache` и HMR затрагивают только состояние процесса.
- Изменения во время выполнения (`$mergeTranslations`, `$defineI18nRoute`) остаются в том рендере или браузере, где они были сделаны, и никогда не записываются в хранилище.

## Размер payload {#payload-size}

Сборка предупреждает, когда вывод payload превышает `translationPayloads.warnFileCount` (500 файлов) или `warnSizeBytes` (10 МБ). В таком случае:

- вынесите ключи, нужные только странице, из корневых файлов;
- свяжите маршруты, показывающие одни и те же ключи (`routesLocaleLinks`);
- на serverless или Edge используйте `translationPayloads.mode: 'source'`, чтобы серверный бандл встраивал компактные исходники вместо каждой пары страница × локаль ([Деплой](/ru/guide/deployment#serverless-and-edge)). Сборка для Edge сама предупреждает о превышении лимита платформы ([Лимиты бандла](/ru/guide/deployment#bundle-limits-on-edge));
- включите `nitro.compressPublicAssets`, чтобы получить копии статических payload в `.gz` / `.br`.

## Измерение {#measuring}

Репозиторий отслеживает, что отправляет playground, с помощью `pnpm run budget:payload`; текущие значения:

Измерено на `playground` для `/`, `/de`:

| Измерение | Размер |
| --- | --- |
| Исходники переводов на диске | 7,8 МБ |
| Отдаётся как отдельные файлы payload | 23,9 МБ |
| Наибольший встроенный `__NUXT_DATA__` | 0,4 КБ |
| Клиентские ресурсы | 624,4 КБ |

Playground — это тестовый стенд со сгенерированными словарями до 100 тыс. ключей, поэтому такие цифры не стоит ожидать от реального
приложения — это фиксированная точка для сравнения. Проверка бюджета падает, когда они неожиданно растут,
и так замечаются случайные изменения в содержимом payload.

Запустите набор бенчмарков самостоятельно с помощью `pnpm test:performance`; как он устроен, описано в [методологии бенчмарков](https://s00d.github.io/nuxt-i18n-micro/contributing/performance-methodology).
