### Описание {#description}

Сравнивает **чистый Nuxt**, **i18n-micro** и **`@nuxtjs/i18n`** с одним общим профилем словарей через `untestutils/perf`.

В фокусе: время сборки, пиковый RSS, развёртываемый объём **кода, переводов (asset) и общий итог**, а также нагрузка (Artillery).

### Примечания к методологии {#methodology-notes}

- Метрики — **средние значения 3 последовательных запусков для каждой фикстуры** (без чередования).
- **Артефакт**: Nitro node-server `.output/server/index.mjs` после принудительного `nuxi build`; `nuxt-i18n-micro` — это **собранный dist модуля** (а не заглушка jiti из `dev:prepare`). См. [методологию бенчмарков](https://s00d.github.io/nuxt-i18n-micro/contributing/performance-methodology).
- **Переводы** = `bundle.asset` (JSON локалей, `chunks/raw/`, подходящие чанки локалей через `isTranslationFile`).
- **Код** не включает source maps (`*.map`): фикстуры подключают модуль из репозитория, поэтому Nitro пишет для него полные карты, а для npm-зависимостей — никаких.
- **plain-nuxt** отдаёт тот же объём конечных ключей как статический JSON — под нагрузкой это сильно нагружает I/O, а не является «накладными расходами i18n».
- Профиль нагрузки `--load full`: прогрев 6s@6 + основная фаза 60s@60 без ограничения (исторически).
- Паузы `--cool fast` (см. документ о методологии).
- Каждая из сборок `runs` выполняется **принудительно** (без обнуления времени сборки за счёт тёплого кэша).
- **Error rate** Artillery в таблицах — это ошибки HTTP-статусов из метрик нагрузки. На графиках также отображается `vusers.failed` (таймауты клиента при насыщении); они могут быть высокими, пока доля ошибок HTTP остаётся 0%.

## Примечания {#notes}

- Общий профиль: 4 локали × 2 страницы × ~16.8k конечных ключей index.
- Нагрузка: только программный Artillery — прогрев **6s@6** + основная фаза **60s@60**, без ограничения VU (историческая методология YAML). Пути из runtime-профиля — см. `scripts/src/perf/load.ts`.
- Паузы: 2s после сборки, 3s между запусками, 5s между фикстурами. Сборки выполняются принудительно в каждом запуске, поэтому средние не размываются попаданиями в кэш.
- Повседневный повторный запуск: `pnpm test:performance` (`--load short --cool fast`).
- Перегенерировать эту страницу: `pnpm -C scripts cli performance --load full --only all --runs 3`.
- Флаги: `--locales N --keys K --only all|micro|i18n|plain --runs N --skip-load --cool fast|strict`.
