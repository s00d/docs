# ❓ FAQ: типичные проблемы и решения

Ответы на часто задаваемые вопросы и решения распространённых проблем с Nuxt I18n Micro.

## 🚀 Проблемы на старте

### ❓ Что делать, если маршрут не загружается?

При использовании `Nuxt I18n Micro` некоторые маршруты могут не загружаться так, как ожидается, особенно если роутер не назначает имя маршруту в подпапках автоматически.

**Решение:**
Задайте имя маршрута вручную, добавив в соответствующий Vue-файл:

```javascript
definePageMeta({ name: 'pageName' })
```

Это обеспечит корректную регистрацию маршрута и стабильную навигацию в приложении.

### ❓ Почему `$t` или другие i18n-композаблы не работают в плагинах Nuxt?

Композаблы Nuxt I18n (`$t`, `$getLocale`, `$localePath` и т. п.) могут работать некорректно в Nuxt-плагинах или утилитных функциях, что приводит к ошибкам в рантайме.

**Причина и решение:**
Композаблы Nuxt требуют определённых контекстов (например, Nuxt-хуков или Vue setup-функций) для доступа к инстансу Nuxt. Если использовать их вне этих контекстов (в утилитах или плагинах), в консоли появится подобная ошибка:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Решение 1: используйте `runWithContext`**
Чтобы вызвать i18n-композабл после асинхронной операции, используйте [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext), сохраняющую нужный контекст.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Решение 2: получите значение заранее**
Как вариант, получите строку перевода первым, а затем передайте её в утилитарную функцию.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Решение 3: передавайте ключи переводов в сервисах**
В сервисах или утилитах передавайте ключи переводов, а не вызывайте `$t` напрямую. Затем получайте перевод в компоненте.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Переключение локали

### ❓ Сменить локаль без изменения URL?

Да, но это зависит от вашей [стратегии роутинга](/guides/routing-strategies).

**Стратегия `no_prefix`** — локаль не является частью URL. Используйте `$switchLocale()`, чтобы сменить локаль и перезагрузить переводы, оставаясь на том же пути:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Либо обновляйте только предпочтение через `useI18nLocale().setLocale('de')`. Для полной клиентской перезагрузки переводов предпочтительнее `$switchLocale()`.

**Префиксные стратегии** (`prefix`, `prefix_except_default`, …) — локаль и URL связаны. `$switchLocale()` всегда переходит на локализованный маршрут. Опции `redirect: false` нет.

Если нужен только целевой URL (например, для ссылки-переключателя языка), используйте `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Все методы переключения см. в [Route & Locale Switching](/api/methods#-route-locale-switching).

### ❓ Страница скроллит вверх (или прыгает) при смене локали?

Это ожидаемое поведение — так работает **Vue Router / Nuxt scroll behavior**, а не что-то специфичное для nuxt-i18n-micro.

При префиксных стратегиях (`prefix`, `prefix_except_default`, …) `$switchLocale()` выполняет обычный клиентский переход (`/en/page` → `/de/page`). Дефолтный [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) в Nuxt при смене маршрута скроллит вверх (кроме навигации браузерных back/forward через `savedPosition`).

nuxt-i18n-micro не добавляет скрытой логики скролла — используйте небольшой компонент-обёртку в приложении.

**Обёртка `SwitchLocalePreserve`**

Скопируйте [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) в свой проект (`components/SwitchLocalePreserve.vue`). Рабочее демо: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

На странице задайте `scrollToTop: false` и оберните ваш UI переключения. Помечайте кликабельные элементы `data-locale` — обёртка перехватывает клики, вызывает `$switchLocale` и восстанавливает скролл (в том числе когда длина переводов меняет разметку):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Компонент:

1. **По клику** — читает `data-locale` у элемента, по которому кликнули внутри слота (кнопки, ссылки или любая своя разметка).
2. **Перед** `$switchLocale` — сохраняет `scrollY` и позицию кликнутого элемента (чтобы он остался под курсором).
3. **Во время** навигации — один раз патчит `router.options.scrollBehavior` и возвращает `\{ top: scrollY \}` вместо скролла в самый верх.
4. **После** навигации — ждёт `page:finish`, затем повторно применяет скролл, а `ResizeObserver` ловит layout-сдвиги от разной длины переводов.

`scrollToTop: false` обязателен на страницах, где вы используете эту обёртку. Документация: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Не вызывайте `$switchLocale` напрямую на обёрнутых элементах — обёртка сама делает переключение. Для `<NuxtLink :to="$switchLocalePath('fr')">` вне обёртки поведение скролла соответствует обычному роутингу Nuxt, если только вы не добавите свой `app/router.options.ts`.

## 🌐 Проблемы с переводами

### ❓ Почему переводы ломаются при переходах между страницами, особенно с `defineAsyncComponent`?

При использовании `nuxt-i18n-micro` с переходами между страницами переводы могут временно переставать работать во время перехода. Причина в том, что маршрут меняется до завершения перехода, и переводы новой страницы подгружаются, пока старая ещё видна.

**Корень проблемы:**

- Переходы между страницами меняют маршрут ещё до полной загрузки переводов.
- `defineAsyncComponent` и `useAsyncData` могут задерживать загрузку переводов.
- Ключи переводов на время загрузки могут отображаться как сырые пути.

**Решение 1: кумулятивный merge (встроен, конфигурация не нужна)**

В v3 модуль автоматически применяет стратегию кумулятивного merge. При навигации внутри одной локали новые переводы страницы мёржатся в активный словарь вместо замены. Значит, переводы предыдущей страницы остаются доступными во время анимации перехода. После завершения перехода (хук `page:transition:finish`) старые ключи автоматически убираются.

Конфигурация не требуется — это работает из коробки.

**Решение 2: явный контекст маршрута**

Если вы предпочитаете ручной контроль, явно передавайте текущий маршрут в `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Решение 3: состояния загрузки**

Реализуйте состояния загрузки, чтобы аккуратно обрабатывать подгрузку переводов:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Почему ключи переводов не разрешаются при SSR на Vercel?

**Ограничения `$fetch` при SSR**
На serverless-платформах вроде Vercel `$fetch` может забирать статические файлы только с CDN, но не из внутреннего Nitro-сервера. Значит, статические файлы переводов могут быть недоступны напрямую, если не задан корректный базовый URL.

**Решение через `apiBaseClientHost` и `apiBaseServerHost`**
Если переводы размещены на CDN или другом домене, используйте `apiBaseClientHost` для клиентских запросов и `apiBaseServerHost` для серверных. В `apiBaseUrl` оставляйте только префикс пути (например, `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Или через переменные окружения:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Переводы будут забираться с `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` и на клиенте, и на сервере.

## 🔗 Проблемы роутинга и навигации

### ❓ Можно ли использовать `NuxtLink` или `<i18n-link>` прямо в строках перевода?

Да, `Nuxt I18n Micro` позволяет использовать `NuxtLink` или `<i18n-link>` внутри переводов через компонент `<i18n-t>`. Это особенно полезно при обработке грамматики и требований RTL-языков, без разбивки строки перевода.

**Пример:**

Файл перевода:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Шаблон Vue:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Так вы получаете динамические ссылки внутри переводов, сохраняя правильную структуру локализации.

## 🏗️ Проблемы сборки и деплоя

### ❓ Почему payload'ы переводов оказываются в `public/_locales/` (или в серверном бандле на Edge)?

SSR и клиент нуждаются в одних и тех же payload'ах `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. Способ упаковки зависит от Nitro-таргета:

**Пояснение:**

- **Node (по умолчанию):** модуль **не** встраивает переводы как Nitro `serverAssets` / Rollup `raw:` (это раздувало сборочную память на крупных каталогах). Вместо этого он копирует premerged-дерево в `public/<apiBaseUrl>/` (по умолчанию `_locales`), а SSR читает эти файлы через `readFile`. Клиент `$fetch`ит те же URL — либо как статические файлы, либо через Nitro-хендлер.
- **Edge** (`nitro.node === false`): устойчивой публичной FS для SSR нет, поэтому payload'ы встраиваются через Nitro `serverAssets` (`assets:i18n`). Предпочтительнее `translationPayloads.mode: 'source'`, чтобы embed оставался компактным. Задавайте `publicAssets: true`, только если нужна и CDN/статическая копия.
- **`prerenderRoutes`:** опционально. В режиме premerged `publicAssets` уже пишет `\{page\}/\{locale\}/data.json`, так что пререндер этих маршрутов обычно избыточен.

### ❓ Почему появляется ошибка сборки, ссылающаяся на `@unhead/vue` или неопределённый объект, особенно на Cloudflare Pages?

**Причина:**
В некоторых проектах при использовании `nuxt-i18n-micro` возникают конфликты сборки или отсутствуют зависимости. В частности:

- Деплой на **Cloudflare Pages** или **Cloudflare Workers** может требовать дополнительных флагов совместимости.
- Шаги пререндера могут падать, если зависимости вроде `@unhead/vue` установлены некорректно.
- Некоторые модули (например, **nuxthub**, **nitro-cloudflare-dev**) могут вносить конфликты без правильных флагов или зависимостей.

**Возможные решения:**

**Решение 1: установите `@unhead/vue` вручную**
Если сборка жалуется на отсутствие `@unhead/vue`, установите его непосредственно в зависимости проекта:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Это гарантирует его доступность на этапе пререндера Nitro.

**Решение 2: добавьте флаги совместимости Cloudflare**
При использовании Cloudflare Pages или Workers совместимость с Node.js часто отключена по умолчанию. Включите её в `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Этот флаг позволяет многим Node.js-модулям (включая используемые `nuxt-i18n-micro`) работать корректно.

## 🔍 SEO и `@nuxtjs/seo`

### ❓ Ошибка: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Это происходит, когда **`@nuxtjs/seo`** тянет старый **`nuxt-site-config` 3.x**, регистрирующий свой i18n-плагин только для `@nuxtjs/i18n`, а не для **nuxt-i18n-micro**.

**Решение:**

1. Обновитесь до **`@nuxtjs/seo` 3+** (включает `nuxt-site-config` 4+ с поддержкой micro).
2. Ставьте **`nuxt-i18n-micro` перед `@nuxtjs/seo`** в `modules`.
3. Оставьте **`i18n.meta: true`** для head-тегов, учитывающих локаль.

Полный пример см. в [руководстве по SEO — раздел Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo).

## 🔧 Конфигурация и совместимость

### ❓ Вдохновлён ли `Nuxt I18n Micro` `vue-i18n`? А что с модификаторами?

`Nuxt I18n Micro` — производительная альтернатива `nuxt-i18n`, но построен независимо от `vue-i18n`. Некоторые имена методов и параметры могут быть похожи, однако устройство существенно отличается.

**Модификаторы**: Мейнтейнер изначально рассматривал модификаторы, но пришёл к выводу, что компоненты вроде `<i18n-t>` и `<i18n-link>` эффективно закрывают эти потребности.

Например:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Такой подход достаточно гибок, поэтому релизить модификаторы сейчас не требуется. Однако модификаторы могут появиться в будущем, если будет спрос.
