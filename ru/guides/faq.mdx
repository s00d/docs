# ❓ FAQ: распространённые проблемы и решения

Найдите ответы на часто задаваемые вопросы и решения распространённых проблем с Nuxt I18n Micro.

## 🚀 Проблемы при начале работы

### ❓ Что делать, если маршрут не загружается?

При использовании `Nuxt I18n Micro` некоторые маршруты могут не загружаться, как ожидается, особенно если маршрутизатор не назначает автоматически имя маршруту во вложенных папках.

**Решение:**
Чтобы решить эту проблему, вручную определите имя маршрута для страницы, добавив следующее в соответствующий Vue-файл:

```javascript
definePageMeta({ name: 'pageName' })
```

Это гарантирует правильную регистрацию маршрута, обеспечивая плавную навигацию в приложении.

### ❓ Почему `$t` или другие i18n composables не работают в плагинах Nuxt?

Composables Nuxt I18n (`$t`, `$getLocale`, `$localePath` и т. д.) могут не работать как ожидается внутри плагинов Nuxt или утилитарных функций, что приводит к ошибкам во время выполнения.

**Причина и решение:**
Composables Nuxt требуют определённых контекстов (например, хуков Nuxt или setup-функций Vue) для доступа к экземпляру Nuxt. При использовании вне этих контекстов (например, в утилитарных функциях или плагинах) в консоли может появиться следующая ошибка:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Решение 1: используйте `runWithContext`**
Чтобы вызвать i18n composables после асинхронной операции, используйте [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) для сохранения необходимого контекста.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Решение 2: сначала получите значение**
Как альтернативу, сначала получите значение перевода, а затем передайте его в утилитарную функцию.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Решение 3: передавайте ключи переводов в сервисы**
В сервисах или утилитарных функциях передавайте ключи переводов вместо прямого использования `$t`. Затем получайте перевод в компоненте.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Переключение локалей

### ❓ Переключить локаль без изменения URL?

Да — но это зависит от вашей [стратегии маршрутизации](/guides/routing-strategies).

**Стратегия `no_prefix`** — локаль не является частью URL. Используйте `$switchLocale()` для смены локали и перезагрузки переводов, оставаясь на том же пути:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Или обновляйте только предпочтение с помощью `useI18nLocale().setLocale('de')`. Для полной клиентской перезагрузки переводов предпочтительнее `$switchLocale()`.

**Стратегии с префиксами** (`prefix`, `prefix_except_default`, …) — локаль и URL связаны. `$switchLocale()` всегда переходит к локализованному маршруту. Опции `redirect: false` нет.

Если вам нужен только целевой URL (например, ссылка для переключателя языка), используйте `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

См. все методы переключения в разделе [Маршрут и переключение локалей](/api/methods#-route-locale-switching).

### ❓ При переключении локали страница прокручивается вверх (или прыгает)?

Это ожидаемое поведение — это **поведение прокрутки Vue Router / Nuxt**, а не что-то специфичное для nuxt-i18n-micro.

При использовании стратегий с префиксами (`prefix`, `prefix_except_default`, …) `$switchLocale()` выполняет обычную клиентскую навигацию (`/en/page` → `/de/page`). Стандартное [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) Nuxt прокручивает вверх при смене маршрута (кроме навигации назад/вперёд через `savedPosition`).

nuxt-i18n-micro не добавляет скрытой обработки прокрутки — используйте небольшой компонент-обёртку в вашем приложении.

**Обёртка `SwitchLocalePreserve`**

Скопируйте [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) в свой проект (`components/SwitchLocalePreserve.vue`). Рабочее демо: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

На странице установите `scrollToTop: false` и оберните UI переключателя. Отметьте кликабельные элементы атрибутом `data-locale` — обёртка перехватывает клики, вызывает `$switchLocale` и восстанавливает прокрутку (в том числе, когда длина перевода меняет вёрстку):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Компонент:

1. **При клике** — читает `data-locale` на кликнутом элементе внутри слота (кнопки, ссылки или любая пользовательская разметка).
2. **Перед** `$switchLocale` — сохраняет `scrollY` и позицию кликнутого элемента (оставляет его под курсором).
3. **Во время** навигации — один раз патчит `router.options.scrollBehavior` и возвращает `\{ top: scrollY \}` вместо прокрутки вверх.
4. **После** навигации — ждёт `page:finish`, затем повторно применяет прокрутку, пока `ResizeObserver` отслеживает сдвиги вёрстки из-за разной длины переводов.

`scrollToTop: false` обязателен на страницах, где вы используете эту обёртку. Документация: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Не вызывайте `$switchLocale` напрямую на обёрнутых элементах — обёртка сама обрабатывает переключение. Для `<NuxtLink :to="$switchLocalePath('fr')">` вне обёртки поведение прокрутки следует обычной маршрутизации Nuxt, если вы не добавите собственный `app/router.options.ts`.

## 🌐 Проблемы с переводами

### ❓ Почему переводы ломаются во время переходов между страницами, особенно с `defineAsyncComponent`?

При использовании `nuxt-i18n-micro` с переходами страниц переводы могут ненадолго перестать работать во время перехода. Это происходит потому, что маршрут меняется до завершения перехода, из-за чего переводы для новой страницы загружаются, пока ещё видна старая страница.

**Основная причина:**

- Переходы страниц вызывают смену маршрута до полной загрузки переводов
- `defineAsyncComponent` и `useAsyncData` могут задерживать загрузку переводов
- Ключи переводов могут отображаться как сырые пути во время загрузки

**Решение 1: накопительное слияние (встроено, без настройки)**

В v3 модуль автоматически использует стратегию накопительного слияния. При навигации внутри одной локали переводы новой страницы объединяются с активным словарём, а не заменяют его. Это означает, что переводы предыдущей страницы остаются доступными во время анимации перехода. После завершения перехода (хук `page:transition:finish`) старые ключи автоматически очищаются.

Настройка не требуется — это работает «из коробки».

**Решение 2: явный контекст маршрута**

Если вы предпочитаете ручной контроль, явно передавайте текущий маршрут в `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Решение 3: состояния загрузки**

Реализуйте состояния загрузки, чтобы корректно обрабатывать загрузку переводов:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Почему ключи переводов не разрешаются во время SSR на Vercel?

**Ограничения `$fetch` при SSR**
На serverless-платформах вроде Vercel `$fetch` может получать только статические файлы с CDN, но не с внутреннего сервера Nitro. Это означает, что статические файлы переводов могут быть недоступны напрямую, если не задан правильный базовый URL.

**Исправление через `apiBaseClientHost` и `apiBaseServerHost`**
Если переводы размещены на CDN или другом домене, используйте `apiBaseClientHost` для клиентских запросов и `apiBaseServerHost` для серверных. `apiBaseUrl` должен содержать только префикс пути (например, `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Или через переменные окружения:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Переводы будут получаться с `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` как на клиенте, так и на сервере.

## 🔗 Проблемы маршрутизации и навигации

### ❓ Можно ли использовать `NuxtLink` или `<i18n-link>` непосредственно в строках переводов?

Да, `Nuxt I18n Micro` позволяет использовать `NuxtLink` или `<i18n-link>` внутри переводов через компонент `<i18n-t>`, что особенно полезно для обработки грамматики и требований RTL-языков без разбиения строк переводов.

**Пример:**

Файл переводов:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Шаблон Vue:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Это позволяет использовать динамические ссылки внутри переводов, сохраняя правильную структуру локализации.

## 🏗️ Проблемы сборки и развёртывания

### ❓ Почему payload'ы переводов оказываются в `public/_locales/` (или в серверном бандле на Edge)?

Как SSR, так и клиент нуждаются в одних и тех же payload'ах `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. Как они упаковываются, зависит от целевой платформы Nitro:

**Пояснение:**

- **Node (по умолчанию):** модуль **не** встраивает переводы как Nitro `serverAssets` / Rollup `raw:` (это раздувало оперативную память сборки на больших каталогах). Вместо этого он копирует premerged-дерево в `public/<apiBaseUrl>/` (по умолчанию `_locales`), и SSR читает эти файлы через `readFile`. Клиент делает `$fetch` к тем же URL — как к статическим файлам или через обработчик Nitro.
- **Edge** (`nitro.node === false`): для SSR нет постоянной публичной ФС, поэтому payload'ы встраиваются через Nitro `serverAssets` (`assets:i18n`). Предпочтителен `translationPayloads.mode: 'source'`, чтобы встраивание оставалось компактным. Устанавливайте `publicAssets: true` только если также нужна копия для CDN/статики.
- **`prerenderRoutes`:** опционально. В режиме premerged `publicAssets` уже записывает `\{page\}/\{locale\}/data.json`, поэтому prerendering этих маршрутов обычно избыточен.

### ❓ Почему я получаю ошибку сборки, ссылающуюся на `@unhead/vue` или undefined объект, особенно на Cloudflare Pages?

**Причина:**
Некоторые проекты сталкиваются с конфликтами сборки или отсутствующими зависимостями при использовании `nuxt-i18n-micro`. В частности:

- Развёртывания на **Cloudflare Pages** или **Cloudflare Workers** могут требовать дополнительных флагов совместимости.
- Этапы prerendering могут падать, если зависимости вроде `@unhead/vue` не установлены должным образом.
- Некоторые модули (например, **nuxthub**, **nitro-cloudflare-dev**) могут вносить конфликты без правильных флагов или зависимостей.

**Возможные решения:**

**Решение 1: установите `@unhead/vue` вручную**
Если ошибка сборки жалуется, что не найден `@unhead/vue`, установите его напрямую в зависимости проекта:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Это гарантирует его доступность на этапе prerender Nitro.

**Решение 2: добавьте флаги совместимости Cloudflare**
При использовании Cloudflare Pages или Cloudflare Workers совместимость с Node.js часто отключена по умолчанию. Включите её в `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Этот флаг позволяет многим модулям Node.js (включая используемые `nuxt-i18n-micro`) работать корректно.

## 🔍 SEO и `@nuxtjs/seo`

### ❓ Ошибка: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Это происходит, когда **`@nuxtjs/seo`** подтягивает старую версию **`nuxt-site-config` 3.x**, которая регистрирует свой i18n-плагин только для `@nuxtjs/i18n`, а не для **nuxt-i18n-micro**.

**Исправление:**

1. Обновитесь до **`@nuxtjs/seo` 3+** (включает `nuxt-site-config` 4+ с поддержкой micro).
2. Поместите **`nuxt-i18n-micro` перед `@nuxtjs/seo`** в `modules`.
3. Сохраните **`i18n.meta: true`** для head-тегов, учитывающих локаль.

Полный пример см. в [руководстве по SEO — раздел Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo).

## 🔧 Конфигурация и совместимость

### ❓ Вдохновлён ли `Nuxt I18n Micro` от `vue-i18n`? А что насчёт модификаторов?

Хотя `Nuxt I18n Micro` служит производительной альтернативой `nuxt-i18n`, он построен независимо от `vue-i18n`. Хотя некоторые имена методов и параметры могут быть похожи, лежащая в основе функциональность существенно отличается.

**Модификаторы**: сопровождающий изначально рассматривал модификаторы, но пришёл к выводу, что компоненты вроде `<i18n-t>` и `<i18n-link>` эффективно закрывают эти потребности.

Например:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Такой подход достаточно гибок, поэтому выпуск модификаторов в настоящее время не требуется. Однако модификаторы могут быть добавлены в будущих релизах при наличии спроса.
