# ❓ PMF: problemes habituals i solucions

Troba respostes a les preguntes més freqüents i solucions a problemes habituals amb Nuxt I18n Micro.

## 🚀 Problemes per començar

### ❓ Què passa si una ruta no es carrega?

Quan es fa servir `Nuxt I18n Micro`, algunes rutes poden no carregar-se com s'espera, especialment si el router no assigna automàticament un nom a una ruta en subcarpetes.

**Solució:**
Per solucionar-ho, defineix manualment el nom de la ruta per a la pàgina afegint el següent al fitxer Vue corresponent:

```javascript
definePageMeta({ name: 'pageName' })
```

Això assegura que la ruta es registri correctament, permetent una navegació fluida dins de l'aplicació.

### ❓ Per què `$t` o altres composables d'i18n no funcionen als plugins de Nuxt?

Els composables d'i18n de Nuxt (`$t`, `$getLocale`, `$localePath`, etc.) poden no funcionar com s'espera dins dels plugins de Nuxt o funcions d'utilitat, resultant en errors en temps d'execució.

**Causa i solució:**
Els composables de Nuxt requereixen contextos específics (per exemple, hooks de Nuxt o funcions setup de Vue) per accedir a la instància de Nuxt. Si es fan servir fora d'aquests contextos (per exemple, en funcions d'utilitat o plugins), pot aparèixer l'error següent a la consola:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Solució 1: fer servir `runWithContext`**
Per cridar composables d'i18n després d'una operació asíncrona, fes servir [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) per preservar el context necessari.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Solució 2: obtenir primer el valor**
Alternativament, obtén primer el valor de la traducció i passa'l a una funció d'utilitat.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Solució 3: passar claus de traducció als serveis**
Als serveis o funcions d'utilitat, passa les claus de traducció en lloc de fer servir `$t` directament. Després, obtén la traducció al component.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Canvi de locale

### ❓ Canviar de locale sense canviar la URL?

Sí, però depèn de la teva [estratègia d'enrutament](/guides/routing-strategies).

**Estratègia `no_prefix`**: el locale no forma part de la URL. Fes servir `$switchLocale()` per canviar de locale i recarregar les traduccions mantenint-te al mateix camí:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

O actualitza només la preferència amb `useI18nLocale().setLocale('de')`. Per a una recàrrega completa de traduccions al client, prefereix `$switchLocale()`.

**Estratègies amb prefix** (`prefix`, `prefix_except_default`, …): el locale i la URL estan lligats. `$switchLocale()` sempre navega a la ruta localitzada. No hi ha una opció `redirect: false`.

Si només necessites la URL de destí (per exemple, un enllaç de commutador d'idioma), fes servir `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Consulta [Canvi de ruta i locale](/api/methods#-route-locale-switching) per a tots els mètodes de canvi.

### ❓ La pàgina fa scroll cap amunt (o salta) en canviar de locale?

Això és esperat: és el **comportament de scroll de Vue Router / Nuxt**, no quelcom específic de nuxt-i18n-micro.

Amb estratègies amb prefix (`prefix`, `prefix_except_default`, …), `$switchLocale()` fa una navegació de client normal (`/en/page` → `/de/page`). El [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) per defecte de Nuxt fa scroll cap amunt en els canvis de ruta (excepte enrere/endavant del navegador via `savedPosition`).

nuxt-i18n-micro no afegeix cap gestió amagada de scroll: fes servir un petit component embolcall a la teva app.

**Embolcall `SwitchLocalePreserve`**

Copia [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) al teu projecte (`components/SwitchLocalePreserve.vue`). Demostració en funcionament: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

A la pàgina, defineix `scrollToTop: false` i embolcalla la teva UI del commutador. Marca els objectius clicables amb `data-locale`: l'embolcall intercepta els clics, crida `$switchLocale` i restaura el scroll (fins i tot quan la longitud de la traducció canvia el disseny):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

El component:

1. **En clic**: llegeix `data-locale` a l'element clicat dins l'slot (botons, enllaços o qualsevol marcatge personalitzat).
2. **Abans** de `$switchLocale`: emmagatzema `scrollY` i la posició de l'element clicat (el manté sota el cursor).
3. **Durant** la navegació: pedaça `router.options.scrollBehavior` una vegada i retorna `\{ top: scrollY \}` en lloc de fer scroll cap amunt.
4. **Després** de la navegació: espera `page:finish`, després torna a aplicar el scroll mentre un `ResizeObserver` detecta canvis de disseny per diferents longituds de traducció.

`scrollToTop: false` és necessari a les pàgines on facis servir aquest embolcall. Documentació: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

No cridis `$switchLocale` directament als controls embolcallats: l'embolcall gestiona el canvi. Per a `<NuxtLink :to="$switchLocalePath('fr')">` fora de l'embolcall, el comportament de scroll segueix l'enrutament normal de Nuxt tret que afegeixis el teu propi `app/router.options.ts`.

## 🌐 Problemes de traducció

### ❓ Per què les traduccions es trenquen durant les transicions de pàgina, especialment amb `defineAsyncComponent`?

Quan es fa servir `nuxt-i18n-micro` amb transicions de pàgina, les traduccions poden deixar de funcionar breument durant la transició. Aquest problema ocorre perquè la ruta canvia abans que la transició acabi, fent que les traduccions de la nova pàgina es carreguin mentre l'antiga encara és visible.

**Causa arrel:**

- Les transicions de pàgina fan canviar la ruta abans que les traduccions estiguin totalment carregades.
- `defineAsyncComponent` i `useAsyncData` poden retardar la càrrega de traduccions.
- Les claus de traducció poden aparèixer com a camins bruts durant la càrrega.

**Solució 1: fusió acumulativa (integrada, sense configuració)**

A v3, el mòdul fa servir automàticament una estratègia de fusió acumulativa. En navegar dins del mateix locale, les traduccions de la nova pàgina es fusionen al diccionari actiu en lloc de substituir-lo. Això significa que les traduccions de la pàgina anterior romanen disponibles durant l'animació de transició. Un cop la transició acaba (hook `page:transition:finish`), les claus antigues es netegen automàticament.

No cal cap configuració; funciona de sèrie.

**Solució 2: context de ruta explícit**

Si prefereixes control manual, passa explícitament la ruta actual a `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Solució 3: estats de càrrega**

Implementa estats de càrrega per gestionar la càrrega de traduccions amb elegància:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Per què les claus de traducció no es resolen durant SSR a Vercel?

**Limitacions de `$fetch` en SSR**
A plataformes serverless com Vercel, `$fetch` només pot obtenir fitxers estàtics del CDN i no del servidor Nitro intern. Això significa que els fitxers estàtics de traducció potser no són accessibles directament tret que es defineixi la URL base correcta.

**Correcció definint `apiBaseClientHost` i `apiBaseServerHost`**
Si les traduccions s'allotgen externament en un CDN o domini diferent, fes servir `apiBaseClientHost` per a les peticions del client i `apiBaseServerHost` per a les del servidor. L'`apiBaseUrl` només ha de contenir el prefix del camí (per exemple, `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

O mitjançant variables d'entorn:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Les traduccions s'obtindran de `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` tant al client com al servidor.

## 🔗 Problemes d'enrutament i navegació

### ❓ Puc fer servir `NuxtLink` o `<i18n-link>` directament a les cadenes de traducció?

Sí, `Nuxt I18n Micro` permet fer servir `NuxtLink` o `<i18n-link>` dins les traduccions a través del component `<i18n-t>`, cosa especialment útil per gestionar requeriments gramaticals i d'idiomes RTL sense dividir les cadenes de traducció.

**Exemple:**

Fitxer de traducció:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Plantilla Vue:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Això permet enllaços dinàmics dins de les traduccions preservant una estructura de localització adequada.

## 🏗️ Problemes de compilació i desplegament

### ❓ Per què els payloads de traducció acaben sota `public/_locales/` (o al paquet del servidor a Edge)?

SSR i el client necessiten els mateixos payloads `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. Com s'empaqueten depèn de l'objectiu de Nitro:

**Explicació:**

- **Node (per defecte):** el mòdul **no** incrusta les traduccions com a `serverAssets` de Nitro / `raw:` de Rollup (això inflava la RAM de compilació en catàlegs grans). En lloc d'això, copia l'arbre premerged a `public/<apiBaseUrl>/` (per defecte `_locales`) i SSR llegeix aquests fitxers amb `readFile`. El client fa `$fetch` a les mateixes URL: ja sigui com a fitxers estàtics o via el gestor Nitro.
- **Edge** (`nitro.node === false`): no hi ha un FS públic durable per a SSR, així que els payloads s'incrusten via `serverAssets` de Nitro (`assets:i18n`). Prefereix `translationPayloads.mode: 'source'` perquè la incrustació es mantingui compacta. Defineix `publicAssets: true` només si també necessites una còpia CDN/estàtica.
- **`prerenderRoutes`:** opcional. En mode premerged, `publicAssets` ja escriu `\{page\}/\{locale\}/data.json`, així que fer prerender d'aquestes rutes normalment és redundant.

### ❓ Per què obtinc un error de compilació referint-se a `@unhead/vue` o un objecte indefinit, especialment a Cloudflare Pages?

**Causa:**
Alguns projectes experimenten conflictes de compilació o dependències que falten en fer servir `nuxt-i18n-micro`. En particular:

- Els desplegaments a **Cloudflare Pages** o **Cloudflare Workers** poden requerir flags de compatibilitat addicionals.
- Els passos de prerender poden fallar si dependències com `@unhead/vue` no estan correctament instal·lades.
- Alguns mòduls (per exemple, **nuxthub**, **nitro-cloudflare-dev**) poden introduir conflictes tret que es configurin amb els flags o dependències correctes.

**Solucions possibles:**

**Solució 1: instal·lar `@unhead/vue` manualment**
Si l'error de compilació es queixa de no trobar `@unhead/vue`, instal·la'l directament a les dependències del teu projecte:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Això assegura que estigui disponible durant la fase de prerender de Nitro.

**Solució 2: afegir flags de compatibilitat de Cloudflare**
Quan es fa servir Cloudflare Pages o Cloudflare Workers, la compatibilitat amb Node.js sovint està desactivada per defecte. Activa-la al teu `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Aquest flag permet que molts mòduls de Node.js (inclosos els que fa servir `nuxt-i18n-micro`) funcionin sense problemes.

## 🔍 SEO i `@nuxtjs/seo`

### ❓ Error: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Això passa quan **`@nuxtjs/seo`** arrossega un **`nuxt-site-config` 3.x** antic que només registra el seu plugin d'i18n per a `@nuxtjs/i18n`, no per a **nuxt-i18n-micro**.

**Correcció:**

1. Actualitza a **`@nuxtjs/seo` 3+** (inclou `nuxt-site-config` 4+ amb suport per micro).
2. Posa **`nuxt-i18n-micro` abans de `@nuxtjs/seo`** a `modules`.
3. Manté **`i18n.meta: true`** per a etiquetes head conscients del locale.

Consulta la [guia de SEO — secció Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo) per a un exemple complet.

## 🔧 Configuració i compatibilitat

### ❓ `Nuxt I18n Micro` està inspirat en `vue-i18n`? Què passa amb els modificadors?

Tot i que `Nuxt I18n Micro` serveix com a alternativa de rendiment a `nuxt-i18n`, està construït independentment de `vue-i18n`. Encara que alguns noms de mètodes i paràmetres poden ser similars, la funcionalitat subjacent difereix significativament.

**Modificadors**: el mantenidor va considerar inicialment els modificadors, però va concloure que components com `<i18n-t>` i `<i18n-link>` cobreixen aquestes necessitats de manera efectiva.

Per exemple:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Aquest enfocament és flexible, així que publicar modificadors actualment no és necessari. Tot i això, es podrien afegir modificadors en versions futures si hi ha demanda.
