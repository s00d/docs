# ❓ FAQ: Problemes i solucions comunes

Troba respostes a preguntes freqüents i solucions a problemes comuns amb Nuxt I18n Micro.

## 🚀 Problemes d'inici

### ❓ Què passa si una ruta no es carrega?

Quan utilitzes `Nuxt I18n Micro`, certes rutes potser no es carregaran com s'espera, especialment si el router no assigna automàticament un nom a una ruta a subcarpetes.

**Solució:**
Per solucionar-ho, defineix manualment el nom de la ruta per a la pàgina afegint el següent al fitxer Vue corresponent:

```javascript
definePageMeta({ name: 'pageName' })
```

Això garanteix que la ruta estigui correctament registrada, permetent una navegació fluida dins de l'aplicació.

### ❓ Per què `$t` o altres composables d'i18n no funcionen als plugins de Nuxt?

Els composables d'i18n de Nuxt (`$t`, `$getLocale`, `$localePath`, etc.) potser no funcionaran com s'espera dins dels plugins de Nuxt o funcions d'utilitat, provocant errors en temps d'execució.

**Causa i solució:**
Els composables de Nuxt requereixen contextos específics (per exemple, hooks de Nuxt o funcions de setup de Vue) per accedir a la instància de Nuxt. Si s'utilitzen fora d'aquests contextos (per exemple, en funcions d'utilitat o plugins), pot aparèixer l'error següent a la consola:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Solució 1: Utilitzar `runWithContext`**
Per cridar composables d'i18n després d'una operació asíncrona, utilitza [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) per preservar el context necessari.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Solució 2: Recuperar el valor primer**
Alternativament, recupera el valor de traducció primer i després passa'l a una funció d'utilitat.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Solució 3: Passar claus de traducció als serveis**
En serveis o funcions d'utilitat, passa les claus de traducció en lloc d'utilitzar `$t` directament. Després, obtén la traducció al component.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Canvi de locale

### ❓ Canviar de locale sense canviar l'URL?

Sí, però depèn de la teva [estratègia d'enrutament](/guides/routing-strategies).

**Estratègia `no_prefix`** — el locale no forma part de l'URL. Utilitza `$switchLocale()` per canviar de locale i recarregar les traduccions mantenint la mateixa ruta:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

O actualitza només la preferència amb `useI18nLocale().setLocale('de')`. Per a una recàrrega completa de les traduccions al client, prefereix `$switchLocale()`.

**Estratègies amb prefix** (`prefix`, `prefix_except_default`, …) — el locale i l'URL estan vinculats. `$switchLocale()` sempre navega a la ruta localitzada. No hi ha cap opció `redirect: false`.

Si només necessites l'URL de destinació (per exemple, un enllaç de commutador d'idioma), utilitza `$switchLocalePath()` en el seu lloc:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Consulta [Canvi de ruta i locale](/api/methods#-route-locale-switching) per a tots els mètodes de canvi.

### ❓ La pàgina fa scroll a dalt (o salta) quan es canvia de locale?

Això és esperat — és el **comportament de scroll de Vue Router / Nuxt**, no quelcom específic de nuxt-i18n-micro.

Amb estratègies de prefix (`prefix`, `prefix_except_default`, …), `$switchLocale()` fa una navegació normal al client (`/en/page` → `/de/page`). El [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) per defecte de Nuxt fa scroll a dalt als canvis de ruta (excepte en el retrocés/avanç del navegador mitjançant `savedPosition`).

nuxt-i18n-micro no afegeix gestió d'scroll oculta — utilitza un petit component embolcall a la teva app.

**Embolcall `SwitchLocalePreserve`**

Copia [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) al teu projecte (`components/SwitchLocalePreserve.vue`). Demo en funcionament: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

A la pàgina, defineix `scrollToTop: false` i embolcalla la teva UI de commutador. Marca els objectius clicables amb `data-locale` — l'embolcall intercepta els clics, crida `$switchLocale` i restaura l'scroll (incloent quan la longitud de la traducció canvia el layout):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

El component:

1. **En el clic** — llegeix `data-locale` a l'element clicat dins del slot (botons, enllaços o qualsevol marcatge personalitzat).
2. **Abans** de `$switchLocale` — emmagatzema `scrollY` i la posició de l'element clicat (el manté sota el cursor).
3. **Durant** la navegació — modifica `router.options.scrollBehavior` una vegada i retorna `\{ top: scrollY \}` en lloc de fer scroll a dalt.
4. **Després** de la navegació — espera `page:finish`, i després torna a aplicar l'scroll mentre un `ResizeObserver` capta els canvis de layout de les diferents longituds de traducció.

`scrollToTop: false` és necessari a les pàgines on utilitzes aquest embolcall. Documentació: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

No cridis `$switchLocale` directament als controls embolcallats — l'embolcall gestiona el canvi. Per a `<NuxtLink :to="$switchLocalePath('fr')">` fora de l'embolcall, el comportament de scroll segueix l'enrutament normal de Nuxt tret que afegeixis el teu propi `app/router.options.ts`.

## 🌐 Problemes de traducció

### ❓ Per què les traduccions es trenquen durant les transicions de pàgina, especialment amb `defineAsyncComponent`?

Quan utilitzes `nuxt-i18n-micro` amb transicions de pàgina, les traduccions poden deixar de funcionar breument durant la transició. Aquest problema es produeix perquè la ruta canvia abans que es completi la transició, provocant que les traduccions per a la nova pàgina es carreguin mentre la pàgina anterior encara és visible.

**Causa arrel:**

- Les transicions de pàgina fan que les rutes canviïn abans que les traduccions es carreguin completament
- `defineAsyncComponent` i `useAsyncData` poden endarrerir la càrrega de traduccions
- Les claus de traducció poden aparèixer com a rutes brutes durant la càrrega

**Solució 1: Fusió acumulativa (integrada, no cal configuració)**

A la v3, el mòdul utilitza automàticament una estratègia de fusió acumulativa. Quan es navega dins del mateix locale, les traduccions de la nova pàgina es fusionen al diccionari actiu en lloc de reemplaçar-lo. Això significa que les traduccions de la pàgina anterior romanen disponibles durant l'animació de transició. Un cop finalitzada la transició (hook `page:transition:finish`), les claus antigues es netegen automàticament.

No cal cap configuració — funciona directament.

**Solució 2: Context de ruta explícit**

Si prefereixes un control manual, passa explícitament la ruta actual a `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Solució 3: Estats de càrrega**

Implementa estats de càrrega per gestionar la càrrega de traduccions amb elegància:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Per què les claus de traducció no es resolen durant SSR a Vercel?

**Limitacions de `$fetch` a SSR**
En plataformes serverless com Vercel, `$fetch` només pot obtenir fitxers estàtics de la CDN i no del servidor intern de Nitro. Això significa que els fitxers de traducció estàtics potser no siguin directament accessibles tret que s'estableixi l'URL base correcta.

**Solució establint `apiBaseClientHost` i `apiBaseServerHost`**
Si les traduccions estan allotjades externament en una CDN o un domini diferent, utilitza `apiBaseClientHost` per a les sol·licituds del client i `apiBaseServerHost` per a les sol·licituds del servidor. `apiBaseUrl` només ha de contenir el prefix de ruta (per exemple, `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

O mitjançant variables d'entorn:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Les traduccions s'obtindran des de `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` tant al client com al servidor.

## 🔗 Problemes d'enrutament i navegació

### ❓ Puc utilitzar `NuxtLink` o `<i18n-link>` directament a les cadenes de traducció?

Sí, `Nuxt I18n Micro` permet l'ús de `NuxtLink` o `<i18n-link>` dins de les traduccions mitjançant el component `<i18n-t>`, que és especialment útil per gestionar la gramàtica i els requisits d'idiomes RTL sense dividir les cadenes de traducció.

**Exemple:**

Fitxer de traducció:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Plantilla Vue:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Això permet enllaços dinàmics dins de les traduccions preservant una estructura de localització adequada.

## 🏗️ Problemes de compilació i desplegament

### ❓ Per què els payloads de traducció acaben sota `public/_locales/` (o al bundle del servidor a Edge)?

El SSR i el client necessiten els mateixos payloads `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. Com s'empaqueten depèn de l'objectiu de Nitro:

**Explicació:**

- **Node (per defecte):** el mòdul **no** incrusta traduccions com a Nitro `serverAssets` / Rollup `raw:` (això reventava la RAM de compilació en catàlegs grans). En lloc d'això, copia l'arbre premerged a `public/<apiBaseUrl>/` (per defecte `_locales`) i el SSR llegeix aquests fitxers amb `readFile`. El client fa `$fetch` de les mateixes URLs — ja sigui com a fitxers estàtics o via el handler de Nitro.
- **Edge** (`nitro.node === false`): no hi ha un FS públic durador per a SSR, així que els payloads s'incrusten via Nitro `serverAssets` (`assets:i18n`). Prefereix `translationPayloads.mode: 'source'` perquè l'incrustament sigui compacte. Defineix `publicAssets: true` només si també necessites una còpia CDN/estàtica.
- **`prerenderRoutes`:** opcional. En mode premerged, `publicAssets` ja escriu `\{page\}/\{locale\}/data.json`, per la qual cosa el prerender d'aquestes rutes sol ser redundant.

### ❓ Per què obtinc un error de compilació que fa referència a `@unhead/vue` o un objecte no definit, especialment a Cloudflare Pages?

**Causa:**
Alguns projectes experimenten conflictes de compilació o dependències que falten quan s'utilitza `nuxt-i18n-micro`. En particular:

- Els desplegaments a **Cloudflare Pages** o **Cloudflare Workers** poden requerir flags de compatibilitat addicionals.
- Els passos de prerender poden fallar si dependències com `@unhead/vue` no s'instal·len correctament.
- Alguns mòduls (per exemple, **nuxthub**, **nitro-cloudflare-dev**) poden introduir conflictes tret que es configurin amb els flags o dependències correctes.

**Solucions possibles:**

**Solució 1: Instal·la `@unhead/vue` manualment**
Si l'error de compilació es queixa de no trobar `@unhead/vue`, instal·la'l directament a les dependències del teu projecte:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Això assegura que estigui disponible durant la fase de prerender de Nitro.

**Solució 2: Afegeix flags de compatibilitat de Cloudflare**
Quan utilitzes Cloudflare Pages o Cloudflare Workers, la compatibilitat amb Node.js sovint està desactivada per defecte. Activa-la al teu `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Aquest flag permet que molts mòduls de Node.js (incloent els utilitzats per `nuxt-i18n-micro`) s'executin correctament.

## 🔍 SEO i `@nuxtjs/seo`

### ❓ Error: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Això passa quan **`@nuxtjs/seo`** incorpora una **`nuxt-site-config` 3.x** antiga que només registra el seu plugin d'i18n per a `@nuxtjs/i18n`, no per a **nuxt-i18n-micro**.

**Solució:**

1. Actualitza a **`@nuxtjs/seo` 3+** (inclou `nuxt-site-config` 4+ amb suport de micro).
2. Posa **`nuxt-i18n-micro` abans de `@nuxtjs/seo`** a `modules`.
3. Mantén **`i18n.meta: true`** per a head tags conscients del locale.

Consulta la [guia de SEO — secció de Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo) per veure un exemple complet.

## 🔧 Configuració i compatibilitat

### ❓ `Nuxt I18n Micro` està inspirat en `vue-i18n`? I els modificadors?

Tot i que `Nuxt I18n Micro` serveix com a alternativa de rendiment a `nuxt-i18n`, es construeix independentment de `vue-i18n`. Tot i que alguns noms de mètodes i paràmetres poden ser similars, la funcionalitat subjacent difereix significativament.

**Modificadors**: El mantenidor inicialment va considerar modificadors, però va concloure que components com `<i18n-t>` i `<i18n-link>` aborden efectivament aquestes necessitats.

Per exemple:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Aquest enfocament és flexible, per la qual cosa alliberar modificadors actualment és innecessari. Tanmateix, es poden afegir modificadors en versions futures si hi ha demanda.
