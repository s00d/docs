# ❓ FAQ: Almindelige problemer og løsninger

Find svar på ofte stillede spørgsmål og løsninger på almindelige problemer med Nuxt I18n Micro.

## 🚀 Problemer ved opstart

### ❓ Hvad hvis en rute ikke indlæses?

Når du bruger `Nuxt I18n Micro`, kan visse ruter måske ikke indlæses som forventet, især hvis routeren ikke automatisk tildeler et navn til en rute i undermapper.

**Løsning:**
For at løse dette skal du manuelt definere rutenavnet for siden ved at tilføje følgende til den tilsvarende Vue-fil:

```javascript
definePageMeta({ name: 'pageName' })
```

Det sikrer, at ruten registreres korrekt og muliggør problemfri navigation i applikationen.

### ❓ Hvorfor virker `$t` eller andre i18n-composables ikke i Nuxt-plugins?

Nuxt-i18n-composables (`$t`, `$getLocale`, `$localePath` osv.) fungerer måske ikke som forventet i Nuxt-plugins eller hjælpefunktioner. Det kan resultere i runtime-fejl.

**Årsag og løsning:**
Nuxt-composables kræver specifikke kontekster (f.eks. Nuxt-hooks eller Vue setup-funktioner) for at tilgå Nuxt-instansen. Bruges de uden for disse kontekster (f.eks. i hjælpefunktioner eller plugins), kan følgende fejl vises i konsollen:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Løsning 1: Brug `runWithContext`**
For at kalde i18n-composables efter en asynkron operation kan du bruge [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) til at bevare den nødvendige kontekst.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Løsning 2: Hent værdien først**
Alternativt kan du hente oversættelsesværdien først og derefter sende den til en hjælpefunktion.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Løsning 3: Send oversættelsesnøgler i services**
I services eller hjælpefunktioner sender du oversættelsesnøglerne i stedet for at bruge `$t` direkte. Hent derefter oversættelsen i komponenten.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Locale-skift

### ❓ Skift locale uden at ændre URL'en?

Ja, men det afhænger af din [routingstrategi](/guides/routing-strategies).

**`no_prefix`-strategien** — locale er ikke en del af URL'en. Brug `$switchLocale()` til at ændre locale og genindlæse oversættelser, mens du bliver på samme sti:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Eller opdater kun præferencen med `useI18nLocale().setLocale('de')`. For en fuld klient-side-genindlæsning af oversættelser foretræk `$switchLocale()`.

**Præfiksstrategier** (`prefix`, `prefix_except_default`, …) — locale og URL er knyttet. `$switchLocale()` navigerer altid til den lokaliserede rute. Der er ingen `redirect: false`-indstilling.

Hvis du kun har brug for mål-URL'en (f.eks. et sprogskifter-link), skal du bruge `$switchLocalePath()` i stedet:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Se [Skift af rute og locale](/api/methods#-route-locale-switching) for alle skiftemetoder.

### ❓ Siden scroller til toppen (eller hopper), når locale skifter?

Det er forventet. Det er **Vue Router / Nuxt scroll-adfærd**, ikke noget specifikt for nuxt-i18n-micro.

Med præfiksstrategier (`prefix`, `prefix_except_default`, …) udfører `$switchLocale()` en normal klientnavigation (`/en/page` → `/de/page`). Nuxts standard [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) scroller til toppen ved ruteskift (bortset fra browserens tilbage/frem via `savedPosition`).

nuxt-i18n-micro tilføjer ikke skjult scroll-håndtering. Brug en lille wrapper-komponent i din app.

**`SwitchLocalePreserve`-wrapper**

Kopiér [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) ind i dit projekt (`components/SwitchLocalePreserve.vue`). Fungerende demo: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

På siden skal du sætte `scrollToTop: false` og wrappe din switcher-UI. Marker klikbare mål med `data-locale`. Wrapperen opfanger klik, kalder `$switchLocale` og genopretter scrollen (inklusive når oversættelseslængde ændrer layoutet):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Komponenten:

1. **Ved klik** — læser `data-locale` på det klikkede element inde i slottet (knapper, links eller enhver brugerdefineret markup).
2. **Før** `$switchLocale` — gemmer `scrollY` og det klikkede elements position (holder det under cursoren).
3. **Under** navigationen — patcher `router.options.scrollBehavior` én gang og returnerer `\{ top: scrollY \}` i stedet for at scrolle til toppen.
4. **Efter** navigationen — venter på `page:finish` og anvender derefter scrollen igen, mens en `ResizeObserver` fanger layoutforskydninger fra forskellige oversættelseslængder.

`scrollToTop: false` er påkrævet på sider, hvor du bruger denne wrapper. Docs: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Kald ikke `$switchLocale` direkte på wrappede kontroller. Wrapperen håndterer skiftet. For `<NuxtLink :to="$switchLocalePath('fr')">` uden for wrapperen følger scroll-adfærden normal Nuxt-routing, medmindre du tilføjer din egen `app/router.options.ts`.

## 🌐 Oversættelsesproblemer

### ❓ Hvorfor bryder oversættelser under sideovergange, især med `defineAsyncComponent`?

Når du bruger `nuxt-i18n-micro` med sideovergange, kan oversættelser kortvarigt holde op med at fungere under overgangen. Dette problem opstår, fordi ruten skifter, før overgangen er færdig, hvilket får oversættelser for den nye side til at indlæses, mens den gamle side stadig er synlig.

**Grundårsag:**

- Sideovergange forårsager ruteskift, før oversættelser er fuldt indlæst
- `defineAsyncComponent` og `useAsyncData` kan forsinke indlæsningen af oversættelser
- Oversættelsesnøgler kan vises som rå stier under indlæsningen

**Løsning 1: Kumulativ fletning (indbygget, ingen konfiguration nødvendig)**

I v3 bruger modulet automatisk en kumulativ fletningsstrategi. Ved navigation inden for samme locale flettes den nye sides oversættelser ind i den aktive ordbog i stedet for at erstatte den. Det betyder, at oversættelser fra den forrige side stadig er tilgængelige under overgangsanimationen. Efter overgangen er færdig (`page:transition:finish`-hook), ryddes gamle nøgler op automatisk.

Ingen konfiguration er nødvendig. Det fungerer ud af boksen.

**Løsning 2: Eksplicit rutekontekst**

Hvis du foretrækker manuel kontrol, kan du eksplicit sende den aktuelle rute til `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Løsning 3: Loading states**

Implementer loading states for at håndtere indlæsning af oversættelser elegant:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Hvorfor resolverer oversættelsesnøgler ikke under SSR på Vercel?

**Begrænsninger for `$fetch` under SSR**
På serverless-platforme som Vercel kan `$fetch` kun hente statiske filer fra CDN'en og ikke fra den interne Nitro-server. Det betyder, at statiske oversættelsesfiler måske ikke er direkte tilgængelige, medmindre den korrekte base-URL er sat.

**Løsning ved at sætte `apiBaseClientHost` og `apiBaseServerHost`**
Hvis oversættelser hostes eksternt på et CDN eller andet domæne, skal du bruge `apiBaseClientHost` til klient-side requests og `apiBaseServerHost` til server-side requests. `apiBaseUrl` bør kun indeholde sti-præfikset (f.eks. `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Eller via miljøvariabler:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Oversættelserne hentes så fra `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` både på klient og server.

## 🔗 Routing- og navigationsproblemer

### ❓ Kan jeg bruge `NuxtLink` eller `<i18n-link>` direkte i oversættelsesstrenge?

Ja, `Nuxt I18n Micro` tillader brug af `NuxtLink` eller `<i18n-link>` inde i oversættelser via komponenten `<i18n-t>`. Det er især nyttigt til at håndtere grammatik og RTL-sprog uden at opdele oversættelsesstrenge.

**Eksempel:**

Oversættelsesfil:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue-template:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Dette giver dynamiske links inde i oversættelser, samtidig med at den korrekte lokaliseringsstruktur bevares.

## 🏗️ Build- og deploymentproblemer

### ❓ Hvorfor havner oversættelses-payloads under `public/_locales/` (eller i server-bundlen på Edge)?

SSR og klienten skal begge bruge de samme `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`-payloads. Hvordan de pakkes afhænger af Nitro-target'et:

**Forklaring:**

- **Node (standard):** modulet indlejrer **ikke** oversættelser som Nitro `serverAssets` / Rollup `raw:` (det sprængte build-RAM på store kataloger). I stedet kopierer det det premerged træ til `public/<apiBaseUrl>/` (standard `_locales`), og SSR læser disse filer med `readFile`. Klienten `$fetch`er de samme URL'er, enten som statiske filer eller via Nitro-handleren.
- **Edge** (`nitro.node === false`): der er ingen holdbar offentlig FS til SSR, så payloads indlejres via Nitro `serverAssets` (`assets:i18n`). Foretræk `translationPayloads.mode: 'source'`, så indlejringen forbliver kompakt. Sæt `publicAssets: true`, kun hvis du også har brug for en CDN-/statisk kopi.
- **`prerenderRoutes`:** valgfri. I premerged-tilstand skriver `publicAssets` allerede `\{page\}/\{locale\}/data.json`, så prerendering af disse ruter er normalt overflødigt.

### ❓ Hvorfor får jeg en build-fejl, der refererer til `@unhead/vue` eller et undefined-objekt, især på Cloudflare Pages?

**Årsag:**
Nogle projekter oplever build-konflikter eller manglende afhængigheder, når `nuxt-i18n-micro` bruges. Særligt:

- Deployments på **Cloudflare Pages** eller **Cloudflare Workers** kan kræve ekstra kompatibilitetsflags.
- Prerendering-trin kan fejle, hvis afhængigheder som `@unhead/vue` ikke er korrekt installeret.
- Visse moduler (f.eks. **nuxthub**, **nitro-cloudflare-dev**) kan introducere konflikter, medmindre de konfigureres med korrekte flags eller afhængigheder.

**Mulige løsninger:**

**Løsning 1: Installer `@unhead/vue` manuelt**
Hvis build-fejlen klager over, at `@unhead/vue` ikke kan findes, skal du installere den direkte i dit projekts afhængigheder:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Det sikrer, at den er tilgængelig under Nitros prerender-fase.

**Løsning 2: Tilføj Cloudflare-kompatibilitetsflags**
Når du bruger Cloudflare Pages eller Cloudflare Workers, er Node.js-kompatibilitet ofte deaktiveret som standard. Aktivér den i din `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Dette flag tillader mange Node.js-moduler (inklusive dem, `nuxt-i18n-micro` bruger) at køre problemfrit.

## 🔍 SEO og `@nuxtjs/seo`

### ❓ Fejl: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Dette sker, når **`@nuxtjs/seo`** trækker en gammel **`nuxt-site-config` 3.x** ind, som kun registrerer sit i18n-plugin for `@nuxtjs/i18n`, ikke for **nuxt-i18n-micro**.

**Løsning:**

1. Opgrader til **`@nuxtjs/seo` 3+** (inkluderer `nuxt-site-config` 4+ med micro-understøttelse).
2. Placer **`nuxt-i18n-micro` før `@nuxtjs/seo`** i `modules`.
3. Behold **`i18n.meta: true`** for locale-bevidste head-tags.

Se [SEO-guiden — Nuxt SEO-afsnittet](/guides/seo#nuxt-seo-nuxtjs-seo) for et komplet eksempel.

## 🔧 Konfiguration og kompatibilitet

### ❓ Er `Nuxt I18n Micro` inspireret af `vue-i18n`? Og hvad med modifiers?

Selvom `Nuxt I18n Micro` fungerer som et performance-alternativ til `nuxt-i18n`, er det bygget uafhængigt af `vue-i18n`. Selvom nogle metodenavne og parametre kan minde om hinanden, adskiller den underliggende funktionalitet sig markant.

**Modifiers**: Vedligeholderen overvejede oprindeligt modifiers, men konkluderede, at komponenter som `<i18n-t>` og `<i18n-link>` effektivt dækker de behov.

For eksempel:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Denne tilgang er fleksibel, så det er unødvendigt at udgive modifiers nu. Modifiers kan dog blive tilføjet i fremtidige udgivelser, hvis der er efterspørgsel.
