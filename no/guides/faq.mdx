# ❓ FAQ: Vanlige problemer og løsninger

Finn svar på ofte stilte spørsmål og løsninger på vanlige problemer med Nuxt I18n Micro.

## 🚀 Kom-i-gang-problemer

### ❓ Hva om en rute ikke lastes?

Ved bruk av `Nuxt I18n Micro` kan noen ruter ikke lastes som forventet, spesielt hvis ruteren ikke automatisk tildeler et navn til en rute i undermapper.

**Løsning:**
For å løse dette kan du definere rutenavnet manuelt for siden ved å legge til følgende i den tilhørende Vue-filen:

```javascript
definePageMeta({ name: 'pageName' })
```

Dette sikrer at ruten registreres riktig og muliggjør sømløs navigasjon i applikasjonen.

### ❓ Hvorfor virker ikke `$t` eller andre i18n-composables i Nuxt-plugins?

Nuxt I18n-composables (`$t`, `$getLocale`, `$localePath` osv.) fungerer kanskje ikke som forventet i Nuxt-plugins eller hjelpefunksjoner, og resulterer i runtime-feil.

**Årsak og løsning:**
Nuxt-composables krever spesifikke kontekster (f.eks. Nuxt-hooks eller Vue setup-funksjoner) for å få tilgang til Nuxt-instansen. Hvis de brukes utenfor disse kontekstene (f.eks. i hjelpefunksjoner eller plugins), kan følgende feilmelding vises i konsollen:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Løsning 1: Bruk `runWithContext`**
For å kalle i18n-composables etter en asynkron operasjon, bruk [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext) for å bevare nødvendig kontekst.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Løsning 2: Hent verdien først**
Alternativt kan du hente oversettelsesverdien først, og deretter sende den videre til en hjelpefunksjon.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Løsning 3: Send oversettelsesnøkler i tjenester**
I tjenester eller hjelpefunksjoner sender du oversettelsesnøkler i stedet for å bruke `$t` direkte. Deretter henter du oversettelsen i komponenten.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Locale-bytte

### ❓ Bytte locale uten å endre URL-en?

Ja — men det avhenger av [rutestrategien din](/guides/routing-strategies).

**`no_prefix`-strategi** — locale er ikke en del av URL-en. Bruk `$switchLocale()` for å endre locale og laste inn oversettelser på nytt mens du forblir på samme sti:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Eller oppdater kun preferansen med `useI18nLocale().setLocale('de')`. For en full omlasting av oversettelser på klientsiden, foretrekk `$switchLocale()`.

**Prefiks-strategier** (`prefix`, `prefix_except_default`, …) — locale og URL er knyttet sammen. `$switchLocale()` navigerer alltid til den lokaliserte ruten. Det finnes ingen `redirect: false`-mulighet.

Hvis du kun trenger mål-URL-en (for eksempel en språkbytter-lenke), bruk `$switchLocalePath()` i stedet:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Se [Rute- og locale-bytte](/api/methods#-route-locale-switching) for alle byttermetoder.

### ❓ Siden ruller til toppen (eller hopper) når locale byttes?

Det er forventet — det er **Vue Router / Nuxt scroll-adferd**, ikke noe spesifikt for nuxt-i18n-micro.

Med prefiks-strategier (`prefix`, `prefix_except_default`, …) utfører `$switchLocale()` en normal klientnavigasjon (`/en/page` → `/de/page`). Nuxts standard-[`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) ruller til toppen ved ruteendringer (unntatt nettleser tilbake/frem via `savedPosition`).

nuxt-i18n-micro legger ikke til skjult scroll-håndtering — bruk en liten wrapper-komponent i appen din.

**`SwitchLocalePreserve`-wrapper**

Kopier [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) inn i prosjektet ditt (`components/SwitchLocalePreserve.vue`). Fungerende demo: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

På siden setter du `scrollToTop: false` og pakker inn switcher-UI-et. Marker klikkbare mål med `data-locale` — wrapperen fanger opp klikk, kaller `$switchLocale` og gjenoppretter scroll (også når oversettelseslengder endrer layouten):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Komponenten:

1. **Ved klikk** — leser `data-locale` på elementet du klikker inne i sloten (knapper, lenker eller egendefinert markup).
2. **Før** `$switchLocale` — lagrer `scrollY` og posisjonen til det klikkede elementet (holder det under markøren).
3. **Under** navigasjon — patcher `router.options.scrollBehavior` én gang og returnerer `\{ top: scrollY \}` i stedet for å rulle til toppen.
4. **Etter** navigasjon — venter på `page:finish`, og reapplyer scroll mens en `ResizeObserver` fanger opp layoutforskyvninger fra ulike oversettelseslengder.

`scrollToTop: false` er påkrevd på sider der du bruker denne wrapperen. Dokumentasjon: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Ikke kall `$switchLocale` direkte på wrappede kontroller — wrapperen håndterer byttet. For `<NuxtLink :to="$switchLocalePath('fr')">` utenfor wrapperen følger scroll-adferden vanlig Nuxt-ruting med mindre du legger til din egen `app/router.options.ts`.

## 🌐 Oversettelsesproblemer

### ❓ Hvorfor blir oversettelser ødelagt under sideoverganger, spesielt med `defineAsyncComponent`?

Ved bruk av `nuxt-i18n-micro` med sideoverganger kan oversettelser kortvarig slutte å virke under overgangen. Dette skjer fordi ruten endres før overgangen fullføres, slik at oversettelser for den nye siden lastes mens den gamle siden fortsatt er synlig.

**Rotårsak:**

- Sideoverganger fører til ruteendringer før oversettelser er ferdig lastet
- `defineAsyncComponent` og `useAsyncData` kan forsinke lasting av oversettelser
- Oversettelsesnøkler kan vises som råstier under lasting

**Løsning 1: Kumulativ merge (innebygd, ingen konfigurasjon nødvendig)**

I v3 bruker modulen automatisk en kumulativ merge-strategi. Ved navigasjon innenfor samme locale slås nye sideoversettelser sammen med den aktive ordlisten i stedet for å erstatte den. Dette betyr at oversettelser fra den forrige siden fortsatt er tilgjengelige under overgangsanimasjonen. Etter at overgangen er ferdig (`page:transition:finish`-hook), ryddes gamle nøkler opp automatisk.

Ingen konfigurasjon er nødvendig — dette fungerer rett ut av boksen.

**Løsning 2: Eksplisitt rutekontekst**

Hvis du foretrekker manuell kontroll, kan du eksplisitt sende gjeldende rute til `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Løsning 3: Lastetilstander**

Implementer lastetilstander for å håndtere lasting av oversettelser elegant:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Hvorfor løses ikke oversettelsesnøkler under SSR på Vercel?

**`$fetch`-begrensninger under SSR**
På serverless-plattformer som Vercel kan `$fetch` bare hente statiske filer fra CDN-en, og ikke fra den interne Nitro-serveren. Dette betyr at statiske oversettelsesfiler kanskje ikke er direkte tilgjengelige med mindre riktig base-URL er satt.

**Fiks ved å sette `apiBaseClientHost` og `apiBaseServerHost`**
Hvis oversettelser hostes eksternt på et CDN eller på et annet domene, bruk `apiBaseClientHost` for klientside-forespørsler og `apiBaseServerHost` for serverside-forespørsler. `apiBaseUrl` skal kun inneholde sti-prefikset (f.eks. `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Eller via miljøvariabler:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Oversettelsene hentes da fra `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` på både klient og server.

## 🔗 Rutings- og navigasjonsproblemer

### ❓ Kan jeg bruke `NuxtLink` eller `<i18n-link>` direkte i oversettelsesstrenger?

Ja, `Nuxt I18n Micro` tillater bruk av `NuxtLink` eller `<i18n-link>` i oversettelser gjennom `<i18n-t>`-komponenten, noe som er spesielt nyttig for å håndtere grammatikk og RTL-språkkrav uten å splitte opp oversettelsesstrenger.

**Eksempel:**

Oversettelsesfil:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue-template:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Dette gir dynamiske lenker inne i oversettelser samtidig som lokaliseringsstrukturen bevares.

## 🏗️ Bygg- og deployment-problemer

### ❓ Hvorfor havner oversettelses-payloads under `public/_locales/` (eller i server-bundlet på Edge)?

Både SSR og klienten trenger de samme `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`-payloadene. Hvordan de pakkes avhenger av Nitro-målet:

**Forklaring:**

- **Node (standard):** modulen embedder **ikke** oversettelser som Nitro `serverAssets` / Rollup `raw:` (det sprengte bygge-RAM på store kataloger). I stedet kopieres det premerged-treet til `public/<apiBaseUrl>/` (standard `_locales`), og SSR leser filene med `readFile`. Klienten gjør `$fetch` mot de samme URL-ene — enten som statiske filer eller via Nitro-handleren.
- **Edge** (`nitro.node === false`): det finnes ingen holdbar offentlig FS for SSR, så payloads embeddes via Nitro `serverAssets` (`assets:i18n`). Foretrekk `translationPayloads.mode: 'source'` slik at embed-en holder seg kompakt. Sett `publicAssets: true` bare hvis du også trenger en CDN-/statisk kopi.
- **`prerenderRoutes`:** valgfritt. I premerged-modus skriver `publicAssets` allerede `\{page\}/\{locale\}/data.json`, så prerendering av disse rutene er vanligvis overflødig.

### ❓ Hvorfor får jeg en byggefeil som refererer til `@unhead/vue` eller et udefinert objekt, spesielt på Cloudflare Pages?

**Årsak:**
Enkelte prosjekter opplever byggekonflikter eller manglende avhengigheter ved bruk av `nuxt-i18n-micro`. Spesielt:

- Deployments på **Cloudflare Pages** eller **Cloudflare Workers** kan kreve ekstra kompatibilitetsflagg.
- Prerendering-trinn kan feile hvis avhengigheter som `@unhead/vue` ikke er riktig installert.
- Enkelte moduler (f.eks. **nuxthub**, **nitro-cloudflare-dev**) kan skape konflikter uten riktige flagg eller avhengigheter.

**Mulige løsninger:**

**Løsning 1: Installer `@unhead/vue` manuelt**
Hvis byggefeilen klager på at `@unhead/vue` ikke finnes, installer det direkte i prosjektets avhengigheter:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Dette sikrer at den er tilgjengelig under Nitros prerender-fase.

**Løsning 2: Legg til Cloudflare-kompatibilitetsflagg**
Ved bruk av Cloudflare Pages eller Cloudflare Workers er Node.js-kompatibilitet ofte deaktivert som standard. Aktiver den i `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Dette flagget lar mange Node.js-moduler (inkludert de som brukes av `nuxt-i18n-micro`) kjøre sømløst.

## 🔍 SEO og `@nuxtjs/seo`

### ❓ Feil: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Dette skjer når **`@nuxtjs/seo`** trekker inn en gammel **`nuxt-site-config` 3.x** som kun registrerer sin i18n-plugin for `@nuxtjs/i18n`, ikke for **nuxt-i18n-micro**.

**Fiks:**

1. Oppgrader til **`@nuxtjs/seo` 3+** (inkluderer `nuxt-site-config` 4+ med micro-støtte).
2. Plasser **`nuxt-i18n-micro` før `@nuxtjs/seo`** i `modules`.
3. Behold **`i18n.meta: true`** for locale-bevisste head-tagger.

Se [SEO-guiden — Nuxt SEO-seksjonen](/guides/seo#nuxt-seo-nuxtjs-seo) for et fullstendig eksempel.

## 🔧 Konfigurasjon og kompatibilitet

### ❓ Er `Nuxt I18n Micro` inspirert av `vue-i18n`? Hva med modifikatorer?

Selv om `Nuxt I18n Micro` fungerer som et ytelsesalternativ til `nuxt-i18n`, er den bygget uavhengig av `vue-i18n`. Selv om enkelte metodenavn og parametere kan være like, skiller den underliggende funksjonaliteten seg vesentlig.

**Modifikatorer**: Vedlikeholderen vurderte i utgangspunktet modifikatorer, men konkluderte med at komponenter som `<i18n-t>` og `<i18n-link>` effektivt dekker disse behovene.

For eksempel:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Denne tilnærmingen er fleksibel, så det er foreløpig ikke nødvendig å lansere modifikatorer. Modifikatorer kan imidlertid legges til i fremtidige utgivelser hvis det er etterspørsel.
