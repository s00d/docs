Значення за замовчуванням налаштовано для типового застосунку: один JSON payload на сторінку й локаль, переклади не потрапляють в HTML, обмежені кеші на сервері. На цій сторінці перелічено кілька налаштувань, які варто змінити, коли каталог великий, сервер обмежений у пам'яті або payload надходять з іншого хоста. Виміряні показники порівняно з `@nuxtjs/i18n` і чистим Nuxt дивіться в [Бенчмарках](/uk/guide/performance-results).

## Що вже роблять значення за замовчуванням {#what-the-defaults-already-do}

- **Один payload на сторінку.** Збірка зливає кореневі ключі, ключі сторінки та ключі резервної локалі в `/_locales/<page>/<locale>/data.json`, тож сторінка завантажує один файл, а `$t` — це один пошук.
- **Жодного словника в HTML.** SSR тримає переклади в пам'яті сервера; браузер завантажує payload замість того, щоб розбирати його з `__NUXT_DATA__`.
- **Кеш браузера.** `?v=` змінюється лише тоді, коли змінюються переклади, тож браузер зберігає свої payload між розгортаннями, які їх не зачепили. Статична копія на хостингу свіжа протягом 60 секунд, після чого проходить повторну перевірку: повторне завантаження чекає на одну відповідь `304`. Серверний маршрут відповідає `immutable` на рік ([Розгортання](/uk/guide/deployment#cache-headers-and-datebuild)).
- **Обмежена пам'ять сервера.** За замовчуванням сервер кешує щонайбільше 1000 payload і видаляє ті, що використовувалися найдавніше.

## Розділення перекладів за сторінками {#split-translations-by-page}

Ключі, що використовуються на одній сторінці, належать до `locales/pages/<page>/<locale>.json`, а не до кореневих файлів: кореневі ключі входять до payload кожної сторінки. Див. [Файли перекладів](/uk/guide/translations).

Два налаштування змінюють це розділення:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    // pages that show the same keys share one payload: /de/products/123 loads the products payload
    routesLocaleLinks: { 'products-id': 'products' },
    // or: no page files at all, every page loads only the root dictionary
    // disablePageLocales: true,
  },
})
```

[`routesLocaleLinks`](/uk/api/module-options#routeslocalelinks) прибирає дублікати payload для пов'язаних маршрутів. [`disablePageLocales`](/uk/api/module-options#disablepagelocales) підходить для невеликих застосунків, де простіше мати один словник на локаль.

## Серверні кеші {#server-caches}

| Налаштування | За замовчуванням | Ефект |
| --- | --- | --- |
| [`cacheMaxSize`](/uk/api/module-options#cachemaxsize) | `0` | Максимальна кількість записів у кешах payload. `0` = без обмеження в браузері, 1000 на сервері. |
| [`cacheTtl`](/uk/api/module-options#cachettl) | `0` | Кількість секунд, після якої закешований запис перезавантажується. `0` = ніколи; задайте, коли payload надходять з `apiBaseServerHost` і змінюються без повторного розгортання. |
| `serverTranslationPreload` | `false` | Завантажувати payload `index` у middleware Nitro для кожного запиту сторінки, щоб серверні хелпери й головна сторінка використовували його повторно. |

Зменште `cacheMaxSize` на невеликому інстансі з великою кількістю сторінок × локалей. Локально відредагованим перекладам TTL ніколи не потрібен: у режимі розробки файли читаються наживо, а продакшн-payload змінюються лише з розгортанням.

## Пам'ять на сервері Node {#memory-on-a-node-server}

Під стабільним навантаженням сервер Node може займати приблизно в 12 разів більше, ніж його живий heap, і залишатися на цьому рівні. У стрес-тесті зі 100k ключів на сторінку живий heap у 90 MB працював приблизно з 1.1 GB RSS. Це не витік. Після одного надмірного циклу GC V8 підвищує свій ліміт heap і зберігає звільнені сторінки в пулі для повторного використання, поки триває навантаження. Приблизно через 8 секунд після припинення навантаження пул спорожнюється, і RSS падає приблизно до 160 MB. `global.gc()` цю пам'ять не повертає. Чистий Nuxt без модуля поводиться так само, пропорційно до свого меншого heap.

Це коштує запасу пам'яті: якщо ліміт пам'яті нижчий за цей рівень і heap не обмежено, процес може бути вбито. Задайте обмеження, яке вписується у ваш ліміт і значно перевищує живий heap:

```bash
NODE_OPTIONS=--max-old-space-size=512 node .output/server/index.mjs
```

| 100k ключів, 12 локалей, від 5 до 30 хвилин навантаження | За замовчуванням | `--max-old-space-size=512` |
| --- | --- | --- |
| RSS під навантаженням | близько 1,150 MB | 254-287 MB |
| Запитів на секунду | 624 | 517-572 |

Тобто обмеження обмінює 8–10 % пропускної здатності на пам'ять. Каталог звичайного розміру має менший heap і менший стрибок. Ці запуски виконувалися на macOS з Node 22, не в контейнері.

## Час розбору та `dir` {#parse-time-and-dir}

`dir: 'auto'` для локалі змушує браузер визначати напрям за вмістом під час розбору. У Chromium DOMContentLoaded для 20,000 елементів становив близько 1.1 с з `dir="auto"` і 0.1 с без нього, а для 5,000 елементів — близько 130 мс проти 45 мс. Залиште `dir` незаданим або задайте `ltr` чи `rtl` ([Напрям тексту](/uk/guide/seo#text-direction)).

## Спільний кеш для кількох інстансів {#shared-cache-for-several-instances}

Для кількох інстансів однієї збірки [`cacheStorage`](/uk/api/module-options#other) надає їм один кеш словників у будь-якому сховищі Nitro, через з'єднання, яке ваш застосунок налаштовує в `nitro.storage`. Модуль не додає жодного конектора й жодної залежності.

**Це кеш, а не джерело.** Переклади надходять із вбудованих або публічних payload чи з `apiBaseServerHost`. Записується лише те, що надійшло з джерела, а ключі містять збірку, тож сховище, заповнене вручну, не читається. Щоб віддавати переклади з KV чи бази даних, розмістіть на `apiBaseServerHost` невеликий маршрут, який їх читає.

**Коли це допомагає.** Лише з віддаленим `apiBaseServerHost`. Три інстанси, що обходили 39 словників, зробили 117 запитів до хоста без нього і 48 з ним. Коли файли на диску, влучання в сховище не швидше за файл, а перший прохід по 12 сторінках зайняв 280-296 мс без опції і 308-325 мс із заповненим Redis, тож залиште її незаданою. На пресеті, що вбудовує словники, без хоста вона нічого не робить, і збірка про це повідомляє.

Холодний словник, один клієнт, по одному обходу, тож дані приблизні, і більша частина часу — це відстань до хоста:

| Сховище | З хоста | Зі сховища |
| --- | --- | --- |
| Cloudflare KV | близько 300 мс | близько 110 мс |
| D1 | близько 230 мс | близько 115 мс |
| Deno KV | близько 430 мс | близько 100 мс |
| Upstash, Vercel serverless | близько 445 мс | близько 245 мс |
| Upstash, Vercel Edge | близько 505 мс | близько 235 мс |

### Redis {#redis}

Потребує `ioredis` у вашому проєкті.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    storage: {
      redis: { driver: 'redis', url: process.env.REDIS_URL },
    },
  },
  i18n: {
    cacheStorage: 'redis', // the mount name
    apiBaseServerHost: 'https://translations.internal',
    cacheTtl: 300,
  },
})
```

### Upstash на Vercel і Vercel Edge {#upstash-on-vercel-and-vercel-edge}

Використовуйте драйвер `upstash` для обох: він працює через REST, тоді як драйверу `redis` потрібен TCP. Він потребує `@upstash/redis` у вашому проєкті й читає `UPSTASH_REDIS_REST_URL` та `UPSTASH_REDIS_REST_TOKEN` зі змінних середовища.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    storage: {
      upstash: { driver: 'upstash' },
    },
  },
  i18n: {
    cacheStorage: 'upstash',
    apiBaseServerHost: 'https://translations.example.com',
  },
})
```

### Cloudflare KV {#cloudflare-kv}

Прив'яжіть простір імен до Worker як `I18N_KV` (`kv_namespaces` у його конфігурації wrangler).

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    storage: {
      kv: { driver: 'cloudflare-kv-binding', binding: 'I18N_KV' },
    },
  },
  i18n: {
    cacheStorage: 'kv',
    apiBaseServerHost: 'https://translations.example.com',
  },
})
```

Хосту, який є іншим Worker в тому самому акаунті, потрібен прапорець сумісності `global_fetch_strictly_public`, інакше запит до нього не дійде.

### Cloudflare D1 {#cloudflare-d1}

`nitro.storage` не може містити об'єкт бази даних, тому драйвер монтує плагін Nitro. Монтування перевіряється під час першого використання, тож цього достатньо рано. Прив'яжіть базу даних як `I18N_DB` (`d1_databases`) і додайте `unstorage` до свого проєкту.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    experimental: { database: true },
    database: {
      default: { connector: 'cloudflare-d1', options: { bindingName: 'I18N_DB' } },
    },
  },
  i18n: {
    cacheStorage: 'd1',
    apiBaseServerHost: 'https://translations.example.com',
  },
})
```

```ts
// server/plugins/i18n-storage.ts
import dbDriver from 'unstorage/drivers/db0'

export default defineNitroPlugin(() => {
  useStorage().mount('d1', dbDriver({ database: useDatabase() }))
})
```

Драйвер `db0` позначено як експериментальний, і він ігнорує TTL: рядки старих збірок залишаються, доки ви їх не видалите.

### Deno KV {#deno-kv}

На Deno Deploy створіть базу даних (`deno deploy database provision <name> --kind denokv`), призначте її застосунку (`deno deploy database assign`) і використовуйте драйвер:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  nitro: {
    storage: {
      kv: { driver: 'deno-kv' },
    },
  },
  i18n: {
    cacheStorage: 'kv',
    apiBaseServerHost: 'https://translations.example.com',
  },
})
```

### Як це працює {#how-it-behaves}

Словник шукається у власному кеші інстансу, потім у спільному сховищі, потім у його джерелі. Власний кеш інстансу залишається, оскільки `$t` синхронний і потребує дерева в пам'яті: це розділяє того, хто завантажує, і того, хто віддає, але не економить пам'ять.

- **Хто завантажує.** З віддаленим хостом — один запит до бекенду на словник замість одного на інстанс. Інстанси, які отримують промах одночасно, завантажують його кожен окремо, бо блокування немає.
- **Сторінки без власного словника** не зберігаються, щоб вигадані назви сторінок не могли додавати ключі. Кожен інстанс завантажує таку сторінку з хоста один раз, а на Workers, де ізоляти з'являються й зникають, це постійний потік запитів.
- **Хост недоступний.** Сторінки зі збереженим словником працюють. Сторінка без нього рендериться зі збереженого кореневого словника, її власні ключі виводяться як є, з [`503`, який жоден кеш не зберігає](/uk/guide/deployment#when-a-dictionary-cannot-be-read), а `/_locales` відповідає для неї `503`, доки хост не відновиться. `useTranslationServerMiddleware` повертає ключі для словника, який не може прочитати.
- **Хост** — це `NUXT_I18N_APP_BASE_SERVER_HOST` під час виконання, або ж `apiBaseServerHost` зі збірки, так само як і без опції. На пресеті, що вбудовує словники (Cloudflare, Vercel, Netlify, див. [Розгортання](/uk/guide/deployment#serverless-and-edge)), шар застосовується лише з хостом: дані вже є в бандлі, і копія в KV була б мережевим читанням того, що вже є в пам'яті.
- **Ключі** мають вигляд `i18n-micro:<buildId>~<dateBuild>~<fallbackLocale>~<host>:<locale>:<page>`, тож дві збірки під час поступового розгортання ніколи не читають одна одну, як і два бекенди одного артефакту. Кожен інстанс має походити з однієї збірки (один артефакт або зафіксований Nuxt [`buildId`](https://nuxt.com/docs/api/nuxt-config#buildid)); інстанси, зібрані окремо, просто не мають спільного кешу. Із зафіксованим `buildId` і `dateBuild: 0` дві різні збірки мають спільні ключі. Шукаються лише ввімкнені локалі, а назви сторінок понад 200 символів обходять шар.
- **Що зберігається.** Перед записом словник порівнюється з кореневим (`__root`) і потрапляє до сховища лише тоді, коли містить кожен кореневий ключ і відрізняється від кореневого. Тож вигадана сторінка, на яку відповіли кореневим словником, не додає ключа, як і тіло помилки з кодом 200 на сторінці. Кожен інстанс читає таку сторінку з джерела один раз. Хост має відповідати на невідомі сторінки кореневим словником, порожнім об'єктом або 404 і віддавати `__root`. Хост без `__root` або той, що віддає сторінки без кореневих ключів, нічого не робить спільним. Якщо хост відповідає на сам `__root` коректно сформованою помилкою, вона зберігається: тримайте `cacheTtl` коротким, якщо бекенд на таке здатен.
- **Термін дії.** Запис спливає через `cacheTtl` секунд після запису або через один день, якщо `cacheTtl` дорівнює `0`, тож ключі старих збірок не накопичуються. Значення може залишатися у власному кеші інстансу ще `cacheTtl`, а в кеші чанків рендеру — ще один: зміни на бекенді з'являються протягом трьох `cacheTtl`. Драйвери без терміну дії (`fs`) зберігають старі ключі, доки ви їх не видалите.
- **Коли сховище збоїть**, сторінка не збоїть. Читання може тривати 1 секунду, що покриває встановлення з'єднання й ключ Cloudflare KV, холодний у цій локації. Після збою ліміт становить 250 мс, доки сховище знову не відповість. Три збої поспіль закривають шар на 5 секунд. Поки він закритий і поки читання щойно не вдалося, нічого не записується. Невдалий запис нічого не закриває, тож репліка лише для читання і далі обслуговує читання. Сховище, чиї відповіді тривають довше за ці ліміти, вважається збійним: це промах, і словник надходить із джерела. З ioredis це починається десь із 400 мс на команду, бо встановлення з'єднання займає три обміни. Модуль записує в лог одне попередження на хвилину; ioredis додатково виводить власні помилки. Значення, яке не є словником, вважається промахом і перезаписується. Невідома назва монтування видає попередження один раз під час першого використання; після цього застосунок працює без шару.
- **Коли збоїть джерело**, збій ніде не зберігається. Невдалий запит чи нечитабельний файл не потрапляє до жодного кешу — ні до цього, ні до власного кешу інстансу, і наступний запит читає знову. Див. [Розгортання](/uk/guide/deployment#when-a-dictionary-cannot-be-read).
- **Вимкнено в режимі розробки та під час пререндерингу**, які читають свої файли й не повинні потребувати вашого продакшн-Redis.
- **Інвалідація.** Виклику очищення немає: нова збірка використовує нові ключі. Щоб одразу оновити запущену збірку, видаліть ключі `i18n-micro:` зі сховища й перезапустіть інстанси. `clearCache` і HMR впливають лише на стан процесу.
- Зміни під час виконання (`$mergeTranslations`, `$defineI18nRoute`) залишаються в рендері чи браузері, що їх зробив, і ніколи не записуються до сховища.

## Розмір payload {#payload-size}

Збірка видає попередження, коли вивід payload перевищує `translationPayloads.warnFileCount` (500 файлів) або `warnSizeBytes` (10 MB). У такому разі:

- винесіть ключі, що стосуються лише сторінок, з кореневих файлів;
- зв'яжіть маршрути, які показують ті самі ключі (`routesLocaleLinks`);
- на serverless чи Edge використовуйте `translationPayloads.mode: 'source'`, щоб серверний бандл вбудовував компактні джерела замість кожної комбінації сторінка × локаль ([Розгортання](/uk/guide/deployment#serverless-and-edge)). Збірка для Edge сама попереджає про перевищення ліміту платформи ([Обмеження бандла](/uk/guide/deployment#bundle-limits-on-edge));
- увімкніть `nitro.compressPublicAssets` для копій `.gz` / `.br` статичних payload.

## Вимірювання {#measuring}

Репозиторій відстежує, що постачає playground, за допомогою `pnpm run budget:payload`; поточні показники:

Виміряно на `playground` для `/`, `/de`:

| Вимірювання | Розмір |
| --- | --- |
| Джерела перекладів на диску | 7.8 MB |
| Віддається як окремі файли payload | 23.9 MB |
| Найбільший вбудований `__NUXT_DATA__` | 0.4 KB |
| Клієнтські ресурси | 624.4 KB |

Playground — це тестовий стенд зі згенерованими словниками до 100k ключів, тож це не ті показники, яких варто очікувати від реального
застосунку, — це фіксована точка для порівняння. Бюджет не проходить, коли вони несподівано зростають,
і саме так помічають випадкову зміну того, що містить payload.

Запустіть набір бенчмарків самостійно за допомогою `pnpm test:performance`; як він працює, описано в [методології бенчмарків](https://s00d.github.io/nuxt-i18n-micro/contributing/performance-methodology).
