### Опис {#description}

Порівнює **звичайний Nuxt**, **i18n-micro** і **`@nuxtjs/i18n`** з одним спільним профілем словників через `untestutils/perf`.

Фокус: час збирання, пікове RSS, розгортуваний **код vs переклади (asset) vs загалом** і навантаження (Artillery).

### Примітки щодо методології {#methodology-notes}

- Метрики — це **середні значення 3 послідовних запусків для кожної фікстури** (не чергуються).
- **Артефакт**: Nitro node-server `.output/server/index.mjs` після примусового `nuxi build`; `nuxt-i18n-micro` — це **зібраний dist модуля** (не заглушка jiti з `dev:prepare`). Див. [методологію бенчмарків](https://s00d.github.io/nuxt-i18n-micro/contributing/performance-methodology).
- **Переклади** = `bundle.asset` (JSON локалей, `chunks/raw/`, відповідні чанки локалей через `isTranslationFile`).
- **Код** не включає source maps (`*.map`): фікстури підключають модуль із репозиторію, тому Nitro записує для нього повні карти, а для npm-залежностей — жодних.
- **plain-nuxt** віддає той самий обсяг листових ключів як статичний JSON — під навантаженням це інтенсивний I/O, а не «накладні витрати i18n».
- Профіль навантаження `--load full`: розігрів 6s@6 + основний 60s@60 без обмежень (історично).
- Паузи охолодження `--cool fast` (див. документ із методології).
- Кожне зі збирань `runs` є **примусовим** (без обнулення часу збирання через теплий кеш).
- **Частка помилок** Artillery у таблицях — це помилки HTTP-статусу з метрик навантаження. Графіки також показують `vusers.failed` (тайм-аути клієнта під час насичення); вони можуть бути високими, тоді як частка HTTP-помилок залишається 0%.
### Запуски {#runs}

Усі метрики нижче — **середні значення 3 запусків**.

## Примітки {#notes}

- Спільний профіль: 4 локалі × 2 сторінки × ~16.8k листових ключів index.
- Навантаження: лише програмний Artillery — розігрів **6s@6** + основний **60s@60**, без обмеження VU (історична методологія YAML). Шляхи з runtime-профілю — див. `scripts/src/perf/load.ts`.
- Паузи охолодження: 2s після збирання, 3s між запусками, 5s між фікстурами. Збирання виконуються примусово під час кожного запуску, тож середні значення не розмиваються влученнями в кеш.
- Повторний запуск у щоденній роботі: `pnpm test:performance` (`--load short --cool fast`).
- Перегенерувати цю сторінку: `pnpm -C scripts cli performance --load full --only all --runs 3`.
- Прапорці: `--locales N --keys K --only all|micro|i18n|plain --runs N --skip-load --cool fast|strict`.
