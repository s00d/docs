Модуль працює з будь-яким пресетом Nitro без додаткової конфігурації: він обирає, де зберігатимуться файли перекладів, залежно від пресета, для якого ви збираєте. Значення за замовчуванням підходять більшості застосунків; прочитайте розділ для своєї платформи. Ця сторінка пояснює:

- що потрапляє в `.output/` і які заголовки отримують payload;
- що змінити для статичного хостингу, великих каталогів, підшляху, проксі або CDN.

<Note>

Розгорнуто й перевірено на реальних хостингах: Cloudflare Workers і Pages, Vercel і Vercel Edge, Netlify і Netlify Edge, Cloud Run і Deno Deploy, кожен із тим, що перелічено в розділі [Платформи](#platforms). Інші пресети збиралися й запускалися локально.

</Note>

## Як доставляються переклади {#how-translations-are-delivered}

Під час збирання модуль перетворює `locales/` (з об’єднаними всіма шарами) на **payload**: по одному JSON-файлу на сторінку та локаль. Їх зчитують два споживачі:

- **SSR** завантажує payload сторінки, що рендериться, у межах процесу — без HTTP-запиту, і словник не вбудовується в HTML.
- **Браузер** отримує `/_locales/<page>/<locale>/data.json?v=<dateBuild>` під час гідратації та навігації.

`_locales` — це [`apiBaseUrl`](/uk/api/module-options#apibaseurl). Вбудований серверний маршрут відповідає на цей URL; статична копія в `public/` відповідає на нього без сервера.

## Node-сервер {#node-server}

```bash
npx nuxi build
node .output/server/index.mjs
```

З `node-server` (пресет за замовчуванням), `node-cluster`, `bun`, `deno-server` чи будь-яким іншим пресетом, що віддає `public/` з диска, коли `public/` лежить поруч із текою `server/`:

- payload копіюються в `.output/public/_locales/<page>/<locale>/data.json`;
- SSR зчитує їх із цієї теки через `fs` (нічого не вбудовується в сервер);
- браузер отримує їх як статичні файли або із серверного маршруту.

Розгортайте весь каталог `.output/`. Модулю потрібен Node 20 або новіший, а Nuxt має власний мінімум: Nuxt 4.5 декларує `^22.19.0 || ^24.11.0 || >=26.0.0`.

Процес під постійним навантаженням може утримувати значно більше пам’яті, ніж його живий heap. Перегляньте [Пам’ять на Node-сервері](/uk/guide/performance#memory-on-a-node-server), перш ніж встановлювати ліміт контейнера.

З іншою структурою модуль вбудовує payload, як описано в наступному розділі. Це стосується:

- власного `nitro.output.publicDir`, який збирання зчитує один раз;
- `serveStatic: true` на пресеті, що зберігає статичні файли деінде.

<Warning>

Якщо збирання зчитує `public/`, а тека не потрапляє на сервер, як з `aws-lambda` і `serveStatic: true`, сервер записує в лог одну помилку, а сторінки показують сирі ключі. Встановіть `nitro.serveStatic: false`, щоб вбудувати payload.

</Warning>

## Serverless та Edge {#serverless-and-edge}

Ці пресети не можуть зчитувати `public/` під час виконання:

- пресети функцій, що відправляють `public/` на CDN або не віддають його: `vercel`, `netlify`, `aws-lambda`, `aws-amplify`, `azure-swa`, `firebase`, `stormkit`, `zeabur`, `node-listener`;
- Edge-пресети без файлової системи: `cloudflare-module`, `cloudflare-pages`, `vercel-edge`, `netlify-edge`, `deno_deploy`;
- `serveStatic: 'inline'`, як-от `winterjs`.

Там модуль вбудовує payload у серверний бандл як серверні ресурси Nitro (`assets:i18n`) і все одно записує публічну копію для браузера.

Вбудовування повної матриці сторінка × локаль робить бандл великим. Після перевищення ліміту Edge-платформи збирання попереджає та називає його, див. [Ліміти бандла](#bundle-limits-on-edge). Для великих каталогів перейдіть на режим `source`, який вбудовує компактні вихідні файли та об’єднує кореневі, сторінкові й резервні переклади під час виконання:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    translationPayloads: {
      mode: 'source',
    },
  },
})
```

У режимі `source` браузер завжди отримує payload із серверного маршруту, який об’єднує їх на запит (будь-яка публічна копія містить компактне дерево вихідних файлів, яке читає лише сервер). Для цього потрібен запущений сервер, тож не використовуйте `source` для суто статичного сайту.

### Ліміти бандла на Edge {#bundle-limits-on-edge}

| Платформа          | Ліміт                                                                                  |
| ------------------ | -------------------------------------------------------------------------------------- |
| Cloudflare Workers | 64 MiB без стиснення, на Free і Paid. Ліміту на стиснений розмір немає. 1 s запуску, 128 MB пам’яті |
| Vercel Edge        | 1 MB gzip на Hobby, 2 MB на Pro, 4 MB на Enterprise                                    |
| Netlify Edge       | 20 MB у стисненому вигляді                                                             |

Збирання підсумовує розмір словників, які вбудовує, і попереджає лише після перевищення найнижчого ліміту платформи. Воно рахує лише словники, тож застосунок додається зверху. Наприклад, 120 сторінок × 4 локалі з кореневим файлом 60 KB вбудовують:

| Режим | Вбудовано | Вміщується |
| --- | --- | --- |
| `premerged` | 34.9 MiB | Cloudflare; не Vercel Edge і не Netlify Edge |
| `source` | 5.7 MiB | Усе ще 3 MB gzip на Vercel Edge |

Каталог такого розміру на Vercel Edge потребує [хоста для payload](#app-baseurl-and-payload-hosts).

`source` платить за об’єднання для кожної сторінки й локалі в кожному isolate: близько 1 ms у цьому прикладі та 7 ms CPU в холодному. Це зростає з розміром ланцюжка резервних локалей: близько 43 ms для 4 MB файлів ланцюжка. Netlify Edge дозволяє 50 ms CPU на запит, а план Free у Cloudflare — 10 ms.

### Дати в Edge-середовищах {#dates-on-edge-runtimes}

`$td` використовує `Intl` середовища виконання, а його дані ICU можуть відрізнятися від браузерних. На Netlify Edge відформатована дата може містити U+202F (вузький нерозривний пробіл) там, де в Chrome звичайний пробіл, тож Vue записує в лог одну невідповідність гідратації, а текст виправляється під час гідратації. Звичайний Nuxt зі звичайним `Intl` поводиться там так само; Deno Deploy — ні.

<Tip>

`<i18n-t>` з `date` або `relativeDate` вже допускає цю невідповідність. Для `$td` у шаблоні додайте до елемента `data-allow-mismatch="text"`.

</Tip>

## Статичний сайт (nuxi generate) {#static-site-(nuxi-generate)}

```bash
npx nuxi generate
```

`nuxi build --preset <static preset>` робить те саме.

- Режим за замовчуванням `premerged` записує кожен payload у `.output/public/_locales/`, тож будь-який статичний хостинг може їх віддавати.
- Сторінки попередньо рендеряться для кожної локалі: за `prefix` модуль додає кожен локалізований корінь (`/en`, `/de`), а `/` залишається заглушкою-перенаправленням.
- Залиште [`prerenderRoutes`](/uk/api/module-options#translationpayloads) вимкненим: публічна копія вже містить файли payload.
- З режимом `source` або `publicAssets: false` браузеру нічого читати, і збирання попереджає.

<Note>

Немає сервера, який прочитав би cookie чи `Accept-Language`, тож збережена локаль не перенаправляє `/` під час першого завантаження. За `no_prefix` HTML містить локаль за замовчуванням, і збережена cookie не застосовується під час завантаження: `$switchLocale` усе одно працює на відкритій сторінці.

</Note>

Для Cloudflare Pages див. [Cloudflare Pages](#cloudflare-pages).

Для збирання з [доменами локалей](/uk/guide/layers#multiple-domains) запускайте generate один раз для кожного домену, з `NUXT_I18N_DOMAIN` як хостом цього запуску. Тоді кожне дерево містить сторінки та payload цього домену. Nitro не має змінної для вихідної теки, тож зчитуйте власну з конфігурації:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: { output: { publicDir: process.env.PUBLIC_DIR } },
})
```

```bash
NUXT_I18N_DOMAIN=example.de PUBLIC_DIR=sites/example.de npx nuxi generate
NUXT_I18N_DOMAIN=example.com PUBLIC_DIR=sites/example.com npx nuxi generate
```

- Тримайте теки поза `.output`: кожен запуск очищує її.
- Абсолютні посилання на інші домени не обходяться краулером.
- Без змінної збирання з локаллю з `baseUrl` попереджає та генерує конфігурацію збирання, у якій ці локалі є посиланнями й не отримують сторінок.
- На Node-сервері та сама змінна прив’язує процес до одного домену, хай що каже `Host`.

Статичний хостинг застосовує до цих файлів власні заголовки; налаштовуйте кешування в конфігурації хостингу. Правило модуля для `/_locales/*` таки потрапляє в Cloudflare Pages через `_headers` і у Vercel через `config.json` як `public, max-age=60`. Щоб відправляти поруч файли `.gz` / `.br`, увімкніть `nitro.compressPublicAssets`: модуль стисне копію payload з тими самими налаштуваннями.

## Заголовки кешування та dateBuild {#cache-headers-and-datebuild}

| Запит                                                                                    | `Cache-Control`                                                                                                 |
| ---------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| Node-сервер або маршрут, `?v=` дорівнює поточному `dateBuild`, непорожній словник        | `private, max-age=<httpCacheDuration>, immutable`                                                               |
| Node-сервер або маршрут, без `?v=`, зі старим значенням або з порожнім словником         | `public, max-age=0, must-revalidate`                                                                            |
| Копія `public/` на хостингу, будь-яке `?v=`                                              | `public, max-age=60` ([`httpCacheControl`](/uk/api/module-options#other)) |
| Режим `source`, `cacheTtl` або `apiBaseServerHost`: словник може змінитися без збирання  | заголовок `httpCacheControl`, завжди                                                                            |
| Серверний маршрут, словник не вдалося прочитати                                          | `503`, `no-store`                                                                                               |
| сервер розробки                                                                          | немає                                                                                                           |

Чому таблиця виглядає саме так:

- URL з поточним `v` закріплюється як хешований ресурс, і сказати це може лише те, що бачить query: серверний маршрут і Node-сервер, який встановлює заголовок для своїх статичних файлів.
- Він `private`, тож CDN, що ігнорує query, не може відповісти на наступний `v` цією відповіддю.
- Статичні файли хостингу отримують заголовок для всього шляху з правила маршруту `/_locales/**`, яке не бачить query, тож він залишається коротким; повторне завантаження все одно ні на чому не блокується.
- Старий `v` залишається доступним, оскільки його згадує кешований HTML.

`httpCacheControl: false` залишає всі статичні файли на `max-age=0, must-revalidate`. [`httpCacheDuration`](/uk/api/module-options#httpcacheduration) за замовчуванням дорівнює одному року; `0` не надсилає заголовка. `$clearCache()` перевалідовує все, що завантажує далі.

Safari запитує попередньо завантажений payload ще раз, коли не може повторно використати відповідь: з `no-cache` і `ETag` другий запит — це `304`, а без заголовка кешування й без валідатора — друге повне завантаження. `max-age` понад `0` дає один запит. Платить за це лише `httpCacheDuration: 0` на хостингу, який не додає валідатора.

[`dateBuild`](/uk/api/module-options#datebuild) — це значення `?v=`. За замовчуванням це хеш ваших файлів перекладів, тож він змінюється лише тоді, коли змінюються переклади, і браузери зберігають кешовані payload між розгортаннями, які їх не торкалися. Він також змінюється разом із ланцюжком резервних локалей.

- Встановіть його самостійно, щоб закріпити значення.
- Встановіть `0` або `''`, щоб повністю прибрати `?v=`; тоді payload ніколи не будуть `immutable`.

<Tip>

Після заміни словника на місці на Node-сервері перезапустіть із `NUXT_I18N_DATE_BUILD=<new value>`: ніщо інше не змінює `v` без перезбирання.

</Tip>

### Кореневі та дельта-файли {#root-and-delta-files}

`premerged` записує один корінь на локаль, `__root/<locale>/data.json`, а у файлі кожної сторінки — лише те, що від нього відрізняється.

- Файл сторінки позначає корінь, відносно якого його створено, ключем `__i18n_root`.
- Браузер отримує обидва, сторінка нічого не показує, доки не надійдуть обидва, а SSR об’єднує їх один раз на чанк.
- Файл без позначки — це цілий словник, і він самодостатній: сервер розробки, режим `source`, серверний маршрут і хостинг, що досі містить старіші файли, — усі відповідають таким, без жодних налаштувань.

Тож будь-хто, хто читає `_locales/*/data.json` напряму, читає дельту. Встановіть `translationPayloads.rootDelta: false`, щоб зберігати цілі файли.

Вкладка, відкрита під час розгортання, яка запитує нову дельту, бачить, що її створено відносно іншого кореня, і отримує цей корінь, перш ніж показувати її.

### Коли словник не вдається прочитати {#when-a-dictionary-cannot-be-read}

Невдалий запит до хостингу (будь-що, крім 404), нечитабельний чи пошкоджений файл або 200, що не є JSON-об’єктом, не потрапляє в жоден кеш, і наступний запит читає знову:

- рендеринг сторінки записує попередження, показує сирі ключі для цього словника й відповідає `503` з `Cache-Control: no-store`, так само в кожному CDN-заголовку (`CDN-Cache-Control`, `Cloudflare-CDN-Cache-Control`, `Netlify-CDN-Cache-Control`, `Vercel-CDN-Cache-Control`, `Surrogate-Control`, поверх будь-яких із правила маршруту) і `Retry-After: 60`;
- `/_locales/...` відповідає `503` з `no-store`;
- `useTranslationServerMiddleware` дає `t`, що повертає ключ або значення за замовчуванням.

Що відбувається під час збою:

- **Відвідувачі:** тіло цієї відповіді 503 — це сама сторінка. Під час гідратації браузер знову читає словник, і текст з’являється, щойно хостинг повертається, з однією помилкою Vue в консолі про невідповідність гідратації, оскільки HTML сервера містив ключі.
- **Краулерам** повідомляється повернутися пізніше.
- **Кеші:** правило маршруту `swr` або `cache` нічого не зберігає зі статусом 400 і вище, а CDN отримує `no-store`, тож жоден кеш не зберігає сирі ключі, і перший запит після відновлення рендерить справжній текст.
- **Сторінки, вже кешовані** правилом, залишаються як є: перевалідація не вдається й нічого не зберігає. На Vercel невдала перевалідація `isr` так само зберігає останню сторінку.

Це охоплює кожен чанк, який завантажує рендеринг, включно з невдалим чанком сторінки, корінь якого доступний, і чанком, об’єднаним пізніше під час рендерингу. Сторінка зі справним словником, перенаправлення та сторінка помилки зберігають свій статус. Виняток — [острів компонента](/uk/guide/server-side-translations): він залишається 200, бо 503 прибрав би його зі сторінки, тож сторінку, власний словник якої завантажується, може бути збережено із сирими ключами острова. Кожен запит під час збою звертається до хостингу, без власного тайм-ауту модуля, окрім 60 секунд на заголовки відповіді.

404 від хостингу означає, що такого файлу немає, і це не збій. Рендеринг сторінки показує кореневий словник, як і браузер, а `/_locales/...` відповідає тим самим 404. Жоден кеш не зберігає ні того, ні іншого, тож файл, що з’являється, читається під час наступного запиту ціною одного запиту до хостингу на кожен рендеринг такої сторінки. Якщо немає й кореневого файлу, словник порожній, і [пререндеринг](/uk/guide/upgrade#server,-build-and-deployment) завершується помилкою.

Сервер зберігає завантажені payload у LRU-кеші в процесі розміром до `cacheMaxSize` записів (за замовчуванням 1000), який перезавантажує запис після `cacheTtl`, якщо його задано; обидва описано в розділі [Налаштування продуктивності](/uk/guide/performance), а [`cacheStorage`](/uk/guide/performance#shared-cache-for-several-instances) додає кеш, спільний для кількох екземплярів. Не додавайте зверху правило маршруту Nitro `cache` на `/_locales/**`: воно ключує за повним URL, включно з query, і зберігає третю копію.

## App baseURL і хости payload {#app-baseurl-and-payload-hosts}

**`app.baseURL`** більше нічого не потребує. З `app.baseURL: '/shop/'` браузер отримує `/shop/_locales/...`; копія залишається в `.output/public/_locales/`, яку Nitro віддає під базовим шляхом (статичний хостинг має змонтувати вивід у `/shop/`). Префікси локалей і [виключені шляхи](/uk/guide/excluding-static-files) зіставляються без базового шляху.

**`app.cdnURL`** теж переносить payload, коли вони є файлами в `public/`: браузер отримує та попередньо завантажує `<cdnURL>/_locales/...`.

- CDN має містити `_locales/` поруч із `_nuxt/` за цим шляхом.
- Він має дозволяти походження вашого сайту (CORS), оскільки файл надходить через `fetch`.
- Словник, на який відповідає лише серверний маршрут (режим `source`, без публічної копії), залишається на походженні застосунку.

Runtime-змінна `NUXT_APP_BASE_URL` на `cloudflare-module` потребує сумісності з Node (`nodejs_compat`). З вимкненим `nitro.cloudflare.nodeCompat`, до якого Nitro також переходить зі старою датою без прапорця, вона не бачить змінну й віддає `/`, включно зі звичайним Nuxt, тоді як перенаправлення локалі все одно веде на базовий шлях. Там встановлюйте `app.baseURL` під час збирання.

Щоб віддавати payload з іншого походження, спрямуйте на нього клієнт і сервер та вимкніть локальні виводи:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  modules: ['nuxt-i18n-micro'],
  i18n: {
    apiBaseClientHost: 'https://cdn.example.com',
    apiBaseServerHost: 'https://cdn.example.com',
    translationPayloads: {
      serverHandler: false,
      publicAssets: false,
      serverAssets: false,
    },
  },
})
```

- На Node `serverAssets` записує ту саму копію для власних читань сервера, і цей файл відповідає на `/_locales`: його також треба вимкнути, навіть якщо ви залишаєте серверний маршрут для браузера, до якого той ніколи б не дійшов.
- Хостинг має віддавати ту саму структуру `<apiBaseUrl>/<page>/<locale>/data.json`.
- Збирання попереджає, коли всі локальні виводи вимкнено, а хоста немає.

Ті самі значення можуть надходити з `NUXT_I18N_APP_BASE_URL`, `NUXT_I18N_APP_BASE_CLIENT_HOST` і `NUXT_I18N_APP_BASE_SERVER_HOST` під час збирання. `NUXT_I18N_APP_BASE_SERVER_HOST` також працює під час виконання й має перевагу над значенням зі збирання. Подробиці див. у [`apiBaseServerHost`](/uk/api/module-options#apibaseserverhost).

## Платформи {#platforms}

Лише те, що потрібно модулю або його виводу. Облікові записи, регіони та входи через CLI описано в документації платформи.

### Cloudflare Workers {#cloudflare-workers}

Пресет `cloudflare_module`. `wrangler deploy` вдруге збирає вивід Nitro за допомогою esbuild, і після цього сирий `defineAsyncComponent(() => import('./X.vue'))` рендериться на сервері порожнім. Сторінка помилки Nuxt за замовчуванням — саме такий компонент, тож 404 має порожнє тіло, а браузер записує в лог невідповідність гідратації. Потім клієнт рендерить сторінку, і статус залишається 404, але без JavaScript сторінка порожня. Це [nuxt#33270](https://github.com/nuxt/nuxt/issues/33270): звичайний Nuxt без модуля поводиться так само. Маршрутів сторінок це не стосується.

Вимкніть друге збирання:

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: {
    preset: 'cloudflare_module',
    cloudflare: {
      deployConfig: true, // `wrangler` below applies only with it
      wrangler: {
        no_bundle: true,
        find_additional_modules: true,
        rules: [{ type: 'ESModule', globs: ['**/*.mjs'] }],
      },
    },
  },
})
```

```bash
npx nuxi build
cd .output/server && npx wrangler deploy -c wrangler.json
```

Встановіть `compatibilityDate` на `2024-09-19` або пізніше: старіша дата обирає застарілий пресет, який не записує `wrangler.json` і не видає помилки. Тоді 404 рендериться, а завантаження стає меншим: 190 KiB gzip проти 246 KiB на тестовому застосунку. Інший вихід — власний `error.vue`, але він охоплює лише сторінку помилки.

Сам модуль не потребує `nodejs_compat`. Про ліміти див. [Ліміти бандла](#bundle-limits-on-edge).

### Cloudflare Pages {#cloudflare-pages}

Використовуйте пресет `cloudflare-pages-static`. `nuxi generate --preset cloudflare-pages` — це серверне збирання без `index.html`.

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  nitro: {
    preset: 'cloudflare-pages-static',
    prerender: { autoSubfolderIndex: false },
  },
})
```

```bash
npx nuxi generate
npx wrangler pages project create my-site --production-branch main --force
npx wrangler pages deploy dist --project-name my-site --branch main
```

- **Вивід.** Пресет записує в `dist/`, а не в `.output/public`.
- **`--force`.** Без нього новий wrangler (тут 4.156) передає `pages project create` до Workers. З ним ви отримуєте класичний проєкт Pages. Він потрібен один раз, для створення.
- **`autoSubfolderIndex: false`.** Pages відповідає на `/de` кодом 308 на `/de/`, тоді як canonical і `hreflang` вказують `/de`, тож вони вказують на перенаправлення. З цією опцією файл — `de.html`, і перенаправлення зникає.
- **`NUXT_E1005` у консолі на 404** — це звичайний 404. Nuxt повідомляє про нього так, бо `404.html` стартує на клієнті, до монтування застосунку. Сторінка працює, а звичайний Nuxt виводить той самий рядок.

### Vercel і Vercel Edge {#vercel-and-vercel-edge}

Пресети `vercel` і `vercel_edge`, без змін у застосунку. Теги працюють без `metaBaseUrl`, завдяки перенаправленим заголовкам платформи. Vercel Edge має малий ліміт бандла: див. [Ліміти бандла](#bundle-limits-on-edge). Для спільного кешу використовуйте [драйвер `upstash`](/uk/guide/performance#upstash-on-vercel-and-vercel-edge).

### Netlify {#netlify}

Пресети `netlify` і `netlify_edge`.

```bash
npx nuxi build --preset netlify
npx netlify deploy --prod --no-build --dir dist --functions .netlify/functions-internal
```

- **Не встановлюйте `nitro.output`.** Пресет сам записує `.netlify/` і `dist/`.
- **Тримайте `package.json` у теці, з якої розгортаєте.** Без нього CLI дивиться в батьківську теку й не розгортає жодної функції, без помилки.
- **Netlify Edge** розгортається лише з `--dir dist`. Див. [Дати в Edge-середовищах](#dates-on-edge-runtimes).

### Cloud Run {#cloud-run}

Використовуйте стандартне збирання `node-server`. `gcloud run deploy --source` потребує `Dockerfile` у вихідній теці, коли docker не запущено локально:

```dockerfile
# .output/Dockerfile
FROM node:22-slim
WORKDIR /app
COPY . .
ENV NODE_ENV=production
CMD ["node", "server/index.mjs"]
```

```bash
cd .output && gcloud run deploy my-app --source .
```

Теги працюють без `metaBaseUrl`, завдяки перенаправленим заголовкам платформи.

### Deno Deploy {#deno-deploy}

Пресет `deno_deploy`. `deno deploy` замінює `deployctl`. Створіть динамічний застосунок із точкою входу `server/index.ts` і розгортайте з вихідної теки.

### Firebase {#firebase}

| Продукт | Налаштування |
| --- | --- |
| App Hosting | Запускає збирання Node: використовуйте пресет за замовчуванням або `firebase-app-hosting` і Node 20+ |
| Cloud Functions | Пресет `firebase` вбудовує payload і потребує `firebase-functions` |
| Hosting (статичний) | Віддає `.output/public` як файли, тож `/_locales/**` отримує заголовки Hosting |

На статичному Hosting, якщо JSON повертається з неправильним `Content-Type` або кешуванням, додайте запис `headers` для `/_locales/**` у `firebase.json`. Заголовки `routeRules` Nuxt не застосовуються до файлів, які Hosting віддає сам; маршрут payload встановлює власні `Content-Type` і `Cache-Control` для відповідей, що таки доходять до сервера.

### AWS Amplify {#aws-amplify}

`aws-amplify` зберігає статичні файли поруч зі своєю обчислювальною текою, а не поруч із сервером, тож payload вбудовуються, як на платформі функцій.

### Кілька екземплярів одного збирання {#several-instances-of-one-build}

Один артефакт може запускатися з іншою локаллю за замовчуванням чи вимкненою локаллю для кожного екземпляра через змінні середовища: див. [Runtime-перевизначення](/uk/guide/runtime-overrides). Локаль, вимкнена лише під час виконання, усе ще має свої статичні файли в `public/`; вимкніть її під час збирання, якщо вони не мають бути доступними.

Екземпляри, що завантажують словники з віддаленого хоста, можуть ділитися ними в Redis, Upstash, Cloudflare KV чи D1, Deno KV або іншому сховищі Nitro, тож бекенд отримує один запит замість одного на екземпляр. Це кеш, а не джерело перекладів: див. [Спільний кеш для кількох екземплярів](/uk/guide/performance#shared-cache-for-several-instances).

## За проксі або CDN {#behind-a-proxy-or-cdn}

Застосунок має дізнатися публічний хост і схему із запиту.

| Проксі надсилає                              | Звичайне збирання                                | Збирання з `baseUrl` у локалей                                                    |
| -------------------------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------- |
| Справжній `Host`                             | Нічого налаштовувати                             | Нічого налаштовувати                                                              |
| `Host` походження плюс `X-Forwarded-Host`    | Нічого налаштовувати                             | [`trustForwardedHost: true`](/uk/api/module-options#trustforwardedhost)           |
| Жодного                                      | [`metaBaseUrl`](/uk/api/module-options#metabaseurl) | Жодне налаштування не допоможе: кожен запит виглядає як хост походження, тож змініть проксі |

- **Маршрути під `swr` або `cache`.** Там таблиця не діє: див. [Кешування HTML](#caching-html). Встановіть `metaBaseUrl` або `site.url`.
- **`X-Forwarded-Proto`.** Надсилайте його, інакше канонічні URL матимуть `http://` за HTTPS-проксі. `metaBaseUrl` також це виправляє.
- **У збиранні з доменами** домен обирає базовий URL тегів. `metaTrustForwardedHost` там не обирає домен, це робить лише `trustForwardedHost`.
- **Перенаправлення відносні, а cookie локалі не має `Domain`,** тож обидва залишаються на публічному хості.

<Warning>

**Закріпіть `metaBaseUrl`, коли походження залишається доступним** — У звичайному збиранні без `metaBaseUrl` чи `site.url` canonical, `hreflang` і `og:url` беруть хост із запиту. [`metaTrustForwardedHost`](/uk/api/module-options#metatrustforwardedhost) увімкнено за замовчуванням, тож прямий запит з `X-Forwarded-Host: evil.example` отримує `https://evil.example` у цих тегах, а кеш попереду поширює цю сторінку. Хост платформи, як-от `*.workers.dev`, — саме таке походження. `metaBaseUrl` закриває це й для `Host`. Відомий хост збирання з доменами зберігає власний `baseUrl`. З `trustForwardedHost: true` прямий клієнт може обрати сторінку іншого домену, тож вмикайте це лише за проксі, який перезаписує заголовок.

</Warning>

## Кешування HTML {#caching-html}

Більшість URL безпечно кешувати, бо вони вказують свою локаль. Ці залежать від відвідувача:

| Налаштування                   | URL                                               |
| ------------------------------ | ------------------------------------------------- |
| За замовчуванням, `autoDetectPath: '/'` | `/`                                      |
| `prefix`                       | `/` і кожен URL без префікса, які лише перенаправляють |
| `autoDetectPath: '*'`          | Кожен URL                                         |
| `no_prefix`                    | Кожна сторінка                                    |

- **`Vary`.** Ці відповіді містять `Vary` з `Cookie`, коли встановлено [`localeCookie`](/uk/api/module-options#localecookie), і з `Accept-Language`, коли увімкнено `autoDetectLanguage`. Кеш, що його враховує, розрізняє відповіді.
- **Кеш, що ігнорує `Vary`,** як-от «кешувати все за URL», має пропускати ці URL. Інакше `302 /de` одного відвідувача потрапить до наступного, а збережена сторінка за замовчуванням прибере перенаправлення для всіх. На `/` можна також встановити `redirects: false`. Кеш маршрутів Nitro ключує за шляхом і своїм списком `varies`, тож також не включайте `/` у правила `swr` і `cache`.
- **`Set-Cookie`.** Зі встановленим `localeCookie` кожна відрендерена на сервері сторінка під префіксом містить `Set-Cookie`, і коректний CDN її не збереже. Для кешованого HTML залиште `localeCookie` вимкненим або видаляйте заголовок на edge.
- **Правила `swr` і `cache` потребують `metaBaseUrl` або `site.url`.** Nitro рендерить такий маршрут лише із заголовками з `cache.varies`, тож `Host`, `X-Forwarded-Host` і `X-Forwarded-Proto` зникають, а URL запиту стає `http://localhost`. Без фіксованого походження canonical, `hreflang` і `og:url` на цих маршрутах вказують на `http://localhost` на кожній платформі. `useRequestURL()` звичайного Nuxt там показує те саме. Якби хост брався від відвідувача, `X-Forwarded-Host` одного відвідувача потрапляв би на сторінку, яку отримують усі. Збирання з доменами це не зачіпає: його теги використовують `baseUrl` локалей.

  Якщо одне збирання обслуговує кілька хостів і жодне окреме походження не підходить, дозвольте правилу бачити заголовки та зберігайте по одній копії на значення: `'/blog/**': { swr: 60, cache: { varies: ['host', 'x-forwarded-host', 'x-forwarded-proto'] } }`. Кожне окреме значення — це новий запис кешу, тож клієнт, що надсилає вигадані заголовки, заповнює кеш: розмістіть походження за проксі, який їх встановлює.
- **Правила `swr` і `cache` у збиранні з доменами.** Модуль додає `host` до `cache.varies` кожного такого правила, а з `trustForwardedHost` — і `x-forwarded-host`, тож один домен не віддає іншому свою сторінку. Правило з `cache: false` залишається як написано. `isr` — це кеш платформи: перевірте, що він ключує за хостом. Коли хост є в ключі, клієнт, що надсилає вигадані хости, додає записи в кеш.

Про файли payload див. [Заголовки кешування та dateBuild](#cache-headers-and-datebuild).
