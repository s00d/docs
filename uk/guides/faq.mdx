# ❓ FAQ: поширені проблеми та рішення

Знайдіть відповіді на часті запитання та рішення поширених проблем з Nuxt I18n Micro.

## 🚀 Проблеми на старті

### ❓ Що робити, якщо маршрут не завантажується?

Під час використання `Nuxt I18n Micro` деякі маршрути можуть не завантажуватися, як очікувалося, особливо якщо роутер автоматично не присвоює імʼя маршруту у підтеках.

**Рішення:**
Щоб це виправити, задайте імʼя маршруту сторінці вручну, додавши таке до відповідного Vue-файлу:

```javascript
definePageMeta({ name: 'pageName' })
```

Це забезпечує, що маршрут коректно зареєстровано, уможливлюючи безшовну навігацію у застосунку.

### ❓ Чому `$t` або інші i18n-композабли не працюють у Nuxt-плагінах?

Композабли Nuxt I18n (`$t`, `$getLocale`, `$localePath` тощо) можуть не працювати як очікується у Nuxt-плагінах чи утилітарних функціях, спричиняючи рантайм-помилки.

**Причина та рішення:**
Композабли Nuxt потребують специфічних контекстів (наприклад, хуки Nuxt чи setup-функції Vue), щоб отримати доступ до інстансу Nuxt. Якщо їх викликають поза цими контекстами (наприклад, у утилітарних функціях чи плагінах), у консолі може зʼявитися така помилка:

```
[nuxt] A composable that requires access to the Nuxt instance was called outside of a plugin, Nuxt hook, Nuxt middleware, or Vue setup function. This is probably not a Nuxt bug. Find out more at https://nuxt.com/docs/guide/concepts/auto-imports#vue-and-nuxt-composables
```

**Рішення 1: використати `runWithContext`**
Щоб викликати i18n-композабли після асинхронної операції, використовуйте [`runWithContext`](https://nuxt.com/docs/api/composables/use-nuxt-app#runwithcontext), щоб зберегти необхідний контекст.

```javascript
await nuxtApp.runWithContext(() => $t('test_key'))
```

**Рішення 2: спершу отримати значення**
Альтернативно, спочатку отримайте значення перекладу, потім передайте його у утилітарну функцію.

```javascript
const val = nuxtApp.$t('common.errors.unknown.title')
showError({
  title: val,
})
```

**Рішення 3: передавайте ключі перекладу у сервіси**
У сервісах чи утилітарних функціях передавайте ключі перекладу замість прямого використання `$t`. Потім отримуйте переклад у компоненті.

```javascript
showError({
  title: 'common.errors.unknown.title',
  message: 'common.errors.unknown.message',
  i18n: true,
})
```

## 🌐 Перемикання локалей

### ❓ Перемикання локалі без зміни URL?

Так, але це залежить від вашої [стратегії маршрутизації](/guides/routing-strategies).

**Стратегія `no_prefix`** — локаль не є частиною URL. Використовуйте `$switchLocale()`, щоб змінити локаль і перезавантажити переклади, залишаючись на тому ж шляху:

```typescript
const { $switchLocale } = useNuxtApp()
$switchLocale('de') // /about stays /about, content switches to German
```

Або оновіть лише вподобання через `useI18nLocale().setLocale('de')`. Для повного клієнтського перезавантаження перекладів надавайте перевагу `$switchLocale()`.

**Префіксні стратегії** (`prefix`, `prefix_except_default`, …) — локаль і URL повʼязані. `$switchLocale()` завжди виконує навігацію на локалізований маршрут. Опції `redirect: false` немає.

Якщо вам потрібен лише цільовий URL (наприклад, посилання перемикача мови), використовуйте `$switchLocalePath()`:

```vue
<NuxtLink :to="$switchLocalePath('fr')">Français</NuxtLink>
```

Усі методи перемикання див. у [Перемиканні маршрутів і локалей](/api/methods#-route-locale-switching).

### ❓ Сторінка прокручується вгору (або стрибає) при перемиканні локалі?

Це очікувано — це **поведінка прокрутки Vue Router / Nuxt**, а не щось специфічне для nuxt-i18n-micro.

З префіксними стратегіями (`prefix`, `prefix_except_default`, …) `$switchLocale()` виконує звичайну клієнтську навігацію (`/en/page` → `/de/page`). Стандартна [`scrollBehavior`](https://github.com/nuxt/nuxt/blob/main/packages/nuxt/src/pages/runtime/router.options.ts) Nuxt прокручує до верху при зміні маршруту (окрім браузерного назад/вперед через `savedPosition`).

nuxt-i18n-micro не додає прихованої обробки прокрутки — використовуйте маленький компонент-обгортку у вашому застосунку.

**Обгортка `SwitchLocalePreserve`**

Скопіюйте [`playground/components/SwitchLocalePreserve.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/components/SwitchLocalePreserve.vue) у ваш проєкт (`components/SwitchLocalePreserve.vue`). Робоче демо: [`playground/pages/scroll-test.vue`](https://github.com/s00d/nuxt-i18n-micro/blob/main/playground/pages/scroll-test.vue).

На сторінці встановіть `scrollToTop: false` і оберніть UI перемикача. Позначайте клікабельні цілі через `data-locale` — обгортка перехоплює кліки, викликає `$switchLocale` і відновлює прокрутку (включно з випадками, коли довжина перекладу змінює розкладку):

```vue
<script setup lang="ts">
definePageMeta({ scrollToTop: false })

const { $getLocales, $getLocale } = useI18n()
</script>

<template>
  <SwitchLocalePreserve root-id="lang-switcher">
    <button v-for="locale in $getLocales()" :key="locale.code" :data-locale="locale.code" :disabled="locale.code === $getLocale()">
      {{ locale.code }}
    </button>
  </SwitchLocalePreserve>
</template>
```

Компонент:

1. **При кліку** — читає `data-locale` на клікнутому елементі всередині слоту (кнопки, посилання чи будь-яка кастомна розмітка).
2. **До** `$switchLocale` — зберігає `scrollY` та позицію клікнутого елемента (тримає його під курсором).
3. **Під час** навігації — одноразово патчить `router.options.scrollBehavior` і повертає `\{ top: scrollY \}` замість прокрутки до верху.
4. **Після** навігації — очікує `page:finish`, потім повторно застосовує прокрутку, поки `ResizeObserver` ловить зсуви розкладки від різних довжин перекладу.

`scrollToTop: false` обовʼязковий на сторінках, де ви використовуєте цю обгортку. Документація: [Nuxt — `definePageMeta` / `scrollToTop`](https://nuxt.com/docs/4.x/api/utils/define-page-meta#meta).

Не викликайте `$switchLocale` напряму на обгорнутих контролах — обгортка сама виконує перемикання. Для `<NuxtLink :to="$switchLocalePath('fr')">` поза обгорткою поведінка прокрутки слідує звичайній маршрутизації Nuxt, якщо ви не додасте власний `app/router.options.ts`.

## 🌐 Проблеми з перекладами

### ❓ Чому переклади ламаються під час переходів між сторінками, особливо з `defineAsyncComponent`?

Під час використання `nuxt-i18n-micro` з переходами сторінок переклади можуть тимчасово перестати працювати під час переходу. Ця проблема виникає, бо маршрут змінюється до завершення переходу, тож переклади для нової сторінки завантажуються, поки стара ще видима.

**Корінь проблеми:**

- Переходи сторінок спричиняють зміну маршруту до повного завантаження перекладів
- `defineAsyncComponent` та `useAsyncData` можуть затримати завантаження перекладів
- Ключі перекладу можуть відображатися як сирі шляхи під час завантаження

**Рішення 1: кумулятивне злиття (вбудовано, без конфігу)**

У v3 модуль автоматично використовує стратегію кумулятивного злиття. При навігації в межах однієї локалі переклади нової сторінки зливаються в активний словник замість заміни. Це означає, що переклади з попередньої сторінки залишаються доступними під час анімації переходу. Після завершення переходу (хук `page:transition:finish`) старі ключі очищаються автоматично.

Жодних налаштувань не потрібно — це працює з коробки.

**Рішення 2: явний контекст маршруту**

Якщо ви віддаєте перевагу ручному керуванню, явно передавайте поточний маршрут у `$_t`:

```vue
<script lang="ts" setup>
import { useNuxtApp } from '#imports'
const route = useRoute()
const { $_t } = useNuxtApp()

const $t = $_t(route)
</script>

<template>
  {{ $t('page::blog-slug.title') }}
</template>
```

**Рішення 3: стани завантаження**

Реалізуйте стани завантаження, щоб коректно обробляти завантаження перекладів:

```vue
<template>
  <div v-if="pending">
    <div class="loading-skeleton">
      <!-- Loading placeholder -->
    </div>
  </div>
  <div v-else>
    {{ $t('page.title') }}
  </div>
</template>

<script setup>
const { data, pending } = await useAsyncData('page-data', () => {
  // Your async data loading
})
</script>
```

### ❓ Чому ключі перекладу не розвʼязуються під час SSR на Vercel?

**Обмеження `$fetch` на SSR**
На serverless-платформах на кшталт Vercel `$fetch` може отримувати лише статичні файли з CDN, а не з внутрішнього Nitro-сервера. Це означає, що статичні файли перекладів можуть бути напряму недоступні, якщо не задано правильний базовий URL.

**Виправлення через `apiBaseClientHost` та `apiBaseServerHost`**
Якщо переклади розміщені зовні на CDN чи іншому домені, використовуйте `apiBaseClientHost` для клієнтських запитів та `apiBaseServerHost` для серверних. `apiBaseUrl` має містити лише префікс шляху (наприклад, `_locales`).

```typescript
export default defineNuxtConfig({
  i18n: {
    apiBaseUrl: '/_locales', // Path prefix only
    apiBaseClientHost: 'https://cdn.example.com', // CDN domain for client
    apiBaseServerHost: 'https://cdn.example.com', // CDN domain for server (SSR)
  },
})
```

Або через змінні оточення:

```bash
NUXT_I18N_APP_BASE_URL=_locales
NUXT_I18N_APP_BASE_CLIENT_HOST=https://cdn.example.com
NUXT_I18N_APP_BASE_SERVER_HOST=https://cdn.example.com
```

Переклади отримуватимуться з `https://cdn.example.com/_locales/\{routeName\}/\{locale\}/data.json` як на клієнті, так і на сервері.

## 🔗 Проблеми маршрутизації та навігації

### ❓ Чи можна використовувати `NuxtLink` або `<i18n-link>` безпосередньо у рядках перекладу?

Так, `Nuxt I18n Micro` дозволяє використовувати `NuxtLink` або `<i18n-link>` усередині перекладів через компонент `<i18n-t>`, що особливо корисно для роботи з граматикою та RTL-мовами без розбиття рядків перекладу.

**Приклад:**

Файл перекладу:

```json
{
  "example": "Share your {link} with friends",
  "link_text": "translation link"
}
```

Vue-шаблон:

```vue
<template>
  <i18n-t keypath="example">
    <template #link>
      <nuxt-link :to="{ name: 'referral' }">
        <i18n-t keypath="link_text" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Це дозволяє мати динамічні посилання всередині перекладів, зберігаючи правильну структуру локалізації.

## 🏗️ Проблеми збірки та розгортання

### ❓ Чому пейлоади перекладу опиняються під `public/_locales/` (або у серверному бандлі на Edge)?

SSR і клієнт обидва потребують однакових пейлоадів `/\{apiBaseUrl\}/\{page\}/\{locale\}/data.json`. Як вони пакуються, залежить від таргета Nitro:

**Пояснення:**

- **Node (за замовчуванням):** модуль **не** вбудовує переклади як Nitro `serverAssets` / Rollup `raw:` (це роздувало RAM збірки на великих каталогах). Натомість він копіює premerged-дерево у `public/<apiBaseUrl>/` (за замовчуванням `_locales`), а SSR читає ці файли через `readFile`. Клієнт `$fetch`ає ті самі URL — як статичні файли або через хендлер Nitro.
- **Edge** (`nitro.node === false`): для SSR немає постійної публічної FS, тож пейлоади вбудовуються через Nitro `serverAssets` (`assets:i18n`). Надавайте перевагу `translationPayloads.mode: 'source'`, щоб вбудовування залишалося компактним. Встановлюйте `publicAssets: true`, лише якщо вам також потрібна CDN/статична копія.
- **`prerenderRoutes`:** опційно. У режимі premerged `publicAssets` вже записав `\{page\}/\{locale\}/data.json`, тож pre-render цих маршрутів зазвичай зайвий.

### ❓ Чому я отримую помилку збірки з посиланням на `@unhead/vue` або невизначений обʼєкт, особливо на Cloudflare Pages?

**Причина:**
Деякі проєкти зіштовхуються з конфліктами збірки або відсутніми залежностями при використанні `nuxt-i18n-micro`. Зокрема:

- Розгортання на **Cloudflare Pages** або **Cloudflare Workers** можуть потребувати додаткових прапорців сумісності.
- Кроки pre-render можуть падати, якщо залежності на кшталт `@unhead/vue` не встановлені належним чином.
- Деякі модулі (наприклад, **nuxthub**, **nitro-cloudflare-dev**) можуть вносити конфлікти, якщо не налаштовані з правильними прапорцями чи залежностями.

**Можливі рішення:**

**Рішення 1: встановіть `@unhead/vue` вручну**
Якщо помилка збірки скаржиться на відсутність `@unhead/vue`, встановіть його безпосередньо у залежностях проєкту:

<CodeGroup>
```bash npm
npm install @unhead/vue
```

```bash yarn
yarn add @unhead/vue
```

```bash pnpm
pnpm add @unhead/vue
```
</CodeGroup>

Це гарантує, що він доступний під час фази pre-render Nitro.

**Рішення 2: додайте прапорці сумісності Cloudflare**
При використанні Cloudflare Pages чи Cloudflare Workers сумісність з Node.js часто вимкнена за замовчуванням. Увімкніть її у вашому `wrangler.toml`:

```toml
compatibility_flags = [ "nodejs_compat_v2" ]
```

Цей прапорець дозволяє багатьом Node.js-модулям (включно з тими, що використовує `nuxt-i18n-micro`) працювати без проблем.

## 🔍 SEO та `@nuxtjs/seo`

### ❓ Помилка: `nuxt-seo:defaults depends on nuxt-site-config:i18n but they are not registered`

Це трапляється, коли **`@nuxtjs/seo`** підтягує стару **`nuxt-site-config` 3.x**, яка реєструє свій i18n-плагін лише для `@nuxtjs/i18n`, а не для **nuxt-i18n-micro**.

**Виправлення:**

1. Оновіть до **`@nuxtjs/seo` 3+** (містить `nuxt-site-config` 4+ з підтримкою micro).
2. Поставте **`nuxt-i18n-micro` перед `@nuxtjs/seo`** у `modules`.
3. Тримайте **`i18n.meta: true`** для locale-aware head-тегів.

Повний приклад див. у [SEO-посібнику — розділ Nuxt SEO](/guides/seo#nuxt-seo-nuxtjs-seo).

## 🔧 Конфігурація та сумісність

### ❓ Чи натхнений `Nuxt I18n Micro` бібліотекою `vue-i18n`? А що з модифікаторами?

Хоча `Nuxt I18n Micro` виступає продуктивною альтернативою `nuxt-i18n`, він побудований незалежно від `vue-i18n`. Хоча деякі назви методів і параметрів можуть бути схожими, базова функціональність суттєво відрізняється.

**Модифікатори**: мейнтейнер спершу розглядав модифікатори, але дійшов висновку, що компоненти на кшталт `<i18n-t>` та `<i18n-link>` ефективно закривають ці потреби.

Наприклад:

```vue
<template>
  <i18n-t keypath="feedback.text">
    <template #link>
      <nuxt-link :to="{ name: 'index' }">
        <i18n-t keypath="feedback.link" />
      </nuxt-link>
    </template>
  </i18n-t>
</template>
```

Цей підхід гнучкий, тож випуск модифікаторів наразі не потрібен. Однак модифікатори можуть бути додані у майбутніх релізах, якщо буде попит.
